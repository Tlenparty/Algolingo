# Трек «Backend на Kotlin: 0 → 100» — дизайн

Дата: 2026-11-07 · Статус: черновик брейншторма, ждёт ответов заказчика на открытые вопросы

## Цель

Третий учебный трек в Алголинго: путь бэкенд-разработчика на Kotlin от нуля до «готов к собесу и к первому
рабочему сервису». Та же механика, что и везде: теория-карточки → упражнения «тап по облачку → дырка» →
«Проверить» → эталон с граблями → XP, streak, повторы 1/3/7. Без клавиатуры, офлайн.

**Успех первого среза:** на Android и iOS-симуляторе есть трек «Backend» с тремя уроками разных типов
(компилируемый Kotlin, фреймворк-код без компиляции, SQL), каждый проходится целиком; прогресс и повторы
работают как у алгоритмов.

## Что сказал заказчик / что предположено

Сказал: нужен «блок от 0 до 100 для бэкенд Kotlin-разработчика».

Предположено (поправь на ревью):
- «0» = Kotlin уже знаком на уровне Android-разработчика; язык с нуля — отдельный опциональный уровень BK0,
  который можно пропустить. Если трек для стора «с нуля» — BK0 становится обязательным и расширяется.
- «100» = уверенный middle: сам поднимает сервис, БД, очередь, кеш, тесты, Docker/CI, отвечает на собесе
  по надёжности, безопасности и архитектуре.
- Основной фреймворк — **Spring Boot** (рынок вакансий), **Ktor** — параллельная ветка тех же уроков по
  образцу переключателя Kotlin | Python (отдельный файл урока на фреймворк, общий прогресс).
- Трек — отдельная вкладка «Backend» в нижней навигации (4 вкладки), как System Design.
- Код фреймворков не компилируется генератором: проверка контента ревью + жёсткие правила JSON, как у SD.
  Чистый Kotlin (алгоритмическая часть бэкенда) идёт через существующий генератор с компиляцией JVM + Native.

## Программа (≈50 уроков, 11 уровней; срез отмечен ★)

Нумерация `bk<уровень>.<номер>`. В скобках — тип урока: **V** verified (генератор, компилируется),
**R** reviewed (ручной JSON с подсветкой, как SD), **D** design (схема/шаги, как SD).

**BK0 · Kotlin для бэкенда** (опционально, пропускаемо)
1. `bk0.1` Null-safety и типы: `?.`, `?:`, `!!`, smart cast (V)
2. `bk0.2` Коллекции и лямбды: `map/filter/groupBy/associateBy`, `Sequence` (V)
3. `bk0.3` Классы: `data`, `sealed`, `object`, `when` без `else` (V)
4. `bk0.4` Ошибки: `Result`, `runCatching`, своя иерархия исключений (V)

**BK1 · HTTP и API**
1. `bk1.1` Путь запроса от телефона до сервера: DNS, TLS, LB, App, БД (D, ссылка на sd0.4)
2. `bk1.2` Методы и статусы: GET/POST/PUT/PATCH/DELETE, 2xx/4xx/5xx, идемпотентность методов (R, текст запроса с дырками)
3. `bk1.3` REST-дизайн ресурсов: имена, вложенность, фильтры, пагинация, версионирование (R)
4. `bk1.4` JSON и сериализация: `@Serializable`, `@SerialName`, nullable-поля, `ignoreUnknownKeys` (V)

**BK2 · Первый сервис** (Spring Boot | Ktor)
1. ★ `bk2.1` Контроллер и роутинг: `@RestController`/`routing {}`, path и query параметры, тело запроса (R)
2. `bk2.2` Слои: controller → service → repository, DTO ↔ domain (R)
3. `bk2.3` Ошибки наружу: `@ControllerAdvice`/`StatusPages`, RFC 7807 problem+json (R)
4. `bk2.4` Конфигурация и профили: `application.yaml`, env, секреты не в репо (R)
5. `bk2.5` Логирование: уровни, структурные логи, correlation id (R)

**BK3 · Корутины на сервере**
1. `bk3.1` `suspend` в хендлере: где блокировать нельзя, `Dispatchers.IO` vs `Default` (V, если генератор получит kotlinx-coroutines; иначе R)
2. `bk3.2` Параллельные вызовы: `coroutineScope + async`, `awaitAll`, отмена при ошибке (V/R)
3. `bk3.3` Таймауты и `SupervisorJob`: `withTimeout`, падение одного не роняет всех (V/R)
4. `bk3.4` `Mutex`, `Channel`, актор для фоновой очереди (V/R)
5. `bk3.5` Flow для стримов: SSE из `Flow`, backpressure (R)

**BK4 · Базы данных и SQL**
1. ★ `bk4.1` SELECT/WHERE/ORDER/LIMIT, JOIN, GROUP BY + HAVING (R, подсветка SQL)
2. `bk4.2` Индексы: B-tree, составной индекс и порядок колонок, когда индекс не работает (R)
3. `bk4.3` Транзакции и изоляция: dirty/non-repeatable/phantom, `@Transactional` и его грабли (R)
4. `bk4.4` Доступ из Kotlin: Spring Data JPA / Exposed, N+1 и как его увидеть (R)
5. `bk4.5` Миграции: Flyway/Liquibase, обратимость, деплой без простоя (R)
6. `bk4.6` Пагинация: offset vs keyset, курсор (V: кодирование курсора на чистом Kotlin)
7. `bk4.7` Пул соединений: HikariCP, размер пула, утечки (R)

**BK5 · Надёжный сервис**
1. `bk5.1` Валидация входа и границы: `@Valid`, require, 400 vs 422 (R)
2. ★ `bk5.2` Rate limiter: token bucket на чистом Kotlin (V, пара к sd1.2)
3. `bk5.3` Ретраи: экспоненциальный backoff + jitter, какие ошибки не ретраить (V)
4. `bk5.4` Идемпотентность: `Idempotency-Key`, хранилище ключей, TTL (V/R)
5. `bk5.5` Circuit breaker: состояния, пороги, half-open (V)
6. `bk5.6` Graceful shutdown и health checks: liveness/readiness, дренаж запросов (R)
7. `bk5.7` Кеш: LRU на `LinkedHashMap`, TTL, cache-aside, stampede (V, пара к LRU Cache в базе знаний)

**BK6 · Интеграции**
1. `bk6.1` HTTP-клиент: `WebClient`/Ktor client, таймауты, пул, десериализация ошибок (R)
2. `bk6.2` Kafka producer: ключ → партиция, acks, идемпотентный продюсер (R)
3. `bk6.3` Kafka consumer: группы, оффсеты, at-least-once + дедуп (R, пара к sd1.4)
4. `bk6.4` Outbox: запись и событие в одной транзакции (R, пара к sd1.7)
5. `bk6.5` Redis: кеш, сессии, счётчики, `SETNX` как lock, TTL (R)
6. `bk6.6` Фоновые задачи и планировщик: `@Scheduled`, воркеры, ровно один инстанс (R)
7. `bk6.7` WebSocket и SSE: когда что, heartbeat, реконнект (R, пара к sd0.6)

**BK7 · Безопасность**
1. `bk7.1` Пароли: bcrypt/argon2, соль, почему не SHA-256 (R)
2. `bk7.2` JWT: заголовок/payload/подпись, срок жизни, где хранить, отзыв (R)
3. `bk7.3` OAuth2 + PKCE, access/refresh, ротация (D, пара к sd1.3)
4. `bk7.4` Инъекции и OWASP: параметризованные запросы, XSS в ответах API, CORS (R)
5. `bk7.5` Секреты и TLS: env/vault, терминация TLS на LB, mTLS между сервисами (R)

**BK8 · Тесты**
1. `bk8.1` Юнит-тесты: JUnit 5/Kotest, `assertThrows`, параметризованные (V: тест как упражнение)
2. `bk8.2` MockK: `every/verify`, `coEvery`, когда мок вреден (R)
3. `bk8.3` Тест API-слоя: `MockMvc`/`testApplication`, статус + тело (R)
4. `bk8.4` Testcontainers: настоящая Postgres и Kafka в тесте (R)
5. `bk8.5` Пирамида и контракты: что тестировать где, consumer-driven contracts (D)

**BK9 · Сборка и доставка**
1. `bk9.1` Gradle: `libs.versions.toml`, мультимодуль, `bootJar`/`shadowJar` (R)
2. `bk9.2` Dockerfile: multi-stage, слои и кеш, флаги памяти JVM в контейнере (R)
3. `bk9.3` docker-compose: сервис + Postgres + Redis + Kafka локально (R)
4. `bk9.4` CI: GitHub Actions — сборка, тесты, образ (R, подсветка YAML)
5. `bk9.5` Kubernetes: Deployment, Service, probes, requests/limits (R)
6. `bk9.6` Наблюдаемость: Micrometer → Prometheus, RED, p99, OpenTelemetry tracing (R, пара к sd2.3)

**BK10 · Архитектура и собес**
1. `bk10.1` Гексагональная архитектура и порты/адаптеры на Kotlin (R)
2. `bk10.2` Монолит → микросервисы: границы, общая БД как антипаттерн (D, пара к SD 18)
3. `bk10.3` Событийная архитектура и CQRS на практике (D, пара к SD 16–17)
4. `bk10.4` Финал: собери сервис целиком — шаги «Собери решение из строк» через все слои (R, финальный e4-шаг на каждый слой)

## Механики

- **Три типа уроков в одном треке.** Движок уже умеет `kind: code` (компилируемый, через генератор) и
  `kind: design` (ручной JSON, текстовые дырки, моноширинная схема). Для фреймворк-кода, SQL и YAML нужен
  `kind: design` с кодовой подсветкой: поле `syntax: kotlin | python | sql | yaml | http | none` в уроке,
  `SyntaxLang` в `:design` получает значения `Sql`, `Yaml`, `Http`, `Plain`. Подсветка — те же 3 регулярки +
  набор ключевых слов на язык.
- **Переключатель Spring | Ktor** на уровне BK2, BK6, BK8 (там, где код фреймворка): по образцу Kotlin | Python —
  отдельный файл `lessons/bk/ktor/<id>.json`, общий прогресс по id, сегмент на вкладке Backend. Уроки без
  Ktor-версии показываются как «Скоро на Ktor». Первый срез — только Spring Boot, переключатель позже.
- **Пары с System Design.** Там, где SD-урок уже объясняет «зачем» (rate limiter, outbox, auth), BK-урок
  показывает «как в коде». В теории — `[[ссылка]]` на SD-урок и заметку базы знаний.
- **Упражнения те же:** дырки в коде/запросе/конфиге; «предскажи статус/вывод» — это дырка вида
  `→ ⟦201 Created⟧`; финальный шаг «Собери решение из строк» для полных фрагментов.

## Изменения в приложении (малые)

1. `Track.Backend` рядом с `Code` и `SystemDesign`; `langFilter` для Backend = null (сегмент Kotlin | Python
   не показывается, позже — сегмент Spring | Ktor).
2. Каталог `files/content/bk/index.json`, уроки `files/content/bk/<id>.json`; `lessonPath` ветвится по
   префиксу `bk` так же, как по `sd`.
3. Четвёртый пункт нижней навигации «Backend» → `BkHome`, `HomeTab(..., Track.Backend)`.
4. `syntax` в `LessonDto`/`Lesson` с дефолтом по `kind` (code → по языку, design → plain), `SyntaxLang`
   расширяется, `CodeTemplate`/`TokenChip` берут его из `LocalSyntaxLang` как сейчас.
5. Прогресс: без миграции — статусы и повторы уже по id уроков.

## Контент и проверка

- **Verified (V):** sidecar `content/authoring/bk/<id>.md` в существующей грамматике генератора; эталон и все
  варианты компилируются и проходят `examples` + `checks` на JVM и Native; неверные облачки доказываются
  (G9–G14). Для корутин нужно решение: либо генератор получает `kotlinx-coroutines-core` в classpath
  обеих платформ (одна правка в сборке харнесса), либо уроки BK3 идут как R.
- **Reviewed (R/D):** ручной JSON, как SD. Жёсткие правила `validate()`: у каждого неверного облачка — `why`
  с контрпримером, у каждой дырки — `ok`, банк ≤ 10. Факты сверяются с заметками базы знаний. Ревью заказчика —
  блокирующий чекпоинт на каждый уровень, как в фазах 5–6, 12–13.
- **Опция v2:** JVM-харнесс `tools/bk_harness/` — Gradle-проект со Spring Boot/Ktor/Exposed в зависимостях,
  который компилирует эталоны R-уроков и прогоняет их `checks` (без Native). Медленно, но убирает класс ошибок
  «код не компилируется». Не для первого среза.
- **Теория.** Сначала заметки в Obsidian и в базе знаний (как Phase 11 → 12): на каждый уровень BK — 3–5
  заметок в новом разделе «Backend». Урок ссылается на заметку, а не дублирует её.

## Первый срез (★)

`bk2.1` Контроллер и роутинг (R, Kotlin-подсветка, Spring Boot) · `bk4.1` SQL SELECT/JOIN (R, подсветка SQL) ·
`bk5.2` Token bucket (V, генератор). Три урока закрывают три механики: ручной фреймворк-код, новый язык подсветки,
компилируемый бэкенд-алгоритм. Плюс вкладка, каталог, `Track.Backend`, e2e-смоук на Android и iOS.

## Открытые вопросы (ответы меняют программу)

1. **Для кого:** для себя (собес на Kotlin-бэкенд, Kotlin уже знаком → BK0 опционален) или для стора «с нуля»
   (BK0 обязателен и растёт до 8–10 уроков)?
2. **Фреймворк:** Spring Boot как основной, Ktor как переключатель (предположено), или только один из них?
3. **Место в UI:** четвёртая вкладка «Backend» (предположено) или Home превращается в выбор трека
   «Алгоритмы · Backend · System Design», а вкладок остаётся две?
4. **Проверка фреймворк-кода:** ревью без компиляции (как SD, предположено) достаточно для первого среза?
   JVM-харнесс с зависимостями — v2?
5. **Теория:** сначала заметки в Obsidian → база знаний (предположено), или теорию писать сразу в JSON урока?
6. **Глубина 100:** middle (предположено) или дотягивать до senior-тем (распределённые транзакции, saga,
   консенсус, JVM-тюнинг GC)? Это ещё один уровень BK11.

## Вне рамок

- Запуск и компиляция кода на устройстве или сервере — как и раньше.
- Java как язык решений; Go/Node как альтернативные бэкенды.
- Полный курс SQL-администрирования (репликация, бэкапы) — остаётся в System Design как теория.
- Сертификации, облачные провайдеры (AWS/GCP/Yandex Cloud) — упоминание, не уроки.
