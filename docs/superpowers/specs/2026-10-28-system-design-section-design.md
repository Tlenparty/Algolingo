# Раздел «System Design» — дизайн

Дата: 2026-10-28 · Статус: черновик на ревью

## Цель

Тренировать бэкенд system design так, как его спрашивают на собесах Android-разработчика (абстрактно, «спроектируй сервис»): с телефона, без клавиатуры, тем же жестом «тап по облачку → дырка». Клиентские темы (потеря связи, ретраи, офлайн-очередь) не отдельный блок, а шаги «а если сеть пропала?» внутри задач.

**Успех первого среза:** на Android и iOS-симуляторе есть вкладка «System Design» с тремя уроками (SD0.1, SD1.1, SD1.2); каждый проходится целиком: теория → шаги (требования/API/решения) → финальная схема из блоков с дырками → эталон с граблями. XP, streak и интервальные повторы работают как у алгоритмов.

## Что сказал заказчик / что предположено

Сказал: бэкенд-классика (API, несколько БД, Redis, Kafka, авторизация, защита от спама, потеря связи, мониторинг); механика «схема + шаги»; программа из 13 уроков, первый срез 1, 4, 5.

Предположено (поправь на ревью):
- Отдельная вкладка в нижней навигации, а не продолжение пути алгоритмов.
- Схема рисуется моноширинным текстом (боксы/стрелки символами) внутри существующего `CodeTemplate` — так выглядело превью, которое выбрано. Настоящий рендер графа — только если моноширинная схема окажется некрасивой на телефоне.
- Контент SD пишется руками сразу в JSON (3 урока), без генератора.

## Как устроен урок SD

Тот же `Lesson`: карточки теории (`signals`, `skeleton` — мини-схема, `pitfalls`) → 2–4 шага-упражнения → эталон. Каждый шаг — обычное упражнение «текст с дырками + банк + `why` у неверных облачков», но текст — не Kotlin, а:

- **Требования / решения** — короткие строки-утверждения: `Чтения ≫ записей → [ кеш ]`
- **API** — `POST /v1/[ urls ]`, заголовки, коды ответа
- **Схема** (последний шаг) — вертикальная цепочка блоков:

```
 Client
   ↓
[ Load Balancer ]
   ↓
 App ──→ [ Redis ]
   ↓
[ Postgres ]
```

Неверное облачко объясняет, почему не подходит (как `why` у алгоритмов), например «Memcached: нет атомарного INCR+TTL — два запроса пройдут лимит одновременно».

## Изменения в коде (минимум)

1. **Модель** (`lesson/Model.kt`):
   - `Lesson.kind: LessonKind = Code` (`code` | `design`).
   - `Exercise.title: String? = null` — подпись шага («Шаг 2 · API»), показывается над шаблоном.
   - `Solution.time`/`space` получают default `""`; секция «Сложность» в эталоне скрыта, если пусто.
2. **Валидация** (`validate`) для `design`:
   - шагов 2..4 (у `code` остаётся 2..3);
   - правило «число дырок строго растёт» не применяется (тест `everyCatalogLessonIsStrictAndValid` тоже учитывает `kind`);
   - `segments + ok[0]` **последнего** шага == `solution.code` (финальная схема); у `code` правило прежнее — для каждого шага;
   - каждая строка собранного текста шага ≤ 34 символов — схема и утверждения влезают в экран без горизонтального скролла.
3. **UI**:
   - `CodeTemplate` получает `highlight: Boolean` — для `design` без подсветки Kotlin-ключевых слов.
   - `ExerciseScreen` показывает `ex.title`, если есть.
   - `RevealScreen` для `design`: «Эталон» = собранный текст текущего шага (`segments + ok[0]`, подсветка дырок `solutionSpans`), на последнем шаге — грабли и «🔁 Что спросят дальше» (`variations`).
4. **Контент и загрузка**:
   - Файлы: `files/content/sd/index.json` (тот же формат `Catalog`) и `files/content/sd/<id>.json`. Отдельная папка — чтобы `tools/gen_content.py --check` не считал их сиротами в `lessons/`.
   - `loadLesson(id)`: id с префиксом `sd` читается из `files/content/sd/`.
   - `loadCatalog(path)` параметризуется путём.
5. **Навигация** (`App.kt`): третья вкладка «System Design» → тот же `HomeScreen` (путь уроков, кнопка «Повторить») на SD-каталоге. Прогресс общий (`Progress.lessons` по id, ключи `sd*` не пересекаются с `l*`): XP и streak одни на всё приложение, повторы — на своей вкладке.

Не делаем: генератор SD-контента, рендер графа на Canvas, свободное рисование, отдельный прогресс для SD.

## Контент первого среза (наброски шагов)

**sd0.1 Как вести интервью**
- Теория: шаги интервью (требования → оценки → API → данные → общая схема → углубление → узкие места), F vs NF требования, «не рисуй до вопросов».
- Ш1: расставить 4 шага по порядку (дырки 1–4, лишние: «сразу Kafka», «код»).
- Ш2: разложить требования: `Сократить ссылку → [ F ]`, `p99 < 100 мс → [ NF ]`…
- Ш3: что спросить первым (DAU, чтение/запись, срок хранения) против ловушек.

**sd1.1 URL shortener**
- Ш1 требования/оценка: 100M ссылок/сут ≈ `[ 1200 ]` QPS записи, чтения ×10 → `[ кеш ]`.
- Ш2 API: `POST /v1/[ urls ]` → `[ 201 Created ]`; `GET /{code}` → `[ 302 ]` (302 — ради аналитики; 301 — acceptable с note).
- Ш3 решения: id = `[ base62(счётчик) ]` (хеш — коллизии), хранилище `[ KV / NoSQL ]`, кеш `[ cache-aside ]`.
- Ш4 схема: Client → `[ LB ]` → App → `[ Redis ]` / `[ БД ]`, клики → `[ Kafka ]` → аналитика.

**sd1.2 Rate limiter — защита от спама**
- Ш1: где ставить — `[ API Gateway ]`; ключ — `[ userId / IP ]`.
- Ш2 алгоритм: всплески разрешены → `[ token bucket ]`; ровный поток → `[ leaky bucket ]`; граница окна → почему fixed window плох.
- Ш3 ответ: `[ 429 ]` + `[ Retry-After ]`; клиент при потере связи/429 → `[ backoff + jitter ]`, повтор безопасен благодаря `[ Idempotency-Key ]`.
- Ш4 схема: Client → `[ Gateway ]` ─→ `[ Redis ]` (INCR+EXPIRE в Lua) → App; метрики отказов → `[ Prometheus ]` → `[ Grafana ]`.

Финальные тексты и `why` для каждого облачка — на ревью заказчика (как в Phase 6).

## Ошибки и края

- Битый SD-JSON → тот же экран ошибки урока (`parseLesson` → `Result.failure`).
- Пустой/битый SD-каталог → пустое состояние вкладки, без падения (как `loadCatalog`).
- Старые сборки читают новый прогресс с `sd*`-ключами без проблем (`ignoreUnknownKeys`, ключи — просто id).

## Тесты

- `commonTest`/host: `validate` для `design` — счастливый путь и каждое новое правило (2..4 шага, последний шаг == `solution.code`, строка > 34 символов → ошибка).
- `LessonContentTest`: SD-каталог — уникальные id, файлы на месте, каждый урок strict-валиден.
- `loadLesson` выбирает папку по префиксу.
- E2E smoke (`tools/smoke.sh`): проход SD-уроков на Android и iOS-симуляторе; плюс ручной прогон через adb/idb со скриншотами схемы.
