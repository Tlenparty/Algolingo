## Дайджест уроков

### sd1.3 «Авторизация — вход и токены»

**Условие:** Мобильное приложение: вход через Google или свой SSO, пользователь остаётся залогиненным месяц, при краже телефона все сессии можно отозвать. 🎯 Тренирует: OAuth2 + PKCE, access/refresh с ротацией, где проверять токен, отзыв, хранение на телефоне

**Теория:** Когда это авторизация · Схема · Грабли

**Шаг 1 · Вход через OAuth2**

```text
Мобилка — public client:
  OAuth2 Code + [ PKCE ]
Страница логина — в
  [ Custom Tabs ]
POST /token:
  code + [ code_verifier ]
```

- ✗ `client_secret` — из APK его вытащат декомпиляцией — мобилке секрет не доверяют
- ✗ `WebView` — приложение видит, что вводят в поля, — пароль можно подсмотреть; провайдеры такой логин блокируют
- ✗ `Implicit flow` — устарел: токен приходит прямо в redirect, и его перехватит чужое приложение
- ✗ `code_challenge` — его уже отправили в /authorize; при обмене доказывают знание verifier, из которого он посчитан
- ≈ `системный браузер` (вместо `Custom Tabs`) — Тоже безопасно: пароль видит только провайдер. Custom Tabs — тот же браузер, но без ухода из приложения.
- перестановки: 8 wrongWhy; напр. `Custom Tabs` в [ PKCE ] → «это где открыть страницу логина, а здесь — чем заменить секрет»; `системный браузер` в [ code_verifier ] → «это окно логина; при обмене code нужен verifier»

**Шаг 2 · Access и refresh**

```text
Каждый запрос:
  Bearer [ access ], живёт ~[ 15 мин ]
POST /token([ refresh ]), ~[ 30 дней ]
  → новая пара, старый сгорает
Старый refresh пришёл снова:
  [ отозвать цепочку ]
```

- ✗ `1 год` — access не отзывается до exp: утечка — год доступа
- ✗ `выдать новую пару` — старый refresh уже сгорел; раз им пришли — его украли, а новая пара достанется вору
- ✗ `пароль` — слать его в запросах — утечка навсегда; ради этого и придуманы токены
- перестановки: 20 wrongWhy; напр. `refresh` в [ access ] → «долгий refresh не шлют в каждый запрос: утечёт — доступ на месяц»; `30 дней` в [ отозвать цепочку ] → «здесь не срок, а что сделать с украденной цепочкой»

**Шаг 3 · Проверка, отзыв, клиент**

```text
Подпись и exp проверяет:
  [ API Gateway ]
Убить access до exp:
  jti в denylist в [ Redis ]
Пять 401 разом → refresh
  один, под [ Mutex ]
Токены на диске:
  [ Keystore-шифрование ]
```

- ✗ `SharedPreferences` — открытый текст: читается на рутованном телефоне и из бэкапа
- ✗ `БД сервиса` — denylist нужен в каждом запросе за доли миллисекунды, а записи живут лишь до exp — это работа для TTL в памяти
- ≈ `каждый сервис` (вместо `API Gateway`) — Так делают в zero trust: каждый сервис сам проверяет подпись. Дороже, но не верит внутренней сети. Минимум — на шлюзе.
- ≈ `synchronized` (вместо `Mutex`) — Так и делают в OkHttp Authenticator: он синхронный. Mutex — то же для suspend-кода.
- ≈ `EncryptedSharedPrefs` (вместо `Keystore-шифрование`) — Так делали годами: внутри тот же ключ из Keystore. Но security-crypto с 2025 deprecated — сейчас чаще DataStore + Tink/Keystore.
- перестановки: 21 wrongWhy; напр. `Redis` в [ API Gateway ] → «хранилище denylist; подпись JWT проверяют ключом без похода в базу»; `synchronized` в [ Keystore-шифрование ] → «это замок от гонки, а здесь — как хранить токены»

**Шаг 4 · Схема**

```text
 App
  ├─/token─→ [ Auth-сервис ]
  │             ↓ refresh-токены
  │           [ PostgreSQL ]
  └─Bearer─→ [ API Gateway ]
               ↓ подпись+exp
             сервисы (userId)
 denylist jti: [ Redis ] (TTL)
```

- ✗ `Kafka` — очередь событий, а проверка токена — синхронный ответ «пускать или нет» прямо сейчас
- ✗ `CDN` — кеширует статику; ответы с личными токенами кешировать нельзя
- перестановки: 12 wrongWhy; напр. `PostgreSQL` в [ Auth-сервис ] → «это хранилище; токены выдаёт сервис, который проверяет код и refresh»; `API Gateway` в [ Redis ] → «шлюз читает denylist, а хранится он в общем Redis»

**Грабли:** client_secret в APK: декомпиляция — и секрет общий для всех · Refresh без Mutex: параллельные 401 сжигают refresh, пользователя выкидывает на логин · Logout стирает токены только на телефоне — refresh на сервере остаётся живым · JWT payload — base64, не шифрование: не класть туда лишние личные данные

**Что спросят дальше:** Сессия в Redis или JWT — что выбрать? · Как разлогинить пользователя на всех устройствах? · Зачем параметр state в OAuth2? · Refresh тоже вернул 401 — что делает клиент?

### sd1.4 «Уведомления — пуши, SMS, email»

**Условие:** Сервис уведомлений для приложения на 10 млн пользователей: другие сервисы просят «уведомить юзера», мы шлём пуш, SMS или email, не спамим и не теряем. 🎯 Тренирует: API отправки, очередь на канал, retry и DLQ, дедупликация, настройки пользователя, device tokens

**Теория:** Когда это уведомления · Схема · Грабли

**Шаг 1 · API отправки**

```text
Сервисы → POST /v1/notify
  {userId, type, [ notificationId ]}
  ← [ 202 Accepted ]
Android-пуш → [ FCM ]
iOS-пуш → [ APNs ]
SMS, email → провайдеры
```

- ✗ `timestamp` — два события в одну миллисекунду совпадут, а повтор получит новое время — дубль не поймать
- ✗ `WebSocket` — в фоне Android убьёт соединение; пуш доставит сама ОС, даже когда приложение закрыто
- ✗ `201 Created` — уведомление ещё не отправлено — его только поставили в очередь
- ≈ `200 OK` (вместо `202 Accepted`) — Часто так и отвечают. 202 точнее: «принято в очередь, отправим позже».
- перестановки: 15 wrongWhy; напр. `202 Accepted` в [ notificationId ] → «это код ответа, а здесь — поле запроса»; `200 OK` в [ APNs ] → «это ответ API, а здесь — канал доставки»

**Шаг 2 · Очередь и надёжность**

```text
API → [ Kafka ], топик на канал
Worker: [ at-least-once ]
  дубль → отсечь по notificationId
FCM ответил 5xx →
  [ retry + backoff ]
Падает N раз →
  [ DLQ ]
```

- ✗ `exactly-once` — при внешнем эффекте вроде FCM его не бывает; на практике at-least-once + дедупликация
- ✗ `at-most-once` — worker упал после commit — уведомление потеряно навсегда
- ✗ `Redis Pub/Sub` — fire-and-forget: worker был выключен — сообщение пропало
- ✗ `сразу повтор` — FCM лежит — тысячи мгновенных повторов добьют его и вас; нужна растущая пауза
- ≈ `RabbitMQ` (вместо `Kafka`) — Для задач «отправить» он даже естественнее. Kafka — когда нужен replay и много независимых потребителей.
- перестановки: 15 wrongWhy; напр. `at-least-once` в [ Kafka ] → «это гарантия доставки, а здесь — куда положить задачу»; `retry + backoff` в [ DLQ ] → «уже повторили N раз; дальше бесконечный ретрай заблокирует партицию»

**Шаг 3 · Правила пользователя**

```text
Worker перед отправкой:
  [ preferences ]: тип включён?
  [ quiet hours ]: 23–08 → отложить
  [ rate limit ]: ≤ 5 пушей в час
FCM: UNREGISTERED →
  [ удалить токен ] устройства
```

- ✗ `повторять` — токен мёртв навсегда — приложение удалено; повтор только тратит квоту
- ✗ `дедупликация` — отсекает одинаковые уведомления, но 50 разных лайков всё равно прилетят
- ≈ `батчинг` (вместо `rate limit`) — Тоже работает: схлопнуть в одно «5 новых лайков». Обычно сочетают с лимитом.
- перестановки: 15 wrongWhy; напр. `quiet hours` в [ preferences ] → «это про время суток, а здесь — включён ли тип уведомлений»; `батчинг` в [ удалить токен ] → «схлопывание ни при чём: токен мёртв, приложение удалено»

**Шаг 4 · Схема**

```text
 сервисы
   ↓ POST /v1/notify
 [ Notification API ] ─→ [ PostgreSQL ]
   ↓        prefs, device tokens
 [ Kafka ]: push | sms | email
   ↓
 workers ─→ [ FCM / APNs ] / SMS
   ↓ упало N раз
 [ DLQ ]
```

- ✗ `Redis Pub/Sub` — worker был выключен — уведомление потеряно; нужен брокер с хранением
- ✗ `CDN` — раздаёт статику, к доставке уведомлений отношения не имеет
- перестановки: 20 wrongWhy; напр. `PostgreSQL` в [ Notification API ] → «это хранилище настроек, а запрос принимает API»; `FCM / APNs` в [ DLQ ] → «провайдер уже N раз отказал — откладываем в отдельную очередь»

**Грабли:** Синхронная отправка в FCM из API: упал провайдер — упал и ваш API · Ретрай без backoff и лимита — шторм запросов к провайдеру · Нет quiet hours и rate limit — пользователь отключает все уведомления · Данные в push payload: лимит около 4 КБ, доставка не гарантирована

**Что спросят дальше:** Как сделать уведомление «5 новых лайков» вместо пяти? · Как отправить рассылку на 10 млн пользователей и не положить провайдера? · Как узнать, что пуш реально открыли? · Где хранить device tokens и когда их обновлять?

### sd1.5 «Лента новостей»

**Условие:** Лента как в Instagram: 100 млн пользователей, у обычных — сотни подписчиков, у звёзд — миллионы. Открыть ленту — быстро, новый пост появляется у подписчиков за секунды. 🎯 Тренирует: fan-out on write и on read, гибрид для звёзд, ленты в Redis, пагинация курсором, медиа через CDN

**Теория:** Когда это лента · Схема · Грабли

**Шаг 1 · API**

```text
Читать ленту:
  GET /v1/feed?[ cursor ]=…&limit=20
  ← посты + nextCursor
Опубликовать:
  [ POST ] /v1/posts → [ 201 Created ]
Фото поста — URL на [ CDN ]
```

- ✗ `offset` — новый пост сверху сдвинет страницы — дубли и пропуски в ленте
- ✗ `PUT` — заменяет ресурс по известному id, а id нового поста выдаёт сервер
- ✗ `S3` — бакет приватный и далеко; это origin за CDN, телефону отдают с edge
- ≈ `200 OK` (вместо `201 Created`) — Тоже встречается. 201 точнее: создан новый ресурс, обычно с Location.
- перестановки: 15 wrongWhy; напр. `POST` в [ cursor ] → «это метод, а здесь — параметр пагинации»; `200 OK` в [ CDN ] → «это код ответа, а здесь — откуда раздавать фото»

**Шаг 2 · Fan-out**

```text
Обычный автор (300 подписч.):
  fan-out on [ write ]
Звезда (10 млн подписчиков):
  fan-out on [ read ]
Лента в Redis: [ sorted set ]
  score = время, [ только id ]
```

- ✗ `целые посты` — пост правят и удаляют — копии в миллионе лент не обновить, а память ×N
- ✗ `hash` — поля без порядка: ни сортировки по времени, ни выборки последних N
- ✗ `только write` — у звезды 10 млн подписчиков — каждый её пост это 10 млн записей
- ≈ `list` (вместо `sorted set`) — Так тоже делают (LPUSH + LTRIM). Sorted set удобнее: порядок по времени при опоздавших событиях и курсор по score.
- перестановки: 15 wrongWhy; напр. `read` в [ write ] → «у обычного автора дешевле разложить заранее: чтение ленты станет одним запросом в Redis»; `list` в [ только id ] → «структура уже выше; здесь — что лежит в элементах»

**Шаг 3 · Чтение**

```text
Feed service, GET /feed:
  1) id из [ Redis ]: score < [ cursor ]
  2) подмешать посты звёзд
  3) [ гидрация ]: id → посты
  4) промахи кеша → [ PostgreSQL ]
  ← посты + nextCursor
```

- ✗ `offset` — новые посты сдвигают страницы — дубли; курсор держит место по score
- ✗ `JOIN подписок` — собирать ленту JOIN-ом по всем подпискам на каждое открытие — это fan-out on read для всех, лента тормозит
- ✗ `Kafka` — журнал для записи событий; синхронное чтение ленты в него не ходит
- ≈ `Cassandra` (вместо `PostgreSQL`) — При огромном объёме постов — да, wide-column. По умолчанию начинают с PostgreSQL.
- перестановки: 15 wrongWhy; напр. `cursor` в [ Redis ] → «это граница страницы, а здесь — откуда взять готовую ленту»; `гидрация` в [ PostgreSQL ] → «это название шага, а здесь — куда идти за промахами»

**Шаг 4 · Схема**

```text
 Post service ─→ [ PostgreSQL ]
   ↓ событие PostCreated
 [ Kafka ] ─→ fanout workers
   ↓ ZADD id в ленты
 [ Redis ] (feed:{userId})

 App ─→ Feed service ─→ Redis
   ↓ гидрация из кеша / БД
 фото ─→ [ CDN ]
```

- ✗ `S3` — это origin за CDN: бакет приватный и далеко от пользователя
- ✗ `WebSocket` — ленте не нужен real-time: pull-to-refresh и курсор
- ≈ `Cassandra` (вместо `PostgreSQL`) — При огромном объёме постов — да, wide-column. По умолчанию начинают с PostgreSQL.
- перестановки: 15 wrongWhy; напр. `Kafka` в [ PostgreSQL ] → «журнал событий не источник истины для постов — их читают по id»; `Redis` в [ CDN ] → «фото не держат в памяти — их раздаёт CDN»

**Грабли:** Только fan-out on write: пост звезды кладёт очередь на минуты · Только fan-out on read: каждое открытие ленты собирает посты сотен авторов · Лента без ограничения длины: память Redis растёт бесконечно — храним top-N · Гидрация по одному посту: 20 походов в БД вместо одного пакетного

### sd1.6 «Чат — мессенджер»

**Условие:** Мессенджер на 50 млн пользователей: личные и групповые чаты, сообщения доходят за доли секунды, ничего не теряется при плохой связи, видно «доставлено» и «прочитано». 🎯 Тренирует: WebSocket-шлюзы, маршрутизация между серверами, порядок seq, clientMessageId, офлайн и статусы

**Теория:** Когда это чат · Схема · Грабли

**Шаг 1 · Протокол**

```text
На экране: [ WebSocket ]
→ send
  {chatId, text, [ clientMessageId ]}
← ack {clientMessageId, [ seq ]}
В фоне: [ push ] «есть новое»
```

- ✗ `SSE` — только сервер → клиент; отправка и «печатает…» пошли бы отдельными запросами
- ✗ `timestamp` — часы серверов расходятся — порядок поедет; номер выдают по чату монотонно
- ✗ `polling` — задержка до N секунд и пустые запросы — батарея и сервер страдают
- перестановки: 12 wrongWhy; напр. `clientMessageId` в [ WebSocket ] → «это поле сообщения, а здесь — транспорт»; `seq` в [ push ] → «это номер в чате, а здесь — как достучаться в фоне»

**Шаг 2 · Много шлюзов**

```text
A на WS-1, B на WS-3
Кто на каком шлюзе:
  [ Redis ]: userId → WS-3
Переслать между шлюзами:
  [ Pub/Sub ]
WS-шлюзы за балансером:
  [ least connections ]
Мёртвое соединение:
  [ heartbeat ] раз в 20–30 с
```

- ✗ `round robin` — соединения живут часами — по очереди они лягут неравномерно
- ✗ `PostgreSQL` — карта «кто где» меняется при каждом коннекте и нужна за доли миллисекунды — это память, а не БД
- ≈ `Kafka` (вместо `Pub/Sub`) — Тоже вариант: надёжнее и с историей, но задержка выше. Pub/Sub достаточно — история уже в БД.
- перестановки: 15 wrongWhy; напр. `Pub/Sub` в [ Redis ] → «это рассылка событий, а здесь — карта «юзер → шлюз»»; `least connections` в [ heartbeat ] → «это алгоритм балансера, а «мёртвое» соединение ловят ping/pong»

**Шаг 3 · Офлайн и статусы**

```text
Сервер: сначала [ сохранить ],
  потом разослать
Вернулся в сеть:
  GET /messages?after=[ lastSeq ]
Нет связи при отправке:
  [ outbox ] → ретрай, тот же id
Получил девайс → [ доставлено ]
Открыл чат → [ прочитано ]
```

- ✗ `разослать` — шлюз упал после рассылки — сообщение видели, а в истории его нет
- ✗ `page=1` — пока был офлайн, пришли новые — страницы сдвинулись; нужно «всё после последнего»
- ✗ `отправлено` — это когда сервер принял (ack), а не когда получил собеседник
- перестановки: 20 wrongWhy; напр. `lastSeq` в [ сохранить ] → «это курсор дочитки, а здесь — что сделать первым»; `доставлено` в [ прочитано ] → «это было раньше — когда девайс получил; открыл чат — прочитано»

**Шаг 4 · Схема**

```text
 A ══WS══→ [ WS-шлюз ]
             ↓ seq + сохранить
           [ Cassandra ]
 WS-1 ─→ [ Redis Pub/Sub ] ─→ WS-3
 B офлайн ─→ [ FCM / APNs ]
   ↓ открыл: GET after=lastSeq
```

- ✗ `CDN` — кеширует статику; сообщения приватные и живые
- ✗ `Elasticsearch` — поиск по сообщениям — вторичный индекс, не источник истины
- ≈ `PostgreSQL` (вместо `Cassandra`) — На старте хватит: индекс (chat_id, seq). Cassandra — когда поток сообщений огромный.
- ≈ `Kafka` (вместо `Redis Pub/Sub`) — Тоже вариант: надёжнее и с историей, но задержка выше.
- перестановки: 18 wrongWhy; напр. `Cassandra` в [ WS-шлюз ] → «клиент не ходит в БД; сокет держит шлюз»; `Kafka` в [ FCM / APNs ] → «у офлайн-юзера нет шлюза — читать некому; будит пуш»

**Грабли:** Сначала разослать, потом сохранить: падение между ними — сообщение пропало из истории · Повтор без clientMessageId — дубли при каждом обрыве · Redis Pub/Sub как доставка: офлайн-получатель всё потерял · Переподключение без jitter: после сбоя миллион клиентов кладёт шлюзы разом

**Что спросят дальше:** Как сделать групповой чат на 100 000 участников? · Как показать «печатает…» и «в сети»? · Как синхронизировать чат на нескольких устройствах одного юзера? · Как сделать end-to-end шифрование?

### sd1.7 «Платежи»

**Условие:** Оплата заказа в приложении маркетплейса: деньги списываются ровно один раз, даже при таймаутах и повторах; учёт сходится с банком до копейки. 🎯 Тренирует: Idempotency-Key, PSP и webhook, ledger и двойная запись, outbox, saga, сверка

**Теория:** Когда это платежи · Схема · Грабли

**Шаг 1 · API**

```text
POST /v1/payments
  [ Idempotency-Key ]: <uuid>
  {orderId, amount, currency}
amount: [ Long в копейках ]
← {id, status: [ PENDING ]}
Повтор с тем же ключом:
  ← [ сохранённый ответ ]
```

- ✗ `Double рублей` — двоичная дробь: 0.1 + 0.2 ≠ 0.3 — копейки поплывут
- ✗ `SUCCEEDED` — PSP ещё не ответил — деньги не списаны; финальный статус придёт позже
- ✗ `новый платёж` — двойное списание — ровно то, от чего защищает ключ
- ✗ `X-Request-Id` — id для логов; сервер по нему не дедуплицирует
- ≈ `BigDecimal` (вместо `Long в копейках`) — Тоже корректно — без ошибок округления. Long в копейках проще и быстрее; главное — не Double.
- перестановки: 15 wrongWhy; напр. `Long в копейках` в [ Idempotency-Key ] → «это тип суммы, а здесь — заголовок против дублей»; `PENDING` в [ сохранённый ответ ] → «статус мог измениться; отдают ровно то, что ответили в первый раз»

**Шаг 2 · PSP и webhook**

```text
Карту списывает: [ PSP ]
Webhook от PSP:
  1) проверить [ подпись ]
  2) дубль отсечь по [ eventId ]
Webhook потерялся:
  [ опрос статуса ] у PSP
```

- ✗ `свой процессинг` — хранить карты — аудит PCI DSS и огромный риск; списание отдают внешнему PSP
- ✗ `IP провайдера` — одного IP мало: адреса меняются, а подпись доказывает, что тело не подменено
- ✗ `amount` — две разные оплаты на одну сумму — вторую примут за дубль
- ✗ `ждать вечно` — деньги могли списаться, а заказ висит; через N минут спрашивают PSP сами
- ≈ `сверка` (вместо `опрос статуса`) — Ночная сверка тоже поймает, но заказ провисит до утра. Опрос через минуты — быстрее.
- перестановки: 15 wrongWhy; напр. `подпись` в [ PSP ] → «это проверка webhook, а здесь — кто списывает деньги»; `eventId` в [ опрос статуса ] → «дедуплицировать нечего — webhook не пришёл»

**Шаг 3 · Учёт денег**

```text
Учёт — [ ledger ], двойная запись:
  −1990 клиент, +1990 магазин
Ошибся? Не правим, а
  добавляем [ сторно-запись ]
PaymentSucceeded в Kafka:
  [ outbox ] в той же транзакции
Заказ, склад, платёж:
  [ saga ] + компенсации
Раз в сутки: [ сверка ] с PSP
```

- ✗ `UPDATE баланса` — история теряется — не доказать, откуда сумма; параллельные UPDATE теряют обновления
- ✗ `2PC` — внешний PSP в распределённую транзакцию не встанет, а сервисы будут ждать блокировки
- ✗ `сразу в Kafka` — БД записали, Kafka упала — событие потеряно; outbox пишет в ту же транзакцию
- ✗ `Redis` — в памяти и теряет последнюю секунду при падении — для денег нужен ACID
- перестановки: 20 wrongWhy; напр. `сторно-запись` в [ ledger ] → «это исправление ошибки, а здесь — сам журнал»; `saga` в [ сверка ] → «это шаги сервисов, а здесь — проверка расхождений»

**Шаг 4 · Схема**

```text
 App ─POST + Idempotency-Key─→
 Payment service ⇄ [ PSP ]
   ↓ одна ACID-транзакция
 [ PostgreSQL ]: ledger + outbox
   ↓ relay
 [ Kafka ] ─→ заказы, чеки
 ночью: [ сверка ] ledger ↔ PSP
```

- ✗ `Cassandra` — нет ACID-транзакций на несколько строк — ledger и outbox атомарно не записать
- ✗ `Redis` — в памяти: потеря последней секунды записей — потерянные деньги
- перестановки: 12 wrongWhy; напр. `PostgreSQL` в [ PSP ] → «это наша БД, а списывает карту внешний провайдер»; `Kafka` в [ сверка ] → «это брокер, а здесь — ночная проверка»

**Грабли:** OkHttp сам повторяет POST при сбое соединения — без Idempotency-Key это дубль · Баланс через UPDATE без журнала: не объяснить, откуда взялась сумма · Публикация в Kafka отдельно от транзакции: рассинхрон БД и событий · Нет сверки: расхождение с PSP найдут только жалобы клиентов

**Что спросят дальше:** Как сделать возврат (refund) частично? · Клиент закрыл приложение во время 3-D Secure — что дальше? · Как хранить Idempotency-Key и сколько? · Как платить в нескольких валютах?
