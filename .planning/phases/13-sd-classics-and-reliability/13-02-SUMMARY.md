## Дайджест уроков

### sd2.1 «Потеря связи — офлайн и сбои»

**Условие:** Приложение заметок и заказов должно работать в метро и лифте: запросы не висят, повтор не создаёт дублей, упавший сервис не добивают, правки без сети доходят до сервера. 🎯 Тренирует: таймауты, retry + backoff + jitter, Idempotency-Key, circuit breaker, fail-open/closed, офлайн-очередь, конфликты версий

**Теория:** Когда это про сбои · Схема · Грабли

**Шаг 1 · Таймауты и ретраи**

```text
Весь вызов целиком:
  [ callTimeout ]
Повторять: обрыв, таймаут, [ 503 ]
Не повторять: [ 400 ]
Пауза 1с→2с→4с… + [ jitter ]
POST: тот же [ Idempotency-Key ]
```

- ✗ `readTimeout` — ждёт только паузу между байтами — ответ, который капает по байту, может висеть минутами
- ✗ `новый UUID` — новый ключ на каждый повтор — сервер не узнает повтор и создаст второй заказ
- ✗ `сразу` — повтор без паузы — шторм: миллион клиентов добивает поднимающийся сервер
- ≈ `429` (вместо `503`) — Да, 429 тоже повторяют — но паузу берут из Retry-After, а не свою.
- перестановки: 24 wrongWhy; напр. `503` в [ callTimeout ] → «это код ответа, а здесь — лимит на весь вызов»; `400` в [ Idempotency-Key ] → «это код ответа, а здесь — чем сервер узнает повтор POST»

**Шаг 2 · Circuit breaker**

```text
Соседний сервис упал.
N ошибок подряд → [ open ]:
  сразу отдаём [ fallback ]
Через 30 с → [ half-open ]:
  1 пробный запрос
Упал rate limiter:
  [ fail-open ] — пропускать
Упал антифрод платежей:
  [ fail-closed ] — отказать
```

- ✗ `closed` — это обычный режим — запросы идут насквозь; после серии ошибок цепь размыкается
- ✗ `retry ×5` — долбить лежащий сервис — добивать его и держать свои потоки
- ✗ `ждать таймаут` — каждый запрос висит до таймаута — потоки и пользователь ждут впустую
- перестановки: 20 wrongWhy; напр. `half-open` в [ open ] → «пробовать ещё рано: сначала разомкнуть и переждать»; `fallback` в [ fail-closed ] → «это запасной ответ, а здесь — пускать ли платёж без проверки»

**Шаг 3 · Офлайн-очередь**

```text
Сохранить без сети:
  запись в [ Room ] (outbox)
  UI показывает сразу
Сеть вернулась:
  [ WorkManager ] (CONNECTED)
  шлёт с тем же [ Idempotency-Key ]
PUT /notes/7 {text, [ version ]}
Чужая правка новее → [ 409 Conflict ]
```

- ✗ `список в памяти` — процесс убьют — очередь пропадёт вместе с правками
- ✗ `NetworkCallback` — работает, пока приложение живо; процесс убит — отправка не случится
- ✗ `timestamp` — это Last Write Wins: сервер молча возьмёт последнее, чужая правка пропадёт, а часы телефона врут
- ✗ `200 OK` — сервер молча затрёт чужую правку — lost update
- перестановки: 20 wrongWhy; напр. `WorkManager` в [ Room ] → «это планировщик отправки, а здесь — где лежит правка»; `Idempotency-Key` в [ 409 Conflict ] → «это заголовок запроса, а здесь — ответ сервера»

**Шаг 4 · Схема**

```text
 App
  UI ←Flow─ [ Room ] (источник)
  outbox ─→ [ WorkManager ]
   ↓ таймауты, backoff+jitter
 API: дубль по [ Idempotency-Key ]
 Каталог ─→ рекомендации
   через [ circuit breaker ]
   открыт → [ fallback ] (топ)
```

- ✗ `Service` — обычный Service система убьёт в фоне; отложенную отправку переживёт WorkManager
- ✗ `кеш в памяти` — умрёт с процессом; источник для UI — локальная БД на диске
- ✗ `retry ×10` — долбить лежащего соседа — добить его и повесить свои потоки; предохранитель отвечает сразу
- перестановки: 20 wrongWhy; напр. `WorkManager` в [ Room ] → «это отправщик очереди, а UI читает данные из локальной БД»; `circuit breaker` в [ fallback ] → «он уже открыт; здесь — что отдать вместо рекомендаций»

**Грабли:** Ретрай без backoff и jitter: после падения сервера миллион клиентов добивает его в одну секунду · retryOnConnectionFailure в OkHttp по умолчанию включён — POST без Idempotency-Key может уйти дважды · Ретраить 4xx: 400 и 403 повтор не исправит, на 401 нужен refresh, а не повтор · Офлайн-правки только в памяти — процесс убит, правки пропали · LWW по часам телефона: часы врут, чужая правка молча пропадает

**Что спросят дальше:** Как показать пользователю, что правка ещё не синхронизирована? · Сервер стабильно отвечает 400 на запрос из outbox — что с ним делать? · Как разрешить конфликт, если правили с двух устройств? · Сеть «есть», но запросы не проходят — как это заметить?

### sd2.2 «Несколько БД — реплики, шарды, CDC»

**Условие:** Маркетплейс: заказы и оплаты, поиск по 10 млн товаров, корзина, история просмотров. Чтений в 50 раз больше записей, данные за 5 лет не влезают в один сервер. 🎯 Тренирует: SQL + NoSQL рядом, реплики и replication lag, read-your-writes, шардирование и hot shard, consistent hashing, CDC вместо двойной записи, инвалидация кеша

**Теория:** Когда это про несколько БД · Схема · Грабли

**Шаг 1 · Каждой задаче своё**

```text
Заказы, оплаты:
  [ PostgreSQL ]
Поиск по товарам:
  [ Elasticsearch ]
Корзина, сессии:
  [ Redis ]
История просмотров
  (млрд событий): [ Cassandra ]
```

- ✗ `Neo4j` — графовая — для обхода связей (друзья друзей), здесь связи не главное
- ✗ `Kafka` — журнал событий, а не база для запросов: события через него едут, но хранят их в БД
- ✗ `S3` — это файлы (фото, видео), а не записи с запросами
- ≈ `DynamoDB` (вместо `Redis`) — Тоже key-value из заметки 08 — корзина и сессии; managed-сервис в AWS.
- перестановки: 15 wrongWhy; напр. `Elasticsearch` в [ PostgreSQL ] → «поисковый индекс без транзакций; деньгам нужен ACID»; `DynamoDB` в [ Cassandra ] → «get/put по ключу; историю читают диапазоном по времени — нужна wide-column»

**Шаг 2 · Реплики**

```text
Запись → [ primary ]
Чтение каталога → [ реплики ]
Свой профиль после записи:
  с [ primary ] (read-your-writes)
Реплика отстаёт:
  [ replication lag ]
```

- ✗ `шард` — делит данные по ключу, а не копирует их — у каждого шарда своя часть
- ✗ `Redis` — кеш, а не копия БД: после записи там может лежать старое значение
- ✗ `deadlock` — это взаимная блокировка транзакций, а не отставание копий
- перестановки: 8 wrongWhy; напр. `реплики` в [ primary ] → «копии только повторяют журнал; запись принимает primary»; `реплики` в [ replication lag ] → «это кто отстаёт, а здесь — как называется отставание»

**Шаг 3 · Шарды**

```text
Заказы не влезли в одну БД.
«Мои заказы» → ключ шарда:
  [ userId ]
Раскладка равномерно: [ hash ]
Добавили узел — двигаем мало:
  [ consistent hashing ]
Один ключ — 30% нагрузки:
  [ hot shard ]
```

- ✗ `orderId` — заказы одного пользователя разъедутся — «мои заказы» пойдёт на все шарды
- ✗ `createdAt` — раскладка по дате: все новые заказы бьют в один шард
- ✗ `реплика` — копия всех данных: чтение масштабирует, а объём и запись — нет
- ≈ `consistent hashing` (вместо `hash`) — Тоже hash, причём лучший: при добавлении узла переезжает малая часть ключей.
- перестановки: 11 wrongWhy; напр. `hash` в [ userId ] → «это способ раскладки, а здесь — по какому полю делить»; `consistent hashing` в [ hot shard ] → «это раскладка, а здесь — как называется перегрев»

**Шаг 4 · Схема с CDC**

```text
 Order service
   ↓ запись (одна!)
 [ PostgreSQL ] ─→ реплики
   ↓ журнал (WAL)
 [ CDC ] (Debezium) ─→ [ Kafka ]
   ├→ [ Elasticsearch ] (поиск)
   └→ инвалидация: DEL в [ Redis ]
```

- ✗ `двойная запись` — сервис пишет в БД и в поиск сам: одно упало — данные разъехались навсегда
- ✗ `cron раз в час` — поиск отстаёт на час и каждый раз перечитывает всю базу
- ✗ `Redis Pub/Sub` — fire-and-forget: отключился потребитель — изменение потеряно навсегда
- перестановки: 20 wrongWhy; напр. `CDC` в [ PostgreSQL ] → «это чтение журнала изменений, а пишет сервис в источник истины»; `Elasticsearch` в [ Redis ] → «индекс уже выше; DEL — по ключу кеша»

**Грабли:** Двойная запись из кода в БД и в поиск/кеш: одно упало — данные разъехались · Свой профиль читают с реплики сразу после записи — «изменения откатились» · Ключ шарда не совпадает с главным запросом — scatter-gather по всем шардам · hash % N: добавили узел — переехали почти все ключи · «Возьмём NoSQL, потому что масштабируется» без причины — потом нужны транзакции и JOIN

**Что спросят дальше:** Как сделать операцию, затрагивающую два шарда? · Как перешардировать без простоя? · Поиск отстал от БД на минуту — это проблема? · Когда хватит одного PostgreSQL без NoSQL?

### sd2.3 «Наблюдаемость — логи, метрики, трейсы»

**Условие:** Сервис заказов и мобильное приложение. Пользователи пишут «лента грузится 10 секунд», ночью растут ошибки. Нужно узнавать о проблеме раньше пользователей и находить причину за минуты. 🎯 Тренирует: структурные логи и X-Request-Id, метрики RED/USE, p99 вместо среднего, Prometheus и Grafana, трейсинг OpenTelemetry, алерты по SLO, мобильная сторона

**Теория:** Когда это про наблюдаемость · Схема · Грабли

**Шаг 1 · Логи**

```text
Строка лога — [ JSON ] с полями
Сквозной id запроса:
  [ X-Request-Id ]
  создаёт [ приложение ]
Нельзя в логи: [ токены ]
Сбор: stdout → [ ELK ]
```

- ✗ `строка текста` — по свободному тексту не найти «все ошибки userId=42 за час»
- ✗ `диск сервера` — под пересоздали — логи исчезли; и искать по N серверам руками
- ✗ `userId` — у пользователя тысячи запросов; нужен id одного запроса сквозь все сервисы
- ≈ `шлюз` (вместо `приложение`) — Если клиент не прислал — шлюз создаёт сам. Но id из приложения связывает жалобу пользователя с логами сервера.
- ≈ `Loki` (вместо `ELK`) — Тоже вариант из заметки 12: ELK/OpenSearch или Loki — оба собирают логи в один поиск.
- перестановки: 29 wrongWhy; напр. `X-Request-Id` в [ JSON ] → «это одно поле, а здесь — формат всей строки»; `токены` в [ ELK ] → «это секреты, а здесь — где логи ищут»

**Шаг 2 · Метрики**

```text
Сервис (запросы): [ RED ]
  rate, errors, duration
Пул соединений, CPU: [ USE ]
Время ответа смотрим: [ p99 ]
Собирает [ Prometheus ] → Grafana
Метки: route, status
  нельзя: [ userId ]
```

- ✗ `среднее` — 98 быстрых и 2 по 5 с дают «нормальное» среднее — хвост не виден
- ✗ `p50` — медиана: половина запросов быстрее — медленный хвост не виден
- ✗ `Crashlytics` — собирает краши приложения, а не метрики сервера
