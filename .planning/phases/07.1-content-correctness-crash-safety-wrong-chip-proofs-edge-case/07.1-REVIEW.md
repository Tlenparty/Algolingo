## Warnings

### WR-01: scenarioWrongChip проходит вхолостую, если «неверное» облачко дало ✅

**Файл:** `shared/src/commonTest/kotlin/com/tlenparty/algolingo/e2e/E2eScenarios.kt:134-147`
**Проблема:** в упражнении `wrongAt.exId` первая ветка Feedback с `verdict != Wrong` просто сверяет заголовок «✅ Отлично!» и делает `return s`. Сценарий должен доказать, что «неверное облачко показывает ❌ и причину». Если движок (или контент после правки) примет облачко, тест зелёный, а ни ❌, ни причина ни разу не показаны. Lockstep тут не спасает: headless-редьюсер использует тот же движок и тоже скажет Ok.
**Исправление:** требовать, чтобы первая проверка этого упражнения была Wrong:
```kotlin
if (wrongAt != null && exId == wrongAt.exId) {
    if (!wrongPlayed) fail("$where: unreachable")
    if (p.check.verdict == Verdict.Wrong) {
        wrongSeen = true
        /* ...текущие проверки причины и дырки... */
    } else {
        assertTrue(wrongSeen, "$where: wrong chip '${wrongAt.text}' in hole ${wrongAt.hole + 1} was accepted")
        assertEquals("✅ Отлично!", m.title, where)
        return s
    }
}
```

### WR-02: WrongChipsTest проходит вхолостую при 0 программ

**Файл:** `shared/src/androidHostTest/kotlin/com/tlenparty/algolingo/lesson/WrongChipsTest.kt:62-95`
**Проблема:** нет ни одной проверки на непустой вход. Если `wrong_variants.json` окажется `[]` (ошибка в `wrong_programs()`, сайдкары без неверных облачков, регрессия фильтра `correct`), тест напишет `# 0 programs, 0 findings` и станет зелёным. `--check` это не поймает: генератор и файл будут согласованно пустыми. Сам `test_wrong_json_is_a_checked_output` проверяет только устаревание файла. В `LessonFuzzTest` такая защита есть (`assertTrue(lessons.isNotEmpty())`), здесь её нет.
**Исправление:**
```kotlin
assertTrue(entries.size >= 200, "wrong_variants.json: only ${entries.size} programs")
assertTrue(entries.map { it.lesson }.toSet().size >= 9, "not every lesson has wrong programs")
```
Ещё можно сверять с числом пар из каталога: все облачка банка, которые не входят в ok/acceptable, по всем дыркам.

### WR-03: на зависание без `while` WrongChipsTest висит бесконечно (D-05)

**Файл:** `shared/src/androidHostTest/kotlin/com/tlenparty/algolingo/lesson/WrongChipsTest.kt:51-55`, `tools/gen_content.py:517-574`
**Проблема:** зависание ловит только `tick()`, а его вставляют исключительно после строк `while (...) {`. G11 запрещает `while`/`do` в других формах, но не трогает остальные способы не завершиться: рекурсию (на JVM получится `StackOverflowError` и метка «crash» вместо «hang», на Native упадёт процесс), `generateSequence`/`repeat`/`for` по огромному диапазону, циклы внутри лямбд. При этом `observe()` вызывает `kinds()` прямо в потоке теста, без таймаута. Неверное облачко, которое зацикливает программу не через `while`, повесит весь `:shared:allTests`. Это прямо нарушает D-05: «тест не должен сам зависнуть». Сейчас в коде заметки 05 таких мест нет, но после правки контента это ничто не остановит.
**Исправление:** на JVM добавить страховочный таймаут поверх `tick()` и не полагаться на него как на основной механизм:
```kotlin
val f = java.util.concurrent.Executors.newSingleThreadExecutor { r -> Thread(r).apply { isDaemon = true } }
try {
    val kinds = f.submit<String> { c.getMethod("kinds").invoke(c.getField("INSTANCE").get(null)) as String }
        .get(30, java.util.concurrent.TimeUnit.SECONDS)
    ...
} catch (e: java.util.concurrent.TimeoutException) {
    return setOf("hang-untracked") // явная находка: tick() не покрыл этот цикл
} finally { f.shutdownNow() }
```
Ещё вариант: в G11 запретить рекурсию и вызовы `generateSequence` в коде заметки.

### WR-04: метки у дистрактора без причины принимаются, но никогда не проверяются

**Файл:** `tools/gen_content.py:361-374` (`check_tags`), `tools/gen_content.py:497-505` (`claim_for`)
**Проблема:** для `kind == "-"` проверка падает только при `why and not tags`. Bullet ``- `T` [hang]`` без причины проходит G9, но `claim_for` берёт chip-claim только при `why`, поэтому метка `[hang]` нигде не становится claim. Получается утверждение, которое выглядит проверенным, но не проверяется. Это противоречит строке докстринга «Every claim is a hard gate». Скрипт показал, что сейчас таких bullet нет, но защиты от их появления тоже нет.
**Исправление:** в `check_tags`:
```python
if kind == "-" and tags and not why:
    raise GenError(file, "G9", "%s: kind tag without a why is never checked; tag the @H overrides instead" % who)
```
и тест в `Tags`.

### WR-05: `[compile]` засчитывается за любую ошибку компиляции, диагностика выбрасывается

**Файл:** `shared/src/androidHostTest/kotlin/com/tlenparty/algolingo/lesson/WrongChipsTest.kt:46-50`
**Проблема:** вывод компилятора уходит в `ByteArrayOutputStream`, которым никто не пользуется. Любой `ExitCode != OK` превращается в `compile`. Если обвязка (`render_object(..., with_kinds=True)`, шим, classpath, версия JVM-таргета) сломается для отдельного урока, все его `[compile]`-утверждения станут зелёными по чужой причине. `classifierSanity` проверяет обвязку без `prelude()`, поэтому этот случай он не закрывает. Сверять текст ошибки D-01 не требует, но в отчёте она нужна, иначе найденное расхождение не понять.
**Исправление:** (1) хранить stderr компилятора и писать первые строки в `build/reports/wrong-chips.txt` для каждого `compile`. (2) Добавить контрольную программу на урок: эталон, собранный тем же путём (`render_object("V", ..., True)`, `"control": true`). Она обязана компилироваться и давать пустое множество. Если контроль не скомпилировался, это находка, а не `[compile]`.

### WR-06: поиск KB мигает пустым списком на каждое нажатие

**Файл:** `shared/src/commonMain/kotlin/com/tlenparty/algolingo/kb/ui/KbListScreen.kt:36-41,54-55`
**Проблема:** `value = null` выполняется в начале каждого перезапуска `produceState`. Поэтому на каждое нажатие клавиши список результатов исчезает минимум на 150 мс плюс время сканирования, а скролл сбрасывается. Пока идёт поиск, нет ни прежних результатов, ни индикатора, экран под полем ввода пустой. При быстром наборе пустой экран держится всё время. Вывод «Ничего не найдено» скрыт правильно, но остальное поведение регрессирует по сравнению с синхронной версией.
**Исправление:** до прихода нового результата показывать старый, а `null` оставить только для «ещё ни разу не искали»:
```kotlin
val hits by produceState<List<SearchHit>?>(null, query, notes) {
    if (query.isBlank()) { value = null; return@produceState }
    delay(150)
    value = withContext(Dispatchers.Default) { search(query) }
}
```
Тогда на время поиска «Ничего не найдено» стоит прятать отдельным флагом `searching`.

**Файл:** `shared/src/commonMain/kotlin/com/tlenparty/algolingo/kb/ui/KbListScreen.kt:40`, `shared/src/commonMain/kotlin/com/tlenparty/algolingo/kb/KbRepository.kt:55-67`

При наборе с паузами больше 150 мс устаревшие сканы работают параллельно. Утверждение в комментарии «a new query cancels the pending one» верно только до окончания `delay`.
**Исправление:** передать `ensureActive` в цикл, например сделать `search` suspend и вызывать `coroutineContext.ensureActive()` на каждой заметке. Или честно поправить комментарий.

### IN-04: проверка iOS-симулятора в smoke.sh не про тот девайс

**Файл:** `tools/smoke.sh:12`
**Проблема:** скрипт проверяет, что запущен хоть какой-то симулятор. `iosSimulatorArm64Test` запускает тесты на своём `device` (по умолчанию из KGP) через `simctl spawn --standalone`, и от запущенного симулятора это не зависит. Проверка даёт ложное «нет симулятора» там, где тест бы прошёл, и не ловит отсутствие нужного девайса.
**Исправление:** проверять, что `xcrun simctl list devices available` содержит device, который использует задача, либо убрать проверку и честно описать это в комментарии.

### IN-05: UI e2e на iOS входит в `:shared:allTests` и опирается на синглтон AppGraph

**Файл:** `shared/src/iosTest/kotlin/com/tlenparty/algolingo/e2e/E2eSmokeTest.kt:12-28`, `shared/src/commonMain/kotlin/com/tlenparty/algolingo/progress/ProgressRepository.kt:93-99`
**Проблема:** `iosTest` попадает в `iosSimulatorArm64Test`, поэтому полный проход всех уроков через UI каждый раз запускается внутри основного гейта. Тест рассчитывает, что в процессе он первый вызывает `AppGraph.progress(dataDir)`. Если появится любой второй тест, который вызывает `App()` или `AppGraph`, e2e получит чужой `dataDir` с непустым прогрессом и упадёт на «Опыт: 0 XP» в зависимости от порядка запуска.
**Исправление:** выделить в `AppGraph` тестовый сброс (`internal fun resetForTest()`) или передавать `ProgressRepository` в `App()` параметром.

### IN-06: тестовый манифест объявляет exported LAUNCHER-активити

**Проблема:** для `runComposeUiTest` достаточно объявить `ComponentActivity`. Intent-filter MAIN/LAUNCHER и `exported="true"` добавляют тестовому APK иконку в лаунчере. Этот лишний вход ловит monkey.

### IN-07: нет теста на проброс отмены в KbRepository.load

**Файл:** `shared/src/commonTest/kotlin/com/tlenparty/algolingo/kb/KbRepositoryTest.kt`
**Проблема:** ветки `catch (e: CancellationException) { throw e }` в `load()` ничем не покрыты. Если их уберут при рефакторинге (тогда `catch (e: Exception)` превратит отмену в `Result.failure`), тесты останутся зелёными, а уход с вкладки во время загрузки покажет «Не удалось загрузить базу знаний» вместо повтора.
**Исправление:** fake reader, который бросает `CancellationException`, и `assertFailsWith<CancellationException> { repo.load() }`, затем `repo.load().isSuccess` после замены reader.
