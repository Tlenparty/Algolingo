# Обработка ошибок в корутинах

Связано: [[Coroutines]], [[Structured Concurrency]], [[Coroutines. Вопрос ответ]]

Тема — это два переплетённых механизма:

1. **Отмена (cancellation)** — кооперативная остановка корутины через специальное исключение `CancellationException`. Штатный, ожидаемый способ завершения.
2. **Обработка ошибок (exception handling)** — что происходит, когда корутина падает с обычным исключением, и как оно распространяется по дереву корутин.

Оба механизма используют один канал — исключения, — но `CancellationException` обрабатывается особо и **не считается ошибкой**.

---

## 1. Как устроена отмена

### 1.1. Отмена кооперативна

`job.cancel()` не убивает поток принудительно — он лишь помечает `Job` отменённым (`isCancelled = true`) и просит код **самостоятельно** проверить это и остановиться. Корутина «узнаёт» об отмене только в специальных точках:

- **suspend-функции из `kotlinx.coroutines`** (`delay`, `yield`, `withContext`, `await`/`join` и т. д.) — сами проверяют отмену и бросают `CancellationException`.
- **Ручные проверки** в CPU-bound коде без естественных suspend-точек — `isActive` (проверка в условии) или `ensureActive()` (бросает сразу).

```kotlin
val job = scope.launch {
    var i = 0
    while (true) { i++ } // НЕ проверяет отмену — будет работать вечно
}
job.cancel() // помечен отменённым, но цикл этого не узнает

val job2 = scope.launch {
    while (isActive) { /* ... */ } // кооперативная проверка — остановится
}
```

`yield()` — тоже точка проверки отмены, плюс отдаёт диспетчер другим корутинам.

**Вывод:** долгие CPU-bound циклы без suspend-вызовов нужно явно усеивать `isActive`/`ensureActive()`, иначе `cancel()` не сработает вовремя.

### 1.2. `CancellationException` — не ошибка

Когда отменённая корутина доходит до следующей suspend-точки, внутри неё бросается `CancellationException`. Рантайм трактует его особо: он **не** распространяется как сбой родителю и **не** попадает в `CoroutineExceptionHandler`.

Если ловите `Exception`/`Throwable` в `try-catch` — `CancellationException` тоже туда попадёт. **Обязательно** перебрасывайте его дальше, иначе случайно «проглотите» отмену:

```kotlin
scope.launch {
    try {
        delay(1000)
    } catch (e: CancellationException) {
        throw e // обязательно прокинуть дальше!
    } catch (e: Exception) {
        // реальные ошибки — здесь
    }
}
```

> [!warning] Частая ошибка
> `catch (e: Exception) { log(e) }` без отдельной ветки для `CancellationException` делает корутину «неубиваемой» — отмена ловится как обычная ошибка, логируется, и корутина продолжает работать.

### 1.3. Очистка ресурсов — `finally` и `NonCancellable`

`finally` выполняется и при отмене — штатный способ освободить ресурсы. Но **suspend-вызов** внутри `finally` сам немедленно бросит `CancellationException` (корутина уже в состоянии отмены) — для доработки оборачивайте в `withContext(NonCancellable)`:

```kotlin
scope.launch {
    try {
        delay(1000)
    } finally {
        withContext(NonCancellable) {
            delay(100) // без NonCancellable тут бы тоже бросило CancellationException
            saveStateBeforeExit()
        }
    }
}
```

### 1.4. withTimeout / withTimeoutOrNull

Частный случай отмены: по истечении времени блок отменяется через `TimeoutCancellationException` (наследник `CancellationException`).

```kotlin
withTimeout(1000) { delay(2000) } // упадёт TimeoutCancellationException через 1с

val result = withTimeoutOrNull(1000) {
    delay(2000)
    "result"
} // result == null, наружу ничего не бросается
```

## 2. Как отменяются дочерние корутины (structured concurrency)

### 2.1. Job — это дерево

Каждая корутина создаёт свой `Job`, дочерний по отношению к `Job` родительского scope: `parentJob → child1, child2, ...`, у детей могут быть свои дети.

### 2.2. Правила распространения

1. **Отмена родителя → отменяет всех потомков**, рекурсивно, только вниз по дереву.
2. **Ошибка (не CancellationException) в обычном дочернем `Job` → пробрасывается вверх своему непосредственному родителю.** Родитель, получив её, сам переходит в отмену и каскадом отменяет всех остальных своих детей — ошибка одного ребёнка фатальна для всего scope.
3. **Если у родителя есть свой родитель — каскад идёт ещё выше**, пока не дойдёт до корня дерева или ближайшего `SupervisorJob` (см. 2.3), который его обрывает.
4. Соседи получают `CancellationException` немедленно, но физически останавливаются только на следующей suspend-точке (кооперативность).
5. Родитель ждёт завершения **всех** детей, прежде чем сам перейти в `Completed` — даже отменённый, он формально в `Cancelling`, пока не довершат отмену все дети.

**Получает ли родитель ошибку ребёнка? Да** — разбор на примере:

```kotlin
fun main() = runBlocking {
    val parent = launch {
        launch { // child 1
            delay(500)
            println("child 1 done") // не успеет — родитель отменится раньше
        }
        launch { // child 2
            delay(100)
            throw RuntimeException("boom")
        }
    }
    delay(1000)
    println("parent isCancelled = ${parent.isCancelled}") // true
}
```

child 2 падает через 100мс → исключение идёт вверх к `parent` → `parent` отменяется сам и каскадом отменяет child 1 (тот ещё спит в `delay(500)`, поэтому `"child 1 done"` не успевает напечататься). Если бы у `parent` был свой родитель — каскад пошёл бы дальше вверх.

### 2.3. SupervisorJob / supervisorScope — разрыв правила №2

`SupervisorJob` меняет одно: **ошибка ребёнка больше не отменяет родителя и соседей** — гасится изолированно в этом ребёнке. Отмена родителя по-прежнему отменяет всех детей (правило №1 не меняется — рвётся только распространение ошибок вверх/вбок). Дети под `SupervisorJob` друг с другом не связаны.

```kotlin
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
scope.launch { throw RuntimeException("error in child 1") } // не затронет child 2
scope.launch { delay(1000); println("child 2 completed normally") }
```

`supervisorScope { ... }` — то же самое как suspend-функция для блока кода, без отдельного `CoroutineScope`.

> [!warning] supervisorScope не "ловит" исключение, а только изолирует
> Сама упавшая корутина всё равно должна быть обработана отдельно (try-catch внутри неё или `CoroutineExceptionHandler`). Без этого исключение всё равно необработанное — просто не заденет соседей. И `CoroutineExceptionHandler` **никогда** не ловит `CancellationException` — ни с `SupervisorJob`, ни с обычным `Job`: рантайм (`Job.handleJobException`) явно исключает отмену из доставки в обработчик, она не сбой.

**Где именно произошёл `throw`, меняет поведение:**

**А. `throw` прямо в теле `supervisorScope { ... }`** (не во вложенном `launch`) — обычный синхронный throw, не «падение дочерней корутины». Пробрасывается наружу к коду, вызвавшему `supervisorScope`, ловится обычным `try-catch` вокруг вызова:

```kotlin
try {
    supervisorScope { throw RuntimeException("boom") } // не в launch
} catch (e: Exception) {
    println("Caught at call site: ${e.message}") // сработает
}
```

**Б. `throw` внутри дочернего `launch { ... }`** — ошибка вызывающему коду **не передаётся**:

```kotlin
launch { // outer
    supervisorScope {
        launch { throw RuntimeException("boom") } // child 1
    }
    launch { // child 2 — вне supervisorScope, но внутри outer
        delay(1000)
        println("child 2 done") // выполнится — никто его не тронул
    }
}
println("after supervisorScope") // выполнится сразу — launch не блокирует
```

Порядок: `outer` приостанавливается на `supervisorScope { ... }` → внутри child 1 падает, но `SupervisorJob` не отменяет ни `supervisorScope`, ни `outer` → `supervisorScope` дожидается своих детей и **возвращается нормально** → только после этого `outer` запускает child 2, которая ничего не знает о падении и спокойно допечатывает `"child 2 done"`.

> [!danger] SupervisorJob спасает дерево Job, но не спасает от краша процесса
> Исключение child 1 никуда не делось: без `CoroutineExceptionHandler` оно необработанное и на Android по умолчанию долетает до `Thread.UncaughtExceptionHandler`, убивая процесс — почти сразу, ещё до того, как child 2 успеет доработать `delay(1000)`. Изоляция в дереве `Job` ≠ обработка исключения: `SupervisorJob` защищает только от каскадной отмены по дереву, а от краша из-за необработанного исключения всё ещё отвечает `CoroutineExceptionHandler` (или `try-catch`).

### 2.4. Сравнение

| | `Job` (обычный) | `SupervisorJob` |
|---|---|---|
| Ошибка ребёнка отменяет родителя | да | нет |
| Ошибка ребёнка отменяет соседних детей | да (каскадом через родителя) | нет |
| Отмена родителя отменяет всех детей | да | да |
| Где применять | связанные, зависимые задачи (всё или ничего) | независимые задачи (один виджет упал — остальные живут) |

## 3. Где и как ловить ошибки

### 3.1. Локально — `try-catch` внутри корутины

```kotlin
scope.launch {
    try {
        riskyOperation()
    } catch (e: CancellationException) {
        throw e // отмену не глушим
    } catch (e: Exception) {
        println("Caught: ${e.message}")
    }
}
```

Плюс: ошибка не уходит в родителя — корутина обрабатывает её сама и продолжает жить.

### 3.2. Глобально — `CoroutineExceptionHandler`

Элемент `CoroutineContext`, ловящий **необработанные** исключения, дошедшие до самого верха дерева и не пойманные по пути.

```kotlin
val handler = CoroutineExceptionHandler { _, exception ->
    println("Caught globally: ${exception.message}")
}
val scope = CoroutineScope(Dispatchers.IO + SupervisorJob() + handler)
scope.launch { throw RuntimeException("boom") }
```

Ограничения:

- **Только для `launch`** (и наследников типа `actor`) — у `async` исключение всплывает через `await()`, в обработчик не уходит.
- **Должен стоять в контексте корневой/родительской корутины** — навешанный на дочерний `launch` обработчик не сработает: ищется только у самого верхнего `Job`.
- **Не перехватывает `CancellationException`** — отмена туда не долетает в принципе.

```kotlin
// НЕ сработает: handler на дочерней корутине
scope.launch {
    launch(handler) { throw RuntimeException("error") } // проигнорирован
}
// сработает: handler в контексте root
val scope2 = CoroutineScope(SupervisorJob() + handler)
scope2.launch { throw RuntimeException("error") }
```

### 3.3. Исключения в `async`

Не пробрасывается автоматически в момент падения — «упаковывается» в `Deferred` и всплывает только при `await()`:

```kotlin
val deferred = scope.async { throw RuntimeException("error in async") }
scope.launch {
    try {
        deferred.await() // именно тут вылетит
    } catch (e: Exception) {
        println("Caught from async: ${e.message}")
    }
}
```

Нюанс: если `async` создан под обычным `Job` (не `SupervisorJob`), отмена/проброс по дереву происходит **сразу** в момент падения — независимо от того, вызван `await()` или нет. `try-catch` вокруг `await()` лишь перехватывает то же самое исключение в вашем коде, а не управляет тем, когда оно случилось.

### 3.4. `withContext` — исключение как обычный `throw`

`withContext` не создаёт нового `Job`, а временно меняет контекст текущей корутины — исключение из неё всплывает как самый обычный `throw`:

```kotlin
scope.launch {
    try {
        withContext(Dispatchers.IO) { throw RuntimeException("io error") }
    } catch (e: Exception) {
        println("Caught: ${e.message}") // обычный try-catch
    }
}
```

### 3.5. Несколько детей упали одновременно — `suppressed exceptions`

Если под обычным `Job` почти одновременно упали несколько детей, наружу пробрасывается **первое** исключение, остальные прикрепляются к нему как `suppressed` (`exception.suppressedExceptions`):

```kotlin
scope.launch {
    launch { throw IOException("io") }
    launch { throw RuntimeException("rt") }
} // наружу уйдёт одно, второе — в suppressedExceptions
```

## 4. Резюме (шпаргалка на собес)

1. **Отмена кооперативна** — `cancel()` ставит флаг, реальная остановка на ближайшей suspend-точке или ручной `isActive`/`ensureActive()`.
2. **`CancellationException` — не ошибка**, а сигнал остановки. Ловите `Exception` — не забывайте перебрасывать `CancellationException` дальше.
3. **Очистка ресурсов** — `finally` (выполняется и при отмене); suspend-работу в `finally` — через `withContext(NonCancellable)`.
4. **Дерево `Job`**: отмена идёт только вниз (родитель → дети), ошибка обычного `Job` — вверх и вбок (ребёнок → родитель → остальные дети).
5. **`SupervisorJob`/`supervisorScope`** — рвут распространение ошибки вверх/вбок, но не отмены вниз. Каждый ребёнок обязан обработать свою ошибку сам — иначе она всё равно необработанная, просто не заденет соседей.
6. **`CoroutineExceptionHandler`** — только для `launch`, только на root-корутине/scope, не ловит `CancellationException`.
7. **`async`** — исключение всплывает через `await()`; отмена/распространение по дереву (если `Job` не supervisor) происходит сразу при падении, независимо от вызова `await()`.
8. **`withContext`** — смена контекста той же корутины, не новый узел дерева; исключение ведёт себя как обычный `throw`/`try-catch`.
9. **`SupervisorJob` ≠ обработка ошибки** — изолирует дерево `Job` от каскадной отмены, но необработанное исключение без `CoroutineExceptionHandler` всё ещё может уронить процесс.
