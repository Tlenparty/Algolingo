# Kotlin Multiplatform (KMP)

**Kotlin Multiplatform** — технология JetBrains для переиспользования Kotlin-кода между платформами (Android, iOS, desktop/JVM, web, backend) при сохранении **нативного UI и нативной интеграции** на каждой платформе. Стабилен с **Kotlin 1.9.20 (ноябрь 2023)**.

## Главная идея: делим логику, не делим UI (по умолчанию)

В отличие от Flutter/React Native, KMP **не навязывает** свой рантайм и UI-фреймворк. Базовый сценарий — вынести в общий код всё, что не про отрисовку:
- сетевой слой, парсинг, бизнес-логику, валидацию;
- модели данных, мапперы, use-case'ы;
- работу с БД, кэш, репозитории;
- ViewModel/презентеры (часто на корутинах).

А UI остаётся нативным: **Jetpack Compose / Views** на Android и **SwiftUI / UIKit** на iOS. Опционально UI тоже шарится через **[[KMP. Compose Multiplatform|Compose Multiplatform]]**.

## Как это компилируется

Kotlin — мультибэкендовый компилятор. Один общий код собирается под разные таргеты:

| Таргет | Бэкенд | Во что превращается |
| --- | --- | --- |
| Android / JVM / backend | **Kotlin/JVM** | JVM-байткод (`.class`, `.jar`, `.aar`) |
| iOS / macOS / Linux | **Kotlin/Native** (LLVM) | нативный бинарь / `*.framework` для Xcode |
| Web | **Kotlin/JS**, **Kotlin/Wasm** | JS-бандл / WebAssembly |

> [!info] Что физически уезжает в iOS-приложение
> Общий модуль компилируется Kotlin/Native в **`.framework`** (или `XCFramework`), который Xcode-проект подключает как обычную зависимость. iOS-разработчик вызывает Kotlin-код как обычный Objective-C/Swift API. Подробнее — [[KMP. iOS interop и корутины]].

> [!tip] Платформенные различия решает expect/actual
> Когда общему коду нужно что-то платформо-зависимое (генерация UUID, текущее время, доступ к файлам, БД-драйвер), используется механизм **`expect`/`actual`**: в `commonMain` объявляется «ожидаемый» API, в `androidMain`/`iosMain` — реализации. См. [[KMP. expect-actual]].

## Структура проекта (source sets)

```text
commonMain      // общий код — здесь живёт большая часть логики
├── androidMain  // реализации под Android (Context, Room, и т.д.)
├── iosMain      // реализации под iOS (через Kotlin/Native)
└── …
commonTest      // общие тесты
```

Иерархия и Gradle-конфигурация разобраны в [[KMP. Source sets и Gradle]].

## Зрелость памяти и корутин

> [!important] Старый «замораживающий» memory model мёртв
> Раньше Kotlin/Native требовал «замораживать» (`freeze()`) объекты для передачи между потоками — главная боль ранних KMP-проектов. С **Kotlin 1.7.20** включён **новый memory manager** (без freezing), а старый удалён. Сегодня `kotlinx.coroutines` работает мультиплатформенно почти как на JVM, многопоточность — без ритуалов.

## Когда выбирать KMP

> [!note] Сильные и слабые стороны на собесе
> **За:** нативный UX/перформанс, постепенное внедрение (можно вынести один модуль), переиспользование команды Kotlin, прямой доступ к платформенным API.
> **Против:** iOS-разработчику нужно немного вникнуть в Kotlin/настройку; экосистема библиотек уже, чем у чисто-нативной; шаринг UI (CMP) на iOS молод; debugging Kotlin/Native сложнее JVM.
> **Чем отличается от Flutter:** Flutter рисует свой UI собственным движком (Skia/Impeller) и несёт рантайм Dart; KMP по умолчанию использует нативный UI и не навязывает рантайм — делится только логика.
