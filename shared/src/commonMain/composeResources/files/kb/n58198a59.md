# Модуляризация

**Модуляризация** — разбиение приложения на независимые Gradle-модули. На Senior это одна из главных архитектурных тем: ускоряет сборку, изолирует команды, навязывает чистые границы.

## Зачем (что отвечать на собесе)

> [!important] Выгоды
> 1. **Скорость сборки** — Gradle пересобирает и **кэширует** только изменившиеся модули, остальные берёт из build cache; независимые модули собираются **параллельно**.
> 2. **Изоляция и границы** — модуль скрывает реализацию, наружу торчит только публичный API → меньше связности (low coupling).
> 3. **Переиспользование** — общие модули (core, design, network) тянут многие фичи.
> 4. **Команды** — разные команды владеют разными модулями без конфликтов.
> 5. **Контроль зависимостей** — фича не может случайно дёрнуть внутренности другой фичи.

## Стратегии деления

| Подход | Деление | Минус |
| --- | --- | --- |
| **By layer** | `:data`, `:domain`, `:presentation` | плохо масштабируется: правка фичи трогает все слои |
| **By feature** | `:feature_cart`, `:feature_profile` | лучше для масштаба, но риск дублирования общего |
| **Гибрид (рекомендуемый)** | feature-модули + `:core_*`/`:design`/`:network` | требует дисциплины |

## Паттерн API / IMPL

> [!info] Зачем разделять `:feature_x_api` и `:feature_x_impl`
> Чтобы фичи зависели **от контракта, а не от реализации**:
> • `:feature_x_api` — интерфейсы, модели, навигационные точки (лёгкий, его видят другие).
> • `:feature_x_impl` — реализация (её **не видит** никто, кроме DI-сборки в `:app`).
> Это инверсия зависимостей ([[SOLID]] → DIP) на уровне модулей: `feature_a_impl` зависит от `feature_b_api`, но не от `feature_b_impl`. Реализации связываются в графе DI ([[Dagger 2]]/[[Hilt]]) в `:app`. Так правка реализации одной фичи **не пересобирает** зависящие модули.

> [!tip] Gradle-нюансы
> • **`api` vs `implementation`** в зависимостях: `implementation` **не протекает** транзитивно (ускоряет сборку, прячет детали), `api` — пробрасывает дальше. По умолчанию — `implementation`, `api` только осознанно.
> • **Version catalogs** (`libs.versions.toml`) — единый источник версий зависимостей для всех модулей.
> • **Convention plugins** (`build-logic`) — общая конфигурация модулей без копипасты в каждом `build.gradle.kts`.

> [!warning] Чего избегать
> • **Циклические зависимости** модулей — Gradle их запрещает, это сигнал неверных границ.
> • **God-модуль `:core`**, в который сваливают всё — он становится узким горлышком сборки. Дробить core по назначению (`:core_network`, `:core_ui`, `:core_common`).
> • Преждевременная модуляризация на крошечном проекте — оверхед без выгоды.

> [!note] Связь с KMP
> В [[KMP]] модуль `shared` — это, по сути, мультиплатформенный модуль с теми же принципами: чёткий публичный API, скрытая реализация, деление по фичам/слоям.
