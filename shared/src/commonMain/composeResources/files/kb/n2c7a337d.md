# Гонка данных (Race Condition)

**Гонка данных** — ситуация, когда несколько потоков **одновременно** обращаются к общему изменяемому состоянию, и хотя бы один из них его **пишет**, без синхронизации. Итоговый результат зависит от порядка выполнения потоков (кто успел первым) → он **недетерминирован**.

> **На собес одной фразой:** гонка данных — это когда результат зависит от того, в каком порядке потоки успели прочитать/записать общую переменную. Причина — неатомарность операций и отсутствие синхронизации. Лечится атомиками, `Mutex`/`synchronized` или отказом от общего мутабельного состояния.

## Почему возникает: неатомарность

Безобидный на вид `counter++` — это **три** операции (read-modify-write):
1. прочитать текущее значение;
2. прибавить 1;
3. записать обратно.

Два потока могут прочитать одно и то же значение, оба прибавить 1 и записать — один инкремент **потеряется** (lost update).

```kotlin
var counter = 0   // общий мутабельный ресурс — БЕЗ синхронизации

fun main() {
    val threads = List(100) {
        Thread {
            repeat(1000) {
                counter++          // НЕ атомарно: read -> +1 -> write
            }
        }
    }
    threads.forEach { it.start() }
    threads.forEach { it.join() }

    println(counter)   // ожидаем 100_000, но получаем МЕНЬШЕ и каждый раз по-разному
}
```

## Как чинить

### 1. Атомарные операции (CAS)
Для одной переменной — `Atomic*`-классы: read-modify-write становится неделимым. См. [[Атомарность]].
```kotlin
import java.util.concurrent.atomic.AtomicInteger

val counter = AtomicInteger(0)
// ...
counter.incrementAndGet()   // атомарно -> ровно 100_000
```

### 2. Взаимное исключение (`Mutex` / `synchronized`)
Когда надо атомарно изменить **несколько** переменных или защитить целый блок — только один поток в критической секции одновременно.
```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

val mutex = Mutex()
var counter = 0

suspend fun inc() = mutex.withLock {   // критическая секция
    counter++
}
```
```kotlin
// «Классический» вариант на JVM
@Synchronized
fun inc() { counter++ }
```

### 3. Не делить мутабельное состояние (лучшее решение)
Нет общего изменяемого состояния — нет и гонки. Иммутабельные данные (`val`, `data class` + `copy()`), ограничение состояния одним потоком/корутиной (confinement), передача данных через сообщения/`Channel`.

## Гонка данных vs Race Condition (нюанс)

- **Data race** (гонка данных) — конкурентный доступ к одной ячейке памяти без синхронизации, хотя бы один пишет. Это про память.
- **Race condition** (состояние гонки) — шире: корректность зависит от тайминга/порядка. Может быть даже без data race (например, «проверил-потом-сделал», check-then-act).

На практике термины часто используют как синонимы, но на собесе различие плюс.
