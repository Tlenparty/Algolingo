
RecyclerView.RecycledViewPool — это класс, который используется для **повторного использования** (recycling) элементов представлений (ViewHolder), а точнее для **оптимизации повторного использования представлений в нескольких RecyclerView** в вашем приложении.

Когда в приложении используется несколько RecyclerView, каждый из которых имеет свой собственный пул переработанных (перераспределённых) представлений, то это может привести к увеличению затрат памяти и потере производительности. В таких случаях ==RecycledViewPool позволяет **совместно использовать пул переработанных представлений** между несколькими RecyclerView, что снижает потребление памяти и повышает производительность.==

### **Зачем нужен RecyclerView.RecycledViewPool?**

По умолчанию каждый RecyclerView имеет свой собственный пул переработанных представлений (представлений, которые были убраны с экрана и могут быть повторно использованы). Однако, если у вас есть несколько RecyclerView в одном экране, каждый из которых имеет свой собственный пул, это может привести к излишнему потреблению памяти, особенно если вы работаете с большими списками.

RecyclerView.RecycledViewPool позволяет централизованно управлять пулом представлений и **поделиться пулом между несколькими RecyclerView**. Это позволяет повторно использовать уже переработанные элементы представлений, что повышает производительность и уменьшает нагрузку на память.

### **Как работает RecycledViewPool?**

Когда вы создаете несколько RecyclerView в вашем приложении и хотите, чтобы они использовали один и тот же пул переработанных представлений, вы можете создать объект RecycledViewPool и установить его в каждый RecyclerView с помощью метода setRecycledViewPool().

**Пример использования RecyclerView.RecycledViewPool:**

Предположим, у вас есть два RecyclerView, которые должны использовать один общий пул переработанных представлений:
```kotlin
// Создаем RecycledViewPool
val viewPool = RecyclerView.RecycledViewPool()

// Настроим первый RecyclerView
val recyclerView1: RecyclerView = findViewById(R.id.recyclerView1)
recyclerView1.setRecycledViewPool(viewPool) // Используем общий пул

// Настроим второй RecyclerView
val recyclerView2: RecyclerView = findViewById(R.id.recyclerView2)
recyclerView2.setRecycledViewPool(viewPool) // Используем общий пул

// Устанавливаем адаптеры для RecyclerView
recyclerView1.adapter = MyAdapter()
recyclerView2.adapter = MyAdapter()
```

В этом примере оба RecyclerView будут использовать **один и тот же пул** переработанных представлений. Когда один из RecyclerView освобождает ViewHolder (то есть элементы, которые уже не видны на экране), другой RecyclerView может использовать эти представления, что экономит память и увеличивает производительность.

**Почему это полезно?**

1. **Оптимизация памяти**: Пул переработанных представлений предотвращает создание и уничтожение новых представлений каждый раз, когда они появляются на экране. Это полезно, если у вас есть несколько RecyclerView, так как объекты представлений (ViewHolder) могут быть повторно использованы между всеми этими списками.

2. **Улучшение производительности**: Когда каждый RecyclerView использует свой собственный пул, это может привести к большому количеству неиспользуемых объектов и затратам на их создание/удаление. Общий пул помогает уменьшить такие затраты.

3. **Совместное использование представлений**: Когда несколько списков (например, горизонтальный и вертикальный RecyclerView) показывают схожие данные, использование одного пула позволяет эффективно делиться переработанными представлениями между ними.

**Особенности работы с RecycledViewPool:**

• **Максимальное количество**: Пул имеет механизм ограничения на количество объектов в нем. Например, вы можете установить лимит на количество переработанных ViewHolder, чтобы не использовать слишком много памяти.

• **Автоматическое управление памятью**: Android автоматически управляет использованием памяти в пуле, используя эвикцию (удаление) старых или неактивных представлений из пула, если они не используются в течение некоторого времени.

**Пример с лимитом на количество представлений:**

Вы можете задать максимальное количество ViewHolder, которое может быть в пуле для каждого типа элемента:

```kotlin
val viewPool = RecyclerView.RecycledViewPool()

// Настройка лимита для типов элементов
viewPool.setMaxRecycledViews(MyAdapter.TYPE_ITEM, 10)  // 10 для типа TYPE_ITEM

// Устанавливаем общий пул для RecyclerView
recyclerView1.setRecycledViewPool(viewPool)
recyclerView2.setRecycledViewPool(viewPool)
// В этом примере мы задаем лимит на 10 переработанных представлений для каждого типа данных, которые обрабатываются в адаптере.
```

### **Заключение**
RecyclerView.RecycledViewPool — это механизм для эффективного повторного использования представлений (ViewHolder) между несколькими RecyclerView. Это улучшает производительность, снижает потребление памяти и ускоряет работу приложения, особенно когда вы используете несколько RecyclerView в одном экране или внутри других компонентов.

## Payloads

**Payloads** в **RecyclerView** — это механизм, позволяющий передавать дополнительные данные при обновлении отдельных элементов списка, вместо того чтобы обновлять весь элемент. Это позволяет оптимизировать производительность и гибко управлять обновлением содержимого в RecyclerView.

***Payloads** позволяют передавать дополнительные данные, которые указывают, что именно в элементе изменилось. Это позволяет обновить только ту часть элемента, которая изменилась, вместо того чтобы пересоздавать весь элемент.

**Как работают Payloads?**
Когда вызывается метод notifyItemChanged(position, payload), система передает объект **payload** в метод onBindViewHolder адаптера, который будет вызываться для этого элемента. Этот объект payload содержит информацию о том, какие именно данные нужно обновить в элементе.

**Пример использования Payloads:**

Допустим, у нас есть список пользователей, и мы хотим обновить только имя пользователя, не изменяя его фотографию и другие данные.

1. **Создаем адаптер**:
```kotlin
class UserAdapter : RecyclerView.Adapter<UserViewHolder>() {
    private var users: List<User> = emptyList()

    fun updateUsers(newUsers: List<User>) {
        val diffResult = DiffUtil.calculateDiff(UserDiffCallback(users, newUsers))
        users = newUsers
        diffResult.dispatchUpdatesTo(this)
    }

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): UserViewHolder {
        val binding = ItemUserBinding.inflate(LayoutInflater.from(parent.context), parent, false)
        return UserViewHolder(binding)
    }

    override fun onBindViewHolder(holder: UserViewHolder, position: Int, payloads: List<Any>) {
        val user = users[position]
        if (payloads.isEmpty()) {
            // Обновляем весь элемент
            holder.bindFull(user)
        } else {
            // Обновляем только измененную часть
            for (payload in payloads) {
                when (payload) {
                    is String -> {
                        // Обновляем только имя
                        holder.updateName(user.name)
                    }
                }
            }
        }
    }

    override fun getItemCount(): Int = users.size
}
```

2. **Используем DiffUtil для вычисления изменений**:
```kotlin
class UserDiffCallback(private val oldList: List<User>, private val newList: List<User>) : DiffUtil.Callback() {
    override fun getOldListSize(): Int = oldList.size

    override fun getNewListSize(): Int = newList.size

    override fun areItemsTheSame(oldItemPosition: Int, newItemPosition: Int): Boolean {
        return oldList[oldItemPosition].id == newList[newItemPosition].id
    }

    override fun areContentsTheSame(oldItemPosition: Int, newItemPosition: Int): Boolean {
        return oldList[oldItemPosition] == newList[newItemPosition]
    }

    override fun getChangePayload(oldItemPosition: Int, newItemPosition: Int): Any? {
        val oldUser = oldList[oldItemPosition]
        val newUser = newList[newItemPosition]

        // Если изменилось имя, возвращаем его как payload
        return if (oldUser.name != newUser.name) {
            newUser.name // передаем только измененное значение
        } else {
            null
        }
    }
}
```

3. **Обновление данных**:
```kotlin
// Например, обновляем имя пользователя
val updatedUser = User(id = 1, name = "New Name", photoUrl = "url_to_photo")
val updatedList = users.map { if (it.id == updatedUser.id) updatedUser else it }
userAdapter.updateUsers(updatedList)
```

**Важные моменты:**

• **Метод** getChangePayload в DiffUtil.Callback определяет, какие данные были изменены. Он возвращает объект **payload**, который может быть использован в onBindViewHolder для частичного обновления элемента.

• **Метод** onBindViewHolder(holder, position, payloads) в адаптере теперь получает второй параметр — **payloads**. Это список, содержащий все объекты payload для данного элемента. Если **payloads пустой**, это означает, что весь элемент должен быть обновлен.

**Преимущества использования Payloads:**

• **Эффективность**: Вместо обновления всего элемента вы можете обновить только ту его часть, которая изменилась (например, только текст или изображение).

• **Оптимизация производительности**: Это уменьшает нагрузку на UI и помогает избежать ненужных перерасходов ресурсов (перерисовка всех элементов).

• **Гибкость**: Payloads позволяют передавать любые данные, которые нужны для обновления части элемента.

**Заключение:**
**Payloads** в **RecyclerView** — это мощный механизм для частичного обновления данных в списке. Вместо того чтобы пересоздавать весь элемент, можно обновить только те части, которые действительно изменились. Это улучшает производительность, особенно в случае, когда данные содержат большие элементы, и необходимо обновлять только их часть.

AdapterDelegate — это библиотека, которая **упрощает работу с** RecyclerView.Adapter, избавляя от **многочисленных** ViewType **и** when**-блоков**.

**❌ Стандартный RecyclerView.Adapter без AdapterDelegate**

Когда у нас **разные типы элементов**, код быстро становится сложным:
```kotlin
override fun getItemViewType(position: Int): Int {
    return when (items[position]) {
        is TextItem -> 0
        is ImageItem -> 1
        else -> throw IllegalArgumentException("Unknown type")
    }
}

override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): RecyclerView.ViewHolder {
    return when (viewType) {
        0 -> TextViewHolder(LayoutInflater.from(parent.context).inflate(R.layout.item_text, parent, false))
        1 -> ImageViewHolder(LayoutInflater.from(parent.context).inflate(R.layout.item_image, parent, false))
        else -> throw IllegalArgumentException("Unknown viewType")
    }
}
```

❌ **Проблемы:**

• when**-блоки громоздкие** (легко сделать ошибку).
• **Каждый** ViewHolder **создаётся вручную**.
• **Сложно расширять** (новый ViewType → новый when).

**🚀 Решение с AdapterDelegate**

🔹 **Каждый** ViewType **превращается в** delegate **(отдельный класс, отвечающий за отрисовку).**

**✅ Шаг 1: Устанавливаем зависимость**

```kotlin
dependencies {
    implementation "com.hannesdorfmann:adapterdelegates4:4.3.2"
}
```

**✅ Шаг 2: Создаём модели данных**
```kotlin
sealed class ListItem

data class TextItem(val text: String) : ListItem()
data class ImageItem(val imageUrl: String) : ListItem()
```

**✅ Шаг 3: Создаём AdapterDelegate для каждого типа элемента**
```kotlin
fun textItemDelegate() = adapterDelegateViewBinding<TextItem, ListItem, ItemTextBinding>(
    { inflater, parent -> ItemTextBinding.inflate(inflater, parent, false) }
) {
    bind { binding.textView.text = item.text }
}

fun imageItemDelegate() = adapterDelegateViewBinding<ImageItem, ListItem, ItemImageBinding>(
    { inflater, parent -> ItemImageBinding.inflate(inflater, parent, false) }
) {
    bind { binding.imageView.load(item.imageUrl) }
}
```

📌 **Здесь каждый** delegate **отвечает за свой** ViewType.

**✅ Шаг 4: Собираем AdapterDelegatesManager**

```kotlin
class MyAdapter : ListDelegationAdapter<List<ListItem>>() {
    init {
        delegatesManager.addDelegate(textItemDelegate())
        delegatesManager.addDelegate(imageItemDelegate())
    }
}
```
📌 **Теперь** RecyclerView.Adapter **управляет только делегатами, без** when**!**

```kotlin
val adapter = MyAdapter()
adapter.items = listOf(
    TextItem("Hello"),
    ImageItem("https://example.com/image.png"),
    TextItem("World")
)
recyclerView.adapter = adapter
```

**📌 Как работает AdapterDelegate под капотом?**

1️⃣ **Определяется** ViewType **по классу (**isInstance()**)**.
2️⃣ **Каждый** ViewType **получает** ViewHolder **из** delegate.
3️⃣ **Вызов** bind() **в нужном** delegate.
4️⃣ **Неиспользуемые** delegate **игнорируются**.


### **setHasFixedSize(true) в RecyclerView**

```kotlin
recyclerView.setHasFixedSize(true)
```

> [!warning] Частое заблуждение
> `setHasFixedSize(true)` **НЕ означает**, что все элементы одинакового размера. Он говорит, что **размер самого RecyclerView не зависит от содержимого адаптера** — то есть габариты RV фиксированы (`match_parent` или конкретные dp), и при изменении данных (`notifyItem...`) RecyclerView **не нужно перезапрашивать свой размер** (`requestLayout`) у родителя. Это экономит лишний проход measure/layout.

**🔹 Когда стоит ставить `true`?**

- Размеры RecyclerView заданы жёстко (`match_parent`, фиксированные dp) и **не меняются** при добавлении/удалении элементов.

**🔹 Когда нельзя:**

- ❌ Если RecyclerView имеет **`wrap_content`** и его высота меняется в зависимости от количества/размера элементов — тогда RV обязан пересчитываться, и `true` приведёт к неправильной отрисовке.

(Размеры **отдельных item** при этом могут быть любыми/разными — это к `setHasFixedSize` отношения не имеет.)
