Choreographer — это системный компонент в Android, который управляет синхронизацией рендеринга пользовательского интерфейса с частотой обновления экрана. Он позволяет приложениям выполнять анимации и обновления интерфейса в нужные моменты, избегая разрыва кадров (frame drops) и обеспечивая плавность отображения.

**Основные функции Choreographer**

1. **Синхронизация с VSync** – Choreographer привязывает обновления UI к моменту начала нового кадра, предотвращая лишнюю работу процессора.
2. **Оптимизация анимаций** – он управляет вызовом метода doFrame(), который вызывается в начале каждого нового кадра (обычно 16 мс при 60 Гц).
3. **Работа с FrameCallback** – через `Choreographer.postFrameCallback()` можно зарегистрировать обработчик, который будет вызван перед отрисовкой нового кадра.

Публичный API — это `postFrameCallback()` / `postFrameCallbackDelayed()` с интерфейсом `FrameCallback.doFrame(frameTimeNanos)`. Внутри же Choreographer обрабатывает кадр в несколько фаз (внутренние типы коллбэков, недоступные публично): **input → animation → traversal (measure/layout/draw) → commit**.

**Как использовать Choreographer?**
```java
Choreographer.getInstance().postFrameCallback(new Choreographer.FrameCallback() {
    @Override
    public void doFrame(long frameTimeNanos) {
        // Код обновления UI или анимации
        Choreographer.getInstance().postFrameCallback(this); // Повторный вызов
    }
});
```

**Где используется?**

• Внутри Android для управления View и RecyclerView.
• В библиотеках анимации (например, ObjectAnimator).
• В играх и высокопроизводительном UI-коде.

Если работа UI привязана к Choreographer, это помогает избежать лагов и снижает нагрузку на процессор.

**📌 Пример использования Choreographer:**

```kotlin
class MyFrameCallback : Choreographer.FrameCallback {
    override fun doFrame(frameTimeNanos: Long) {
        // Здесь можно обновить UI или выполнить анимацию
        println("Frame rendered at: $frameTimeNanos")

        // Регистрируем коллбэк на следующий кадр
        Choreographer.getInstance().postFrameCallback(this)
    }
}

// В Activity или Fragment
val frameCallback = MyFrameCallback()

override fun onResume() {
    super.onResume()
    Choreographer.getInstance().postFrameCallback(frameCallback)
}

override fun onPause() {
    super.onPause()
    Choreographer.getInstance().removeFrameCallback(frameCallback)
}
```

### **📌 Нужно ли создавать Choreographer для каждого экрана?**

❌ **Нет, не нужно создавать его вручную для каждого экрана.**

По умолчанию Choreographer уже используется системой:

• View и ViewGroup сами синхронизируются с помощью Choreographer.
• RecyclerView, MotionLayout, TransitionManager и другие стандартные компоненты также используют его.
• Jetpack Compose автоматически оптимизирует рендеринг через Choreographer.


📌 **Когда стоит использовать Choreographer вручную:**

• Для создания кастомных анимаций или отрисовки.
• Для синхронизации сложных визуальных эффектов с частотой кадров.
• Для профилирования производительности и выявления пропусков кадров (например, в играх или сложной графике).

### **SurfaceFlinger в Android**

SurfaceFlinger — это системный сервис в Android, отвечающий за композитинг (отрисовку и отображение) графических буферов на экране. Он работает на уровне **низкоуровневого рендеринга** и управляет слоями (Surface) от различных приложений, комбинируя их в один окончательный кадр, который отправляется на дисплей.

**🔹 Основные задачи SurfaceFlinger**

1. **Композитинг (смешивание) слоев**

• Каждое приложение рисует свой UI в буферах (Surface), которые отправляются в SurfaceFlinger.

• SurfaceFlinger объединяет все буферы в один кадр с учетом прозрачности, порядка слоев и других параметров.

1. **Синхронизация с VSync**

• Отображение кадров привязывается к частоте обновления экрана, чтобы избежать разрывов кадров (screen tearing).

1. **Работа с GPU и Hardware Composer**

• Использует **Hardware Composer (HWC)** для передачи части работы на GPU и DSP, снижая нагрузку на CPU.

1. **Обновление экрана**

• Отправляет готовые кадры в Framebuffer, который затем выводится на дисплей.

**🔹 Как это работает?**

1. **Приложение** → Создает Surface и рисует в него (Canvas или OpenGL ES).
2. **SurfaceFlinger** → Получает буферы от всех приложений.
3. **Hardware Composer** → Выбирает, какие слои рисовать через GPU, а какие через аппаратные блоки.
4. **Вывод на экран** → Объединенный кадр отправляется в Framebuffer.

**🔹 Где используется SurfaceFlinger?**

• Вся система Android UI (от рисования View до SurfaceView и TextureView).

• В проигрывателях видео (например, ExoPlayer).

• В играх и OpenGL-приложениях.


**Пример связи между SurfaceView и SurfaceFlinger:**

1. SurfaceView создает Surface и отправляет его в SurfaceFlinger.

2. Приложение рисует кадры и отправляет их в BufferQueue.

3. SurfaceFlinger забирает кадры, смешивает их и передает в дисплей.

SurfaceFlinger — это ключевой компонент графической системы Android, который обеспечивает эффективное и плавное отображение UI. 🚀

> [!tip] Весь конвейер кадра одной картинкой
> **VSYNC** (сигнал дисплея ~ каждые 16.6 мс при 60 Гц) → **Choreographer** планирует кадр → **UI Thread** делает measure/layout/draw, формируя DisplayList → **RenderThread** отдаёт команды GPU → буфер кладётся в **BufferQueue** → **SurfaceFlinger** + **Hardware Composer (HWC)** компонуют слои всех приложений → кадр на дисплей.
>
> **Jank (пропуск кадра)** = не успели подготовить кадр за период VSYNC (>16 мс на 60 Гц). Причины: тяжёлая работа на UI-потоке, лишние measure/layout, аллокации в `onDraw`. Диагностика — Profile GPU Rendering, Systrace/Perfetto, Macrobenchmark.
