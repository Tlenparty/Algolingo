### **Перемещаются ли объекты в памяти JVM?**

Ответ: **Да, объекты могут перемещаться в памяти JVM.**

JVM использует **сборщик мусора (Garbage Collector, GC)**, который может перемещать объекты при работе.

### **Когда объекты могут перемещаться в памяти?**

• **Молодое поколение (Young Generation)** → Когда объект “стареет”, он может быть перемещен из Eden в Survivor Space или в Old Generation.

• **Компактность кучи (Heap Compaction)** → При сборке мусора в некоторых алгоритмах (например, G1 GC, Parallel GC) происходит дефрагментация памяти, и объекты могут перемещаться.

• **Перемещение объектов при отложенной инициализации** → Например, при JIT-компиляции или оптимизации.

### **Как узнать, переместился ли объект?**

Обычно JVM скрывает от нас детали расположения объектов в памяти. Но можно попытаться проверить:

**Пример на JNI (**System.identityHashCode()**):**

```kotlin
Object obj = new Object();
int hash1 = System.identityHashCode(obj);
System.gc(); // Запрос на сборку мусора (не гарантирует выполнение)
int hash2 = System.identityHashCode(obj);

System.out.println(hash1 == hash2); // Скорее всего, true, но адрес мог измениться

Метод System.identityHashCode(obj) возвращает тот же хеш-код, что и Object.hashCode(), но даже если объект переместится в памяти, этот хеш останется прежним.
```

### **Может ли измениться хешкод у объекта?**

Ответ: **Да, может, но не всегда.**

Хеш-код объекта в Java зависит от реализации метода hashCode(). Есть два основных варианта:

• **Если метод** hashCode() **не переопределен**, то используется реализация по умолчанию из класса Object, которая вычисляет хеш-код на основе адреса объекта в памяти (native hash). В этом случае **хеш-код объекта обычно остается неизменным** на протяжении жизни объекта.

• **Если метод** hashCode() **переопределен**, например, на основе значений полей объекта, то хеш-код может изменяться, если изменяются поля объекта. Это важно, если объект используется в HashMap, HashSet или других структурах, зависящих от хеш-кода.


## **Отличие System.identityHashCode(obj) и Object.hashCode()**

### **Object.hashCode()**

Это метод, определенный в классе Object, и он может быть **переопределен** в подклассах.

• Если метод **не переопределен**, он возвращает **уникальный идентификатор объекта**, который, как правило, основан на его адресе в памяти (но это не гарантируется).

• Если метод **переопределен**, он может возвращать любое значение, определенное разработчиком (например, на основе значений полей объекта).

```kotlin
class Person {
    String name;

    Person(String name) {
        this.name = name;
    }

    @Override
    public int hashCode() {
        return name.hashCode(); // Переопределенный hashCode()
    }
}

public class Main {
    public static void main(String[] args) {
        Person p1 = new Person("Alice");
        Person p2 = new Person("Alice");

        System.out.println(p1.hashCode()); // Завиcит от name
        System.out.println(p2.hashCode()); // Тоже завиcит от name, может совпадать с p1.hashCode()
    }
🔹 В этом примере hashCode() зависит от поля name, а не от фактического расположения объекта в памяти.
}

```

 
### **System.identityHashCode(obj)**
 
Этот метод **не зависит от переопределенного** hashCode(). Он всегда возвращает значение, которое было бы сгенерировано Object.hashCode(), если бы метод не был переопределен.

• Даже если hashCode() переопределен, System.identityHashCode(obj) возвращает оригинальный хеш-код объекта.

```kotlin
public class Main {
    public static void main(String[] args) {
        Person p = new Person("Alice");

        System.out.println(p.hashCode()); // Вернет хеш на основе name
        System.out.println(System.identityHashCode(p)); // Вернет оригинальный хеш объекта
    }
}
🔹 Даже если Person.hashCode() зависит от name, System.identityHashCode(p) все равно выдаст значение, которое не зависит от полей объекта.
```

### **Когда использовать System.identityHashCode(obj)?**

1. **Отладка** — если hashCode() переопределен, а вам нужен настоящий идентификатор объекта.
2. **Сравнение объектов по ссылке** — можно использовать как альтернативу ``==``, если equals() переопределен.
3. **Диагностика работы JVM** — можно проверить, переместился ли объект в памяти.

> [!info] Почему identity hash НЕ меняется при перемещении объекта
> Это ключевой момент. Identity-хеш (то, что возвращает `Object.hashCode()` по умолчанию и `System.identityHashCode()`) **не является адресом**. Он вычисляется **лениво** при первом запросе и затем **сохраняется в заголовке объекта** (mark word). Поэтому, даже когда GC перемещает объект и его физический адрес меняется, хеш остаётся прежним — он «приклеен» к объекту, а не к адресу. Если бы хеш был адресом, перемещающий GC ломал бы любую `HashMap`.

> [!warning] JIT не перемещает объекты в куче
> Пункт «перемещение объектов при JIT-компиляции» — неточность. **Перемещает объекты только GC.** JIT работает с другим: через **escape-анализ** он может вообще **не аллоцировать** объект в куче (scalar replacement — разложить на локальные переменные / положить на стек), если объект не «убегает» из метода. Это устранение аллокации, а не перемещение уже существующего объекта.

> [!tip] Какие GC двигают объекты, а какие нет
> • **Перемещающие (moving/compacting):** copying-сборка молодого поколения (Eden → Survivor → Old) — всегда копирует живые объекты; **G1**, **Parallel**, **ZGC**, **Shenandoah** — уплотняют кучу.
> • **Неперемещающие (исторически):** старый **CMS** в основном не компактил Old Gen (отсюда фрагментация и фоллбэк на Full GC).
> На Android используется **ART** со своим GC (например, Concurrent Copying), который тоже перемещает объекты.
