# KMP. expect / actual

Механизм **`expect`/`actual`** — способ объявить в общем коде API, у которого на каждой платформе **своя реализация**. Это «мультиплатформенный аналог интерфейса», но проверяемый компилятором: если для какого-то таргета нет `actual` — проект **не соберётся**.

## Базовый пример

```kotlin
// commonMain
expect fun randomUUID(): String

// androidMain
actual fun randomUUID(): String = java.util.UUID.randomUUID().toString()

// iosMain
import platform.Foundation.NSUUID
actual fun randomUUID(): String = NSUUID().UUIDString()
```

Работает для **функций, свойств, классов, объектов**:

```kotlin
// commonMain
expect class Platform() {
    val name: String
}

// androidMain
actual class Platform actual constructor() {
    actual val name: String = "Android ${android.os.Build.VERSION.SDK_INT}"
}

// iosMain
import platform.UIKit.UIDevice
actual class Platform actual constructor() {
    actual val name: String = UIDevice.currentDevice.systemName()
}
```

> [!info] expect/actual классы стали стабильными
> Долгое время `expect class` был в Beta и выдавал warning. В свежих версиях Kotlin **expect/actual классы стабилизированы**. На собесе достаточно знать, что они есть и что под капотом каждый `actual` — это отдельный тип в своём source set.

## actual через typealias — частый приём

Если на платформе уже есть подходящий тип, `actual` можно свести к существующему классу:

```kotlin
// commonMain
expect class Throwable

// на JVM достаточно:
actual typealias Throwable = java.lang.Throwable
```

Так делают, например, для `Parcelable`, `Date`, `AtomicReference` — переиспользуют платформенный тип без обёртки.

> [!warning] expect/actual — не единственный и часто не лучший способ
> Главная ловушка: новички пихают `expect/actual` повсюду. Чаще чище — **обычный интерфейс в `commonMain` + платформенные реализации**, прокинутые через DI:
> ```kotlin
> // commonMain
> interface Analytics { fun track(event: String) }
> // androidMain / iosMain — свои классы, регистрируются в Koin/вручную
> ```
> `expect/actual` оправдан, когда нужен **единый тип/функция без полиморфизма** (фабрики, top-level функции, платформенные синглтоны, typealias на нативный тип). Интерфейс — когда есть несколько реализаций или нужна подмена в тестах.

> [!tip] Правила, которые любят спросить
> • Каждый `expect`-объявление обязано иметь `actual` **в каждом** скомпилированном таргете — иначе ошибка компиляции (в этом сила: статическая гарантия полноты).
> • `actual` должен **точно** соответствовать сигнатуре `expect` (имя, параметры, типы).
> • `expect` не может иметь тела/реализации (кроме случаев с дефолтами в Kotlin последних версий) — это только контракт.
> • `actual`-класс может иметь **дополнительные** члены сверх объявленных в `expect`.
