
**📌 Пример: Создание кастомного Executor с Handler и Looper**

**1. Создание CustomExecutor с пулом потоков**

```kotlin
import android.os.Handler
import android.os.HandlerThread
import android.os.Looper
import java.util.concurrent.BlockingQueue
import java.util.concurrent.Executors
import java.util.concurrent.LinkedBlockingQueue
import java.util.concurrent.ThreadPoolExecutor
import java.util.concurrent.TimeUnit

class CustomExecutor {

    // Размеры пула потоков
    private val corePoolSize = 4      // Минимальное количество потоков
    private val maximumPoolSize = 8   // Максимальное количество потоков
    private val keepAliveTime = 60L   // Время простоя потоков до завершения

    // Очередь задач
    private val workQueue: BlockingQueue<Runnable> = LinkedBlockingQueue()

    // ThreadPoolExecutor для выполнения задач в пуле потоков
    private val threadPoolExecutor: ThreadPoolExecutor = ThreadPoolExecutor(
        corePoolSize,
        maximumPoolSize,
        keepAliveTime,
        TimeUnit.SECONDS,
        workQueue,
        Executors.defaultThreadFactory(),
        ThreadPoolExecutor.DiscardPolicy() // Политика отклонения задач при переполнении очереди
    )

    // HandlerThread и Handler для работы с Looper
    private val handlerThread = HandlerThread("CustomHandlerThread").apply { start() }
    val handler = Handler(handlerThread.looper)

    // Функция для выполнения задачи в пуле потоков
    fun execute(runnable: Runnable) {
        threadPoolExecutor.execute(runnable)
    }

    // Функция для выполнения задачи в Looper через Handler
    fun postToHandler(runnable: Runnable) {
        handler.post(runnable)
    }

    // Функция для остановки Executor и освобождения ресурсов
    fun shutdown() {
        threadPoolExecutor.shutdown()
        handlerThread.quitSafely()
    }
}
```

**2. Пример использования CustomExecutor в Android**

```kotlin
import android.os.Bundle
import android.os.Looper
import android.util.Log
import androidx.appcompat.app.AppCompatActivity

class MainActivity : AppCompatActivity() {

    private val customExecutor = CustomExecutor()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // Задача в пуле потоков (background thread)
        customExecutor.execute {
            Log.d("CustomExecutor", "Running in background thread: ${Thread.currentThread().name}")
            
            // Переход в UI поток
            if (Looper.myLooper() != Looper.getMainLooper()) {
                customExecutor.postToHandler(Runnable {
                    Log.d("CustomExecutor", "Back to handler thread: ${Thread.currentThread().name}")
                })
            }
        }
    }

    override fun onDestroy() {
        super.onDestroy()
        customExecutor.shutdown() // Освобождение ресурсов при закрытии активности
    }
}
```


**📌 Объяснение:**

1. **ThreadPoolExecutor:**

• corePoolSize: Минимальное количество потоков, которые всегда активны.
• maximumPoolSize: Максимальное количество потоков в пуле.
• keepAliveTime: Время ожидания перед завершением неиспользуемого потока.
• LinkedBlockingQueue: Очередь задач.
• ThreadPoolExecutor.DiscardPolicy: Политика отклонения задач при переполнении очереди.

2. **HandlerThread:**

• Создает отдельный поток с **Looper**, что позволяет отправлять задачи через **Handler**.

• **Handler** привязан к **Looper** этого потока, и задачи выполняются в порядке очереди.

3. **Выполнение задач:**

• execute(Runnable): Выполнение задачи в пуле потоков.

• postToHandler(Runnable): Отправка задачи в **Handler**, связанный с **HandlerThread**.

4. **Освобождение ресурсов:**

• shutdown(): Корректно завершает выполнение задач в **ThreadPoolExecutor** и закрывает **HandlerThread**.

> [!important] Как `ThreadPoolExecutor` реально решает, создавать ли поток
> Логика **неинтуитивная**, это классический вопрос на собесе:
> 1. Потоков меньше `corePoolSize` → создаётся новый поток (даже если другие свободны).
> 2. Иначе задача кладётся в **очередь**.
> 3. Только если очередь **переполнена**, создаются потоки сверх core — до `maximumPoolSize`.
> 4. Если и максимум достигнут, и очередь полна → срабатывает **RejectedExecutionHandler**.
> ⚠️ С **неограниченной** `LinkedBlockingQueue` (как в примере) шаг 3 **никогда не наступит**: очередь не переполнится, поэтому `maximumPoolSize = 8` бесполезен — фактически работают только 4 core-потока, а задачи копятся в очереди без предела (риск OOM).

> [!warning] `DiscardPolicy` молча теряет задачи
> При переполнении `DiscardPolicy` **тихо отбрасывает** задачу без исключения — данные пропадают незаметно. Варианты:
> • `AbortPolicy` (по умолчанию) — кидает `RejectedExecutionException`.
> • `CallerRunsPolicy` — выполняет задачу в вызывающем потоке (естественный backpressure).
> • `DiscardOldestPolicy` — выбрасывает самую старую задачу из очереди.

> [!tip] Стоит ли вообще писать свой Executor
> На практике сегодня — почти никогда. Для разовых пулов есть фабрики `Executors.newFixedThreadPool/newCachedThreadPool`, а в Kotlin фоновую работу делают **корутинами** (`Dispatchers.IO/Default`), которые внутри используют свой пул. Ручной `ThreadPoolExecutor` нужен, когда требуется тонкий контроль над размером пула, очередью и политикой отклонения. `HandlerThread` же удобен, когда нужно **строго последовательное** выполнение задач на одном потоке с `Looper`.
