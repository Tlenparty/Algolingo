# Performance. Обзор и метрики

Хаб по производительности Android. На Senior спрашивают не «что тормозит», а **как измерить, какие метрики важны и какими инструментами их ловить**. Оптимизация без измерения — антипаттерн.

## Три кита производительности

1. **Запуск (startup)** — как быстро приложение становится интерактивным. См. [[Performance. Baseline и Startup Profiles]].
2. **Плавность (rendering / jank)** — нет ли пропущенных кадров при скролле/анимациях. См. [[Performance. Рендеринг, jank и Macrobenchmark]].
3. **Память** — нет ли утечек и избыточных аллокаций, как ведёт себя GC. См. [[Performance. Память и утечки]].

## Типы запуска

| Тип | Что происходит | Цель |
| --- | --- | --- |
| **Cold start** | процесса нет → создаётся `Application`, потом первая Activity | самый дорогой, главный таргет оптимизации |
| **Warm start** | процесс жив, Activity пересоздаётся | дешевле |
| **Hot start** | Activity в памяти, выводится на передний план | почти мгновенно |

> [!important] Ключевые метрики запуска
> • **TTID (Time To Initial Display)** — время до первого отрисованного кадра.
> • **TTFD (Time To Full Display)** — время до полностью готового контента (вызывается вручную `reportFullyDrawn()`).
> Google советует cold start **< 500 мс**. Метрики видны в Play Console (Android Vitals), Macrobenchmark и Perfetto.

## Что считается «jank»

Кадр должен укладываться в бюджет: при **60 fps ≈ 16.6 мс**, при 90 fps ≈ 11 мс, при 120 fps ≈ 8.3 мс. Не уложились — кадр «пропущен» (dropped frame), пользователь видит рывок.

> [!info] Frozen frames и Android Vitals
> Play Console штрафует за два порога: **slow frames** (> 16 мс) и **frozen frames** (> 700 мс). Превышение бьёт по видимости в Play Store, поэтому это бизнес-метрика, а не только инженерная.

## Инструменты (что чем смотреть)

| Инструмент | Для чего |
| --- | --- |
| **Android Studio Profiler** | CPU, Memory, Energy, Network в реальном времени |
| **Perfetto / System Trace** | системная трассировка, поиск узких мест по потокам |
| **Macrobenchmark** | воспроизводимые замеры startup/scroll в CI |
| **Microbenchmark** | замер «горячих» функций/алгоритмов |
| **LeakCanary** | автоматический детект утечек в debug |
| **Layout Inspector / Compose recomposition counts** | лишние рекомпозиции |
| **Android Vitals (Play Console)** | реальные метрики с устройств пользователей (field data) |

> [!tip] Lab data vs Field data
> **Lab** (Macrobenchmark, локальные замеры) — воспроизводимо, но на твоих устройствах. **Field** (Android Vitals, Firebase Performance) — реальные пользователи, разные устройства/сети. Senior смотрит оба: лаб — чтобы ловить регрессии в CI, поле — чтобы знать реальную картину.

> [!warning] Главное правило
> **Сначала измерь, потом оптимизируй.** Преждевременная оптимизация по интуиции чаще вредит читаемости, чем помогает скорости. Профилируй → найди узкое место → исправь → перемерь.
