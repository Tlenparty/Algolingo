# 04 Авторизация

Как сервер узнаёт, кто прислал запрос (**аутентификация**), и решает, что ему можно (**авторизация**). Для мобилки это вопросы: сессия или JWT, как жить с access/refresh, как логиниться через OAuth2 и где хранить токены.

> [!tip] Аналогия из Android
> Access-токен — как временный пропуск в офис на день, refresh-токен — паспорт, по которому пропуск перевыпускают на ресепшене. А OkHttp `Authenticator` — это охранник, который на 401 сам идёт на ресепшен за новым пропуском и пускает запрос повторно.

## Как работает

### Сессии vs JWT

- **Сессия (stateful).** После логина сервер создаёт запись `sessionId → userId` в хранилище (часто Redis) и отдаёт `sessionId` клиенту (cookie или заголовок). На каждый запрос сервер идёт в хранилище. Плюс: отозвать доступ мгновенно — удалить запись. Минус: лишний поход в хранилище, нужен общий store для всех серверов.
- **JWT (stateless).** Токен `header.payload.signature`: в payload — `sub` (userId), `exp`, роли; подпись сервера (HS256/RS256/ES256). Любой сервер проверяет подпись без похода в БД. Минус: до `exp` токен не отозвать (только чёрным списком, что снова stateful). Payload — это base64url, **не шифрование**: секретов туда не класть.

### Access + refresh

```text
login ─► access(15 мин)+refresh(30 дн)
запрос + access ─► 200
...access протух...
запрос + access ─► 401
POST /token(refresh) ─► новые оба
повтор запроса ─► 200
```

Access — короткий JWT, шлётся в каждом запросе (`Authorization: Bearer ...`). Refresh — длинный, шлётся только на `/token`, сервер хранит его у себя (можно отозвать). Утёк access — вред ограничен минутами.

**Rotation + reuse detection.** На каждый refresh сервер выдаёт **новую пару**, старый refresh становится недействительным. Если кто-то приходит со старым (уже использованным) refresh — значит, его украли: сервер отзывает всю цепочку токенов этого устройства, пользователь логинится заново.

### OAuth2 Authorization Code + PKCE

Стандарт входа «через Google/VK/свой SSO» для мобилок. Мобильное приложение — **public client**: `client_secret` из APK достаётся декомпиляцией, поэтому вместо секрета используется PKCE.

```text
App: verifier = random(43..128)
     challenge=b64url(sha256(verifier))
App ─► браузер: /authorize?
       code_challenge=...&method=S256
Юзер логинится на сайте провайдера
Браузер ─► app://callback?code=XYZ
App ─► POST /token code=XYZ
       + code_verifier
Сервер: sha256(verifier) == challenge?
       ─► access + refresh
```

Смысл: перехватить `code` из redirect может чужое приложение с тем же deep link, но без `code_verifier` (он не покидал память приложения) обменять его на токены нельзя. Логин открывают в **Custom Tabs** (не WebView — там приложение может подсмотреть пароль), проверяют параметр `state` против CSRF. Готовая библиотека — AppAuth. Implicit flow (токен прямо в redirect) устарел.

### Где хранить токены

- **Не** в обычных `SharedPreferences`/файлах открытым текстом: на рутованном устройстве и в бэкапе они читаются.
- Шифровать ключом из **Android Keystore** (ключ не извлекается из устройства, часто аппаратный). Исторически — `EncryptedSharedPreferences`; библиотека security-crypto в 2025 помечена deprecated, сейчас чаще DataStore + шифрование через Keystore/Tink.
- Исключить файл токенов из Auto Backup (`dataExtractionRules`), на iOS — Keychain.

### Refresh под мьютексом

Пять параллельных запросов получили 401 → без защиты будет пять refresh-запросов, а с rotation четыре из них ещё и сработают как reuse и разлогинят пользователя. Поэтому refresh делается один раз под замком:

```kotlin
class TokenAuthenticator(
    private val store: TokenStore,
    private val api: AuthApi,
) : Authenticator {
    override fun authenticate(route: Route?, response: Response): Request? {
        if (responseCount(response) >= 2) return null
        synchronized(this) {
            val sent = response.request.header("Authorization")
            val current = "Bearer ${store.access}"
            // кто-то уже обновил, пока мы ждали замок
            if (sent != current) return withToken(response, store.access)
            val pair = api.refresh(store.refresh) ?: run {
                store.clear(); return null // → экран логина
            }
            store.save(pair)
            return withToken(response, pair.access)
        }
    }
}
// responseCount — длина цепочки priorResponse,
// withToken — копия запроса с новым Authorization
```

`Authenticator` вызывается синхронно на потоке OkHttp, поэтому `synchronized`; в suspend-коде то же самое делают `Mutex` из корутин. Ключевой приём — сравнить токен из упавшего запроса с текущим: если он уже другой, не рефрешить второй раз.

## Когда применять в SD-задаче

Сигналы: «логин», «вход через соцсети», «остаться залогиненным месяц», «разлогинить на всех устройствах», «украли телефон».

Фраза на собес: «OAuth2 Authorization Code + PKCE через Custom Tabs; короткий access JWT и длинный refresh с ротацией и детектом повторного использования; токены шифрую ключом из Keystore; refresh один на все параллельные 401 — под мьютексом в OkHttp Authenticator».

> [!warning] Грабли
> - Refresh stampede: без мьютекса параллельные 401 сжигают refresh-токен, и пользователя выкидывает на логин.
> - Бесконечный цикл: если refresh тоже возвращает 401, `Authenticator` без счётчика попыток будет крутиться вечно — нужен лимит и `return null`.
> - JWT в payload читается кем угодно — не класть туда email/телефон, если это лишнее.
> - Logout должен отзывать refresh на сервере, а не только стирать токены на клиенте.
> - 403 не лечится refresh-ем: обновлять токен надо только на 401.

> [!question]- Сессия или JWT — что выбрать?
> Сессия — проще отзыв (удалил запись), но каждый запрос требует общего хранилища. JWT — проверяется подписью на любом сервере без похода в БД, удобно для микросервисов и масштаба, но не отзывается до `exp`. На практике — гибрид: короткий JWT-access (минуты) + refresh, хранящийся на сервере и отзываемый.

> [!question]- Зачем нужен PKCE, если есть client_secret?
> Мобильное приложение не может хранить секрет: APK декомпилируется. Без секрета перехваченный authorization code (например, другим приложением с тем же deep link) можно обменять на токены. PKCE привязывает code к случайному `code_verifier`, известному только этому запуску приложения: сервер принимает обмен, только если `sha256(verifier)` совпал с присланным ранее `code_challenge`.

> [!question]- Как избежать параллельных refresh, когда несколько запросов получили 401?
> Один `Authenticator` на клиент, refresh под `synchronized`/`Mutex`. Войдя в замок, сравнить токен из упавшего запроса с текущим сохранённым: если они различаются — токен уже обновил другой поток, просто повторить запрос с новым. Иначе сделать refresh, сохранить пару, повторить. При неудаче refresh — очистить токены и отправить на логин.

> [!question]- Чем 401 отличается от 403 в контексте авторизации?
> 401 — аутентификация не прошла: токена нет, он протух или подпись неверна — клиент рефрешит токен или ведёт на логин. 403 — пользователь опознан, но прав на ресурс нет — refresh не поможет, нужно показать «нет доступа».
