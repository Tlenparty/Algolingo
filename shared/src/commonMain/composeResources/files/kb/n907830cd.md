**Data class** в Kotlin — это специальный тип класса, предназначенный для хранения данных. Такие классы автоматически предоставляют стандартные реализации для методов, таких как equals(), hashCode(), toString(), copy() и др., что облегчает работу с объектами, содержащими только данные (свойства).

Ключевое отличие **data class** от обычного класса заключается в том, что в нем все поля считаются значимыми и используются для вычисления стандартных методов.
**Основные особенности Data Class:**

1. **Автоматическая генерация методов:**

При объявлении класса как data class, Kotlin автоматически генерирует несколько стандартных методов:

• equals(): Сравнивает два объекта класса по значениям их свойств.
• hashCode(): Генерирует хэш-код на основе значений свойств.
• toString(): Создает строковое представление объекта в виде“ClassName(property1=value1, property2=value2)”.
• copy(): Создает копию объекта, с возможностью изменения некоторых свойств.
• (Если есть свойства с модификаторами val или var) componentN(): Автоматически генерируются методы для доступа к значениям свойств по порядку (для деструктуризации объектов).

2. **Конструктор с параметрами:** В **data class** параметры конструктора автоматически становятся свойствами класса.

3. **Необходимые требования для использования** data class**:**

• Класс должен быть final (по умолчанию), то есть не может быть абстрактным или наследоваться.
• Он должен содержать хотя бы один параметр в конструкторе.
• Все свойства конструктора должны быть либо val, либо var.

### **Почему нельзя наследовать Data Class?**

• **Data class** нельзя наследовать, потому что они автоматически генерируют стандартные методы, такие как equals(), hashCode() и toString(), которые зависят от всех свойств в классе. Наследование и переопределение этих методов может нарушить их логику, так как потомки могут изменить поведение этих методов.

• Если вам нужно расширить функциональность класса данных, можно использовать обычный класс и вручную реализовать эти методы или использовать композицию, а не наследование.

### Почему лучше не стоит использовать var в data class  ? 

**1. Нарушение концепции неизменности (immutability):**
Одной из основополагающих концепций при использовании **data class** является принцип **неизменности** (immutable objects). Когда вы создаете объект данных, хорошей практикой является использование val для всех свойств, чтобы объект после создания нельзя было изменить.

Использование var в **data class** нарушает эту концепцию, так как свойство становится изменяемым, и объект может быть изменен после его создания. Это приводит к следующими проблемам:

• Потенциально сложнее отслеживать изменения объекта, особенно когда это данные, которые передаются между различными частями программы или компонентами.

• Усложняется поддержка, особенно когда объекты передаются по ссылке и могут быть изменены в одном месте, что влияет на другие части кода.

**2. Проблемы с equals() и hashCode():**

Методы equals() и hashCode() в **data class** автоматически генерируются на основе всех свойств класса. Если вы используете var для одного из этих свойств, то изменение значения этого свойства может нарушить правильное поведение этих методов.

• equals(): Сравнивает два объекта на основе значений их свойств. Если свойство изменится после создания объекта, то два объекта с одинаковыми значениями полей могут начать восприниматься как разные из-за изменения значения одного из полей.

• hashCode(): Метод, который генерирует уникальный хэш-код объекта на основе его значений. Если одно из полей изменяется, то хэш-код объекта изменится, что нарушит его способность работать в коллекциях, таких как HashMap, где хэш-код используется для поиска.

**3. Лучше использовать copy() для изменения данных

Когда вам нужно изменить значения свойств в объекте **data class**, лучше использовать метод copy(), который генерируется автоматически в data class. Это позволяет создать новый объект с измененным значением, не изменяя сам исходный объект, что сохраняет неизменность.

**4. Непредсказуемое поведение в многозадачности:**

Когда данные изменяются после создания объекта, особенно если объект используется в многозадачном или многопоточном контексте, это может привести к проблемам с синхронизацией и состоянием данных.

Использование val для всех свойств делает объект потокобезопасным, так как данные не могут быть изменены после создания. Это уменьшает вероятность ошибок при параллельной работе с объектами.

**Минусы data class**

1. Они не поддерживают наследование.
2. Могут быть проблемами с производительностью при работе с большими объемами данных.
3. Автоматически генерируются методы toString(), equals(), hashCode() и copy(), что может ограничить гибкость.
4. Не поддерживают управление деструктуризацией и сериализацией для сложных случаев.

## **Что можно переопределить у data class ??** 

toString() - для безопасности лучше переопределить, чтобы не было утечек данных из конструктора.

### **Функция componentN() в Kotlin**

Функции componentN() в Kotlin используются для ==**деструктуризации объектов**==. Они позволяют получать отдельные части объекта, если он является **data class** или реализует operator fun componentN() вручную.

**✅ 1. componentN() в data class**

При объявлении data class, Kotlin автоматически создаёт методы componentN() для его свойств (где N — номер свойства).

Пример:
```kotlin
data class User(val name: String, val age: Int)

fun main() {
    val user = User("Alice", 25)

    // Вызовы componentN() вручную (редко используются так)
    println(user.component1()) // "Alice"
    println(user.component2()) // 25

    // Деструктуризация (использует componentN() автоматически)
    val (name, age) = user
    println(name) // "Alice"
    println(age)  // 25
}
```

 **Как это работает?**

• component1() → возвращает name
• component2() → возвращает age
• При деструктуризации (val (name, age) = user) **Kotlin сам вызывает** component1() **и** component2().

**✅ 2. componentN() в List**

В List (и Array) тоже есть componentN() для доступа к элементам

```kotlin
fun main() {
    val numbers = listOf(10, 20, 30)

    // componentN() в списке
    println(numbers.component1()) // 10
    println(numbers.component2()) // 20
    println(numbers.component3()) // 30

    // Деструктуризация списка (использует componentN())
    val (first, second, third) = numbers
    println(first)  // 10
    println(second) // 20
    println(third)  // 30
}
```

**✅ 3. Реализация componentN() вручную**

Можно определить componentN() вручную в обычном классе:

```kotlin
class Point(val x: Int, val y: Int) {
    operator fun component1() = x
    operator fun component2() = y
}

fun main() {
    val point = Point(3, 7)

    // Деструктуризация (вызывает component1() и component2())
    val (a, b) = point
    println(a) // 3
    println(b) // 7
}
```

🔹 Теперь `Point` поддерживает деструктуризацию, хотя это обычный класс, а не `data class`.

> [!tip] Частые вопросы на собесе
> - **Почему `data class` нельзя наследовать?** Сгенерированные `equals`/`hashCode`/`copy` строятся по полям первичного конструктора; наследование сломало бы их контракт. Расширяй через композицию.
> - **`equals`/`hashCode` учитывают только свойства первичного конструктора.** Поля, объявленные в теле класса, в них **не** попадают (и в `toString`/`copy` тоже).
> - **`copy()` — поверхностная (shallow).** Вложенные объекты копируются по ссылке.
> - **`var` в data class опасен:** объект-ключ в `HashMap` «потеряется», если после вставки изменить поле (поменяется `hashCode`). Предпочитай `val` + `copy()`.
