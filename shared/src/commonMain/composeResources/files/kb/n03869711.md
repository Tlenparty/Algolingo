# Корутины

**Корутины** в Kotlin — это легковесный механизм асинхронного программирования: код выполняется в неблокирующем режиме, но выглядит как синхронный. Они дают высокоуровневый способ работы с потоками и асинхронными операциями, упрощая управление многопоточностью.

## Базовые интерфейсы

`CoroutineScope` нужен только для того, чтобы корутина могла получить `CoroutineContext`:

```kotlin
interface CoroutineScope {
    val coroutineContext: CoroutineContext
}
```

`CoroutineContext` построен по паттерну **Компоновщик**: это дерево из вложенных элементов с общим родителем. Обычные элементы (`Job`, `CoroutineName`, `CoroutineDispatcher`) — «листья»:

```kotlin
interface Element : CoroutineContext {
    val key: Key<*>

    // переопределённый get позволяет писать coroutineContext[Job]
    // вместо coroutineContext.get(Job)
    override operator fun <E : Element> get(key: Key<E>): E? =
        if (this.key == key) this as E else null
}
```

`Continuation` — это «продолжение» после приостановки корутины (то самое состояние `SUSPENDED`). Никакой магии: при возобновлении сюда кладутся результаты suspend-функций:

```kotlin
public interface Continuation<in T> {
    public val context: CoroutineContext

    // вызывается после возврата корутины из приостановки;
    // сюда кладётся результат suspend-функции
    public fun resumeWith(result: Result<T>)
}
```

## CoroutineContext

**CoroutineContext** описывает контекст корутины: как и где она выполняется (поток/диспетчер), какие данные ей доступны, как обрабатываются исключения. Каждая корутина запускается с определённым контекстом.

Контекст состоит из элементов, реализующих `CoroutineContext.Element`. Основные:

1. **Job** — описывает работу корутины: её состояние (запущена, отменена, завершена), управление жизненным циклом (отмена). Примеры: `Job()`, `SupervisorJob()`.
2. **CoroutineDispatcher** — определяет поток/пул потоков:
    - `Dispatchers.Main` — главный (UI) поток;
    - `Dispatchers.IO` — операции ввода-вывода (файлы, сеть);
    - `Dispatchers.Default` — CPU-интенсивные задачи;
    - `Dispatchers.Unconfined` — текущий поток (до первой приостановки).
3. **CoroutineName** (опционально) — имя корутины для отладки: `CoroutineName("MyCoroutine")`.
4. **CoroutineExceptionHandler** — обработчик необработанных исключений.

> Элементы контекста комбинируются оператором `+`: `Dispatchers.IO + SupervisorJob() + CoroutineName("io")`.

## Билдеры корутин: launch, async, runBlocking, withContext

### 1. launch

Запускает корутину, которая **не возвращает результат** (аналог `Runnable`).

- Возвращает `Job` для контроля (отмена, ожидание).
- Выполнение начинается сразу (если не `CoroutineStart.LAZY`).
- Подходит для «fire-and-forget» задач, где результат не нужен.

```kotlin
val job = CoroutineScope(Dispatchers.IO).launch {
    delay(1000)
    println("Task completed")
}
job.cancel() // отмена корутины
```

**Когда:** фоновые задачи без возврата результата (например, запись в БД).

### 2. async

Запускает корутину, которая **возвращает результат** (аналог `Callable`).

- Возвращает `Deferred<T>` — отложенный результат.
- Результат получают через `await()` (приостанавливает до готовности).
- Удобно для параллельного запуска нескольких задач.

```kotlin
val deferred = CoroutineScope(Dispatchers.Default).async {
    delay(1000)
    "Result"
}
println(deferred.await())
```

Параллельная загрузка из двух источников:

```kotlin
coroutineScope {
    val result1 = async { fetchDataFromServer1() }
    val result2 = async { fetchDataFromServer2() }
    println("Combined: ${result1.await() + result2.await()}")
}
```

**Когда:** нужен результат; параллельное выполнение независимых операций.

### 3. runBlocking

Запускает корутину в **блокирующем** режиме: текущий поток блокируется до завершения.

- Применяется в тестах и точках входа (`main`).
- **Нельзя** использовать в основном коде Android — блокирует поток и подвешивает UI.

### 4. withContext

Меняет контекст выполнения. Часто — чтобы выполнить работу в одном диспетчере (например, `Dispatchers.IO`) и вернуть результат.

- Это suspend-функция: приостанавливает, пока задача не завершится.
- Возвращает результат блока.

```kotlin
val data = withContext(Dispatchers.IO) { api.loadData() }
```

## Job и Deferred

### Job

Базовый интерфейс, представляющий задачу внутри корутины. Позволяет управлять жизненным циклом, отслеживать выполнение и отменять.

Основные свойства и методы:

- `isActive` — выполняется ли корутина.
- `isCompleted` — завершена ли.
- `isCancelled` — отменена ли.
- `cancel()` — отменить выполнение.
- `join()` — приостановить текущую корутину до завершения этой.

### Deferred

Расширяет `Job`, представляет задачу с результатом.

- `await()` — получить результат (приостанавливает, пока не готов).
- Наследует методы `Job` (`cancel()`, `isCompleted`).

**Когда:** важен результат корутины; параллельный запуск нескольких задач с последующим объединением.

## Suspend-функции

`suspend`-функция может быть **приостановлена и возобновлена**. При её вызове корутина не блокирует поток, а освобождает его для других задач.

Под капотом suspend-функции компилируются в **state machine** (машину состояний), которая:

- сохраняет текущее состояние выполнения;
- позволяет возобновиться с того же места после приостановки.

Реализуется через **CPS (Continuation Passing Style)**: компилятор добавляет в сигнатуру скрытый параметр `Continuation`, через который возвращается результат.

## Диспетчеры

### 1. Dispatchers.Main

UI-поток. Для обновления интерфейса и лёгких задач. Не для долгих операций.

```kotlin
CoroutineScope(Dispatchers.Main).launch {
    textView.text = "Hello from Main"
}
```

### 2. Dispatchers.IO

Операции ввода-вывода (сеть, файлы, БД). Пул потоков масштабируется под нагрузку.

- Лимит потоков = **max(64, число ядер)**.

```kotlin
CoroutineScope(Dispatchers.IO).launch {
    val data = fetchFromNetwork()
    withContext(Dispatchers.Main) {
        textView.text = data
    }
}
```

### 3. Dispatchers.Default

CPU-интенсивные задачи (расчёты, обработка больших данных).

- Размер пула = **max(2, число ядер)**.

```kotlin
CoroutineScope(Dispatchers.Default).launch {
    val result = calculateSomething()
    println("Result: $result")
}
```

> `Dispatchers.IO` и `Dispatchers.Default` **разделяют общий пул потоков**; `IO` лишь разрешает создавать больше потоков для блокирующих операций.

### 4. Dispatchers.Unconfined

Не привязывает корутину к конкретному потоку: до первой приостановки выполняется там, где запущена, а после — на потоке, который её возобновил.

- Не рекомендуется для большинства задач; полезен в тестах.

### Сравнение диспетчеров

| Диспетчер              | Потоки                    | Назначение                              | Примеры задач                            |
| ---------------------- | ------------------------- | --------------------------------------- | ---------------------------------------- |
| Dispatchers.Main       | Главный поток UI          | Работа с интерфейсом                    | Обновление текста, обработка кликов      |
| Dispatchers.IO         | Пул для I/O               | Операции ввода-вывода                   | Сетевые запросы, чтение файлов           |
| Dispatchers.Default    | Пул (CPU-bound)           | Вычислительные задачи                   | Математика, генерация данных             |
| Dispatchers.Unconfined | Текущий поток             | Лёгкие операции без привязки к потоку   | Тесты, упрощённые операции               |

## Потокобезопасность корутин

**Почему по умолчанию не потокобезопасны:**

- **Разделяемые ресурсы.** Несколько корутин меняют один объект без синхронизации → проблемы согласованности.
- **Многопоточность.** Диспетчер (`Default`, `IO`) может выполнять корутины на разных потоках → параллельный доступ.

### Способ 1. Mutex

`Mutex` — взаимное исключение для корутин: критическую секцию выполняет только одна корутина.

- Только одна корутина захватывает `Mutex` в момент времени.
- Остальные **приостанавливаются** (не блокируют поток), пока он не освободится.

```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

val mutex = Mutex()
var sharedResource = 0

suspend fun safeIncrement() {
    mutex.withLock {
        sharedResource++
    }
}
```

#### Mutex vs synchronized — почему нельзя `synchronized`

**Причина 1. Потоков мало, корутин много.** Корутины мультиплексируются поверх маленького пула потоков (у `Default` потоков ≈ числу ядер). `synchronized`/`ReentrantLock.lock()` **блокируют сам поток ОС** — он паркуется и простаивает. `Mutex.lock()` — это `suspend`-функция: она **приостанавливает корутину**, а поток возвращается в пул под другую работу. Заблокировать все потоки пула на `synchronized` = **thread starvation / дедлок диспетчера**.

**Причина 2 (главная). Монитор привязан к потоку, а корутина мигрирует.** `synchronized` держит **монитор объекта**, а монитор в JVM строго потоко-зависимый: захватить и отпустить его обязан **один и тот же поток** (иначе `IllegalMonitorStateException`). Но корутина на точке приостановки может **продолжиться на другом потоке**. Поэтому удерживать монитор *через* `suspend` семантически невозможно — и **компилятор Kotlin это запрещает** ещё на этапе компиляции:

```kotlin
suspend fun broken() {
    synchronized(lock) {
        val data = loadFromNetwork()  // ❌ ошибка компиляции:
        // "synchronized call contains a suspension point"
        // Захватили монитор на потоке A, после suspend — уже на потоке B.
    }
}
```

`Mutex` владельцем считает **не поток, а логический токен (owner)**, поэтому спокойно переживает миграцию корутины между потоками.

**Нереентрантность.** `synchronized`/`ReentrantLock` реентрантны (считают владельца-поток + счётчик захватов). `Mutex` счётчика вложенности не ведёт → повторный `lock()` из той же корутины ждёт сам себя → **дедлок**:

```kotlin
suspend fun outer() = mutex.withLock { inner() } // 💀 если inner берёт тот же mutex
suspend fun inner() = mutex.withLock { /* ... */ }
```

Лечится **реструктуризацией** (вынести общий код в приватную функцию, которая уже под локом), а не «реентрантным мьютексом».

**Когда `synchronized` в корутинах всё-таки ок.** Если критическая секция **чисто синхронная — без единого `suspend`-вызова** (инкремент поля, работа с обычной `HashMap`), `synchronized` корректен и даже **быстрее** мьютекса (нет корутинного состояния, JIT его отлично оптимизирует), плюс реентрантен:

```kotlin
private val lock = Any()
private var counter = 0

fun tick() = synchronized(lock) {
    counter++   // никаких suspend → монитор берётся и отпускается на одном потоке
}
```

> [!tip] Коротко на собесе
> - `synchronized`/`ReentrantLock` **блокируют поток** и требуют захвата/освобождения монитора **на одном потоке**; корутина мигрирует между потоками на suspend-точках → компилятор **запрещает** `suspend` внутри `synchronized`.
> - `Mutex.lock()` — **suspend**: приостанавливает корутину, не блокируя поток; владение логическое (по токену), а не по `Thread`.
> - `Mutex` **нереентрантный** → повторный `lock()` из той же корутины = дедлок.
> - Секция без suspend → `synchronized` ок и быстрее. Ещё лучше — вообще убрать разделяемое состояние (confinement, actor, атомики).

### Способ 2. Atomic-переменные

Для примитивов — атомарные классы из `java.util.concurrent.atomic`:

```kotlin
import java.util.concurrent.atomic.AtomicInteger

val atomicCounter = AtomicInteger(0)

fun main() = runBlocking {
    val scope = CoroutineScope(Dispatchers.Default)
    repeat(100) {
        scope.launch { atomicCounter.incrementAndGet() }
    }
    delay(1000)
    println("Final: ${atomicCounter.get()}")
}
```

### Способ 3. Thread confinement

Все операции над общими данными — на одном потоке/диспетчере:

```kotlin
var confinedCounter = 0

fun main() = runBlocking {
    val singleThreadContext = newSingleThreadContext("MyThread")
    val scope = CoroutineScope(singleThreadContext)

    repeat(100) {
        scope.launch { confinedCounter++ }
    }

    delay(1000)
    println("Final: $confinedCounter")
    singleThreadContext.close()
}
```

### Способ 4. Channel

Канал даёт потокобезопасный обмен данными: одна корутина отправляет, другая принимает.

```kotlin
import kotlinx.coroutines.channels.Channel

fun main() = runBlocking {
    val channel = Channel<Int>()
    var sharedCounter = 0

    launch { // producer
        repeat(100) { channel.send(1) }
        channel.close()
    }

    launch { // consumer
        for (value in channel) sharedCounter += value
    }

    delay(1000)
    println("Final: $sharedCounter")
}
```

### Способ 5. StateFlow / SharedFlow

Потокобезопасное управление состоянием (подробнее — [[SharedFlow vs Flow vs StateFlow]]):

```kotlin
import kotlinx.coroutines.flow.MutableStateFlow

val stateFlowCounter = MutableStateFlow(0)

fun main() = runBlocking {
    val scope = CoroutineScope(Dispatchers.Default)

    launch {
        stateFlowCounter.collect { println("Counter: $it") }
    }

    repeat(100) {
        scope.launch { stateFlowCounter.update { it + 1 } } // update — атомарно
    }

    delay(1000)
}
```

> [!warning] `value += 1` не атомарно
> `stateFlowCounter.value += 1` — это чтение + запись, и при параллельном доступе значения теряются. Для атомарного обновления используйте `update { it + 1 }`.

### Резюме

- Разделяемые ресурсы на разных потоках → не защищены от гонок.
- Способы: `Mutex`, атомарные переменные, thread confinement, `Channel`, `StateFlow`/`SharedFlow`.

## Виды CoroutineScope

`CoroutineScope` определяет область жизни корутин и управляет их запуском/отменой.

### GlobalScope (⚠️ не рекомендуется)

Глобальная область, живущая всё время работы приложения. Корутины не привязаны к Activity/Fragment.

```kotlin
fun main() {
    GlobalScope.launch {
        delay(1000L)
        println("GlobalScope completed")
    }
    Thread.sleep(1500L)
}
```

**Минусы:** не управляется жизненным циклом UI → утечки памяти и неконтролируемые задачи.

### lifecycleScope (Android)

Привязан к жизненному циклу Activity/Fragment. Корутины автоматически отменяются при уничтожении компонента.

```kotlin
// во фрагменте
viewLifecycleOwner.lifecycleScope.launch { /* пока жив фрагмент */ }

// в активити
lifecycleScope.launch { /* пока жива Activity */ }
```

### viewModelScope (Android)

Привязан к жизненному циклу `ViewModel`; отменяется в `onCleared()`. Идеален для асинхронных задач, не зависящих от UI-компонента.

```kotlin
viewModelScope.launch { /* пока жив ViewModel */ }
```

### Локальный CoroutineScope

Собственная область под конкретную логику:

```kotlin
val myScope = CoroutineScope(Dispatchers.Default)
myScope.launch { /* ... */ }
// myScope.cancel() — не забыть отменить
```

### coroutineScope { } (✅ не блокирует поток)

Создаёт новый scope, который **не блокирует поток**, но **ждёт завершения всех вложенных корутин**. Используется внутри suspend-функций.

```kotlin
suspend fun doWork() {
    coroutineScope {
        launch {
            delay(500L)
            println("Task 1 done")
        }
        launch {
            delay(300L)
            println("Task 2 done")
        }
    }
    println("All tasks completed") // после обоих launch
}

fun main() = runBlocking { doWork() }
```

Вывод:

```text
Task 2 done
Task 1 done
All tasks completed
```

### supervisorScope { } (✅ не отменяет соседей при ошибке)

Работает как `coroutineScope`, но исключение в одной корутине не отменяет остальные. Для независимых задач.

```kotlin
suspend fun doWork() {
    supervisorScope {
        launch {
            delay(500L)
            throw RuntimeException("Error in Task 1")
        }
        launch {
            delay(800L)
            println("Task 2 completed") // всё равно выполнится
        }
    }
}
```

### MainScope() (Android)

`MainScope` = `SupervisorJob() + Dispatchers.Main`:

```kotlin
public fun MainScope(): CoroutineScope = ContextScope(SupervisorJob() + Dispatchers.Main)
```

```kotlin
class MyViewModel : ViewModel() {
    private val scope = MainScope()

    fun loadData() {
        scope.launch {
            delay(1000L)
            println("Data loaded")
        }
    }

    override fun onCleared() {
        super.onCleared()
        scope.cancel() // отменяем корутины при уничтожении ViewModel
    }
}
```

> [!tip] coroutineScope vs supervisorScope — на собесе
> - **`coroutineScope`** — «всё или ничего»: падение одной дочерней корутины отменяет весь scope. Для зависимых задач (если одна часть не загрузилась — экран невалиден).
> - **`supervisorScope`** — независимые задачи: один виджет упал, остальные живут.
> - **`Job` vs `SupervisorJob`** — то же различие, но на уровне scope, а не временного блока.

> [!info] Корутины в Kotlin Multiplatform
> `kotlinx.coroutines` — мультиплатформенная библиотека: тот же код работает на Android (Kotlin/JVM) и iOS (Kotlin/Native). На границе с Swift `suspend`-функции становятся `async`, а `Flow` причёсывается через SKIE. См. [[KMP. iOS interop и корутины]].
