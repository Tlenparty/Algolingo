# 17 CQRS: разделение чтения и записи

Command and Query Responsibility Segregation: команда меняет состояние и проверяет правила, запрос читает и оптимизирован под отображение. У них разные модели, разные обработчики, иногда разные базы. CQRS — инструмент управления различиями между чтением и записью, а не самоцель: курс повторяет это на каждом слайде.

> [!tip] Аналогия из Android
> В приложении это уже есть: `Room` entity с инвариантами для записи и отдельный `@Query` с JOIN в плоскую `FeedItemView` для списка. UI не читает доменную модель, он читает проекцию под экран. CQRS делает то же на бэкенде, а «разные БД» — как отдельная таблица-кеш ленты, которую пересобирают из событий.

## Зачем разделять

- **Нагрузка** — Read-heavy система: чтений в 100 раз больше, чем команд.
- **Модели данных** — UI нужна денормализация (плоские списки), записи — инварианты и нормальная форма.
- **Производительность** — Разные индексы и способы хранения под чтение и под запись.
- **Масштабирование** — Чтение и запись масштабируются по-разному: реплики против шардов.
- **Команда** — Разные компоненты и владельцы.
- **Интеграции** — Изменения удобно публиковать как события.

Command отвечает на вопрос «что изменить?», Query — «что показать?».

## Два варианта

**A. Логическое разделение, одна БД.** Отдельные API и обработчики для команд и запросов, модель записи и модель чтения, но хранилище общее. Плюс: просто. Минус: чтение и запись всё ещё конкурируют за одну базу.

**Б. Разные хранилища.** База для записи и база для чтения (одна или несколько проекций), между ними синхронизация через канал сообщений. Плюс: read-side масштабируется независимо, под каждый экран своя проекция. Цена: временная несогласованность. Главный вопрос, который нужно решить до внедрения: насколько допустима задержка между состоянием записи и чтения?

```text
Client ─ POST /orders ─→ Command API
                            ↓ инварианты, транзакция
                         БД записи ─→ outbox ─→ Брокер
                                                  ↓ события
Client ─ GET /orders ──→ Query API ←── проекции:
                                      список, детали,
                                      поисковый индекс
```

**CQRS ≠ Event Sourcing ≠ брокер.** CQRS: разные модели и обработчики для команд и запросов. Event Sourcing: источник истины — поток событий, из которого строится состояние. Брокер: транспорт для асинхронной доставки. Их часто комбинируют, но одно не подразумевает другое: CQRS не требует ни двух БД, ни event sourcing.

## Согласованность и надёжность

**Transactional Outbox.** Бизнес-изменение и запись события в таблицу outbox — в одной транзакции. Отдельный сервис доставки читает outbox и шлёт в брокер, при неудаче повторяет. Поэтому потребители должны быть идемпотентными: доставка at-least-once.

**Проекция — представление под запрос.** `OrderListView`, `OrderDetails`, поисковый индекс — каждая строится из доменных событий. Быстрые специализированные чтения, но проекции нужно поддерживать и уметь восстанавливать (replay событий или rebuild из БД записи).

**Что увидит запрос после команды.** В окне между commit и обновлением проекции read-side устаревшая. Три режима:

- **Консистентность** — Чтение после записи отдаёт новое состояние (читаем с write-side).
- **Eventual** — Новое состояние появляется с задержкой.
- **Business SLA** — Допустимая задержка задана по пользовательским сценариям: автор видит свой пост сразу, остальные через 5 с.

**Повторы и порядок.** Идемпотентность: повтор одного события не меняет результат повторно. Последовательность: понимать, какие события должны идти по порядку (ключ партиции). Повторы: только безопасные операции и с backoff. DLQ: изолировать то, что не удалось обработать.

## Кейс курса: управление заказами

`POST /orders` → Order Command → БД заказов (инварианты, транзакции, резерв товара) → события → read side (списки, фильтры, поиск) → `GET`. Наблюдение: чтение может быть временно устаревшим, и это записано в SLA.

Типичные ошибки: CQRS ради CQRS (архитектура сложнее, проблема не решена); «CQRS это Event Sourcing» (разные решения); нет SLA (непонятно, допустимы ли устаревшие данные); нет дедупликации (дубли и побочные эффекты); слишком умная модель чтения (бизнес-логика переехала в проекции).

## Эволюция

1. CRUD: одна модель, одна БД.
2. Logical CQRS: разные обработчики для команд и запросов, общее хранилище.
3. CQRS + отдельная БД для чтения: проекция, асинхронная доставка.
4. Event-driven: события, повторная отправка, несколько получателей.

Переходим на следующий уровень только тогда, когда он снимает измеримую проблему.

## Когда применять в SD-задаче

Сигналы: «чтений на порядки больше», «экран собирает данные из пяти таблиц», «поиск и список тормозят запись», «нужно независимо масштабировать чтение». Требования к чтению и записи заметно отличаются; допустима или управляемо компенсируется временная несогласованность; есть эксплуатационные практики (retries, monitoring, replay).

Фраза на собес: «Запись идёт через команду с проверкой инвариантов в PostgreSQL, в той же транзакции кладу событие в outbox. Из событий строю проекции под экраны: список, детали, поиск в Elasticsearch. Для автора делаю read-after-write с write-side, для остальных допускаю задержку до 5 секунд, это зафиксировано в SLA».

> [!warning] Грабли
> - Две БД без ответа «сколько можно отставать». Сначала SLA, потом архитектура.
> - Публикация события отдельным вызовом после commit: потерянные события. Только outbox.
> - Проекция без способа пересборки: сломалась — данных нет.
> - Логика в проекциях: «если статус X и сумма > Y, то показать…» должна жить в домене.
> - Путать CQRS с event sourcing и тащить поток событий как источник истины там, где хватило бы таблицы.

> [!question]- Что такое CQRS и требует ли он две базы данных?
> Разделение команд (меняют состояние, проверяют инварианты) и запросов (читают, оптимизированы под представление) на разные модели и обработчики. Две БД не требуются: логический CQRS работает на одном хранилище. Отдельная БД для чтения появляется, когда нужно независимо масштабировать чтение или строить проекции под экраны, и приносит временную несогласованность.

> [!question]- Как надёжно доставить изменение из БД в брокер?
> Transactional outbox: в одной транзакции с бизнес-изменением пишем событие в таблицу outbox; отдельный процесс читает её и публикует в брокер с повторами. Доставка at-least-once, поэтому потребители дедуплицируют по id события.

> [!question]- Пользователь создал заказ и сразу не видит его в списке. Что делать?
> Это окно между commit и обновлением проекции. Варианты: читать «свои» данные с write-side (read-after-write), показать оптимистично на клиенте, ждать подтверждения обработки события перед ответом, или зафиксировать в SLA, что список обновляется с задержкой, и объяснить это в UI.

> [!question]- Быстрый self-check по CQRS
> Две БД обязательны? Нет. Event Sourcing обязателен? Нет. Временная несогласованность возможна? Да. Повторы требуют идемпотентности? Да. Модель чтения можно пересобрать? Да, если есть надёжный источник: БД записи или поток событий.
