# Решение вопросов с собеседования Яндекс

## Задача 1. Обернуть `LegacyApi` в свой suspend-API

### Условие

Есть колбэчный legacy-API. Нужно обернуть его в свой API на корутинах, чтобы можно было отправить пачку запросов и получить список ответов.

```kotlin
class Request { /**/ }
class Response { /**/ }

interface LegacyApi {
    fun doRequest(request: Request, onComplete: (Response) -> Unit)
}
```

### Моё решение на собеседовании (с ошибками)

```kotlin
class BatchLegacyHelper(
    private val legacyApi: LegacyApi
) {
    val responseList = mutableListOf<Deffered<Response>>()

    suspend fun doRequests(
        requests: List<Request>,
        onComplete: (responses: List<Response>) -> Unit
    ) {
        suspendCancellableCallback { c ->
            requests.forEach { request ->
                val deffereed = async {
                    legacyApi.doRequest(request) { response ->
                        c.resumeWith(respinse)
                    }
                }
            }
            responseList.add(deffereed)
        }
        onComplete(responseList.awaitAll())
    }
}
```

### Разбор ошибок

1. **`suspendCancellableCallback` — такого билдера нет.** Правильно — `suspendCancellableCoroutine`. Именно он превращает один колбэк в `suspend`-функцию.

2. **Смешаны два разных подхода.** `suspendCancellableCoroutine` (обёртка одного колбэка в одну suspend-точку) и `async { … }.awaitAll()` (запуск пачки параллельных задач) — это два независимых механизма. В решении они вложены друг в друга, из-за чего логика ломается: континуация `c` одна на всю пачку, а `resume` можно вызвать у неё **только один раз**. При нескольких запросах будет `IllegalStateException: Already resumed`.

3. **`async` нельзя вызвать внутри `suspendCancellableCoroutine`.** `async` — метод `CoroutineScope`, а внутри блока континуации скоупа нет. Не скомпилируется.

4. **`responseList.add(deffereed)` вне цикла `forEach`.** `deffereed` объявлен внутри лямбды `forEach`, снаружи он не виден (не скомпилируется), а по смыслу в список попал бы только последний элемент.

5. **`responseList` — это поле класса, а не локальная переменная.** Общий мутабельный стейт: при повторном вызове `doRequests` в списке останутся старые `Deferred`. Список должен быть локальным.

6. **`c.resumeWith(respinse)`** — две проблемы:
   - опечатка: `respinse` → `response`;
   - `resumeWith` принимает `Result<T>`, а не сам объект. Либо `c.resume(response)`, либо `c.resumeWith(Result.success(response))`.

7. **Опечатки в типах:** `Deffered` → `Deferred`, `deffereed` → `deferred`.

### Как я бы решил

Ключевая идея — **разделить два уровня**:

- обернуть **один** колбэчный вызов в `suspend`-функцию через `suspendCancellableCoroutine`;
- запустить **пачку** таких вызовов параллельно через `coroutineScope { … async … }.awaitAll()`.

```kotlin
class BatchLegacyHelper(
    private val legacyApi: LegacyApi
) {

    // 1. Один колбэк -> одна suspend-функция
    private suspend fun doRequest(request: Request): Response =
        suspendCancellableCoroutine { cont ->
            legacyApi.doRequest(request) { response ->
                cont.resume(response)
            }
        }

    // 2. Пачка запросов параллельно -> список ответов
    suspend fun doRequests(requests: List<Request>): List<Response> =
        coroutineScope {
            requests
                .map { request -> async { doRequest(request) } }
                .awaitAll()
        }
}
```

Вариант с `onComplete`-колбэком, если по условию он обязателен:

```kotlin
suspend fun doRequests(
    requests: List<Request>,
    onComplete: (List<Response>) -> Unit
) = coroutineScope {
    val responses = requests
        .map { request -> async { doRequest(request) } }
        .awaitAll()
    onComplete(responses)
}
```

### Почему так правильно

- `coroutineScope` даёт `CoroutineScope`, внутри которого легально работает `async`, и ждёт завершения всех дочерних корутин (structured concurrency).
- `map { async { … } }` запускает все запросы **параллельно**, `awaitAll()` собирает ответы, сохраняя порядок исходного списка.
- Локальный `responseList`/`map` — нет общего стейта между вызовами.
- `suspendCancellableCoroutine` поддерживает отмену: если корутину отменят, ожидание корректно прервётся.

Импорты, которые понадобятся:

```kotlin
import kotlinx.coroutines.async
import kotlinx.coroutines.awaitAll
import kotlinx.coroutines.coroutineScope
import kotlinx.coroutines.suspendCancellableCoroutine
import kotlin.coroutines.resume
```

## Задача 2. Репозиторий-кеш для медиа-сущностей

### Условие (по памяти)

Есть 3 класса с одинаковыми полями — `Artist`, `Album`, `Track` — у всех есть `title`, `duration`, `dateAdded`. Нужно реализовать репозиторий (кеш), который:

1. отдаёт все элементы;
2. отдаёт отсортированные по длительности;
3. кеширует результат сортировки;
4. отдаёт отсортированные по дате добавления;
5. умеет добавлять и удалять.

Репозиторий переиспользуется во многих местах → важны **дженерики** и **многопоточность (блокировки)**.

### Что здесь на самом деле проверяют

Это не про алгоритм, а про **дизайн**. Интервьюер смотрит на 4 вещи:

1. **Переиспользование** — увидеть, что 3 класса с одинаковыми полями надо свести к общему интерфейсу и сделать репозиторий дженериком.
2. **Кеш и его инвалидация** — считать сортировку лениво и сбрасывать кеш при изменении данных.
3. **Потокобезопасность** — репо шарится → нужен доступ под блокировкой; workload read-heavy → `ReadWriteLock`.
4. **Инкапсуляция** — не отдавать наружу ссылку на внутренний мутабельный список (иначе вся потокобезопасность бессмысленна).

### Шаг 1. Общий интерфейс (переиспользование)

Три класса с одинаковыми полями → выносим общий контракт:

```kotlin
interface MediaItem {
    val title: String
    val duration: Duration     // kotlin.time.Duration
    val dateAdded: Instant     // kotlinx.datetime.Instant / java.time.Instant
}

data class Artist(
    override val title: String,
    override val duration: Duration,
    override val dateAdded: Instant,
) : MediaItem

data class Album(/* те же поля */) : MediaItem
data class Track(/* те же поля */) : MediaItem
```

`data class` важен: он даёт корректные `equals`/`hashCode`, без которых `remove` не будет работать.

### Шаг 2. Контракт репозитория (дженерик)

```kotlin
interface MediaRepository<T : MediaItem> {
    fun add(item: T)
    fun remove(item: T)
    fun getAll(): List<T>
    fun sortedByDuration(): List<T>
    fun sortedByDate(): List<T>
}
```

Дженерик `T : MediaItem` — один и тот же репозиторий переиспользуется для любого типа: `MediaRepository<Album>`, `MediaRepository<Track>` и т.д. А если нужно хранить все типы вместе — `MediaRepository<MediaItem>`.

### Шаг 3. Реализация: кеш + потокобезопасность

```kotlin
class InMemoryMediaRepository<T : MediaItem> : MediaRepository<T> {

    private val items = mutableListOf<T>()

    // Кеши отсортированных представлений; null = невалиден, нужно пересчитать
    private var byDurationCache: List<T>? = null
    private var byDateCache: List<T>? = null

    // Read-heavy: много читателей, редкие записи -> ReadWriteLock
    private val lock = ReentrantReadWriteLock()

    override fun add(item: T) = lock.write {
        items.add(item)
        invalidate()
    }

    override fun remove(item: T) = lock.write {
        items.remove(item)
        invalidate()
    }

    override fun getAll(): List<T> = lock.read {
        items.toList()   // защитная копия — не отдаём внутренний список наружу
    }

    override fun sortedByDuration(): List<T> = getOrBuild(
        get = { byDurationCache },
        set = { byDurationCache = it },
        comparator = compareBy { it.duration },
    )

    override fun sortedByDate(): List<T> = getOrBuild(
        get = { byDateCache },
        set = { byDateCache = it },
        comparator = compareBy { it.dateAdded },
    )

    private inline fun getOrBuild(
        get: () -> List<T>?,
        set: (List<T>) -> Unit,
        comparator: Comparator<T>,
    ): List<T> {
        // Быстрый путь: под read-lock проверяем готовый кеш
        lock.read { get()?.let { return it } }
        // Медленный путь: под write-lock, с повторной проверкой (double-check)
        return lock.write {
            get() ?: items.sortedWith(comparator).also(set)
        }
    }

    private fun invalidate() {
        byDurationCache = null
        byDateCache = null
    }
}
```

Импорты:

```kotlin
import java.util.concurrent.locks.ReentrantReadWriteLock
import kotlin.concurrent.read
import kotlin.concurrent.write
```

### Почему именно так

- **`ReentrantReadWriteLock`** вместо `synchronized`/`Mutex`: чтений много (`getAll`, обе сортировки), записей мало (`add`/`remove`). RW-lock пускает читателей параллельно и блокирует эксклюзивно только на запись.
- **Ленивый кеш + инвалидация**: сортировку `O(n log n)` считаем один раз и переиспользуем, пока данные не изменились. Любая мутация → `invalidate()` сбрасывает оба кеша.
- **Double-checked locking** в `getOrBuild`: сначала дешёвая проверка под read-lock; строим (под write-lock) только если кеша нет, и там же перепроверяем — чтобы два потока не пересобрали кеш дважды.
- **Защитная копия `items.toList()`**: если вернуть сам `items`, вызывающий сможет менять список снаружи, в обход блокировки — гонки и `ConcurrentModificationException`. Отданные списки иммутабельны.
- **`data class`**: `remove` опирается на `equals`, а сортировка стабильна.

### О чём сказать вслух (что зачтут на собесе)

- **Альтернативы блокировкам:** `CopyOnWriteArrayList` (идеально для read-heavy, но дорогая запись), `ConcurrentHashMap` (если нужен доступ по id), корутинный `Mutex` вместо `ReentrantReadWriteLock`, если репозиторий живёт в suspend-мире (тогда методы становятся `suspend`).
- **Стратегия инвалидации:** здесь самая простая — сбрасываем весь кеш на любую запись. Можно точечно, но это усложнение без явной необходимости (преждевременная оптимизация).
- **Хранить 3 типа вместе или раздельно:** `InMemoryMediaRepository<MediaItem>()` держит все типы; выборка по конкретному через extension:

```kotlin
inline fun <reified R : MediaItem> MediaRepository<MediaItem>.getAllOfType(): List<R> =
    getAll().filterIsInstance<R>()
```

- **Реентерабельность:** `ReentrantReadWriteLock` допускает повторный захват тем же потоком, но **апгрейд read→write не поддерживается** — поэтому в `getOrBuild` сначала выходим из read-lock и только потом берём write-lock, а не вкладываем их.
