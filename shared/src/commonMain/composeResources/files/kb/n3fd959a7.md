В Java ключевое слово static используется для обозначения членов класса (переменных, методов, блоков кода или вложенных классов), которые принадлежат классу, а не его экземплярам. Это означает, что статические члены не зависят от конкретного объекта класса и доступны напрямую через имя класса.

**Основные особенности static:**

1. **Принадлежность классу:**

• Статические члены создаются и загружаются в память, когда класс загружается.
• Они общие для всех объектов класса и не зависят от конкретного экземпляра.

2. **Доступ через имя класса:**

• Можно обращаться к статическим членам напрямую через имя класса.
• Однако статические члены также доступны через экземпляр (не рекомендуется).

3. **Общий ресурс:**

• Используется для данных или методов, которые должны быть общими для всех объектов класса.

4. **Нет `this`:**

• Внутри статического метода `this` не существует — метод не привязан к объекту, поэтому не видит поля и методы экземпляра (им не на чем вызваться).
• Обратное работает: из метода экземпляра статические члены доступны.

5. **Жизненный цикл:**

• Статические поля инициализируются при **загрузке класса** classloader'ом (лениво, при первом обращении к классу), а не при создании объектов.
• Живут в памяти у объекта `Class` (метаспейс/куча), одна копия на classloader — не внутри экземпляров.
• `static final` — константы; `static { }` — блок статической инициализации, выполняется один раз при загрузке.

**Как происходит вызов статики — уровень байткода**

В JVM разные инструкции вызова, и в этом суть отличия статики от методов экземпляра:

| Инструкция | Что вызывает | Как ищется метод |
| --- | --- | --- |
| `invokevirtual` | метод экземпляра | по **реальному** классу объекта в рантайме через vtable → полиморфизм |
| `invokestatic` | статический метод | адрес известен **на этапе компиляции**, объекта и vtable нет |
| `invokespecial` | конструкторы, `private`-методы | без виртуальной диспетчеризации |
| `invokeinterface` | вызов через интерфейс | поиск по itable |

Следствия для статики:

• `invokestatic` **дешевле**: нет поиска по vtable, нет null-check получателя, скрытый параметр `this` не передаётся, JIT легко инлайнит.
• Статические методы **не переопределяются** — полиморфизма нет, метод жёстко привязан к классу. В наследнике его можно только «затенить» (method hiding) — частый источник багов: какой метод вызовется, решает **тип ссылки на компиляции**, а не реальный объект.
• Именно поэтому методы `value class` компилируются в статические функции: объекта в рантайме нет, `this` заменяется явным параметром со значением обёртки → см. [[Inline class, value class, typealias, infix]].

**Типичное применение static в Java:** утилиты (`Math.max`), фабрики (`Integer.valueOf`), константы (`static final`), синглтоны (поле `INSTANCE`).

**1. Что такое “статика” в Kotlin?**

В Kotlin ключевого слова `static` нет — сознательно. Вместо него **четыре механизма**, и все они в байткоде превращаются в джавовую статику или около неё:

• **top-level функции/свойства** — просто объявление в файле, вне класса. Компилируется в `static`-метод класса `ИмяФайлаKt` (`Utils.kt` → `UtilsKt.formatPrice(...)`). Идиоматичная замена джавовым утилитным классам.
• **object** — для создания синглтонов (singleton).
• **companion object** — для замены static членов внутри классов.
• **const val / @JvmStatic** — мосты к настоящей статике из object/companion.

Все они дают элементы, доступные без создания экземпляра класса. Но важно понимать, **что реально в байткоде**:

| Kotlin | Байткод | Вызов |
| --- | --- | --- |
| top-level `fun` | настоящий `static` в `FileKt` | `invokestatic` |
| `object Analytics` | класс + статическое поле `INSTANCE`; методы — **экземплярные** | `invokevirtual` на `INSTANCE` |
| `companion object` | синглтон в статическом поле `Companion`; `User.create()` — сахар для `User.Companion.create()` | `invokevirtual` на `Companion` |
| `@JvmStatic fun` в companion/object | дополнительно генерируется настоящий `static`-метод в самом классе | `invokestatic` |
| `const val` | настоящее `static final` поле, значение инлайнится в места использования | без вызова вообще |

**Фичи Kotlin, которые под капотом работают на статике**

**1. Extension-функции — главный пример.** Никакой магии «добавления метода в чужой класс» нет: extension компилируется в **статическую функцию, где receiver передаётся первым параметром**:

```kotlin
// Kotlin: StringExt.kt
fun String.lastChar(): Char = this[length - 1]

// Байткод (Java-эквивалент):
public final class StringExtKt {
    public static char lastChar(String $this) {   // this стал параметром!
        return $this.charAt($this.length() - 1);
    }
}

// вызов "abc".lastChar() → invokestatic StringExtKt.lastChar("abc")
```

Из этого следуют все свойства extension-функций, о которых спрашивают:

• **Не видят `private`/`protected` члены receiver'а** — это чужой статический метод, а не член класса.
• **Member всегда побеждает extension** при совпадении сигнатур — компилятор сначала ищет настоящий метод.
• **Extension на nullable работает** (`fun String?.orEmpty()`) — обычный статический метод спокойно принимает `null` параметром, `this == null` внутри легален.
• **Диспетчеризация СТАТИЧЕСКАЯ** — какой extension вызовется, решает **тип ссылки на этапе компиляции**, а не реальный объект. Классическая ловушка:

```kotlin
open class A; class B : A()
fun A.name() = "A"
fun B.name() = "B"

val x: A = B()
println(x.name())   // "A"! Не "B" — полиморфизма нет, invokestatic по типу ссылки
```

Это ровно то же поведение, что method hiding у статики в Java (см. таблицу инструкций выше): `invokestatic` не смотрит на реальный класс объекта. Extension-**свойства** — то же самое: статические `getX($this)`/`setX($this, v)`, backing field невозможен.

**2. Default-параметры.** Для `fun greet(name: String = "World")` компилятор генерирует **синтетический статический мост** `greet$default(...)` с битовой маской — она кодирует, какие аргументы пропущены, и подставляет дефолты. Поэтому из Java дефолты не видны (Java зовёт полную сигнатуру), лечится `@JvmOverloads` — генерирует настоящие перегрузки. У `data class` так же устроен `copy$default` — статический синтетический метод.

**3. Лямбды без захвата.** **Захват (capture)** — когда лямбда использует переменные из окружающего кода (локальные, параметры функции, `this`); такая лямбда — замыкание (closure):

```kotlin
val double = { x: Int -> x * 2 }        // НЕ захватывает: всё нужное приходит аргументом

fun makeMultiplier(factor: Int) =
    { x: Int -> x * factor }             // ЗАХВАТЫВАЕТ factor из внешней функции
```

Лямбда в байткоде — объект с методом `invoke`. **Без захвата** объекту нечего хранить → все вызовы могут разделять **один экземпляр** — компилятор кладёт его в статическое поле `INSTANCE`, ноль аллокаций. **С захватом** каждой лямбде нужно своё значение (`makeMultiplier(2)` и `makeMultiplier(10)` — разные функции) → значение кладётся в поле объекта через конструктор → **`new` при каждом создании** лямбды (в цикле — объект на каждую итерацию).

Два нюанса:
- Захват **`var`**: Java требует effectively final, Kotlin разрешает — но оборачивает переменную в `Ref.IntRef` и захватывает обёртку (лямбда и внешний код видят изменения друг друга). Это лишняя аллокация + косвенное обращение — дороже обычного захвата.
- **`inline` убирает всё**: лямбда, переданная в inline-функцию (`forEach`, `let`, `withPermit`…), встраивается в место вызова — объект не создаётся вообще, ни для какой. Разговор про `INSTANCE`/аллокации — только про не-inline случаи (лямбда в поле, в коллекции, в обычной функции).

**4. Методы `value class`** — статические `-impl`-функции, `this` заменён параметром (подробно: [[Inline class, value class, typealias, infix]]).

**5. `const val`** — значение инлайнится в места использования на компиляции: в байткоде вызывающего кода лежит литерал, обращения к полю нет вообще (поэтому при смене константы в библиотеке без перекомпиляции потребителей они видят старое значение).

Общий вывод для собеседования: почти весь «синтаксический сахар» Kotlin поверх Java — это **статические функции с явной передачей того, что выглядит как `this`**. Понимаешь `invokestatic` — понимаешь extension'ы, value class, top-level функции и их общие ограничения (нет полиморфизма, нет доступа к private, разрешение на этапе компиляции).

**2. Разница между companion object и object**

| Особенность              | companion object                      | object                                                   |
| ------------------------ | ------------------------------------- | -------------------------------------------------------- |
| Где используется         | Внутри класса (один на класс)         | Вне класса или как вложенный объект                      |
| Цель                     | Замена static-членов класса           | Создание синглтона или объекта с конкретной реализацией  |
| Доступ к членам          | Через имя класса (`MyClass.method()`) | Через имя объекта (`MyObject.method()`)                  |
| Наследование/реализация  | Может реализовывать интерфейсы        | Может реализовывать интерфейсы и наследовать классы      |
**5. Когда использовать?**

**companion object:**

• Для создания аналогов статических методов и переменных в классе.
• Когда нужно, чтобы статические элементы были связаны с конкретным классом.
• Удобен для создания фабрик (factory), констант, статических утилит класса.
Простой пример фабрики:
```kotlin
class User private constructor(val name: String, val age: Int) {
    companion object {
        fun create(name: String): User {
            return User(name, 18) // Возвращаем объект с дефолтным возрастом
        }
    }
}

fun main() {
    val user = User.create("Alice")
    println("${user.name}, ${user.age}") // Alice, 18
}
```

**object:**

• Для создания синглтонов.
• Для хранения глобальных данных или общих функций.
• Для объявления анонимных объектов (например, в интерфейсах, лямбда-выражениях).
• Для создания вложенных объектов, выполняющих специфические задачи.

> [!tip] Что часто уточняют на собесе
> - **`object` — это потокобезопасный синглтон.** Инициализируется лениво при первом обращении (через статический инициализатор JVM), без `synchronized` в вашем коде.
> - **`companion object` — НЕ совсем static.** Это реальный объект-синглтон внутри класса; в байткоде — статическое поле `Companion`. Чтобы метод стал настоящим static (для вызова из Java без `.Companion`), нужна аннотация `@JvmStatic`.
> - Companion может **иметь имя**, **реализовывать интерфейсы** и **иметь расширения** — поэтому его используют для фабрик и `Factory`-паттерна.
> - Константы: `const val` можно объявить только в `companion object`/`object`/top-level (значение известно на этапе компиляции). Обычный `val` в companion — это поле с геттером.

> [!abstract] Формула для интервью
> «`static` в Java — член класса, а не экземпляра: нет `this`, живёт с момента загрузки класса, вызывается через `invokestatic` — адрес известен на компиляции, без vtable и полиморфизма, поэтому дёшево и легко инлайнится JIT'ом. В Kotlin ключевого слова нет: top-level функции компилируются в статику файлового класса, `object`/`companion object` — синглтоны с вызовами через экземпляр (`INSTANCE`/`Companion`), а настоящую статику из них делают `@JvmStatic` и `const val`. Методы value class компилируются именно в статические функции, потому что объекта в рантайме нет — `this` заменяется явным параметром».
