# Volatile, Synchronized, Atomic

Три инструмента низкоуровневой синхронизации на JVM. Коротко:

- **`synchronized`** — даёт и **видимость**, и **атомарность** (взаимное исключение), но через блокировку.
- **`volatile`** — даёт только **видимость**, без атомарности.
- **Atomic** — даёт **видимость + атомарность** отдельных операций без блокировок (через CAS).

---

## synchronized

**`synchronized`** управляет доступом к критической секции кода: гарантирует, что только один поток одновременно выполняет указанный блок, захватывая **монитор** (lock) определённого объекта.

### Как работает

- Каждый объект на JVM имеет «монитор» (lock), который потоки могут захватывать и освобождать.
- Поток, входящий в `synchronized`, захватывает монитор объекта на время выполнения блока.
- Другие потоки, использующие тот же монитор, ждут его освобождения.

### Что выступает монитором: static vs не-static

В Kotlin для пометки метода используется аннотация `@Synchronized`.

**Обычный (нестатический) метод** — монитором будет **сам объект** (`this`):

```kotlin
class Example {
    @Synchronized
    fun instanceMethod() {
        // блокировка на "this" (экземпляр объекта)
    }
}
```

**Статический метод** (в `companion object`) — монитором будет **сам класс/компаньон**, а не экземпляр:

```kotlin
class Example {
    companion object {
        @Synchronized
        fun staticMethod() {
            // блокировка на companion-объекте (≈ Example.class в Java)
        }
    }
}
```

### Явная блокировка на объекте

Чаще всего синхронизируются на отдельном объекте-замке. Все потоки, использующие **один и тот же** объект, ждут его освобождения:

```kotlin
val lock = Any() // объект-замок
var counter = 0

fun incrementCounter() {
    synchronized(lock) {
        counter++
        println("Counter: $counter by ${Thread.currentThread().name}")
    }
}
```

### Где можно писать synchronized

**1. На уровне метода** (весь метод потокобезопасен — только один поток выполняет его одновременно):

```kotlin
class Counter {
    private var count = 0

    @Synchronized
    fun increment() {
        count++
    }
}
```

**2. На уровне блока** (более гибко — синхронизируем только критическую секцию):

```kotlin
class Counter {
    private var count = 0
    private val lock = Any()

    fun increment() {
        synchronized(lock) { // синхронизируем только эту часть
            count++
        }
    }
}
```

**Преимущества блока:** синхронизируется только критическая секция, а не весь метод; можно использовать разные объекты-замки.

### Особенности

- **Автоосвобождение.** Монитор освобождается, даже если блок завершился исключением.
- **Реализация на уровне JVM.** Работает быстро в большинстве случаев, но чрезмерное использование снижает производительность (потоки простаивают в ожидании).

## volatile

**`volatile`** (в Kotlin — аннотация `@Volatile`) обеспечивает **видимость** изменений переменной между потоками. Он указывает JVM не кэшировать значение в регистрах/локальном кэше потока, а всегда читать и писать в основную память.

### Зачем это нужно

В многопоточном коде поток может держать локальную копию переменной для производительности — тогда изменения одного потока не видны другим. `@Volatile` это исключает:

1. **Видимость.** Все потоки видят актуальное значение (читается из основной памяти).
2. **Запись.** Изменения сразу попадают в основную память.

### Ограничения

**1. Не делает операции атомарными.** `i++` (чтение → увеличение → запись) состоит из нескольких шагов, и `@Volatile` не защищает от гонки:

```kotlin
@Volatile
var counter = 0

fun incrementCounter() {
    counter++ // ❌ не атомарно: в многопоточной среде значения теряются
}
```

**2. Не помогает со сложными объектами.** Гарантирует видимость самой ссылки, но не безопасность содержимого:

```kotlin
@Volatile
var sharedList = mutableListOf<Int>()

fun addItem(item: Int) {
    sharedList.add(item) // ❌ не потокобезопасно
}
```

Решение — потокобезопасные структуры (`CopyOnWriteArrayList`, `ConcurrentHashMap`).

### Когда использовать volatile

- Для флагов / индикаторов состояния (`isRunning`, `isCancelled`).
- Когда нужна только видимость, а атомарность не требуется.

### Когда НЕ использовать

- Для составных операций (инкремент/декремент) — нужен `Atomic` или `synchronized`.
- Для потокобезопасного изменения содержимого объектов/коллекций.
- Для синхронизации между корутинами — лучше `Mutex`.

### Пример: без @Volatile цикл может зависнуть

```kotlin
import kotlin.concurrent.thread

@Volatile
var signalReceived = false

fun main() {
    thread {
        println("Ожидаем сигнал...")
        while (!signalReceived) {
            // без @Volatile поток может закэшировать false и крутиться вечно
        }
        println("Сигнал получен!")
    }

    Thread.sleep(2000)
    signalReceived = true // отправляем сигнал
}
```

### Сравнение volatile и synchronized

| Критерий            | volatile                       | synchronized                              |
| ------------------- | ------------------------------ | ----------------------------------------- |
| Видимость           | ✅ Обеспечивает                | ✅ Обеспечивает                           |
| Атомарность         | ❌ Не обеспечивает             | ✅ Обеспечивает                           |
| Гибкость            | Только простые операции        | Подходит и для составных операций         |
| Производительность  | Быстрее (нет блокировок)       | Медленнее (требует блокировок)            |

## ReentrantLock

`ReentrantLock` из `java.util.concurrent.locks` — более гибкая альтернатива `synchronized`.

**Особенности:**

1. **Реентрантность.** Один поток может несколько раз захватить ту же блокировку; счётчик захватов растёт на `lock()` и падает на `unlock()`.
2. **Гибкость.** Есть `tryLock()`, `tryLock(timeout)`, `lockInterruptibly()`, проверки `isLocked` / `isHeldByCurrentThread`.
3. **Ручное управление.** Требует явных `lock()` / `unlock()` — больше контроля, но легко забыть `unlock()` (поэтому всегда в `finally`).

```kotlin
import java.util.concurrent.locks.ReentrantLock

val lock = ReentrantLock()
var counter = 0

fun incrementCounter() {
    lock.lock()
    try {
        counter++
        println("Counter: $counter by ${Thread.currentThread().name}")
    } finally {
        lock.unlock() // обязательно освобождаем
    }
}

fun main() {
    val threads = List(10) {
        Thread { repeat(100) { incrementCounter() } }
    }
    threads.forEach { it.start() }
    threads.forEach { it.join() }

    println("Final counter: $counter")
}
```

### Сравнение ReentrantLock и synchronized

| Критерий              | ReentrantLock                                | synchronized                       |
| --------------------- | -------------------------------------------- | ---------------------------------- |
| Гибкость              | Высокая: таймауты, прерывания, `tryLock`     | Низкая: всё фиксировано            |
| Реентрантность        | ✅                                           | ✅                                 |
| Производительность    | Может быть быстрее при высокой конкуренции    | Стабильная, иногда медленнее       |
| Обработка исключений  | Нужен явный `unlock()` в `finally`           | Освобождается автоматически        |
| Проверка состояния    | Есть (`isLocked`, `isHeldByCurrentThread`)   | Нет                                |

> [!note] Зачем @Volatile вместе с synchronized
> Чтобы операции чтения, увеличения и записи выполнялись **транзакционно** (атомарно и с гарантией видимости) в многопоточной среде. На практике для счётчика проще взять `AtomicInteger` (см. ниже).

## Atomic

### Что такое атомарность

**Атомарность** означает, что операция выполняется полностью или не выполняется вовсе и не может быть прервана другим потоком. Например, `i++` атомарным **не** является — он состоит из трёх шагов:

1. Чтение текущего значения.
2. Увеличение.
3. Запись нового значения обратно.

Если два потока выполняют `i++` одновременно, возникает **состояние гонки** (race condition) и результат некорректен. Atomic-классы выполняют такие операции атомарно.

```kotlin
import java.util.concurrent.atomic.AtomicInteger

val counter = AtomicInteger(0)

fun main() {
    val task = Runnable {
        repeat(1000) {
            counter.incrementAndGet() // атомарное увеличение
        }
    }

    val t1 = Thread(task)
    val t2 = Thread(task)

    t1.start(); t2.start()
    t1.join(); t2.join()

    println("Counter: ${counter.get()}") // всегда 2000
}
```

### Преимущества Atomic-классов

1. **Высокая производительность.** Используют процессорный примитив **CAS (Compare-And-Swap)**, который быстрее блокировок.
2. **Готовые методы.** `incrementAndGet()`, `decrementAndGet()`, `compareAndSet()` и т. д.
3. **Минимум блокировок.** Не нужна ручная синхронизация → меньше шансов на deadlock и ошибки.

### Как работает CAS

CAS — это атомарная инструкция «сравнить и заменить»: «если значение всё ещё равно ожидаемому — замени на новое, иначе повтори». Это **lock-free** подход: потоки не блокируются, а в случае конфликта повторяют операцию.

### ATOMIC VS VOLATILE

И `volatile`, и Atomic работают с переменными, изменяемыми из нескольких потоков, но решают разные задачи.

**`volatile`** — модификатор, гарантирующий, что значение читается из основной памяти, а не из кэша процессора:

- **Нет кэширования** — изменения видны всем потокам.
- **Нет атомарных операций** — только видимость, без защиты от гонок.

```kotlin
@Volatile
var flag = false // может быть изменён из другого потока
```

**Atomic** — классы для атомарных операций (инкремент, обмен, CAS):

- **Атомарность** — операция выполняется полностью или не выполняется.
- **Без блокировок** — через CAS-примитив процессора.

```kotlin
val counter = AtomicInteger(0)
counter.incrementAndGet() // атомарно +1
```

| Характеристика     | volatile                                                 | atomic                                                          |
| ------------------ | -------------------------------------------------------- | -------------------------------------------------------------- |
| Видимость          | ✅ Гарантирует                                           | ✅ Гарантирует                                                 |
| Атомарность        | ❌ Не гарантирует                                        | ✅ Атомарные операции (инкремент, compare-and-swap)            |
| Блокировки         | Нет (но и от гонок не защищает)                          | Нет (использует CAS)                                           |
| Применение         | Флаги, редко изменяемые переменные                       | Счётчики, аккумуляторы, состояния с частыми изменениями        |

## Гарантирует ли volatile + synchronized потокобезопасность?

- ✅ **Да**, если использовать правильно.
- ❌ **Нет**, если переменная участвует в составных операциях (`++`, `--`, списки, объекты).

### Что делает volatile

- Гарантирует **актуальность** данных между потоками.
- **Не** предотвращает гонку (race condition).
- **Не** делает операции атомарными.

```kotlin
@Volatile
var counter = 0

fun increment() {
    counter++ // ❌ не атомарно — потоки могут потерять обновления
}
```

### Что делает synchronized

- Обеспечивает **эксклюзивный доступ** к коду в блоке.
- Позволяет **атомарно** изменять переменные.

```kotlin
class Counter {
    @Volatile private var count = 0

    fun increment() {
        synchronized(this) {
            count++ // ✅ теперь атомарно
        }
    }

    fun getCount(): Int = synchronized(this) { count }
}
```

### Когда даже synchronized стоит заменить

**1. Инкременты и составные операции** — проще и быстрее `AtomicInteger`:

```kotlin
import java.util.concurrent.atomic.AtomicInteger

val counter = AtomicInteger(0)

fun increment() {
    counter.incrementAndGet() // ✅ потокобезопасно без synchronized
}
```

**2. Работа с объектами/коллекциями** — `AtomicReference` или потокобезопасные коллекции:

```kotlin
import java.util.concurrent.atomic.AtomicReference

val users = AtomicReference(listOf("Alice"))

fun updateUsers() {
    users.set(listOf("Bob", "Charlie")) // ✅ потокобезопасная замена ссылки
}
```

> [!tip] Как выбрать на собесе
> - Нужен **флаг видимости** (`isRunning`) → `@Volatile`.
> - Нужен **потокобезопасный счётчик/аккумулятор** → `AtomicInteger` / `AtomicLong` (CAS, без блокировок).
> - Нужна **сложная критическая секция** (несколько связанных полей) → `synchronized` или `ReentrantLock`.
> - Работаете **в корутинах** → `Mutex.withLock { }` вместо блокирующего `synchronized`.
