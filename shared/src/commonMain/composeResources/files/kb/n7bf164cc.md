## **Основные компоненты Dagger 2**

**1️⃣ Module**

@Module — это класс, который предоставляет методы для создания зависимостей. Внутри @Module вы определяете методы, которые с помощью аннотации @Provides предоставляют объекты для инъекции.

**2️⃣ Component**

@Component — это интерфейс, который соединяет Module и место, где происходят инъекции. Компонент предоставляет ссылки на объекты, которые должны быть внедрены.

**3️⃣ Inject**

@Inject — это аннотация, которая используется для обозначения мест, куда будут внедряться зависимости. Можно аннотировать конструкторы, поля или методы.

**4️⃣ Qualifier (Квалификаторы)**

@Qualifier используется для различения одинаковых типов зависимостей. Это полезно, когда есть несколько объектов одного типа, и нужно указать, какой из них должен быть внедрён.

**5️⃣ Scopes**

@Scope позволяет задать область жизни зависимостей, что помогает управлять временем жизни объектов. Например, можно создать скоупы для зависимости, которая должна жить, пока существует активность или приложение.

**Простой пример использования Dagger 2**

**1️⃣ Добавляем зависимости Dagger 2 в проект**
Для начала нужно добавить зависимости Dagger 2 в ваш build.gradle (модульный файл):
```kotlin
dependencies {
    implementation 'com.google.dagger:dagger:2.41' // Последняя версия Dagger
    annotationProcessor 'com.google.dagger:dagger-compiler:2.41' // Для компилятора
}
```

**2️⃣ Создаём зависимости с помощью @Module**
Предположим, у нас есть приложение, которое нуждается в Engine и Car:
```kotlin
class Engine @Inject constructor() {
    fun start() = println("Engine started")
}

@Module
class CarModule {
    @Provides
    fun provideEngine(): Engine {
        return Engine() // метод для создания объекта Engine
    }
}
```

- `@Inject constructor()` в классе `Engine` говорит Dagger, что он сам умеет создать `Engine`.
- В `CarModule` через `@Provides` мы явно описываем, как создать `Engine` (нужно, когда `@Inject constructor` поставить нельзя — например, для классов из библиотек).

**3️⃣ Создаём компонент с помощью @Component**

Далее создаём компонент, который будет связывать Module и объекты, куда будем внедрять зависимости:
```kotlin
@Component(modules = [CarModule::class])
interface CarComponent {
    fun inject(activity: MainActivity)
}
```

**4️⃣ Используем Dagger в Activity**

Теперь мы можем использовать Dagger для внедрения зависимостей в нашу MainActivity:
```kotlin

class MainActivity : AppCompatActivity() {

    @Inject lateinit var engine: Engine // Зависимость Engine

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        // Инициализируем компонент
        val carComponent: CarComponent = DaggerCarComponent.create()

        // Внедряем зависимости
        carComponent.inject(this)

        // Теперь можем использовать зависимость
        engine.start() // Engine started
    }
}
```

• @Inject lateinit var engine: Engine — помечаем поле engine, куда нужно будет внедрить зависимость.
• DaggerCarComponent.create() — генерируем компонент с помощью Dagger. Он автоматически создается с использованием аннотации @Component.
• carComponent.inject(this) — внедряем зависимости в MainActivity.


**🔹 Пример с несколькими зависимостями и квалификаторами**

Если у нас есть несколько объектов одного типа, можно использовать **квалификаторы** для различия между ними.

```kotlin
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class DieselEngine

@Module
class CarModule {
    @DieselEngine
    @Provides
    fun provideDieselEngine(): Engine {
        return Engine() // Дизельный двигатель
    }

    @Provides
    fun providePetrolEngine(): Engine {
        return Engine() // Бензиновый двигатель
    }
}

@Component(modules = [CarModule::class])
interface CarComponent {
    @DieselEngine
    fun getDieselEngine(): Engine
    fun getPetrolEngine(): Engine
}
```

## **Разница между @Binds и @Provides в Dagger 2**

**🔹 1. @Provides**

@Provides используется для объявления метода в @Module, который будет создавать и возвращать объект. Этот метод может быть использован для создания зависимостей, в том числе для простых типов, которые не могут быть предоставлены с помощью интерфейсов или абстракций.

• **Как работает:**
• Метод с аннотацией @Provides возвращает объект, который будет использоваться в компоненте.
• Вы можете создать новый объект в методе или настроить его (например, выполнить инициализацию, передать параметры).

• **Пример:**
```kotlin
@Module
class CarModule {

    @Provides
    fun provideEngine(): Engine {
        return Engine()  // Создание нового объекта
    }
}
• В данном примере метод provideEngine() будет создавать новый экземпляр Engine и предоставлять его зависимостям, которые помечены @Inject.
```

**🔹 2. @Binds**

@Binds используется для привязки абстракции (например, интерфейса) к конкретной реализации. В отличие от @Provides, @Binds не создает объект, а связывает интерфейс с его реализацией. Метод с @Binds должен возвращать экземпляр интерфейса или абстракции, и Dagger будет автоматически предоставлять нужную реализацию.

• **Как работает:**

• @Binds используется для связывания интерфейса с конкретной реализацией.
• В методе с @Binds не нужно создавать новый объект, это только связывание абстракции с реализацией.
• Он эффективнее по сравнению с @Provides, потому что Dagger использует существующие объекты для внедрения зависимостей без дополнительных шагов (например, без создания экземпляров вручную).

• **Пример:**

```kotlin
@Module
abstract class CarModule {

    @Binds
    abstract fun bindEngine(engine: DieselEngine): Engine  // Привязка интерфейса Engine к DieselEngine
}
• В этом примере метод bindEngine() связывает интерфейс Engine с конкретной реализацией DieselEngine. Dagger будет предоставлять объект типа DieselEngine всякий раз, когда требуется объект Engine.
```

**🔥 Ключевые различия между @Binds и @Provides**

| Характеристика           | @Provides                                                                           | @Binds                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Создание объекта**     | Создаёт новый объект или выполняет дополнительную логику                            | Не создаёт объект, просто связывает интерфейс с реализацией                    |
| **Используется для**     | Когда необходимо создать объект (или если объект нельзя передать через конструктор) | Когда нужно привязать абстракцию (интерфейс или класс) к конкретной реализации |
| **Типы методов**         | Может быть обычным методом, который создаёт и возвращает объект                     | Только абстрактный метод (класс должен быть абстрактным)                       |
| **Перфоманс**            | Менее эффективен, так как требует создания объекта вручную                          | Более эффективен, так как напрямую связывает интерфейс с реализацией           |
| **Пример использования** | Подходит для создания экземпляров классов                                           | Подходит для внедрения зависимостей для интерфейсов и абстрактных классов      |
```kotlin
// 1. @Provides - для создания зависимостей
@Module
class CarModule {

    @Provides
    fun provideEngine(): Engine {
        return DieselEngine()  // Создаём объект
    }
}

// 2. @Binds - для связывания интерфейса с реализацией
@Module
abstract class CarModuleBinds {

    @Binds
    abstract fun bindEngine(engine: DieselEngine): Engine  // Связываем интерфейс с реализацией
}
```


## Какие могут быть проблемы с даггер при многомодульной архитектуре ? 

При использовании Dagger в многомодульной архитектуре могут возникать несколько проблем, особенно когда речь идет о **сабкомпонентах**. Давайте рассмотрим основные проблемы, которые могут возникнуть, и способы их решения.


**1. Проблемы с зависимостями между модулями и компонентами**

• В многомодульной архитектуре, когда используются сабкомпоненты, важно правильно управлять зависимостями между модулями. Ошибки могут возникнуть, если зависимости из разных модулей или сабкомпонентов неправильно инжектируются.

• Проблема: если один модуль зависит от другого, и вы пытаетесь использовать сабкомпоненты без явной связи между ними, это может привести к ошибкам компиляции или неправильному поведению.
  

**Решение:**

• Убедитесь, что правильно настроены компоненты и сабкомпоненты с правильным порядком инжекции.

• Используйте @Component и @Subcomponent с четким описанием зависимостей, чтобы компоненты могли передавать необходимые зависимости своим сабкомпонентам.

• Важно, чтобы родительский компонент инжектировал зависимости в дочерний компонент, если требуется доступ к зависимостям другого компонента.

  

**2. Сложности с жизненным циклом компонентов**

• В многомодульной архитектуре, особенно при использовании сабкомпонентов, могут возникать проблемы с жизненным циклом объектов. Например, сабкомпоненты часто имеют более короткий жизненный цикл, чем родительский компонент. Это может привести к утечкам памяти или к попытке использовать зависимости после того, как они были уничтожены.

  

**Решение:**

• Убедитесь, что зависимости, передаваемые в сабкомпоненты, имеют правильный жизненный цикл.

• Используйте аннотации, такие как @Singleton или @Scope, для обеспечения правильного управления временем жизни зависимостей.

  

**3. Сложности с инициализацией сабкомпонентов**

• В некоторых случаях может быть трудно правильно инициализировать сабкомпоненты, особенно если они зависят от сложных зависимостей или требуют определенной последовательности инициализации.

  

**Решение:**

• Используйте фабрики для создания сабкомпонентов, чтобы обеспечить правильную инициализацию зависимостей.

• Также важно правильно настроить метод inject() для передачи зависимостей в нужные сабкомпоненты.

  

**4. Дублирование зависимостей между компонентами**

• В многомодульной архитектуре может возникнуть ситуация, когда разные модули или компоненты содержат одинаковые зависимости, что приводит к их дублированию. Например, один и тот же класс может быть инжектирован в несколько компонентов, что приводит к избыточной инжекции.

  

**Решение:**

• Постарайтесь централизовать общие зависимости в базовых модулях или компонентах, чтобы избежать дублирования.

• Важно создавать общие модули и компоненты для общих зависимостей, чтобы избежать избыточного создания объектов.

  

**5. Невозможность наследования зависимостей через сабкомпоненты**

• В некоторых случаях сабкомпоненты могут не наследовать зависимости от родительских компонентов так, как это ожидалось. Это может быть связано с особенностями дизайна Dagger, когда он не может правильно передавать зависимости между компонентами.

  

**Решение:**

• Убедитесь, что в родительском компоненте объявлены все необходимые зависимости, и они доступны для инжекции в дочерние компоненты.

• Используйте @Module и @Provides для явного предоставления зависимостей родительского компонента в сабкомпоненты.

  

**6. Многоуровневое наследование компонентов**

• Когда вы создаете несколько уровней наследования компонентов и сабкомпонентов, это может привести к сложным цепочкам зависимостей. Ошибки могут возникнуть, если вы не определили правильную иерархию и порядок инжекции зависимостей.

  

**Решение:**

• Стремитесь к упрощению иерархии компонентов и сабкомпонентов. Чем проще структура, тем легче избежать ошибок в зависимости.

• Применяйте правила инжекции так, чтобы родительские компоненты могли предоставлять все необходимые зависимости для своих сабкомпонентов.

  

**7. Проблемы с тестированием**

• В многомодульной архитектуре с использованием сабкомпонентов может возникнуть сложность в тестировании, особенно когда нужно правильно настроить моковые объекты для разных уровней зависимостей. Ошибки могут возникнуть, если вы не правильно мокируете зависимости в родительских или дочерних компонентах.

  

**Решение:**

• Используйте интерфейсы или абстракции для компонентов и зависимостей, чтобы упростить тестирование.

• Разделите тестирование на несколько уровней, тестируя каждый компонент и сабкомпонент отдельно.

  

**8. Ошибка при добавлении зависимостей в модуль**

• Если зависимости не правильно добавлены в модуль, это может привести к ошибкам на этапе компиляции или времени выполнения. Например, если вы добавили модуль в сабкомпонент, но забыли добавить его в родительский компонент, это вызовет ошибку инжекции.

  

**Решение:**

• Убедитесь, что вы правильно добавили все модули в компоненты и сабкомпоненты.

• Проверьте, чтобы каждый модуль был доступен для всех компонентов и сабкомпонентов, которые нуждаются в этих зависимостях.

  

**9. Проблемы с производительностью**

• В многомодульной архитектуре с сабкомпонентами могут возникать проблемы с производительностью, особенно если компоненты и их зависимости слишком сложные или их слишком много.

  

**Решение:**

• Оптимизируйте структуру зависимостей. Если это возможно, используйте более легкие компоненты, чтобы избежать лишних вычислений и загрузки.

  

**Заключение:**

  

Использование Dagger с сабкомпонентами в многомодульной архитектуре требует тщательной настройки и внимания к деталям. Чтобы избежать вышеописанных проблем, важно правильно управлять зависимостями, жизненными циклами компонентов и сабкомпонентов, а также обеспечивать хорошую модульность и тестируемость приложения.

> [!important] Сейчас в Android — Hilt поверх Dagger
> **Hilt** — официальная рекомендация Google для DI в Android; он построен на Dagger, но убирает бойлерплейт компонентов:
> - Готовые **компоненты, привязанные к жизненному циклу** (`@HiltAndroidApp`, `@AndroidEntryPoint`, `@HiltViewModel`) — не нужно вручную писать `@Component` и `inject()`.
> - Готовые скоупы: `@Singleton`, `@ActivityScoped`, `@ViewModelScoped` и т.д.
> - Модули привязываются к компонентам через `@InstallIn(SingletonComponent::class)`.
> На голом Dagger 2 спрашивают реже, но понимать `@Module`/`@Component`/`@Inject`/`@Binds`/`@Scope` нужно — Hilt это всё использует под капотом.

> [!tip] Ключевые тезисы про Dagger на собесе
> - **Compile-time DI:** Dagger генерирует код и проверяет граф зависимостей **на этапе компиляции** (в отличие от Koin — рантайм, рефлексия/DSL). Ошибка в графе → не соберётся.
> - **`@Binds` vs `@Provides`:** `@Binds` (абстрактный, связывает интерфейс↔реализацию) генерирует меньше кода и эффективнее; `@Provides` — когда нужно сконструировать объект руками.
> - **`@Scope` (`@Singleton`)** — один экземпляр в пределах компонента, а не на всё приложение «магически»: синглтон живёт столько, сколько живёт его компонент.
> - **`@Qualifier`** — различать несколько биндингов одного типа.
