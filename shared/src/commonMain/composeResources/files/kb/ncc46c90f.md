
**Чистая архитектура (Clean Architecture)** — это концепция, предложенная Робертом Мартином (Uncle Bob), которая направлена на создание гибких, расширяемых и легко тестируемых программных систем. В контексте **Android-разработки** чистая архитектура предполагает правильную организацию и разделение ответственности между слоями приложения.

Чистая архитектура помогает решать проблемы, такие как сложность тестирования, плохая поддерживаемость и слабая масштабируемость приложений.

### **Основные принципы чистой архитектуры в Android**

Чистая архитектура строится на разделении приложения на независимые слои, каждый из которых отвечает за свою задачу. Эти слои взаимодействуют друг с другом через чётко определённые интерфейсы.

1. **Разделение на слои**:

• **Presentation Layer** (слой представления): этот слой отвечает за отображение данных и взаимодействие с пользователем. В Android это, как правило, включает в себя **Activity**, **Fragment** и **ViewModel**.

• **Domain Layer** (доменный слой): слой, который содержит бизнес-логику приложения. Здесь находятся **Use Cases** (сценарии использования), которые отвечают за обработку данных и принятие решений на основе бизнес-правил.

• **Data Layer** (слой данных): этот слой отвечает за работу с данными — их получение, сохранение, преобразование и передача между слоями. Включает **Repositories**, **Data Sources**, а также взаимодействие с базой данных и сетевыми источниками.

2. **Зависимости направлены внутрь**: Важный принцип, который гласит, что зависимости между слоями должны направляться от внешних слоёв к внутренним, то есть **слои с внешним кодом (например, база данных, сеть, UI) не должны зависеть от бизнес-логики (доменного слоя)**. Это позволяет изменять реализацию внешних слоёв, не нарушая работу внутреннего слоя.

3. **Абстракции и интерфейсы**: Для минимизации зависимости между слоями используются абстракции и интерфейсы. Например, слой **Presentation** может зависеть от интерфейсов, реализуемых слоем **Data**, но не от конкретных реализаций (например, не зависит от конкретных классов сетевых запросов или базы данных).

4. **Тестируемость**: Чистая архитектура упрощает тестирование, поскольку каждый слой можно тестировать отдельно, а благодаря инверсии зависимостей можно подменить реальную реализацию зависимостей (например, сделать мок-сервисы или базы данных для тестирования).

### **Структура приложения с чистой архитектурой**

Примерно структура проекта в Android с чистой архитектурой будет выглядеть так:
```text
app/
│
├── data/ (Data Layer)
│   ├── repository/
│   ├── remote/ (для работы с сетью)
│   ├── local/ (для работы с базой данных)
│   └── models/
│
├── domain/ (Domain Layer)
│   ├── models/
│   ├── usecases/ (сценарии использования)
│   └── repository/ (интерфейсы для доступа к данным)
│
└── presentation/ (Presentation Layer)
    ├── ui/
    │   ├── activities/
    │   ├── fragments/
    │   ├── viewmodels/
    │   └── adapters/
    └── di/ (инъекция зависимостей)
```

**1. Data Layer (Слой данных)**

В этом слое находятся все компоненты, связанные с получением данных. Он может включать в себя как удалённые источники (например, REST API через Retrofit), так и локальные источники (например, SQLite или Room для работы с базой данных).

• **Repositories** (Репозитории): классы, которые инкапсулируют всю логику получения данных и бизнес-логику для работы с ними.
• **Data Sources**: могут быть разделены на **remote** (сеть) и **local** (локальное хранилище).

Пример:
```kotlin
interface UserRepository {
    suspend fun getUserDetails(userId: String): User
}

class UserRepositoryImpl(private val remoteDataSource: UserDataSource, private val localDataSource: UserDataSource) : UserRepository {
    override suspend fun getUserDetails(userId: String): User {
        // Логика получения данных, например, сначала из кэша, потом из сети
    }
}
```

**2. Domain Layer (Доменный слой)**

Этот слой содержит **сценарии использования** (Use Cases), которые определяют, как обрабатывать данные. Он полностью независим от конкретных технологий для хранения или получения данных.

• **Use Cases** (сценарии использования): классы, которые инкапсулируют бизнес-логику и правила. Например, они могут вызывать методы репозитория для получения данных, выполнения обработки и возвращения результатов.

Пример:
```kotlin
class GetUserDetailsUseCase(private val userRepository: UserRepository) {
    suspend fun execute(userId: String): User {
        return userRepository.getUserDetails(userId)
    }
}
```

**3. Presentation Layer (Слой представления)**

Этот слой отвечает за взаимодействие с пользователем. В Android это **Activity**, **Fragment**, а также **ViewModel** (если используется архитектура MVVM).

• **ViewModel**: класс, который управляет данными для UI и взаимодействует с Use Cases. ViewModel извлекает данные из доменного слоя и предоставляет их UI.

• **UI-компоненты** (Activity, Fragment): отвечают за отображение данных и взаимодействие с пользователем.

Пример:
```kotlin
class UserViewModel(private val getUserDetailsUseCase: GetUserDetailsUseCase) : ViewModel() {
    private val _user = MutableLiveData<User>()
    val user: LiveData<User> get() = _user

    fun getUserDetails(userId: String) {
        viewModelScope.launch {
            _user.value = getUserDetailsUseCase.execute(userId)
        }
    }
}
```

**Преимущества чистой архитектуры в Android**

1. **Модульность**: Чистая архитектура разделяет приложение на независимые слои, что упрощает поддержку и расширение кода. Можно изменять один слой (например, сменить базу данных или сервисы) без воздействия на другие слои.

2. **Тестируемость**: Каждый слой изолирован, что позволяет легко тестировать каждый компонент приложения независимо, например, использовать mock-объекты для сервисов или репозиториев.

3. **Масштабируемость**: Архитектура легко масштабируется, так как новые фичи или компоненты могут быть добавлены без значительных изменений в существующую структуру.

4. **Поддерживаемость**: Разделение на слои и использование интерфейсов упрощает дальнейшую поддержку и улучшение приложения, минимизируя риски поломки функционала при внесении изменений.

> [!important] Правило зависимостей (Dependency Rule)
> Главное в Clean Architecture: **зависимости направлены только внутрь** — к домену. `Presentation` и `Data` зависят от `Domain`, но **`Domain` не знает ни о ком**. Как это достигается технически:
> - Интерфейс репозитория (`UserRepository`) объявлен **в Domain**, а его реализация (`UserRepositoryImpl`) — **в Data**. Domain зависит от своей же абстракции, а Data реализует её → стрелка зависимости развёрнута внутрь (это и есть [[SOLID|DIP]]).
> - У каждого слоя — **свои модели**: `data.UserDto` ↔ `domain.User` ↔ `presentation.UserUi`. Между слоями стоят **мапперы**. Это защищает домен от протечки деталей сети/БД (например, аннотаций Retrofit/Room).

> [!tip] Что часто спрашивают
> - **Зачем UseCase, если можно звать репозиторий из ViewModel?** UseCase инкапсулирует один сценарий бизнес-логики, переиспользуется между экранами и упрощает тесты. На простых экранах его иногда опускают (ViewModel → Repository напрямую) — это допустимый прагматичный компромисс.
> - **Не оверкилл ли это?** Для маленького приложения — да. Clean Architecture окупается на средних/больших проектах с командой.
