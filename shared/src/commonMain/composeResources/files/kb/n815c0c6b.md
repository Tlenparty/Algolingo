# Dependency Injection vs Service Locator

Service Locator и Dependency Injection (DI) — два паттерна управления зависимостями. Оба убирают жёсткое связывание (hard-coupling), но делают это по-разному.

## 1. Service Locator

Объект, который по запросу выдаёт зависимости другим объектам.

**Как работает:**

- Объект **сам явно запрашивает** зависимость у локатора.
- Локатор решает, как создать или предоставить нужный сервис.

```kotlin
object ServiceLocator {
    private val serviceMap = mutableMapOf<Class<*>, Any>()

    fun <T : Any> addService(clazz: Class<T>, service: T) {
        serviceMap[clazz] = service
    }

    @Suppress("UNCHECKED_CAST")
    fun <T> getService(clazz: Class<T>): T = serviceMap[clazz] as T
}

class Logger {
    fun log(message: String) = println("Log: $message")
}

fun main() {
    ServiceLocator.addService(Logger::class.java, Logger())

    val logger = ServiceLocator.getService(Logger::class.java)
    logger.log("Hello, Service Locator!")
}
```

**Плюсы:**

- Простота настройки.
- Легко внедрять в legacy-код.

**Минусы:**

- **Скрытые зависимости** — по сигнатуре класса не видно, что ему нужно; приходится лезть внутрь кода и искать вызовы локатора.
- Класс жёстко зависит от **самого локатора** (глобальный объект).
- Сложнее тестировать: нужно подменять/мокать локатор и его содержимое.

## 2. Dependency Injection (DI)

Зависимости **передаются объекту извне** (через конструктор, сеттер или интерфейс), а не запрашиваются им самим.

**Как работает:**

- Зависимости передаются автоматически (DI-контейнером) или явно (через конструктор).
- Объект **не знает**, откуда берутся его зависимости.

```kotlin
class Logger {
    fun log(message: String) = println("Log: $message")
}

class UserService(private val logger: Logger) { // зависимость в конструкторе
    fun performAction() = logger.log("Action performed!")
}

fun main() {
    val logger = Logger()                  // зависимость создаётся снаружи
    val userService = UserService(logger)  // внедрение через конструктор
    userService.performAction()
}
```

**Плюсы:**

- **Явные зависимости** — всё видно в конструкторе.
- Легко тестировать: зависимости подменяются моками.
- Контейнер DI управляет жизненным циклом (scoping).

**Минусы:**

- Сложнее настроить (особенно с фреймворками).
- Может потребовать рефакторинг legacy-кода.

## Главное отличие

| Критерий               | Dependency Injection                  | Service Locator                        |
| ---------------------- | ------------------------------------- | -------------------------------------- |
| Получение зависимостей | Передаются извне (push)               | Объект сам запрашивает (pull)          |
| Явность                | ✅ Видны в конструкторе               | ❌ Скрыты в теле класса                |
| Тестируемость          | Высокая (подмена моков)               | Ниже (нужно мокать локатор)            |
| Связь с инфраструктурой| Класс не знает о контейнере           | Класс зависит от глобального локатора  |

> [!important] Что говорить на собесе
> **Service Locator сегодня считают антипаттерном** именно из-за скрытых зависимостей: класс выглядит так, будто у него нет зависимостей, а на деле тянет их из глобального объекта. DI предпочтительнее — зависимости явные, код честнее и тестируемее. Оба паттерна — частные случаи принципа **IoC (Inversion of Control)**: управление зависимостями отдаётся «наружу».
>
> В Android DI реализуют через **Hilt/Dagger** (кодогенерация, проверки на этапе компиляции) или **Koin** (Service-Locator-подобный, проще, но проверки в рантайме).
