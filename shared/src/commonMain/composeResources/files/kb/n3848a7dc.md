# Паттерны проектирования

> [!note] Классификация (GoF)
> - **Порождающие** (создание объектов): Фабрика, Абстрактная фабрика, Строитель, Синглтон, Прототип.
> - **Структурные** (композиция объектов): Компоновщик, Декоратор, Адаптер, Фасад, Прокси.
> - **Поведенческие** (взаимодействие объектов): Стратегия, Наблюдатель, Команда, Состояние, Итератор.
>
> Ниже разобраны самые частые на собесах: Компоновщик, Декоратор, Фабрика, Строитель, Стратегия.

## **Паттерн “Компоновщик” (Composite)**

Паттерн “Компоновщик” используется для работы с иерархиями объектов. Он позволяет организовать объекты в виде древовидной структуры, где можно одинаково обращаться как к отдельным объектам, так и к их группам.

**Когда использовать:**

1. Когда нужно представить иерархию объектов.
2. Когда клиенту нужно одинаково работать как с отдельными объектами, так и с их комбинациями.

**Участники:**

1. **Component** — общий интерфейс для всех компонентов и их групп.
2. **Leaf** — отдельный объект, который не содержит других компонентов.
3. **Composite** — объект, который может содержать другие объекты (и Leaf, и Composite).
4. **Client** — код, который работает с Component.

Предположим, мы создаём структуру файловой системы, где:

• Каждый файл имеет размер.
• Папка может содержать как файлы, так и другие папки.

```kotlin

// Общий интерфейс для файлов и папок
interface FileSystemComponent {
    val name: String
    fun getSize(): Int
    fun display(indent: String = "") // Для отображения структуры
}

// "Лист" — отдельный файл
class File(override val name: String, private val size: Int) : FileSystemComponent {
    override fun getSize(): Int = size
    override fun display(indent: String) {
        println("$indent- File: $name (size: $size)")
    }
}

// "Композит" — папка, которая может содержать файлы и другие папки
class Folder(override val name: String) : FileSystemComponent {
    private val children = mutableListOf<FileSystemComponent>()

    fun add(component: FileSystemComponent) {
        children.add(component)
    }

    fun remove(component: FileSystemComponent) {
        children.remove(component)
    }

    override fun getSize(): Int {
        return children.sumOf { it.getSize() } // Общий размер содержимого папки
    }

    override fun display(indent: String) {
        println("$indent+ Folder: $name (total size: ${getSize()})")
        children.forEach { it.display("$indent  ") }
    }
}

// Клиентский код
fun main() {
    // Создаём файлы
    val file1 = File("File1.txt", 100)
    val file2 = File("File2.txt", 200)
    val file3 = File("File3.txt", 300)

    // Создаём папки
    val folder1 = Folder("Folder1")
    val folder2 = Folder("Folder2")
    val rootFolder = Folder("Root")

    // Строим иерархию
    folder1.add(file1)
    folder1.add(file2)

    folder2.add(file3)

    rootFolder.add(folder1)
    rootFolder.add(folder2)

    // Отображаем структуру
    rootFolder.display()
}
```

**Результат выполнения:**
```text
+ Folder: Root (total size: 600)
  + Folder: Folder1 (total size: 300)
    - File: File1.txt (size: 100)
    - File: File2.txt (size: 200)
  + Folder: Folder2 (total size: 300)
    - File: File3.txt (size: 300)
```

**Объяснение:**

1. **FileSystemComponent:** общий интерфейс для файлов и папок. Клиент работает только с этим интерфейсом.
2. **File:** лист в дереве. Не содержит других компонентов, возвращает свой размер.
3. **Folder:** композит, может содержать и файлы, и другие папки. Размер папки — сумма размеров всех дочерних компонентов.
4. **Клиентский код:**

Клиент работает с объектами через общий интерфейс FileSystemComponent. Это упрощает добавление новых компонентов.

**Преимущества:**
1. Упрощает работу с объектами и их группами.
2. Удобен для построения сложных иерархий.


**Недостатки:**
1. Сложность реализации для сложных структур.
2. Может быть трудно контролировать поведение отдельных элементов в больших иерархиях.


## **Паттерн “Декоратор” (Decorator)**

Паттерн “Декоратор” позволяет динамически добавлять новое поведение объекту, оборачивая его в объекты-декораторы. Он применяется, когда требуется изменить функциональность объекта, не изменяя его класс.

**Когда использовать:**

1. Когда нужно расширить поведение объекта, не создавая новых подклассов.
2. Когда необходимо добавлять поведение динамически во время выполнения.
3. Когда невозможно или нежелательно менять исходный класс.

**Участники:**

1. **Component** — общий интерфейс или абстрактный класс для всех объектов.
2. **ConcreteComponent** — базовая реализация интерфейса (объект, который будет декорироваться)
3. **Decorator** — абстрактный класс или интерфейс, который содержит ссылку на Component.
4. **ConcreteDecorator** — конкретные декораторы, добавляющие новое поведение.

**Задача:**

Есть базовая функция вывода строки в консоль. Нужно дополнительно логировать время вызова и длину строки, но без изменения исходного класса.

```kotlin
// Общий интерфейс
interface Printer {
    fun print(message: String)
}

// Базовый компонент
class SimplePrinter : Printer {
    override fun print(message: String) {
        println(message)
    }
}

// Абстрактный декоратор
abstract class PrinterDecorator(protected val printer: Printer) : Printer {
    override fun print(message: String) {
        printer.print(message)
    }
}

// Конкретный декоратор: логирование времени
class TimestampPrinterDecorator(printer: Printer) : PrinterDecorator(printer) {
    override fun print(message: String) {
        println("[${System.currentTimeMillis()}]") // Логируем время
        super.print(message)
    }
}

// Конкретный декоратор: логирование длины строки
class LengthPrinterDecorator(printer: Printer) : PrinterDecorator(printer) {
    override fun print(message: String) {
        println("Message length: ${message.length}") // Логируем длину
        super.print(message)
    }
}

// Клиентский код
fun main() {
    val simplePrinter = SimplePrinter()

    // Декорируем базовый компонент: добавляем время
    val timestampPrinter = TimestampPrinterDecorator(simplePrinter)

    // Декорируем ещё раз: добавляем логирование длины
    val lengthPrinter = LengthPrinterDecorator(timestampPrinter)

    // Вызываем через декораторы
    lengthPrinter.print("Hello, Decorator!")
}
```

**Результат выполнения:**

```text
Message length: 18
[1674422321674]
Hello, Decorator!
```

**Объяснение:**

1. **Базовый компонент (**SimplePrinter**)**: Просто выводит строку в консоль.
2. **Декораторы (**TimestampPrinterDecorator **и** LengthPrinterDecorator**)**: Оборачивают базовый компонент, добавляя дополнительное поведение:

• Логирование времени.
• Логирование длины строки.

3. **Клиент:** Работает с декорированным объектом, не зная о внутренней реализации.

**Почему “Декоратор”?**

• Поведение объекта (Printer) расширено без изменения его кода.
• Логика добавляется по мере необходимости, без нарушения принципа **OCP** (открытость/закрытость).


## **Паттерн “Фабрика” (Factory)**

Паттерн “Фабрика” предоставляет интерфейс для создания объектов, позволяя подклассам решать, какой класс создавать. Это помогает инкапсулировать логику создания объектов и упростить управление зависимостями.

**Когда использовать:**

1. Когда нужно делегировать создание объектов из клиентского кода в отдельный модуль.
2. Когда создание объектов включает сложную логику.
3. Когда нужно обеспечить расширяемость при добавлении новых типов объектов.

**Основные виды фабрик:**

1. **Простая фабрика (Simple Factory):**

Обычная функция или класс, создающий объекты.

2. **Фабричный метод (Factory Method):**

Определяет интерфейс для создания объектов, но позволяет подклассам изменять тип создаваемых объектов.

3. **Абстрактная фабрика (Abstract Factory):**

Создаёт семейства связанных объектов.


**Простой пример на Kotlin**

Создадим простую фабрику, которая создаёт разные виды автомобилей.

**Реализация:**

```kotlin
// Базовый интерфейс
interface Car {
    fun drive()
}

// Конкретные реализации автомобилей
class Sedan : Car {
    override fun drive() {
        println("Driving a Sedan!")
    }
}

class SUV : Car {
    override fun drive() {
        println("Driving an SUV!")
    }
}

class SportsCar : Car {
    override fun drive() {
        println("Driving a Sports Car!")
    }
}

// Фабрика для создания автомобилей
object CarFactory {
    fun createCar(type: String): Car {
        return when (type) {
            "Sedan" -> Sedan()
            "SUV" -> SUV()
            "SportsCar" -> SportsCar()
            else -> throw IllegalArgumentException("Unknown car type: $type")
        }
    }
}

// Клиентский код
fun main() {
    val sedan = CarFactory.createCar("Sedan")
    sedan.drive() // Output: Driving a Sedan!

    val suv = CarFactory.createCar("SUV")
    suv.drive() // Output: Driving an SUV!

    val sportsCar = CarFactory.createCar("SportsCar")
    sportsCar.drive() // Output: Driving a Sports Car!
}
```


**Объяснение:**

1. **Интерфейс** Car**:**

Определяет общий контракт для всех типов автомобилей.

2. **Реализации** Sedan**,** SUV**,** SportsCar**:**

Конкретные классы, представляющие разные типы автомобилей.

3. CarFactory**:**

Содержит метод createCar, который создаёт объект нужного типа на основе переданного аргумента.

4. **Клиентский код:**

Обращается к CarFactory для создания объектов вместо непосредственного вызова конструкторов.

**Преимущества:**

1. Инкапсулирует логику создания объектов.
2. Упрощает поддержку и модификацию кода (добавление нового типа автомобиля не требует изменения клиентского кода).
3. Соответствует принципу **SRP** (единственная ответственность).

**Недостатки:**

1. Может привести к увеличению количества классов.
2. При большом количестве типов создаваемых объектов фабрика может стать сложной.


**Когда использовать:**

• Если клиентский код не должен зависеть от конкретных классов.
• Когда создание объектов требует дополнительной логики (например, настройка зависимостей


## **Паттерн “Строитель” (Builder)**

Паттерн “Строитель” позволяет создавать сложные объекты пошагово. Он отделяет процесс создания объекта от его представления, делая процесс построения более удобным и читаемым.

**Когда использовать:**

1. Когда объект имеет много параметров или сложную логику создания.
2. Когда нужно обеспечить создание объекта с разными конфигурациями.
3. Когда требуется пошаговое создание объекта.

**Основные участники:**

1. **Builder:** Интерфейс или абстрактный класс, описывающий шаги построения объекта.

2. **ConcreteBuilder:** Конкретная реализация, выполняющая шаги построения.

3. **Director (опционально):** Упрощает процесс создания, управляя последовательностью вызова методов строителя.

4. **Product:** Финальный объект, создаваемый строителем.


**Простой пример: Построение пользователя (User)**

Предположим, у нас есть класс User, у которого есть множество свойств, и некоторые из них необязательны.

```kotlin
// Класс User с большим количеством параметров
data class User(
    val firstName: String,
    val lastName: String,
    val age: Int,
    val email: String?,
    val phoneNumber: String?,
    val address: String?
)

// Класс Builder для создания User
class UserBuilder {
    private var firstName: String = ""
    private var lastName: String = ""
    private var age: Int = 0
    private var email: String? = null
    private var phoneNumber: String? = null
    private var address: String? = null

    fun setFirstName(firstName: String) = apply { this.firstName = firstName }
    fun setLastName(lastName: String) = apply { this.lastName = lastName }
    fun setAge(age: Int) = apply { this.age = age }
    fun setEmail(email: String?) = apply { this.email = email }
    fun setPhoneNumber(phoneNumber: String?) = apply { this.phoneNumber = phoneNumber }
    fun setAddress(address: String?) = apply { this.address = address }

    fun build(): User {
        if (firstName.isEmpty() || lastName.isEmpty()) {
            throw IllegalArgumentException("First name and last name are required")
        }
        return User(firstName, lastName, age, email, phoneNumber, address)
    }
}

// Клиентский код
fun main() {
    val user = UserBuilder()
        .setFirstName("John")
        .setLastName("Doe")
        .setAge(30)
        .setEmail("john.doe@example.com")
        .setAddress("123 Main Street")
        .build()

    println(user)
}
```

Результат
```text
User(firstName=John, lastName=Doe, age=30, email=john.doe@example.com, phoneNumber=null, address=123 Main Street)
```


**Преимущества:**

1. Удобное и читаемое создание сложных объектов.
2. Позволяет избежать перегрузки конструктора с множеством параметров.
3. Легко добавлять новые параметры, не меняя клиентский код.


**Недостатки:**

1. Может добавить сложность, если объект прост и не имеет многих параметров.
2. Требует дополнительного класса для строителя.



## **Паттерн “Стратегия” (Strategy)**

Паттерн “Стратегия” позволяет определить семейство алгоритмов, инкапсулировать каждый из них и делать их взаимозаменяемыми. Это помогает сделать код более гибким, обеспечивая возможность изменения поведения объекта во время выполнения.

**Когда использовать:**

1. Когда у объекта может быть несколько вариантов поведения, которые нужно менять.
2. Когда алгоритмы схожи, но отличаются деталями реализации.
3. Когда необходимо уменьшить количество условных конструкций (if/when).

**Основные элементы:**

1. **Стратегия (Strategy):**

Общий интерфейс или абстрактный класс, который определяет метод для алгоритмов.

2. **Конкретные стратегии (Concrete Strategies):**

Реализации интерфейса с различными вариантами поведения.

3. **Контекст (Context):**

Класс, использующий стратегию для выполнения алгоритма.


**Простой пример: Оплата товаров**

Предположим, у нас есть магазин, где клиент может оплатить покупку разными способами: наличными, банковской картой или через PayPal.

```kotlin
// Общий интерфейс стратегии
interface PaymentStrategy {
    fun pay(amount: Double)
}

// Конкретная стратегия: оплата наличными
class CashPayment : PaymentStrategy {
    override fun pay(amount: Double) {
        println("Paid $amount using Cash.")
    }
}

// Конкретная стратегия: оплата банковской картой
class CardPayment(private val cardNumber: String) : PaymentStrategy {
    override fun pay(amount: Double) {
        println("Paid $amount using Card. Card number: $cardNumber.")
    }
}

// Конкретная стратегия: оплата через PayPal
class PayPalPayment(private val email: String) : PaymentStrategy {
    override fun pay(amount: Double) {
        println("Paid $amount using PayPal. Email: $email.")
    }
}

// Контекст, использующий стратегию
class ShoppingCart(private var paymentStrategy: PaymentStrategy) {

    // Изменение стратегии во время выполнения
    fun setPaymentStrategy(strategy: PaymentStrategy) {
        paymentStrategy = strategy
    }

    // Выполнение оплаты
    fun checkout(amount: Double) {
        paymentStrategy.pay(amount)
    }
}

// Клиентский код
fun main() {
    val cart = ShoppingCart(CashPayment())
    cart.checkout(50.0) // Output: Paid 50.0 using Cash.

    cart.setPaymentStrategy(CardPayment("1234-5678-9876-5432"))
    cart.checkout(150.0) // Output: Paid 150.0 using Card. Card number: 1234-5678-9876-5432.

    cart.setPaymentStrategy(PayPalPayment("user@example.com"))
    cart.checkout(200.0) // Output: Paid 200.0 using PayPal. Email: user@example.com.
}
```

**Объяснение:**

1. **Интерфейс** PaymentStrategy**:**

Определяет метод pay, который будет реализован в каждой стратегии.

2. **Конкретные стратегии:**

CashPayment, CardPayment, PayPalPayment реализуют различные способы оплаты.

3. **Контекст** ShoppingCart**:**

Содержит ссылку на текущую стратегию (PaymentStrategy) и вызывает её метод для выполнения оплаты.

4. **Клиентский код:**

Создаёт объект ShoppingCart и динамически изменяет стратегию оплаты, используя метод setPaymentStrategy.

**Преимущества:**

1. Упрощение кода, устраняя громоздкие условные конструкции.
2. Возможность легко добавлять новые стратегии без изменения существующего кода.
3. Соблюдение принципа **OCP** (открытость/закрытость).


**Недостатки:**

1. Увеличение числа классов из-за создания отдельных стратегий.
2. Усложнение системы, если число стратегий велико.

**Когда использовать:**

• Для реализации алгоритмов с возможностью замены в процессе выполнения.
• Если одна и та же задача может решаться разными способами, но детали реализации должны быть скрыты от клиента.

> [!tip] Где встречается в Android
> - **Строитель** — `AlertDialog.Builder`, `NotificationCompat.Builder`, `OkHttpClient.Builder`.
> - **Фабрика** — `ViewModelProvider.Factory`, `LayoutInflater.from()`.
> - **Декоратор** — обёртки `Context` (`ContextWrapper`), кэширующий репозиторий поверх сетевого.
> - **Стратегия** — `Comparator`, разные `ImageLoader`/`LayoutManager`.
> - **Компоновщик** — дерево `View`/`ViewGroup`, дерево `CoroutineContext`.
