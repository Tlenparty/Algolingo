# Зачем нужен hashCode, если equals даёт точное сравнение

`equals` действительно точный, но он отвечает только на вопрос «равны ли **эти два** объекта». Он ничего не говорит о том, **где искать** объект в коллекции. Без хеша поиск ключа в `HashMap` из миллиона элементов — это миллион вызовов `equals`, то есть O(n). `hashCode` — это быстрый предварительный фильтр, который за O(1) сужает поиск до одного бакета с парой кандидатов.

> **На собес одной фразой:** `equals` точный, но медленный для поиска — он сравнивает только пару объектов. `hashCode` за O(1) говорит, «в каком бакете искать», и `equals` вызывается лишь для пары кандидатов внутри бакета, а не для всей коллекции. Хеш — про скорость поиска, equals — про точность сравнения.

## Разделение труда

| | `hashCode` | `equals` |
|---|---|---|
| Вопрос | «В каком бакете искать?» | «Тот ли это объект?» |
| Скорость | O(1) — одно вычисление | Может быть дорогим (сравнение всех полей) |
| Точность | Приблизительная (коллизии возможны) | Точная |
| Роль в поиске | Отсеивает 99,9% элементов сразу | Финальная проверка пары кандидатов |

## Как это выглядит при поиске в HashMap

1. `map[key]` → вычисляется `key.hashCode()` — **одна** операция.
2. По хешу определяется индекс бакета: `index = hash and (table.size - 1)` — **одна** операция.
3. В бакете обычно 0–1 элемент (при хорошем хеше), и только для них вызывается `equals`.

Итог: вместо `n` вызовов `equals` — один расчёт хеша плюс 1–2 вызова `equals`. Именно поэтому `HashMap`/`HashSet` дают амортизированный O(1) на `get`/`put`/`contains`.

## Что было бы без hashCode

```kotlin
// Так работал бы поиск только на equals — это буквально список:
fun <K, V> findWithoutHash(entries: List<Pair<K, V>>, key: K): V? =
    entries.firstOrNull { it.first == key }?.second   // O(n) — перебор всех элементов

// Коллекция, которая так и делает: contains у List
val list = (1..1_000_000).toList()
list.contains(999_999)              // O(n) — до миллиона сравнений

val set = list.toHashSet()
set.contains(999_999)               // O(1) — хеш сразу указал бакет
```

## Почему нельзя «просто сделать equals быстрым»

- `equals` сравнивает **пару** объектов — он в принципе не может «указать место» в структуре данных. Чтобы найти элемент, нужна функция от **одного** объекта, дающая адрес: это и есть хеш.
- Сам `equals` может быть дорогим: у `data class` с десятком полей или длинной строки это сравнение всех полей/символов. Хеш считается один раз (у `String` он ещё и кешируется).

## Почему они всегда переопределяются вместе

Контракт: `a == b` ⇒ `a.hashCode() == b.hashCode()`. Если переопределить только `equals`, два «равных» объекта попадут в **разные бакеты**, и `HashMap` просто не найдёт ключ — точность `equals` не спасёт, до его вызова дело не дойдёт.

```kotlin
class Broken(val id: Int) {
    override fun equals(other: Any?) = other is Broken && other.id == id
    // hashCode не переопределён — берётся от адреса объекта
}

val set = hashSetOf(Broken(1))
println(set.contains(Broken(1)))   // false! equals равен, но хеши разные — искали не в том бакете
```
