Когда **несколько пользователей** редактируют **один и тот же текст**, важно, чтобы их изменения **не перезаписывали друг друга**, а **синхронизировались в реальном времени**.

**🔍 Основные проблемы при одновременном редактировании:**

1. **Конфликты версий** – один пользователь изменил текст, другой тоже, а сервер не знает, что делать.
2. **Сетевые задержки** – изменения приходят с разным временем, и одно может затереть другое.
3. **Работа в офлайне** – пользователь мог внести изменения без подключения, и их нужно корректно объединить.

  
**🛠 Основные стратегии синхронизации текста:**

1. **Google Docs-подобная работа (Collaborative Editing через WebSockets)**
2. **Версионирование и слияние изменений (Operational Transformation, CRDT)**
3. **Локальные изменения + отправка батчами (Event Sourcing + Conflict Resolution)**

### **1️⃣ Подход 1: WebSockets для мгновенной синхронизации**


💡 **Идея:**

• Клиент подключается к WebSocket-серверу и **получает обновления текста в реальном времени**.
• Любые изменения **сразу отправляются другим пользователям**, чтобы у всех была **актуальная версия**.


📌 **Как работает WebSocket-синхронизация:**

1. Пользователь начинает редактировать текст.
2. Отправляет изменения через WebSocket на сервер.
3. Сервер рассылает изменения всем подключенным клиентам.
4. Клиенты обновляют текст **без полной перезаписи**.

📌 **Пример WebSocket в Android (Kotlin + OkHttp)**
```kotlin
val client = OkHttpClient()
val request = Request.Builder().url("ws://yourserver.com:8080").build()
val ws = client.newWebSocket(request, object : WebSocketListener() {
    override fun onMessage(webSocket: WebSocket, text: String) {
        val json = JSONObject(text)
        if (json.getString("type") == "UPDATE") {
            runOnUiThread {
                editText.setText(json.getString("text")) // Обновляем текст в UI
            }
        }
    }
})

fun sendTextUpdate(text: String) {
    val json = JSONObject().apply {
        put("type", "UPDATE")
        put("text", text)
    }
    ws.send(json.toString()) // Отправляем изменения на сервер
}
```

✅ **Когда использовать WebSockets?**

• Если нужно **редактирование в реальном времени**.
• Если изменения **маленькие и частые**.

❌ **Минусы:**

• Если соединение пропадет, **изменения могут потеряться** (нужна доп. логика хранения офлайн-правок).

### **2️⃣ Подход 2: Версионирование и слияние изменений (Optimistic Locking + CRDT/OT)**

💡 **Идея:**

• Каждый клиент **отправляет версию текста** на сервер.
• Сервер проверяет, **не изменился ли текст за это время**.
• Если версия **не совпадает**, сервер предлагает **объединить версии**.

📌 **Пример обновления через version (Optimistic Locking)**
```kotlin
PUT /text
Content-Type: application/json

{
    "text": "Привет, мир!",
    "version": 2
}
```

📌 **Ответ сервера при конфликте:**
```kotlin
HTTP/1.1 409 Conflict
Content-Type: application/json

{
    "error": "Conflict detected",
    "currentVersion": 3,
    "currentText": "Привет, друзья!"
}
```

💡 **Как разрешать конфликт?**

1. **Спросить пользователя** – предложить выбрать правильную версию.
2. **Merge** – попытаться объединить изменения.
3. **Использовать Operational Transformation (OT) или CRDT** – автоматическое слияние изменений.



✅ **Когда использовать?**

• Если пользователи **работают с текстом не в реальном времени**.
• Если нужен **механизм защиты от потери данных**.

❌ **Минусы:**

• Может быть **сложно объединять изменения** (нужны алгоритмы CRDT или OT).

### **3️⃣ Подход 3: Локальные изменения + отправка батчами (Event Sourcing + Conflict Resolution)**

💡 **Идея:**

• Изменения **сначала сохраняются локально**, а потом **отправляются на сервер батчами**.
• Если сервер обнаружил конфликт, **он предлагает выбрать вариант слияния**.
• Используется **Git-подобное слияние**.

📌 **Пример батчевого обновления:**
```kotlin
val changes = mutableListOf<String>()

fun onTextChanged(newText: String) {
    changes.add(newText)
    debounceSendChanges() // Запускаем таймер
}

fun debounceSendChanges() {
    CoroutineScope(Dispatchers.IO).launch {
        delay(1000) // Отправляем изменения раз в 1 сек
        sendChangesToServer()
    }
}

fun sendChangesToServer() {
    val mergedText = changes.joinToString("\n") // Объединяем изменения
    changes.clear()
    sendToServer(mergedText)
}
```

✅ **Когда использовать?**

• Если данные **нельзя сразу отправлять**.
• Если приложение **работает в офлайне** и нужно отправлять изменения при появлении сети.

### **📊 Сравнительная таблица методов**


| **Метод**                                      | **Когда использовать?**                         | **Плюсы**                         | **Минусы**                                |
| ---------------------------------------------- | ----------------------------------------------- | --------------------------------- | ----------------------------------------- |
| **WebSockets (реальное время)**                | Google Docs, совместное редактирование          | Быстрая синхронизация             | Теряются изменения при разрыве соединения |
| **Версионирование (Optimistic Locking, CRDT)** | Несколько пользователей редактируют одну запись | Защищает от потери данных         | Сложность слияния                         |
| **феризация + отправка батчами**               | Офлайн-режим, слабая сеть                       | Можно синхронизировать постфактум | Возможны конфликты                        |

**🚀 Итог**

1. **Для реального времени → WebSockets** (лучше всего для Google Docs-подобных приложений).
2. **Для контроля версий → CRDT / Optimistic Locking** (если нужно предотвращать конфликты).
3. **Для работы в офлайне → буферизация + батчевые обновления**.


🔥 **Лучшее решение – комбинировать**:

• WebSockets для синхронизации,
• Версионирование для защиты от конфликтов,
• Буферизация для офлайн-режима.
