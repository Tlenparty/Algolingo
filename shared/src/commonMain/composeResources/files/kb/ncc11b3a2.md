public abstract class Context

Context в Android —  **это ==абстрактный класс,**== который предоставляет доступ к системным сервисам и ресурсам приложения. Он является центральным объектом для взаимодействия с многими аспектами системы и приложения, такими как доступ к файлам, базам данных, ресурсам, а также запуск новых компонентов приложения (например, Activity или Service). В сущности, Context предоставляет среду для работы с приложением.

### **Зачем нужен Context в Android?**

**1. Доступ к системным сервисам**
Context позволяет получать доступ к различным системным сервисам, таким как:
• NotificationManager — для управления уведомлениями.
• LocationManager — для работы с геолокацией.
• WifiManager — для работы с Wi-Fi.
• SensorManager — для работы с датчиками устройства.

**2. Доступ к ресурсам приложения**
С помощью Context можно получить доступ к ресурсам, таким как строки, изображения, цвета и другие. Это особенно важно для работы с локализацией и мультимедийными файлами.
**3. Создание и запуск компонентов приложения**
Context используется для старта различных компонентов, таких как Activity, Service, BroadcastReceiver, и для их взаимодействия
**4. Работа с файлами и базами данных**
Context предоставляет методы для чтения и записи данных в локальные файлы, доступ к SharedPreferences, а также для работы с базами данных.
**5. Работа с разрешениями и контекстами безопасности**
Context помогает запрашивать разрешения для выполнения определённых операций (например, доступ к камере или хранилищу). Также он используется для взаимодействия с различными компонентами с учетом правил безопасности.

## **Типы Context в Android**

В Android существует несколько типов Context, каждый из которых имеет свои особенности и назначения:

1. ApplicationContext:

• Это контекст, связанный с самим приложением, а не с конкретной активностью.
• Используется для получения глобальных настроек или доступа к системным сервисам без привязки к UI.

• Не связан с жизненным циклом активности, поэтому может быть использован в любом месте приложения, например, в фоновом потоке.

2. ActivityContext:

• Это контекст, связанный с конкретной активностью.
• Используется, когда нужно взаимодействовать с UI или запускать компоненты в рамках активности, такие как создание Intent, отображение Toast, доступ к ресурсам UI и так далее.

3. ServiceContext:

• Это контекст, который используется внутри сервиса для работы с ресурсами и компонентами, специфичными для сервиса.

## **Основные отличия между ApplicationContext и ActivityContext**

### • ApplicationContext:
• Привязан к жизненному циклу приложения, а не к конкретной активности.
• Лучше использовать, если контекст не зависит от конкретного UI и вам нужно обратиться к системным сервисам или работать с глобальными данными.
• Используется в фоновых задачах, например, в сервисах, менеджерах задач и т. д.

### • ActivityContext:
• Привязан к жизненному циклу активности.
• Используется для работы с элементами UI, такими как отображение Toast, запуск Activity и т. д.
• Может быть очищен, если активность уничтожена (например, при конфигурационных изменениях).

## **Когда и какой Context использовать?**

### • ApplicationContext:

• Когда вам ==не== нужен доступ к элементам UI, и вы работаете с глобальными сервисами, такими как доступ к базе данных, файловой системе, уведомлениям или другим ресурсам, связанным с жизненным циклом всего приложения.
• Например, для работы с фоновыми задачами, серверами, или для того, чтобы передать контекст в долгоживущие объекты (например, в BroadcastReceiver или Service).ё

### • ActivityContext:

• Когда вам нужно взаимодействовать с UI или запускать компоненты UI, такие как активити или диалоги.
• Например, для отображения Toast, старта нового Activity, работы с ресурсами интерфейса.

**Утечка памяти (memory leak)** в Android — это ситуация, когда приложение продолжает удерживать ссылки на объекты, которые больше не нужны, тем самым предотвращая их освобождение сборщиком мусора (Garbage Collector). В результате таких утечек память, занятую этими объектами, нельзя вернуть в систему, что в конечном итоге может привести к **утрате свободной памяти** и, как следствие, к **замедлению работы приложения** или **к краху приложения**.

## **Почему утечки памяти происходят в Android?**

Утечки памяти возникают, когда приложение не освобождает ссылки на объекты, которые уже больше не используются или не нужны. Это мешает сборщику мусора (GC) очищать эти объекты, так как они всё ещё удерживаются ссылками в памяти. В Android утечки памяти особенно опасны, потому что устройство может не иметь столько ресурсов, как настольный компьютер, и из-за ограниченных возможностей устройства (например, мобильных телефонов) такие утечки могут очень сильно повлиять на производительность.
**Основные причины утечек памяти в Android**

### 1. **Неправильное использование ссылок на Context**

• Часто утечка памяти происходит, когда объект (например, Activity, Service) передается в долгоживущий объект (например, в AsyncTask, Handler или Runnable), но не удаляется после завершения работы активности.

• Если Activity или Context сохраняется в переменных, например, в статических полях, это приведет к тому, что объект не будет уничтожен, даже если он больше не нужен.

```kotlin
class MyActivity : Activity() {
    private var handler: Handler? = Handler()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler?.postDelayed({
            // Обработка через несколько секунд
        }, 1000)
    }

    // Утечка памяти, так как handler будет продолжать существовать, даже после уничтожения Activity
}
```

Здесь handler продолжает ссылаться на Activity, даже если сама Activity была уничтожена.

### 2. **Неосвобожденные ресурсы**

• В Android ресурсы, такие как Bitmap, файлы, потоки, базы данных, курсоры и другие тяжелые объекты, которые не освобождаются после использования, могут вызвать утечку памяти.

• Например, если не закрыть курсор после его использования или не вызвать recycle() для Bitmap, это может привести к утечке памяти.

```kotlin
val cursor = contentResolver.query(uri, projection, selection, selectionArgs, sortOrder)
// Не вызывается cursor.close(), что вызывает утечку
```

### 3. **Использование статических ссылок**

• Использование статических переменных для хранения объектов, таких как Activity, может привести к утечкам памяти, так как статические переменные существуют до завершения работы приложения.

• В этом случае, если статическая переменная ссылается на активный объект (например, Activity), этот объект не будет уничтожен, даже если пользователь покинет экран или закроет приложение.

```kotlin
companion object {
    var context: Context? = null
}
```
Если context в статическом поле будет хранить ссылку на Activity, то даже после завершения активности объект не будет очищен сборщиком мусора.

### 4. **Использование** AsyncTask**,** Handler **и** Thread **без должного завершения**

• Часто создаются фоновый потоки или задачи (например, с использованием AsyncTask, Handler, или Thread), которые продолжают работать или хранят ссылки на активные объекты (например, Activity), даже после того, как эти объекты уничтожены.
• Если задачи не отменяются или потоки не останавливаются, они могут удерживать ссылки на объекты, не давая системе освободить память.
**Пример:**

```kotlin
val task = MyAsyncTask()
task.execute()

// Если task не отменяется или не очищается, это может привести к утечке памяти
```

### 5. **Неправильное использование** View **и** Context **в адаптерах**

• В Adapter-ах (например, для RecyclerView) может возникнуть утечка памяти, если адаптер или его элементы (например, ViewHolder) сохраняют ссылку на Context или Activity, а затем не очищают её.

```kotlin
class MyAdapter(private val context: Context) : RecyclerView.Adapter<MyAdapter.ViewHolder>() {
    // Контекст сохраняется, даже если активность уничтожена
}
```

### **Как обнаружить утечку памяти?**

1. **Android Studio Profiler**

• В Android Studio есть инструменты профилирования, которые помогают обнаружить утечки памяти. Вы можете использовать Memory Profiler для отслеживания потребления памяти в реальном времени и поиска объектов, которые не были освобождены.

2. **LeakCanary**

• **LeakCanary** — это библиотека для Android, которая помогает автоматически отслеживать утечки памяти в приложении. Она анализирует кучу памяти и уведомляет о потенциальных утечках.

• Эта библиотека полезна для разработки, так как автоматически обнаруживает утечки в процессе тестирования.

3. **Manual Debugging**

• Проведение ручных проверок кода, таких как освобождение ресурсов в методах жизненного цикла активности (например, в onDestroy()) или сервисов, а также использование слабых ссылок (WeakReference) для объектов, которые могут вызвать утечку.

Context в Android — это мощный и важный класс, но его использование может быть проблематичным с точки зрения **чистой архитектуры (Clean Architecture)** и **принципов SOLID**. Проблемы возникают, когда мы неправильно используем Context, что может привести к нарушению принципов хорошего проектирования, таких как **слабая связанность**, **тестируемость**, **расширяемость** и другие.

###  **✅  Основные отличия между Application Context и Context**

| **Свойство**                   | Application Context                                               | Activity Context **(обычный** Context**)**                 |
| ------------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| **Где используется?**          | Весь жизненный цикл приложения                                    | Только пока активна Activity                               |
| **Жизненный цикл**             | Живет, пока работает приложение                                   | Уничтожается при onDestroy()                               |
| **Утечки памяти**              | Безопасен (можно хранить в синглтонах)                            | Может привести к утечкам, если хранить в статических полях |
| **Где можно использовать?**    | Доступ к ресурсам, SharedPreferences, Services, BroadcastReceiver | Все, что делает Application Context + доступ к UI          |
| **Можно использовать для UI?** | ❌ **Нет!** (не содержит информации о Activity)                    | ✅ **Да** (можно показывать Dialog, Toast, View)            |
### **✅  Почему нельзя хранить Activity Context в синглтонах?**

#### **1. Утечка памяти (Memory Leak):**

• **Activity Context** содержит ссылки на активность и её жизненный цикл. Если вы храните Activity Context в синглтоне, то объект с этим контекстом будет жить долго, даже после уничтожения активности. Это может привести к утечкам памяти, так как синглтон будет удерживать ссылку на активность, не позволяя ей быть собранной сборщиком мусора.

• Когда **Activity** уничтожается (например, при повороте экрана или завершении), система должна освободить ресурсы, связанные с активностью. Однако если контекст активности сохраняется в синглтоне, активность никогда не будет уничтожена, что приводит к утечке памяти.

#### **2. Невозможность безопасного использования контекста:**

• **Activity Context** привязан к жизненному циклу активности. Когда активность уничтожается, её контекст становится недействительным. Если синглтон продолжит хранить ссылку на этот контекст, любые попытки использования этого контекста после того, как активность будет уничтожена, приведут к IllegalStateException или другим ошибкам.

• Например, если вы попытаетесь вызвать метод, который зависит от состояния активности, после того как она будет уничтожена, это может вызвать сбой.

#### **3. Некорректное использование ресурсов:**

• **Application Context** — это контекст, привязанный к приложению, и он доступен на протяжении всего времени работы приложения. Использование Activity Context в синглтоне может привести к попытке доступа к ресурсам, специфичным для активности (например, к ресурсам пользовательского интерфейса или фрагментам), когда они уже не доступны.

#### **4. Нарушение принципов проектирования:**

• Синглтон — это объект, который должен быть независим от жизненного цикла UI компонентов, таких как активность. Хранение Activity Context в синглтоне делает архитектуру приложения более хрупкой и нарушает принципы хорошего проектирования, такие как разделение ответственности.

####  **Правильное использование контекста:**

• Вместо использования Activity Context в синглтонах, всегда используйте Application Context (который доступен через getApplicationContext()), если нужно что-то хранить или работать с контекстом на протяжении всего жизненного цикла приложения.

• Если вам необходимо работать с контекстом активности, передавайте его в нужные компоненты или используйте его внутри самой активности, не храня его глобально.**

### **✅  Когда использовать Application Context, а когда Activity Context?**

| Задача                                        | Какой Context выбрать | **Почему?**                                                     |
| --------------------------------------------- | --------------------- | --------------------------------------------------------------- |
| **Получить ресурсы (Resources)**              | Application Context   | Не зависит от UI                                                |
| **Работа с БД (**Room **и** SharedPreferences | Application Context   | Данные не зависят от Activity                                   |
| **Запуск** Service **или** BroadcastReceiver  | Application Context   | Service живет дольше Activity (частный случай)                  |
| **Отображение** Toast**,** Dialog             | Activity Context      | Application Context не может работать с UI                      |
| **Запуск** startActivity()                    | Activity Context      | Application Context может вызвать ошибку FLAG_ACTIVITY_NEW_TASK |
| **Работа с** View**,** LayoutInflater         | Activity Context      | Только Activity знает, какой у нее UI                           |
### Методы Context

**1. Работа с ресурсами и файлами**

• getResources(): Получает объект Resources, который позволяет работать с ресурсами (strings.xml, drawables, layouts и т. д.).

• getAssets(): Получает объект AssetManager для работы с ресурсами в папке assets.

• getPackageName(): Возвращает имя пакета приложения.

• getPackageResourcePath(): Возвращает путь к APK-файлу приложения.

• getFilesDir(): Получает путь к внутреннему хранилищу приложения.

• getExternalFilesDir(String type): Возвращает путь к внешнему хранилищу для файлов приложения.


**2. Работа с активностями и компонентами**

• startActivity(Intent intent): Запускает Activity, переданную в Intent.

• startService(Intent service): Запускает Service.

• bindService(Intent service, ServiceConnection conn, int flags): Привязывает Service.

• unregisterReceiver(BroadcastReceiver receiver): Разрегистрирует BroadcastReceiver.


**3. Работа с системными сервисами**

• getSystemService(String name): Получает доступ к системным сервисам, таким как LocationManager, ConnectivityManager, Vibrator, NotificationManager.

• getSystemService(``Class<T> serviceClass``): Аналогично предыдущему методу, но использует типизированный аргумент (начиная с API 23).

  
**4. Работа с настройками и базами данных**

• getSharedPreferences(String name, int mode): Получает SharedPreferences для работы с настройками приложения.

• openOrCreateDatabase(String name, int mode, SQLiteDatabase.CursorFactory factory): Открывает или создаёт базу данных.

• deleteDatabase(String name): Удаляет базу данных.

  

**5. Безопасность и разрешения**

• checkPermission(String permission, int pid, int uid): Проверяет, есть ли у процесса/пользователя указанное разрешение.

• checkSelfPermission(String permission): Проверяет, есть ли у приложения определённое разрешение (начиная с API 23).

• enforcePermission(String permission, int pid, int uid, String message): Принудительно проверяет разрешение и выбрасывает исключение при его отсутствии.

  

**6. Работа с уведомлениями**

• getMainExecutor(): Получает Executor, который выполняет задачи в главном потоке приложения.

• getMainLooper(): Возвращает Looper главного потока приложения.

• sendBroadcast(Intent intent): Отправляет широковещательное сообщение.

• sendOrderedBroadcast(Intent intent, String receiverPermission): Отправляет упорядоченное широковещательное сообщение.

  

**Важные производные классы Context**

• ContextWrapper: Обёртка над Context, которая делегирует вызовы другому Context.

• ContextThemeWrapper: Используется для работы с темами (Activity наследуется от него).

• Application: Глобальный Context для всего приложения.

• Activity: Контекст, привязанный к конкретной активности.

• Service: Контекст, привязанный к сервису.

> [!tip] Главное правило про Context (на собес)
> **«UI → Activity context, всё долгоживущее → Application context».**
> - Хранить **Activity context** в синглтоне/static/долгоживущем объекте = **утечка** (Activity не соберётся GC после уничтожения).
> - Для `Toast`, `Dialog`, `LayoutInflater`, `startActivity` без `NEW_TASK` — нужен **Activity context** (он несёт тему и инфо об окне; `ContextThemeWrapper`).
> - Для Room, DataStore, системных сервисов в репозитории — **`applicationContext`**.
> - **`AsyncTask` устарел** (с API 30) — в примерах выше он как иллюстрация утечки; в новом коде — корутины (`viewModelScope`), которые отменяются вместе со скоупом и не держат Activity.
> - Для архитектуры: не таскай `Context` в доменный слой/ViewModel — оборачивай ресурсы за интерфейсом (`ResourceProvider`) и внедряй через DI. См. [[Чистая архитектура]].
