# Блок 1. Kotlin, коллекции, `equals`/`hashCode`, `inline`

### 1. Почему `Task` лучше сделать `data class`?
Потому что это класс-носитель данных. `data class` бесплатно даёт корректные `equals`/`hashCode` (сравнение по значению полей), `toString`, `copy` и `componentN`. Это нужно, чтобы объекты правильно сравнивались, работали в `Set`/`Map` как ключи, и чтобы их можно было легко копировать с изменением части полей (актуально для immutable UI-state).

### 2. Какие методы автоматически создаёт `data class`?
- `equals()` / `hashCode()` — по полям из **первичного конструктора**;
- `toString()` — читаемое представление;
- `copy()` — копия с переопределением части параметров;
- `componentN()` — для деструктуризации (`val (a, b) = task`).

⚠️ Учитываются только свойства первичного конструктора. Поля, объявленные в теле класса, в `equals/hashCode/toString` не попадают.

### 3. Почему `val`, а не `var`?
Иммутабельность: объект нельзя случайно мутировать, он потокобезопасен «по построению», его безопасно использовать как ключ в `HashMap`/элемент `HashSet` (хеш не изменится после вставки). Изменения — через `copy()`, что естественно ложится на однонаправленный поток данных (UDF) в Compose/MVI.

### 4. Чем отличаются `mutable` и `immutable` коллекции?
В Kotlin это разделение на уровне **интерфейсов**, а не реальной неизменяемости.
- `List`, `Set`, `Map` — read-only интерфейсы: только чтение (`get`, `size`, итерация).
- `MutableList`, `MutableSet`, `MutableMap` — добавляют мутирующие методы (`add`, `remove`, `put`).

`List` — это *read-only view*, а не гарантия immutability: под капотом всё равно может лежать `ArrayList`, и через другую ссылку его могут менять.

**Зачем это разделение сделали (почему не как в Java):**

1. **Намерение в системе типов.** В Java интерфейс `List` один и сразу с мутирующими методами — нельзя на уровне типа сказать «даю только почитать». В Kotlin это видно из сигнатуры:
   ```kotlin
   fun render(items: List<Item>)        // НЕ будет менять
   fun fill(items: MutableList<Item>)   // БУДЕТ наполнять
   ```
   Самодокументируемый API + меньше случайных мутаций чужой коллекции.

2. **Ковариантность.** `List<out T>` ковариантен — `List<String>` можно передать туда, где ждут `List<Any>`. Это безопасно **только потому, что список read-only**: будь там `add`, ковариантность ломала бы типобезопасность (в `List<Any>` положили бы `Int`, а это `List<String>`). У `MutableList<T>` — инвариантность (есть `add`), поэтому ковариантность запрещена. То есть разделение интерфейсов — фундамент для безопасной ковариантности. Подробно про `out`/`in`/PECS → [[Generic]].

**Как в Java:**
- Один мутабельный интерфейс `List`, разделения на уровне типов нет.
- «Read-only» — через рантайм-обёртку: `Collections.unmodifiableList(list)` возвращает тот же тип `List`, но `add` бросает `UnsupportedOperationException` **в рантайме** (компилируется!).
- Java 9+: `List.of(...)`/`Set.of(...)`/`Map.of(...)` — по-настоящему immutable, но мутация снова падает `UnsupportedOperationException` в рантайме (тип-то всё равно `List`).

| | Kotlin | Java |
|---|---|---|
| Разделение read-only / mutable | на уровне **типов** | нет, один интерфейс |
| Запрет мутации ловится | **компилятором** | в **рантайме** (`UnsupportedOperationException`) |
| `List` это | read-only **view** (не immutable) | всегда мутабельный интерфейс |
| Ковариантность `List` | да (`out T`) благодаря read-only | нет (коллекции инвариантны) |

**Фраза на собес:** «В Java запрет изменения — это рантайм-обёртка (`unmodifiableList` → `UnsupportedOperationException`), а в Kotlin разделено на уровне типов: `List` vs `MutableList`, и ошибку ловит компилятор. Но котлиновский `List` — это read-only *view*, а не гарантия immutability: за ним может стоять изменяемый `ArrayList`».

⚠️ Read-only ≠ immutable:
```kotlin
val mutable = mutableListOf(1, 2, 3)
val readOnly: List<Int> = mutable   // та же ссылка (ArrayList) под капотом
mutable.add(4)
println(readOnly)                   // [1, 2, 3, 4] — view изменился!
```
Настоящая неизменяемость — `kotlinx.collections.immutable` (persistent collections) или защитная копия.

### 5. Почему для добавления элемента нужен `MutableList`?
У `List` просто нет метода `add()` — он не объявлен в read-only интерфейсе. Чтобы мутировать, нужен `MutableList` (`mutableListOf()` или `ArrayList`).

### 6. За счёт чего реализуется разница между `List` и `MutableList`?
За счёт иерархии интерфейсов: `MutableList : List`. Read-only интерфейс не содержит мутирующих методов. На уровне JVM это всё равно один и тот же `java.util.ArrayList` — разделение существует только в системе типов Kotlin (compile-time), runtime-гарантий неизменяемости нет.

### 7. На чём основана логика работы `HashSet` при добавлении?
Важно развести два уровня:
- **По API это разные коллекции:** `HashSet<E>` хранит уникальные **элементы** (интерфейс `Set`), `HashMap<K,V>` — пары **ключ→значение** (интерфейс `Map`). Разные методы, разный смысл.
- **Но реализован `HashSet` поверх `HashMap`** (буквально, см. исходник JDK): внутри лежит поле `HashMap<E, Object>`, **элемент Set кладётся как ключ Map**, а значением выступает одна общая константа-заглушка `PRESENT` (значение не важно — важен только ключ).

```java
public class HashSet<E> {
    private transient HashMap<E, Object> map;        // внутри — HashMap
    private static final Object PRESENT = new Object(); // заглушка-значение

    public boolean add(E e)            { return map.put(e, PRESENT) == null; }
    public boolean contains(Object o)  { return map.containsKey(o); }
    public boolean remove(Object o)    { return map.remove(o) == PRESENT; }
}
```

Поэтому `set.add(x)` = `map.put(x, PRESENT)`, а уникальность обеспечивается уникальностью **ключей** `HashMap`.

**Зачем так:** переиспользование. Вся механика (hashCode → бакет, equals → сравнение, ресайз, коллизии) уже есть в `HashMap`. Множество — это «словарь, где значения не нужны», поэтому `HashSet` — тонкая обёртка, а не отдельная реализация.

**Фраза на собес:** «`HashSet` и `HashMap` — разные коллекции по API, но `HashSet` реализован поверх `HashMap`: элементы кладутся как ключи, значение — константа `PRESENT`. Логика уникальности у них общая».

### 8. Как устроена проверка уникальности в `HashSet` под капотом?
1. Считается `hashCode()` элемента → определяется бакет (индекс корзины).
2. Если бакет пуст — элемент кладётся туда.
3. Если в бакете уже есть элементы (коллизия) — новый сравнивается с каждым через `equals()`.
4. Если нашёлся равный по `equals()` — новый **не добавляется** (дубликат). Иначе — добавляется в тот же бакет (цепочка/дерево).

То есть сначала грубый отсев по `hashCode` (быстро), потом точное сравнение по `equals` (точно).

### 9. Контракт `equals` / `hashCode`
- Если `a.equals(b) == true`, то **обязательно** `a.hashCode() == b.hashCode()`.
- Обратное неверно: равные хеши не означают равенство объектов (коллизия допустима).
- `hashCode()` должен быть стабильным, пока объект не меняется.

**Свойства `equals` простыми словами** (4 правила, которым он обязан подчиняться):

| Свойство | Что значит | Пример |
|---|---|---|
| **Рефлексивность** | объект равен сам себе | `a.equals(a) == true` |
| **Симметричность** | если `a` равен `b`, то и `b` равен `a` (порядок не важен) | `a.equals(b) == b.equals(a)` |
| **Транзитивность** | если `a == b` и `b == c`, то `a == c` (равенство «передаётся по цепочке») | `a.equals(b) && b.equals(c)` ⟹ `a.equals(c)` |
| **Консистентность** | при одинаковых данных результат всегда один и тот же, сколько ни вызывай | `a.equals(b)` возвращает то же значение, пока `a` и `b` не изменили |

➕ Ещё: `a.equals(null)` всегда `false` (объект не равен «ничему»).

**Зачем это:** коллекции (`HashSet`/`HashMap`, сортировки) полагаются на эти правила. Если нарушить, например, симметричность — поведение `contains`/`get` станет непредсказуемым (результат зависит от того, в каком порядке сравнивали). Поэтому надёжнее всего — `data class` или генерация `equals/hashCode` в IDE, а не руками.

### 10. Что будет, если переопределить только `equals`, но не `hashCode`?
Сломается контракт. Чтобы понять почему — разберём сам контракт и как ведут себя объекты при складывании в `HashSet`/`HashMap`.

**Контракт (главное правило):**
> Если `a.equals(b) == true`, то **обязательно** `a.hashCode() == b.hashCode()`.
Обратное **не** обязано выполняться: равные хеши ≠ равные объекты (это допустимая коллизия).

**Как хеш-коллекция работает с объектом (2 шага):**
1. `hashCode()` → определяет **бакет** (в какую корзину смотреть). Быстрый грубый отсев.
2. внутри бакета `equals()` → точное сравнение (дубликат или нет).
Ключевой момент: **если хеши разные — до шага 2 (`equals`) дело вообще не доходит**, объекты в разных бакетах и заведомо считаются разными.

**Поведение объектов:**

| Ситуация | hashCode | equals | Что в HashSet/Map |
|---|---|---|---|
| Контракт соблюдён, объекты равны | одинаковый → один бакет | `true` | дубликат отсеётся, останется 1 элемент / `get` найдёт ключ ✅ |
| Контракт соблюдён, объекты разные | разный (обычно) → разные бакеты | до `equals` не доходит / `false` | оба лежат как разные ✅ |
| Коллизия (разные объекты, совпал хеш) | одинаковый → один бакет | `false` | оба в одном бакете, но как разные элементы (цепочка/дерево) ✅ |
| **Только equals переопределён** (баг) | **разный** (дефолтный от `Object`, по адресу) → разные бакеты | **`true`, но его не спрашивают** | логически равные считаются **разными** ❌ |

**Что именно ломается при переопределении только `equals`:**
Два логически равных объекта имеют **разные** дефолтные хеши (`Object.hashCode()` — по адресу в памяти). Значит, они попадают в **разные бакеты**, и `equals` (хоть он и вернул бы `true`) **никто не вызывает** — коллекция их даже не сравнивает.

```kotlin
class User(val id: Int) {
    override fun equals(other: Any?) = other is User && other.id == id
    // hashCode НЕ переопределён → дефолтный, по адресу
}

val set = HashSet<User>()
set.add(User(1))
set.add(User(1))          // логически тот же, но другой хеш → другой бакет
println(set.size)         // 2 (!), хотя ожидали 1 — дубликат не схлопнулся

val map = HashMap<User, String>()
map[User(1)] = "Аня"
println(map[User(1)])     // null (!) — искали в другом бакете, ключ "не нашёлся"
```

**Вывод:** `equals` и `hashCode` **всегда переопределяют вместе** (или используют `data class`, который делает оба по полям). Один без другого = тихий баг в `HashSet`/`HashMap`: дубликаты в Set и «пропавшие» ключи в Map.

### 11. Что такое `inline`-функция и как работает встраивание?
`inline` — указание компилятору **подставить тело функции и её лямбд прямо в место вызова**, вместо реального вызова метода и создания объектов-лямбд. Главная выгода — для функций высшего порядка: убираем **аллокацию объекта** `Function`-интерфейса на каждый вызов лямбды и оверхед вызова. Минус — раздувание байткода, поэтому инлайнят небольшие функции (`map`, `filter`, `let`, `apply`, `with`).

**Что значит «аллокация объекта лямбды»** (подробнее → [[Аллокация в jvm]], [[Лямбда]], [[Heap & Stack]]):
Лямбда на JVM — это не «просто код», а **объект**. Компилятор превращает её в экземпляр класса, реализующего интерфейс `FunctionN` (`Function0`, `Function1`, …) с методом `invoke()`. Создание этого объекта = **аллокация в куче (heap)**, а каждый созданный объект потом собирает GC.

```kotlin
// без inline: на каждый вызов repeat создаётся объект-лямбда в куче
inline fun repeatAction(times: Int, action: () -> Unit) {
    for (i in 0 until times) action()
}
```
- **Без `inline`:** вызов `repeatAction(1000) { ... }` создаёт объект `Function0` (а если лямбда захватывает переменные — ещё и хранит их в полях). В цикле/горячем коде это сотни лишних объектов → нагрузка на GC → потенциальный jank ([[Performance. Память и утечки]]).
- **С `inline`:** тело лямбды встраивается прямо в место вызова — **объект-лямбда не создаётся вообще**, аллокации в куче нет.

⚠️ Нюанс: stdlib и компилятор и так оптимизируют **non-capturing** лямбды (которые ничего не захватывают) в синглтоны, поэтому экономия особенно заметна на **захватывающих** лямбдах и в горячих участках. Поэтому stdlib-функции (`map`, `filter`, `forEach`, `let`…) сделаны `inline` — чтобы цепочки вызовов не плодили объекты.

**Фраза на собес:** «Лямбда на JVM — это объект класса `FunctionN`, его создание = аллокация в куче и работа для GC. `inline` встраивает тело в место вызова, поэтому объект-лямбда не создаётся — для функций высшего порядка в горячем коде это убирает лишние аллокации».

### 12. Что такое `reified`-параметр типа?
`reified` позволяет получить доступ к типу `T` в рантайме внутри `inline`-функции — обойти стирание типов (type erasure). Можно писать `T::class`, `is T`, `as T`. Работает только в `inline`-функциях, потому что тип подставляется в месте вызова на этапе компиляции.
```kotlin
inline fun <reified T> Gson.fromJson(json: String): T =
    fromJson(json, T::class.java)
```

### 13. Как сделать так, чтобы `T` оставался `reified`?
Пометить функцию `inline`, а параметр типа — `reified`. Без `inline` `reified` невозможен.

### 14. Что изменится, если сделать функцию `inline`?
- Тело и лямбды встроятся в вызов → нет аллокаций лямбд, нет лишнего вызова.
- Станет доступен `reified`.
- Появится возможность **нелокального `return`** из лямбды.
- Минус: код вызова раздувается, нельзя рекурсию, есть ограничения на видимость (нельзя инлайнить с доступом к `private`-членам в публичной inline-функции).

### 15. Что такое `crossinline`?
Модификатор лямбды-параметра inline-функции, который **запрещает нелокальный return** из этой лямбды, но при этом лямбда остаётся инлайнимой. Нужен, когда лямбда вызывается не напрямую, а из другого контекста (например, внутри объекта `Runnable`/другого лямбда-блока), где нелокальный return был бы небезопасен.
```kotlin
inline fun runOnUi(crossinline block: () -> Unit) {
    Handler(Looper.getMainLooper()).post { block() } // block нельзя выйти return'ом наружу
}
```

### 16. Что такое `noinline`?
Модификатор параметра-лямбды, который **отключает инлайнинг конкретно для неё**, когда сама функция `inline`. Нужно, если лямбду надо сохранить в переменную, передать дальше как объект или вернуть — инлайненную лямбду как объект использовать нельзя.

### 17. Как работают `return` из лямбды внутри `inline`-функции?
Поскольку лямбда встроена в вызывающий код, `return` без метки означает выход **из внешней функции** (нелокальный return) — как будто код написан прямо там. Это возможно только для инлайн-лямбд.

### 18. Локальный vs нелокальный `return`
- **Нелокальный** (`return`) — выходит из функции, в которой написана inline-лямбда (из вызывающего метода). Возможен только в inline.
- **Локальный** (`return@label`, например `return@forEach`) — выходит только из самой лямбды, аналог `continue` в цикле; внешняя функция продолжает работу.

### 19. Что будет, если убрать квалификатор у `return` в inline-лямбде?
`return` станет нелокальным — выйдет из внешней функции целиком. Например, `return` внутри `forEach` прервёт всю функцию, а не только итерацию (часто неожиданно для новичков).

### 20. Как запретить нелокальный `return` в inline-функции?
Пометить лямбду `crossinline`. Тогда компилятор запретит `return` без метки.

### 21. Использовал ли такой набор в реальном коде?
Честный ответ: `inline`/`reified` — постоянно (DI, парсинг json, `getSystemService<T>()`, extension'ы). `crossinline` — когда лямбда уходит в `post`/`runOnUiThread`/билдеры. `noinline` — реже, когда лямбду надо сохранить/передать дальше. Свои inline-функции пишу редко — обычно хватает stdlib, инлайнить вручную имеет смысл только в горячих участках или ради `reified`.

# Блок 2. Корутины, callbacks, параллельное выполнение

### 1. Как параллельно выполнить несколько запросов и собрать ответы?
Запустить каждый через `async`, получить список `Deferred`, дождаться всех через `awaitAll`:
```kotlin
suspend fun loadAll(ids: List<Int>): List<Response> = coroutineScope {
    ids.map { id -> async { api.load(id) } }   // стартуют параллельно
       .awaitAll()                              // ждём все, порядок сохранён
}
```
`coroutineScope` обеспечивает structured concurrency: если один упадёт — отменятся остальные, исключение пробросится наверх.

### 2. Почему подходит `async`?
`async` запускает корутину и сразу возвращает `Deferred<T>` — «обещание» результата, не блокируя. Несколько `async` стартуют конкурентно, а результат забираем позже через `await`. Для «запустить параллельно и получить значения» — ровно его кейс (в отличие от `launch`, который не возвращает результат).

### 3. Что такое `Deferred`?
`Deferred<T>` — это `Job` с результатом (наследник `Job`). Представляет будущее значение корутины, которое можно получить через `await()`.

### 4. Чем `Deferred` отличается от `Job`?
- `Job` — корутина без результата, только статус (active/completed/cancelled). Запускается через `launch`.
- `Deferred<T>` — `Job` + результат типа `T`, получаемый через `await()`. Запускается через `async`.

### 5. Как получить значение из `Deferred`?
Вызвать `await()` — suspend-функция, приостанавливает корутину до готовности результата (или бросает исключение, если корутина упала).

### 6. Что такое `awaitAll` и когда удобно?
`awaitAll(vararg/Collection<Deferred>)` — ждёт завершения всех `Deferred` и возвращает `List` результатов в том же порядке. Удобно при fan-out: запустили N задач параллельно — собрали все результаты одной строкой. Если любая упадёт — `awaitAll` сразу бросит исключение.

### 7. Как обернуть callback-API в корутину?
Через `suspendCancellableCoroutine`: приостанавливаем корутину, в callback вызываем `continuation.resume(...)`:
```kotlin
suspend fun loadUser(id: Int): User = suspendCancellableCoroutine { cont ->
    api.load(id, object : Callback {
        override fun onSuccess(u: User) = cont.resume(u)
        override fun onError(e: Throwable) = cont.resumeWithException(e)
    })
    cont.invokeOnCancellation { api.cancel(id) } // отмена
}
```

### 8. Как уйти от callback-стиля?
Обернуть callback'и в suspend-функции (`suspendCancellableCoroutine`), а потоки событий — во `Flow` (`callbackFlow`). Дальше пишем линейный последовательный код вместо вложенных колбэков (callback hell).

### 9. Что такое `suspend`-функция?
Функция, которая может **приостановить** выполнение без блокировки потока и возобновиться позже. Может вызываться только из корутины или другой suspend-функции. Компилятор превращает её в state machine с дополнительным параметром `Continuation`.

### 10. Что такое `Continuation`?
Объект, хранящий состояние приостановленной корутины и «что делать дальше» (callback возобновления). Содержит `context` и метод `resumeWith(Result)`. По сути — продолжение вычисления.

### 11. Как работает `Continuation` и state machine?
Компилятор превращает suspend-функцию в класс — конечный автомат. Каждая точка приостановки (`suspend`-вызов) = отдельное состояние (метка `label`). Локальные переменные сохраняются в полях этого объекта-Continuation. При возобновлении (`resumeWith`) метод вызывается заново, по `label` прыгает в нужное состояние и продолжает с места остановки. Это и есть CPS (Continuation Passing Style) — каждой suspend-функции добавляется скрытый параметр `Continuation`.

### 12. Как использовать `Continuation.resume` для возврата из callback?
В колбэке вызвать `continuation.resume(value)` (успех) или `resumeWithException(e)` (ошибка). Это возобновляет приостановленную корутину с результатом. Важно: `resume` можно вызвать **только один раз** — повторный бросит `IllegalStateException`.

### 13. Почему `await` нельзя вызвать вне корутины?
`await()` — suspend-функция, ей нужен `Continuation` (контекст корутины) для приостановки. Вне корутины этого контекста нет, поэтому компилятор не даст вызвать. Suspend можно вызывать только из suspend/корутины.

### 14. Нужно ли создавать отдельный `CoroutineScope` для каждого запроса?
Нет. Scope — это менеджер жизненного цикла группы корутин. Создавать по scope на запрос — антипаттерн (утечки, нет structured concurrency). Используем готовые (`viewModelScope`, `lifecycleScope`) или один долгоживущий, а конкретные запросы запускаем через `launch`/`async` внутри него.

### 15. Как работает несколько `launch` в одном `scope`?
Каждый `launch` создаёт **дочернюю** корутину. Они запускаются конкурентно и являются детьми scope (structured concurrency). Scope ждёт завершения всех детей; отмена scope отменяет всех.

### 16. Параллельно или последовательно?
Несколько `launch`/`async` подряд внутри scope/`coroutineScope` — **конкурентно** (параллельно, насколько позволяет диспетчер). А вот если внутри одной корутины писать `api.a(); api.b()` через прямые suspend-вызовы — это **последовательно**. Параллельность даёт именно разделение на разные корутины.

### 17. Как сделать helper потокобезопасным для вызова из разных корутин?
Не хранить мутабельное состояние между вызовами (stateless), либо защищать состояние (`Mutex`, атомики). Suspend-функция без shared mutable state безопасна для конкурентного вызова. Если внутри свой scope — он должен корректно обрабатывать конкурентные запуски.

### 18. Куда вынести `CoroutineScope` для helper-синглтона?
В поле самого синглтона: один долгоживущий scope с понятным `Job` (например, `SupervisorJob()`) и диспетчером, например `CoroutineScope(SupervisorJob() + Dispatchers.IO)`. `SupervisorJob`, чтобы падение одной корутины не убивало остальные.

### 19. Можно ли единый `CoroutineScope` внутри singleton?
Можно, если это осознанно: scope живёт всё время жизни приложения, используем `SupervisorJob`, обрабатываем ошибки, не плодим scope на вызов. Риск — корутины переживут «логический» жизненный цикл, поэтому такой подход уместен для app-level задач (аналитика, кэш), а не для UI.

# Блок 3. Jetpack Compose и вёрстка

### 1. Экран: заголовок сверху + список ниже
`Column` на весь экран: сверху заголовок (`Text`/`TopAppBar`), ниже `LazyColumn` с `Modifier.weight(1f)`, чтобы занять оставшееся пространство.
```kotlin
Column(Modifier.fillMaxSize()) {
    Text("Заголовок", Modifier.fillMaxWidth(), textAlign = TextAlign.Center)
    LazyColumn(Modifier.weight(1f)) { items(list, key = { it.id }) { Card(it) } }
}
```

### 2. Компонент для заголовка сверху
Чаще `TopAppBar` (Material3) — стандартный паттерн с поддержкой title/actions/scroll behavior. Если просто текст — `Text`. На собесе скажи про `TopAppBar` как «правильный» вариант.

### 3. Как сделать заголовок по центру?
- `CenterAlignedTopAppBar` в Material3, либо
- `Text(..., modifier = Modifier.fillMaxWidth(), textAlign = TextAlign.Center)`.

### 4. Контейнер для списка на всю высоту
`LazyColumn` с `Modifier.weight(1f)` внутри `Column` (либо `fillMaxSize`, если он один).

### 5. Почему именно `LazyColumn`, а не `Column`?
`Column` рендерит **все** дочерние элементы сразу — для длинного/бесконечного списка это лишняя память и тормоза. `LazyColumn` компонует и держит в памяти только видимые элементы (+небольшой буфер), переиспользует их при скролле — как `RecyclerView`.

### 6. Чем `LazyColumn` отличается от `Column`?
- `Column` — все элементы создаются сразу, нет переиспользования, скролл вручную (`verticalScroll`).
- `LazyColumn` — ленивая композиция только видимого, встроенный скролл, DSL `item`/`items`, поддержка `key`, `contentPadding`, sticky headers.

### 7. Как работает `key` в `LazyColumn` и зачем?
`key` задаёт **стабильный идентификатор элемента**, привязанный к данным, а не к позиции в списке. Это то, по чему Compose понимает «это тот же самый элемент, что и раньше» при изменении списка.

```kotlin
items(events, key = { it.id }) { EventCard(it) }
```

**Как Compose связывает данные и композицию (identity).**
Каждый элемент списка порождает своё поддерево композиции, у которого есть внутреннее состояние: `remember { ... }`, `rememberSaveable`, состояние анимаций, позиция скролла вложенных элементов и т.д. Чтобы при рекомпозиции понять, какому элементу какое состояние принадлежит, Compose должен сопоставить старые элементы с новыми. Делает он это по **ключу**:
- **Без `key`** ключом становится **позиция (индекс)** элемента в списке. «Элемент №0», «элемент №1»… Состояние привязано к индексу.
- **С `key`** ключом становится значение, которое ты вернул (`it.id`). Состояние привязано к конкретной сущности, а не к её месту в списке.

**Что ломается без `key` — конкретный сценарий.**
Список `[A, B, C]`, у каждой карточки локальный лайк (`rememberSaveable`). Лайкнули только `B`. Теперь в начало вставили новый элемент `X` → список стал `[X, A, B, C]`.

| | Ключ по позиции (без `key`) | Ключ по `id` (с `key`) |
|---|---|---|
| Как Compose видит изменения | поз. 0 был `A`, стал `X` → «изменились данные, но это тот же слот»; поз. 2 был `C`, а лайк был на слоте 1 | слот с `id=B` остался слотом `id=B` |
| Куда «уедет» лайк | лайк остаётся на **позиции 1**, а там теперь `A` → лайкнутым визуально станет `A` ❌ | лайк остаётся на элементе `B` ✅ |
| Рекомпозиция | Compose считает, что содержимое почти всех слотов изменилось → перекомпонует лишнее | переиспользует композиции `A/B/C`, реально новый только `X` |

То есть без `key` состояние (`remember`, анимации, развёрнутость, выделение) **«съезжает» на соседей** при вставке/удалении/перестановке, а не следует за своим элементом.

**Три вещи, которые даёт `key`:**
1. **Сохранение состояния за элементом.** `remember`/`rememberSaveable`/анимации остаются привязаны к своей сущности при любых перестановках списка.
2. **Эффективная рекомпозиция и переиспользование.** Compose точечно понимает, что реально добавилось/удалилось/переместилось, и не перекомпоновывает нетронутые элементы. При перестановке умеет **переместить** уже готовую композицию, а не создавать заново.
3. **Корректные анимации.** `Modifier.animateItem()` (ранее `animateItemPlacement`) работает **только с `key`** — без идентичности Compose не знает, что элемент «тот же самый, но переехал», и анимировать перемещение нечему.

⚠️ **Требования к ключу:**
- **Уникальность** в пределах списка. Дублирующиеся ключи → рантайм-креш (`IllegalArgumentException: Key ... was already used`).
- **Стабильность** — один и тот же элемент всегда даёт один и тот же ключ. Нельзя брать `hashCode()` изменяемого объекта или **индекс** (`key = { index }` бессмысленно — это ровно поведение «без key»).
- **Saveable-тип** (`Int`, `Long`, `String`, `Parcelable`…). Compose сохраняет ключ в `rememberSaveable`-инфраструктуру, чтобы восстановить состояние после смены конфигурации/process death. Кастомный объект без поддержки сохранения не подойдёт.
- Плохой выбор ключа — сам объект данных, если он `data class` и **меняется** (лайк, счётчик): при изменении полей меняется и ключ → элемент считается новым, состояние теряется. Бери **стабильный `id`**, а не весь объект.

**Связь с общей темой identity в Compose:** это тот же принцип, что и `key(...) { }`-обёртка в обычной композиции — управление тем, как Compose сопоставляет вызовы между рекомпозициями. В списках он просто вынесен в параметр `items(key = ...)`.

**Фраза на собес:** «`key` привязывает состояние и композицию к сущности, а не к позиции. Без него ключ — это индекс, и при вставке/удалении/перестановке `remember`, анимации и лайки „съезжают“ на соседей, а рекомпозиция делает лишнюю работу. Ключ должен быть уникальным, стабильным и saveable — обычно это `id` из модели. Плюс `animateItem()` вообще работает только при наличии `key`».

### 16. Как хранить состояние лайка?
Локально — `var liked by rememberSaveable { mutableStateOf(false) }`. Но «правильно»: состояние списка — в `ViewModel` (источник истины), а в UI прокидываем значение + лямбду `onLikeClick`. Локальный `remember` годится для чисто визуального, не привязанного к данным состояния.

### 17. Почему `rememberSaveable` для лайка?
Чтобы состояние пережило **смену конфигурации** (поворот экрана, смерть процесса) — `rememberSaveable` сохраняет значение в `Bundle` (`SavedInstanceState`).

### 18. `rememberSaveable` vs `remember`
Оба «запоминают» значение, чтобы оно не пересоздавалось на каждой рекомпозиции. Разница — **как долго живёт** запомненное и **где** оно хранится.

**Три уровня «времени жизни» состояния** (важно развести, потому что их часто путают):

| Событие | обычная `var` | `remember` | `rememberSaveable` |
|---|---|---|---|
| Рекомпозиция (перевызов composable) | сбрасывается ❌ | переживает ✅ | переживает ✅ |
| Смена конфигурации (поворот, тема, язык) | сбрасывается ❌ | **сбрасывается** ❌ | переживает ✅ |
| Process death (система убила процесс в фоне) | сбрасывается ❌ | сбрасывается ❌ | переживает ✅ |

**`remember` — где живёт.**
Значение кладётся в **slot table** (память композиции) и держится, пока composable **присутствует в дереве**. Оно переживает рекомпозицию, но:
- при смене конфигурации Activity по умолчанию **пересоздаётся** → композиция строится заново → slot table новый → `remember` посчитается заново;
- когда composable **покидает композицию** (ушли с экрана, элемент списка проскроллили за пределы буфера) — значение выбрасывается.

```kotlin
val x = remember { expensiveInit() } // не пересчитывается на рекомпозиции, но обнулится при повороте
```

**`rememberSaveable` — где живёт и как переживает поворот/смерть процесса.**
Помимо slot table, значение сохраняется в **`SavedStateRegistry`** — тот же механизм, что стоит за `onSaveInstanceState`/`Bundle`. Bundle переживает и смену конфигурации, и process death (система сериализует его на диск и восстанавливает при возврате в приложение). Поэтому `rememberSaveable` восстановит значение там, где `remember` его потеряет.

```kotlin
var liked by rememberSaveable { mutableStateOf(false) } // переживёт поворот и убийство процесса в фоне
```

⚠️ **Ограничение: значение должно уметь попасть в `Bundle`.** Из коробки работают примитивы, `String`, `Parcelable`, `Serializable`, а также то, для чего есть встроенный `Saver` (`mutableStateOf` — есть). Для произвольного типа нужен **кастомный `Saver`** — он описывает, как сложить объект в saveable-представление и как собрать обратно:

```kotlin
data class City(val name: String, val country: String)

val CitySaver = listSaver<City, String>(
    save = { listOf(it.name, it.country) },      // объект → список примитивов
    restore = { City(it[0], it[1]) }             // обратно
)

var city by rememberSaveable(stateSaver = CitySaver) {
    mutableStateOf(City("Москва", "RU"))
}
```
(Есть готовые хелперы: `listSaver`, `mapSaver`, `Saver` вручную.)

**Когда что брать (правило):**
- **`remember`** — для того, что дёшево пересчитать при повороте или что и так восстановится из источника истины: закешированные объекты, контроллеры, производные значения, скролл-состояние, которое не жалко.
- **`rememberSaveable`** — для **пользовательского ввода и локального UI-состояния, которое обидно потерять** при повороте: текст в поле, чекбоксы, раскрытые панели, выбранная вкладка, лайк в чисто визуальном примере.
- **Ни то, ни другое, если состояние — это данные экрана.** ⚠️ `rememberSaveable` не замена `ViewModel`. Bundle рассчитан на **маленькие** объёмы (крупный объект → `TransactionTooLargeException`), и «правильный» source of truth для данных списка/загрузки — `ViewModel` (переживает поворот сама) + при необходимости `SavedStateHandle` для переживания process death. Локальный `rememberSaveable` — для мелких UI-нюансов, а не для бизнес-данных.

**Как это связано с рекомпозицией:** и `remember`, и `rememberSaveable` возвращают одно и то же закешированное значение при каждом перевызове composable, потому что composable-функции **идемпотентны и вызываются много раз** (см. п.19–20). Без «запоминания» инициализатор (`{ mutableStateOf(false) }`) выполнялся бы заново на каждой рекомпозиции и состояние постоянно обнулялось бы.

**Фраза на собес:** «`remember` кеширует в slot table и переживает только рекомпозицию — при повороте пересчитается. `rememberSaveable` дополнительно кладёт значение в `SavedStateRegistry`/`Bundle`, поэтому переживает и смену конфигурации, и process death, но требует saveable-тип или кастомный `Saver`. Для крупных или бизнес-данных — не `rememberSaveable`, а `ViewModel` + `SavedStateHandle`, потому что Bundle мал и падает на больших объёмах».

### 19. Почему состояние UI сбрасывается при рекомпозиции?
Если хранить состояние в обычной переменной (`var x = ...`), при каждой рекомпозиции функция вызывается заново и переменная пересоздаётся. Чтобы пережить рекомпозицию, состояние нужно «запомнить» через `remember`/`rememberSaveable` и хранить в `MutableState`.

### 20. Что такое рекомпозиция?
Повторный вызов composable-функций для перерисовки UI при изменении состояния (`State`), от которого они зависят. Compose перевызывает только те функции, чьи входные данные/`State` изменились (умное пропускание — skipping).

### 21. Какие события вызывают рекомпозицию?
Изменение читаемого в composable `State`/`MutableState`, новое значение из `Flow`/`LiveData` через `collectAsState`, изменение параметров composable, нажатие на лайк (меняет state), приход данных из ViewModel.

### 22. Как Compose узнаёт, что нужно обновить UI?
Через **систему наблюдаемого состояния (snapshot state)**. Компилятор не «сканирует всё дерево» на изменения — вместо этого он точно знает, **кто какое состояние читает**, и перекомпоновывает только тех, у кого прочитанные данные изменились.

**Механика в трёх шагах (read → write → invalidate):**
1. **Read-tracking (кто что читает).** Когда composable **читает** значение `State` (например, `state.value` / делегат `by`), это происходит внутри «наблюдаемой области» (recompose scope). Snapshot-система фиксирует зависимость: «эта область читает вот этот `State`». Ключевой момент — важно именно **чтение**: если composable не читает `State`, он от него и не зависит.
2. **Write (запись нового значения).** Когда кто-то пишет новое значение в `MutableState`, snapshot-система сравнивает старое и новое **по `equals`** (структурно). Если равно — ничего не происходит (нет причины перерисовывать). Если изменилось — идём дальше.
3. **Invalidate + планирование.** Все области, которые читали этот `State`, помечаются как недействительные (**invalidate**), и на следующий кадр (сигнал от `Choreographer`) планируется их **рекомпозиция** — перевызов только этих функций, а не всего экрана.

```kotlin
var count by remember { mutableStateOf(0) }   // MutableState — наблюдаемый
Text("$count")                                // ← ЧТЕНИЕ: эта область подписалась на count
Button(onClick = { count++ }) { Text("+") }   // ← ЗАПИСЬ: инвалидирует только Text выше
```
Здесь при клике перекомпонуется **только `Text`** (он читал `count`), а `Button` — нет.

⚠️ **Почему обычная `var` так не работает:** `var count = 0` — это не `State`, чтения никто не отслеживает. Меняй сколько угодно — Compose не узнает, UI не обновится. Наблюдаемость даёт именно `mutableStateOf` (и `Flow`/`LiveData` через `collectAsState`, которые под капотом превращаются в `State`).

**Почему snapshot называется snapshot:** состояние читается через «снимок» — это даёт консистентность (в рамках одной рекомпозиции все чтения видят согласованные данные) и потокобезопасность (можно менять state из фоновой корутины; изменения применяются атомарно). Отсюда же и требование `equals` в шаге 2 — сравнение снимков.

---

**Стабильность: `@Stable` и `@Immutable` — как Compose решает, можно ли ПРОПУСТИТЬ рекомпозицию.**

Отдельная, но связанная тема. Snapshot-система отвечает на вопрос «что изменилось». А стабильность отвечает на вопрос «**можно ли не перекомпоновывать composable, если её параметры на вид не менялись**» (это оптимизация — **skipping**).

**Как работает skipping.** Когда composable вызывается повторно с теми же параметрами, Compose хочет её **пропустить** (не выполнять тело). Чтобы это было безопасно, он должен быть уверен, что по параметрам можно надёжно судить об изменениях через `equals`. Такие типы Compose называет **стабильными (stable)**. Если хоть один параметр **нестабильный**, Compose **не рискует** и перекомпоновывает composable **всегда**, даже когда данные фактически те же → лишняя работа.

**Что считается стабильным автоматически:**
- примитивы (`Int`, `Boolean`, `Float`…), `String`, функциональные типы (лямбды);
- `MutableState` и другие snapshot-state типы;
- `data class`, у которого **все** поля стабильны и `val` (компилятор сам выводит).

**Что считается НЕстабильным (и ломает skipping):**
- `var`-поля в классе (значение может измениться незаметно для `equals`-логики Compose);
- интерфейсы/абстрактные типы как тип параметра (`List`, `Map`, `Set`) — Compose **не знает** реализацию, а за `List` может стоять мутабельный `ArrayList` (см. блок 1 про read-only view ≠ immutable), поэтому `List<T>` по умолчанию считается **нестабильным**;
- классы из других модулей/библиотек, которые компилятор Compose не анализировал.

**`@Stable` и `@Immutable` — это обещание компилятору**, снимающее «неуверенность»:

| Аннотация | Что обещаешь | Пример |
|---|---|---|
| `@Immutable` | после создания объект **не меняется вообще** — все поля финальны, никакой мутации | контракт UI-state, модель с `val`-полями |
| `@Stable` | объект **может меняться**, но: (1) об изменениях публичных свойств Compose узнает (они `State`/наблюдаемые); (2) `equals` консистентен; (3) для одинаковых входов возвращает одинаковый результат | holder с внутренним `MutableState` |

```kotlin
@Immutable
data class Event(val id: Long, val title: String, val date: String)
// теперь параметр Event гарантированно стабилен → EventCard(event) можно пропустить,
// если event.equals(previous) == true
```

⚠️ **Аннотация — это обещание, а не проверка.** Компилятор верит на слово. Если пометить `@Immutable` класс, который на самом деле мутируется, Compose будет **пропускать** нужные рекомпозиции → UI не обновится (баг «экран не перерисовывается»). Помечай только реально неизменяемые типы.

**Практические следствия (частый вопрос на собесе — «почему лишние рекомпозиции»):**
- **`List` нестабилен** → composable с параметром `List` перекомпонуется всегда. Решение: `kotlinx.collections.immutable` (`ImmutableList`/`persistentListOf`) — эти типы помечены стабильными, или обернуть в `@Immutable`-класс-holder.
- **Строгая стабильность UI-state** через `@Immutable data class` даёт корректный и дешёвый skipping — ещё один аргумент, почему UI-state делают immutable (перекликается с блоком 1: `val`, `data class`, `copy()`).
- Диагностика: **Compose compiler metrics / stability reports** показывают, какие классы `stable`/`unstable` и какие composable `skippable`/`restartable`.

**Фраза на собес:** «UI обновляется через snapshot-систему: composable, читающая `State`, подписывается на него; при записи нового значения (сравнение по `equals`) Compose инвалидирует и перекомпонует только эти области. Отдельно есть стабильность: если параметры composable стабильны, Compose пропускает рекомпозицию при равных данных (skipping). `List` и `var`-поля нестабильны и ломают эту оптимизацию, поэтому UI-state делают `@Immutable data class` с `val`-полями, а списки — `ImmutableList`. `@Stable`/`@Immutable` — это обещание компилятору, а не проверка: соврёшь — получишь пропущенные обновления».

### 23. Зачем сохранять состояние списка между поворотами?
Чтобы не терять позицию скролла, состояния лайков, развёрнутых элементов при смене конфигурации. Источник истины — `ViewModel` (переживает поворот), плюс `rememberSaveable`/`rememberLazyListState` для UI-нюансов.

# Блок 4. Архитектура, ViewModel, UI state, навигация

### 1. Экран с кнопкой, делающей сетевой запрос — общий дизайн
UI (Composable) → событие `onClick` → `ViewModel.onButtonClick()` → `UseCase` → `Repository` → сеть. Результат прилетает обратно в `StateFlow<UiState>`, UI на него подписан. Слои: `UI → ViewModel → UseCase → Repository → DataSource`.

### 2. Какой слой инициирует запрос — UI или ViewModel?
Запрос инициирует **ViewModel** (через use case). UI только сообщает о намерении пользователя (event), сам сетевых вызовов не делает. UI «тупой».

### 3. Как организовать `ViewModel`?
Держит `private val _state = MutableStateFlow(UiState.Idle)` и `val state = _state.asStateFlow()`. Метод `onClick()` запускает `viewModelScope.launch { ... }`, переключает state в `Loading`, вызывает use case, на результат пишет `Success`/`Error`. Никаких ссылок на Context/View.

### 4. Как описать `UIState` для загрузки/ошибки?
Через sealed-иерархию или data class с флагами:
```kotlin
sealed interface UiState {
    data object Idle : UiState
    data object Loading : UiState
    data class Success(val phone: String) : UiState
    data class Error(val message: String) : UiState
}
```
Sealed удобен исчерпывающим `when` и тем, что состояния взаимоисключающие.

### 5. Нужен ли отдельный `error`-state?
Да — ошибку нужно показывать пользователю явно (сообщение + кнопка retry). Вариант: отдельное состояние `Error` в sealed, либо поле `error` в общем data class state. Главное — не глотать ошибку молча.

### 6. Как обрабатывать ошибки сетевого запроса?
`try/catch` вокруг suspend-вызова (часто в репозитории/use case), маппинг исключений в доменные ошибки или `Result`. В ViewModel — выставить `UiState.Error`. Использовать `runCatching` или обёртку `Result<T>`/`Either`.

### 7. Какой тип исключения ловить при работе с сетью?
`IOException` (нет сети, таймаут), `HttpException` (Retrofit, не-2xx коды), плюс общий `Exception` как fallback. ⚠️ В корутинах **нельзя глотать `CancellationException`** — её надо пробрасывать дальше, иначе сломается отмена:
```kotlin
catch (e: CancellationException) { throw e }
catch (e: Exception) { /* обработать */ }
```

### 8. Почему для бизнес-логики удобнее use case?
- Инкапсулирует один бизнес-сценарий, переиспользуется между ViewModel'ями.
- Разгружает ViewModel (Single Responsibility).
- Легко тестировать изолированно.
- Может комбинировать несколько репозиториев/правила.

### 9. Как назвать use case для получения телефонов?
По действию: `GetPhonesUseCase` / `GetPhoneNumberUseCase` / `FetchPhonesUseCase`. Глагол + сущность.

### 10. Как должен выглядеть `operator fun invoke`?
Чтобы вызывать use case как функцию: `useCase()`:
```kotlin
class GetPhoneUseCase(private val repo: PhoneRepository) {
    suspend operator fun invoke(): Result<String> = repo.getPhone()
}
// вызов: getPhoneUseCase()
```

### 11. Почему инжектить use case через абстракцию?
Зависимость от интерфейса (`PhoneRepository`), а не от реализации → dependency inversion. Легко подменить (моки в тестах, разные источники), слабая связанность, соблюдение SOLID. ViewModel не знает о деталях сети/БД.

### 12. Как собрать UI, читающий state из ViewModel?
```kotlin
val state by viewModel.state.collectAsStateWithLifecycle()
when (state) {
    is Loading -> CircularProgressIndicator()
    is Success -> Content((state as Success).phone)
    is Error   -> ErrorView(onRetry = viewModel::onClick)
    Idle       -> Button(onClick = viewModel::onClick) { Text("Получить") }
}
```
`collectAsStateWithLifecycle` — учитывает жизненный цикл, не собирает в фоне.

### 13. Как обрабатывать нажатие кнопки?
`Button(onClick = { viewModel.onClick() })`. UI пробрасывает событие в ViewModel, логику не содержит.

### 14. Как открыть стандартную звонилку?
Через `Intent`:
```kotlin
val intent = Intent(Intent.ACTION_DIAL, Uri.parse("tel:$phone"))
context.startActivity(intent)
```
`ACTION_DIAL` открывает звонилку с набранным номером (не требует permission). `ACTION_CALL` — звонит сразу, но требует разрешение `CALL_PHONE`. Для собеса безопаснее `ACTION_DIAL`.

### 15. Как использовать `Intent` для перехода в звонилку?
См. выше: `ACTION_DIAL` + `Uri "tel:номер"` + `startActivity`. Запускать из UI-слоя (нужен Context), по сигналу из ViewModel.

### 16. Как выбрать номер из списка в ответе?
Зависит от бизнес-правила: первый (`list.firstOrNull()`), помеченный основным (`list.first { it.isPrimary }`), или показать выбор пользователю. На собесе: уточнить требование, по умолчанию — `firstOrNull()` с обработкой пустого списка.

### 17. Как выполнить side effect после успешного запроса?
Не делать его прямо в композиции. Использовать одноразовое событие: `Channel`/`SharedFlow` событий навигации из ViewModel, либо `LaunchedEffect(key)`. UI собирает событие и выполняет `startActivity`. Иначе при рекомпозиции звонилка откроется повторно.

### 18. Почему side effect отделять от отрисовки?
Composable должна быть **идемпотентной** и без побочных эффектов — она вызывается много раз при рекомпозиции. Если запускать `startActivity`/навигацию прямо в теле, при каждой рекомпозиции эффект повторится. Эффекты выносят в `LaunchedEffect`/`SideEffect`/события.

### 19. Как обработать retry при ошибке?
В `UiState.Error` показать кнопку «Повторить», по нажатию снова вызвать тот же метод ViewModel. Опционально — авто-ретрай с backoff в репозитории (`retryWhen` у Flow / цикл с задержкой).

### 20. Как открыть звонилку только один раз при изменении state?
Через **one-shot событие**, а не через постоянный state:
- `Channel<UiEvent>(Channel.BUFFERED)` → `receiveAsFlow()`, UI собирает и реагирует один раз;
- либо `LaunchedEffect(key)` с уникальным ключом события;
- либо паттерн «consumed event» (флаг, что событие обработано).
Постоянный state плох тем, что при рекомпозиции/повороте side effect сработает снова.

### 21. MVI: что это, как «готовить» и почему уходят с MVVM

**Коротко.** MVI (Model–View–Intent) — эволюция MVVM, где идею однонаправленного потока данных (UDF) довели до строгого контракта: **UI описывается одним неизменяемым `State`**, а меняется он **только** через поток типизированных **`Intent`** (намерений пользователя). Это не «другая архитектура вместо MVVM», а MVVM с более жёсткими правилами — то же место занимает `ViewModel`, просто её API сведён к «один state наружу + один вход для событий».

**Три (по факту четыре) кирпича:**

| Элемент | Что это | Пример |
|---|---|---|
| **Intent** | намерение/событие пользователя или системы (не Android `Intent`!) | `LikeClicked(id)`, `Refresh`, `TextChanged("abc")` |
| **State** | **всё** состояние экрана в одном immutable-объекте (единый source of truth) | `data class ScreenState(val items: List<..>, val isLoading: Boolean, val error: String?)` |
| **Reducer** | **чистая функция** `(State, Intent/Result) -> State`: как из старого состояния и события получить новое | `state.copy(isLoading = true)` |
| **Effect** (side effect / one-shot) | разовые события, которых нет в state: навигация, тост, открыть звонилку | `Effect.OpenDialer(phone)` |

**Поток данных строго по кругу (UDF-цикл):**
```
View (Compose) --Intent--> ViewModel --> reducer --> new State --> View перерисовывается
                                    \--> Effect (one-shot) --> View выполняет side effect
```
UI ничего не меняет сам: он лишь **посылает `Intent`** и **отрисовывает `State`**. Никаких «UI полез и дёрнул поле» — только через намерение.

**Как «готовить» (минимальный скелет):**
```kotlin
// 1. State — одна immutable-модель всего экрана
data class PhoneState(
    val isLoading: Boolean = false,
    val phone: String? = null,
    val error: String? = null,
)

// 2. Intent — закрытый набор намерений (sealed => исчерпывающий when)
sealed interface PhoneIntent {
    data object LoadClicked : PhoneIntent
    data object Retry : PhoneIntent
}

// 3. Effect — one-shot события, которых НЕТ в state
sealed interface PhoneEffect {
    data class OpenDialer(val phone: String) : PhoneEffect
}

class PhoneViewModel(private val getPhone: GetPhoneUseCase) : ViewModel() {

    private val _state = MutableStateFlow(PhoneState())
    val state: StateFlow<PhoneState> = _state.asStateFlow()   // ОДИН выход наружу

    private val _effects = Channel<PhoneEffect>()
    val effects = _effects.receiveAsFlow()                    // one-shot канал

    // ОДИН вход: все события заходят сюда
    fun onIntent(intent: PhoneIntent) {
        when (intent) {
            PhoneIntent.LoadClicked, PhoneIntent.Retry -> load()
        }
    }

    private fun load() {
        if (_state.value.isLoading) return
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true, error = null) }   // reducer: copy
            getPhone()
                .onSuccess { phone ->
                    _state.update { it.copy(isLoading = false, phone = phone) }
                    _effects.send(PhoneEffect.OpenDialer(phone))        // side effect отдельно
                }
                .onFailure { e ->
                    _state.update { it.copy(isLoading = false, error = e.message) }
                }
        }
    }
}
```
```kotlin
// View: рендерит State, шлёт Intent, слушает Effect
@Composable
fun PhoneScreen(vm: PhoneViewModel) {
    val state by vm.state.collectAsStateWithLifecycle()
    val context = LocalContext.current

    LaunchedEffect(Unit) {
        vm.effects.collect { e ->
            when (e) {
                is PhoneEffect.OpenDialer ->
                    context.startActivity(Intent(Intent.ACTION_DIAL, Uri.parse("tel:${e.phone}")))
            }
        }
    }

    when {
        state.isLoading      -> CircularProgressIndicator()
        state.error != null  -> ErrorView(onRetry = { vm.onIntent(PhoneIntent.Retry) })
        else                 -> Button(onClick = { vm.onIntent(PhoneIntent.LoadClicked) }) { Text("Позвонить") }
    }
}
```

**Ключевые правила «готовки» (что отличает настоящий MVI от «MVVM с копипастой»):**
1. **Один `State` на экран.** Не несколько разрозненных `StateFlow` (`loading`, `data`, `error` по отдельности), а один immutable `data class`. Иначе получаются несогласованные состояния (`isLoading == true` и одновременно `error != null`).
2. **State меняется только через `copy()` в reducer.** Никаких мутаций полей. Reducer — чистая функция → легко тестировать и воспроизводить.
3. **Один вход `onIntent(intent)`** вместо десятка публичных методов `ViewModel`. Все события — один типизированный (`sealed`) поток.
4. **Effect ≠ State.** Навигация/тост/звонилка — one-shot через `Channel`, а не поле в state (см. п.20 — иначе повторится при повороте).

**Почему уходят с MVVM на MVI (в чём боль классического MVVM):**

| Проблема MVVM | Как решает MVI |
|---|---|
| **State разбросан** по нескольким `LiveData`/`StateFlow` → рассинхрон (можно показать и спиннер, и ошибку сразу) | один immutable `State` — состояние всегда консистентно |
| **Много публичных методов** во ViewModel, UI дёргает их вразнобой | один вход `onIntent(Intent)` — контракт очевиден |
| **Мутабельность** — легко случайно поменять поле в обход логики | immutable state + reducer через `copy()` |
| **Трудно воспроизвести баг** — непонятно, какая последовательность вызовов привела к состоянию | поток `Intent`'ов можно логировать/реплеить → детерминизм, time-travel debugging |
| **Тестирование** размазано по методам | тест = «дал `Intent` → проверил новый `State`», reducer чист |
| Плохо ложится на **декларативный Compose** | «State → UI» ровно совпадает с моделью Compose (UI = функция от state) |

**Честный контр-аргумент (важно на собесе — не топить MVVM):** MVI — это **больше кода и церемоний** (sealed-иерархии Intent/Effect, reducer, boilerplate). Для **простого экрана** MVVM с парой полей проще и быстрее. MVI окупается на **сложных экранах** с многими взаимозависимыми состояниями и обилием пользовательских событий. Многие команды берут **гибрид**: UDF + единый immutable `UiState` (это и есть «MVI-lite»), но без формального reducer'а — то, что показано в блоке 3–4 этого документа, уже фактически ⅔ MVI.

**Связь с остальным материалом:** immutable `State` держится на `data class` + `copy()` + `val` (блок 1), консистентный skipping в Compose требует, чтобы `State` был `@Immutable`/стабильным (блок 3, п.22), а `Effect` — это ровно one-shot событие из п.17/п.20.

**Фраза на собес:** «MVI — это MVVM, доведённый до строгого UDF: один immutable `State` на экран как единственный source of truth, один вход `onIntent(Intent)` для всех событий, изменения только через чистый reducer (`copy`), а разовые вещи (навигация, звонилка) — через отдельный `Effect`-канал, не через state. Перешли с MVVM, потому что там state разбросан по нескольким потокам и мутабелен → рассинхрон и трудновоспроизводимые баги; в MVI состояние всегда консистентно, детерминированно и идеально ложится на декларативный Compose. Плата — больше boilerplate, поэтому на простых экранах беру MVVM/MVI-lite».

# Блок 6 (PDF 2). Kotlin, коллекции и равенство объектов

> Здесь ключевая идея: обычный класс (не data class) сравнивается по ссылке.

### 1. Будет ли компилироваться код с классом, списком и `HashSet`?
Обычно да, компилируется (если синтаксис верный). Подвох не в компиляции, а в **поведении** `HashSet` с обычным классом.

### 2. Что напечатает код в текущем виде?
Если класс **обычный** (не `data class`) и не переопределяет `equals/hashCode`, то даже одинаковые по содержимому объекты — разные. В `HashSet` попадут **все** объекты → размер равен числу добавленных (например, 3 объекта → size 3).

### 3. Почему именно такое количество элементов?
Потому что `Object.equals` сравнивает по ссылке (identity), а `Object.hashCode` — по адресу. Два «одинаковых» объекта не равны → оба попадают в Set. Поэтому дубликаты по смыслу не схлопываются.

### 4. Что изменить, чтобы печатался один элемент?
Сделать класс `data class` (тогда `equals/hashCode` сгенерируются по полям) **или** вручную переопределить `equals` и `hashCode`. Тогда логически одинаковые объекты будут равны → в `HashSet` останется один.

### 5. Что такое `data class`?
Класс для хранения данных, автогенерирующий `equals`, `hashCode`, `toString`, `copy`, `componentN` по полям первичного конструктора. (см. блок 1, п.2)

### 6. Что такое `equals` и зачем?
Метод проверки **логического равенства** двух объектов. По умолчанию (`Object`) — сравнение по ссылке. Переопределяют, чтобы сравнивать по содержимому. Нужен коллекциям, сравнениям, контрактам.

### 7. Что такое `hashCode` и зачем?
Метод, возвращающий int-хеш объекта. Используется хеш-коллекциями (`HashMap`/`HashSet`) для быстрого определения бакета. Должен быть согласован с `equals`.

### 8. Разница `equals` и `hashCode` для обычного класса?
- `equals` — точное сравнение (равны ли объекты), даёт boolean.
- `hashCode` — int для распределения по бакетам, быстрый, но не уникальный.
Для обычного класса оба работают по identity (ссылке/адресу), пока не переопределены.

### 9. Как `HashSet` использует `hashCode` и `equals`?
Сначала `hashCode` → бакет. В бакете — сравнение через `equals`. Равный есть → не добавляем; нет → добавляем. (см. блок 1, п.8)

### 10. Что если одинаковый `hashCode`, но не равны по `equals`?
**Коллизия**: объекты попадают в один бакет, но хранятся как разные элементы (связный список/дерево внутри бакета). Оба будут в Set. Производительность бакета деградирует (O(n) поиск в цепочке, в Java 8+ при ≥8 элементах список превращается в дерево → O(log n)).

### 11. Если у `data class` сделать `hashCode` константой, а объекты разные по данным — сколько в `HashSet`?
**Все** (например, 3 разных → size 3). Константный `hashCode` отправит все в один бакет, но `equals` у data class сравнивает по полям → они не равны → остаются разными элементами. Получим деградировавший до списка/дерева бакет, но количество элементов не уменьшится.

### 12. Почему попали в один бакет, но остались разными?
Бакет определяется по `hashCode` (одинаковый → один бакет). Уникальность определяется по `equals` (разные по данным → не равны). Один бакет ≠ один элемент: внутри бакета лежит цепочка разных объектов. Хеш отвечает «куда класть», equals — «дубликат или нет».

## PDF 1 — Задача 2 / PDF 2 — Задача 2. Batch над callback-API
Дано: `doRequest(request, onComplete)` / `request(request, callback)` — один запрос через callback, **асинхронный, многопоточный** (callback приходит в произвольный момент из разных потоков). Нужно: принять список запросов, выполнить параллельно, собрать ответы **в порядке входных запросов**, вызвать один общий callback в конце.

Ключевые сложности: (1) порядок — писать ответ по индексу, не в порядке прихода; (2) потокобезопасность — счётчик завершённых и массив результатов под конкуренцией; (3) один финальный callback.

### Вариант А. На «голых» примитивах (потокобезопасно)
```kotlin
fun batchRequest(
    requests: List<Request>,
    onAllComplete: (List<Response>) -> Unit
) {
    if (requests.isEmpty()) { onAllComplete(emptyList()); return }

    val results = arrayOfNulls<Response>(requests.size) // фикс. размер — порядок по индексу
    val remaining = AtomicInteger(requests.size)        // атомарный счётчик

    requests.forEachIndexed { index, req ->
        api.request(req) { response ->                  // callback в произвольном потоке
            results[index] = response                   // каждый пишет в свою ячейку — гонки нет
            if (remaining.decrementAndGet() == 0) {     // последний завершившийся
                onAllComplete(results.map { it!! })     // порядок сохранён
            }
        }
    }
}
```
Почему безопасно: каждый callback пишет в **свой** индекс `results[index]` (нет общей ячейки → не нужен лок на запись), а согласованность «все готовы» обеспечивает `AtomicInteger.decrementAndGet()`. Финальный callback вызовет ровно тот поток, который завершил последний запрос.

### Вариант Б. Через корутины + Continuation (предпочтительно)
Сначала обернуть один вызов в suspend:
```kotlin
suspend fun requestSuspend(req: Request): Response =
    suspendCancellableCoroutine { cont ->
        api.request(req) { response -> cont.resume(response) }
    }
```
Затем batch через `async` + `awaitAll` (порядок сохраняется автоматически):
```kotlin
suspend fun batch(requests: List<Request>): List<Response> = coroutineScope {
    requests
        .map { req -> async { requestSuspend(req) } } // параллельно
        .awaitAll()                                   // порядок = порядок запросов
}
```
Плюсы: нет ручного счётчика, structured concurrency, отмена, обработка ошибок через try/catch, порядок гарантирован `awaitAll`. На собесе показать оба и объяснить, что корутины — современный способ уйти от callback hell, а `Continuation`/`suspendCancellableCoroutine` — мост между callback-API и корутинами.

## PDF 1 — Задача 4. Экран «кнопка → запрос номера → звонилка»
Архитектура (Clean / MVVM):
- **UI (Composable)**: кнопка по центру (`Box(contentAlignment = Center) { Button { vm.onClick() } }`), подписка на `state`, показ загрузки/ошибки, реакция на событие навигации (открыть звонилку).
- **ViewModel**: `state: StateFlow<UiState>` + `events: Flow<UiEvent>` (one-shot). Метод `onClick()` → `Loading` → `getPhoneUseCase()` → `Success`/`Error`, при успехе шлёт `UiEvent.OpenDialer(phone)`.
- **UseCase**: `GetPhoneUseCase(operator fun invoke): Result<String>` → репозиторий.
- **Repository**: интерфейс + реализация, ходит в сеть (Retrofit), маппит DTO → домен, оборачивает ошибки в `Result`.
- **Обработка ошибок**: try/catch (пробрасывая `CancellationException`), `UiState.Error` + кнопка retry.
- **Звонилка**: `Intent(ACTION_DIAL, Uri.parse("tel:$phone"))` из UI по событию (не из ViewModel — там нет Context).
- **Повторное нажатие/ошибка**: пока `Loading` — игнорировать клики (или disable кнопку); ошибка → retry повторяет `onClick`.
- **Один раз открыть звонилку**: через one-shot событие (`Channel`/`SharedFlow`), не через постоянный state — иначе при повороте откроется снова.

```kotlin
// ViewModel
class PhoneViewModel(private val getPhone: GetPhoneUseCase) : ViewModel() {
    private val _state = MutableStateFlow<UiState>(UiState.Idle)
    val state = _state.asStateFlow()

    private val _events = Channel<UiEvent>()
    val events = _events.receiveAsFlow()

    fun onClick() {
        if (_state.value == UiState.Loading) return       // защита от повторных нажатий
        viewModelScope.launch {
            _state.value = UiState.Loading
            getPhone()
                .onSuccess {
                    _state.value = UiState.Success(it)
                    _events.send(UiEvent.OpenDialer(it))  // one-shot side effect
                }
                .onFailure { _state.value = UiState.Error(it.message ?: "Ошибка") }
        }
    }
}

// UI
@Composable
fun PhoneScreen(vm: PhoneViewModel) {
    val context = LocalContext.current
    val state by vm.state.collectAsStateWithLifecycle()

    LaunchedEffect(Unit) {
        vm.events.collect { e ->
            when (e) {
                is UiEvent.OpenDialer ->
                    context.startActivity(Intent(Intent.ACTION_DIAL, Uri.parse("tel:${e.phone}")))
            }
        }
    }

    Box(Modifier.fillMaxSize(), contentAlignment = Alignment.Center) {
        when (val s = state) {
            UiState.Loading -> CircularProgressIndicator()
            is UiState.Error -> Column(horizontalAlignment = Alignment.CenterHorizontally) {
                Text(s.message); Button(onClick = vm::onClick) { Text("Повторить") }
            }
            else -> Button(onClick = vm::onClick) { Text("Позвонить") }
        }
    }
}
```

## Шпаргалка-минутка (что повторить перед собесом)
- `data class` генерит equals/hashCode/toString/copy/componentN **по полям первичного конструктора**.
- Обычный класс сравнивается по ссылке → дубликаты в HashSet не схлопываются.
- Контракт: equals → одинаковый hashCode (обратное неверно).
- `HashSet` = `HashMap`; уникальность: hashCode (бакет) → equals (точное сравнение).
- Константный hashCode у data class: все в одном бакете, но размер Set не меняется (equals разный).
- `inline` убирает аллокации лямбд + даёт `reified` + нелокальный return; `crossinline` запрещает нелокальный return; `noinline` отключает инлайн лямбды.
- `async` + `awaitAll` = параллельно + порядок сохранён.
- Мост callback→корутина: `suspendCancellableCoroutine` + `cont.resume`.
- suspend = state machine + Continuation (CPS).
- Не глотать `CancellationException`.
- `LazyColumn` vs `Column`: ленивая композиция видимого + переиспользование. `key` — стабильный identity.
- Состояние UI: `remember` (рекомпозиция) / `rememberSaveable` (поворот). Source of truth — ViewModel.
- Side effect (звонилка/навигация) — через one-shot событие или `LaunchedEffect`, не в теле composable.
- Звонилка: `Intent(ACTION_DIAL, "tel:...")` без permission; `ACTION_CALL` требует `CALL_PHONE`.
