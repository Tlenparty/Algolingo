```kotlin
import java.util.concurrent.CountDownLatch

class State {
    var x = 0
    var y = 0
}

fun main() {
    val state = State()
    val latch = CountDownLatch(1)  // Блокируем выполнение println() до нужного момента

    val t1 = Thread {
        state.x = 1  // Устанавливаем x = 1
        latch.await()  // Ждем, пока latch опустится до 0
        println(state.y)  // Теперь гарантированно y = 1
    }

    val t2 = Thread {
        state.y = 1  // Устанавливаем y = 1
        latch.await()  // Ждем, пока latch опустится до 0
        println(state.x)  // Теперь гарантированно x = 1
    }

    t1.start()
    t2.start()

    Thread.sleep(100)  // Ждем, чтобы потоки успели изменить x и y
    latch.countDown()  // Разрешаем выполнение println()

    t1.join()
    t2.join() // Нужен чтобы main поток не завершился раньше чем выполнится работа t2
}
```

join() блокирует выполнение главного потока до тех пор, пока соответствующий поток (например, t1 или t2) не завершит свою работу. Это необходимо, чтобы программа не завершилась до того, как оба потока завершат свои операции и выведут значения.

Ответ на задачу про утечку памяти:

**1. Вложенный класс (inner class) хранит неявную ссылку на Activity**

• inner class Job автоматически содержит **сильную ссылку** на внешний класс Activity.
• Даже несмотря на то, что activityRef — это WeakReference, сама Job содержит сильную ссылку на Activity, так как она является внутренним (inner) классом.


**2. Работа в Thread и жизненный цикл Activity**

• Поток, запущенный в Thread, может работать дольше, чем жизненный цикл Activity.
• Если Activity уничтожена (onDestroy вызван), но поток всё ещё активен, Activity останется в памяти.


**3. Почему WeakReference не спасает?**

• activityRef сам по себе слабый, но объект Job, который его содержит, имеет сильную ссылку на Activity через inner class.
• Это создаёт **замкнутую ссылку**, не позволяющую GC очистить Activity.

> [!danger] Задача №1: главная ловушка — `id` НЕ участвует в equals/hashCode
> `data class User(val name, val address)` генерирует `equals`/`hashCode` **только по параметрам первичного конструктора** — `name` и `address`. Свойство `val id = Random().nextInt()` объявлено **в теле класса**, поэтому в `equals`/`hashCode` **не входит** (хотя у двух объектов оно разное!). Значит результат зависит только от `address`:
> • `Address` — **обычный** класс → `equals` по ссылке → `user1 != user2` → в мапе **2 ключа**, `map[user1]="Описание 1"`, поиск по новому `User(...)` даст `null`.
> • `Address` — **`data class`** → `equals` по `city` → `user1 == user2` → второй `put` **перезаписывает** первый → в мапе **1 запись** со значением `"Описание 2"`, и поиск по новому эквивалентному `User` тоже вернёт `"Описание 2"`.
> Авторские комментарии в коде верны — но именно про `id` интервьюер ждёт, что вы заметите, что Random в теле класса на equality не влияет.

> [!warning] Задача №2: код не скомпилируется без `reified`
> `data.filterIsInstance(T::class.java)` невозможен: на рантайме тип `T` **стёрт** (type erasure), `T::class` недоступен. Нужно `inline` + `reified` (как намекает комментарий):
> ```kotlin
> inline fun <reified T> filterWrapper(data: List<Any>): List<T> = data.filterIsInstance<T>()
> ```
> `reified` работает только в `inline`-функциях: компилятор подставляет реальный тип в место вызова.

> [!tip] Задача №3: как на самом деле чинить утечку
> `WeakReference` бесполезен, потому что `inner class Job` держит **сильную** скрытую ссылку `Activity.this`. Решения:
> • Сделать `Job` **обычным** (не `inner`) классом или `static`-вложенным — тогда неявной ссылки нет, и переданный `WeakReference` заработает.
> • Ещё лучше — не плодить голые `Thread`, а использовать `lifecycleScope`/`viewModelScope`: корутина отменится вместе с ЖЦ.

> [!danger] Задача №4: `CountDownLatch` здесь НЕ гарантирует «1 1»
> В авторском решении единственный happens-before-рубеж — `main.countDown()` → возврат из `await()` в потоках. Но записи `state.x = 1` / `state.y = 1` происходят **до** `await()` в своих потоках и **не связаны** happens-before с `countDown()` главного потока (`Thread.sleep(100)` — это не синхронизация, а гонка). Значит видимость чужой записи строго **не гарантирована**.
> Корректная конструкция — «барьер» на `CountDownLatch(2)`, где каждый поток сначала пишет, потом `countDown`, потом `await`:
> ```kotlin
> val latch = CountDownLatch(2)
> // t1: state.x = 1; latch.countDown(); latch.await(); println(state.y)
> // t2: state.y = 1; latch.countDown(); latch.await(); println(state.x)
> ```
> Теперь `countDown` каждого потока happens-before возврата из `await` другого → оба гарантированно видят `1 1`. (Аналогично решается через `CyclicBarrier`.)
