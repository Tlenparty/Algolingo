# Performance. Рендеринг, jank и Macrobenchmark

Как кадр попадает на экран, где он «застревает» и как это воспроизводимо мерить.

## Путь кадра (frame lifecycle)

```text
Input → Animation → Measure/Layout → Draw (record) → Sync/Upload → RenderThread (GPU) → Display
```

- **VSYNC** — сигнал дисплея «пора готовить кадр». [[Choreographer, SurfaceFlinger|Choreographer]] синхронизирует работу UI-потока с VSYNC.
- **UI Thread** записывает draw-команды (display list), **[[Render Thread]]** отправляет их на GPU.
- **SurfaceFlinger** композитит слои и выводит на дисплей.

> [!important] Бюджет кадра
> 60 fps → **16.6 мс**, 90 fps → 11 мс, 120 fps → 8.3 мс на весь конвейер. Не уложился UI- или Render-поток → **dropped frame** (jank). Цель оптимизации — не «сделать быстрее вообще», а **уложить каждый кадр в бюджет**.

## Частые причины jank

> [!warning] Что роняет кадры
> • Тяжёлая работа на **главном потоке** (парсинг, БД, аллокации) — выносить в корутины/`Dispatchers.Default`.
> • **Overdraw** — многослойная отрисовка одного пикселя (лишние фоны). Смотреть «Debug GPU overdraw».
> • Лишние **рекомпозиции** в Compose — см. [[Performance. Оптимизация Compose]].
> • Аллокации в горячем цикле (`onBindViewHolder`, `onDraw`, draw-фаза Compose) → давление на GC → паузы.
> • Синхронный `inflate`/измерение сложных иерархий View; вложенные `RelativeLayout`/веса.
> • Загрузка/декодирование bitmap на UI-потоке (правильно — Coil/Glide в фоне).

## Macrobenchmark — воспроизводимые замеры

Библиотека для замера **startup и scroll-перформанса** на реальном приложении, пригодная для CI:

```kotlin
@Test
fun startup() = benchmarkRule.measureRepeated(
    packageName = "com.app",
    metrics = listOf(StartupTimingMetric(), FrameTimingMetric()),
    iterations = 10,
    compilationMode = CompilationMode.Partial(), // с Baseline Profile
    startupMode = StartupMode.COLD
) {
    pressHome()
    startActivityAndWait()
}
```

> [!tip] Что меряют метрики
> • **`StartupTimingMetric`** — `timeToInitialDisplay`/`timeToFullDisplay` (TTID/TTFD).
> • **`FrameTimingMetric`** — распределение времени кадров (P50/P90/P99), ловит jank.
> • Сравнение `CompilationMode.None()` vs `Partial()` показывает эффект [[Performance. Baseline и Startup Profiles|Baseline Profile]].

> [!note] Macrobenchmark vs Microbenchmark
> • **Macrobenchmark** — целое приложение «снаружи» (startup, scroll, навигация) через UiAutomator.
> • **Microbenchmark** — изолированный замер «горячей» функции/алгоритма внутри процесса (с прогревом JIT, отбросом выбросов).
> На собесе важно не путать уровни.

> [!info] Perfetto / System Trace для диагностики
> Когда Macrobenchmark показал регрессию, **причину** ищут в **Perfetto**-трейсе: видно, какой поток и какой метод съел бюджет кадра. Кастомные участки размечают `trace("MySection") { … }` (`androidx.tracing`).
