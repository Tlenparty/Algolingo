# Gradle build-оптимизация

Скорость сборки — это DX (сколько разработчик ждёт) и деньги (минуты CI). На Senior спрашивают **что и почему ускоряет сборку**, и просят не путать **configuration cache** с **build cache** — это разные кэши на разных фазах.

## Сначала — три фазы сборки Gradle

> [!important] Без этого нельзя понять кэши
> 1. **Initialization** — определяется, какие модули (`settings.gradle`) участвуют, создаются `Project`-объекты.
> 2. **Configuration** — выполняются все `build.gradle`, строится **граф задач** (task graph). Выполняется **на каждый запуск** и для **всех** модулей, даже если собираешь один таск.
> 3. **Execution** — запускаются нужные задачи (compile, dex, package…).
> **Configuration cache** ускоряет фазу 2, **build cache** — фазу 3. Разные вещи.

## Configuration Cache

> [!info] Что кэширует
> Сериализует и переиспользует **результат фазы configuration** (граф задач). Если ничего, влияющего на конфигурацию, не изменилось — Gradle **пропускает** выполнение build-скриптов и сразу идёт к execution. На крупных мультимодульных проектах фаза configuration занимает секунды-десятки секунд каждый раз — её устранение заметно.

```properties
# gradle.properties
org.gradle.configuration-cache=true
```

> [!warning] Требования к корректности (главная боль внедрения)
> Чтобы граф можно было закэшировать, билд должен соблюдать правила:
> • **Нельзя обращаться к `Project` во время execution** — задача не должна держать ссылку на `project` в `doLast`/action. Вместо этого — внедрять конкретные значения/провайдеры на этапе конфигурации.
> • **Нельзя читать системное состояние на этапе конфигурации** «вживую» (env, `System.getProperty`, время) — только через `providers.environmentVariable(...)`/`gradleProperty(...)`, чтобы Gradle отслеживал инвалидцию.
> • Состояние задач должно **сериализоваться**.
> Старые плагины часто это нарушают — поэтому внедрение конфиг-кэша обычно упирается в апгрейд/фиксы плагинов. С новыми AGP/KGP работает из коробки.

## Build Cache (local + remote)

> [!info] Что кэширует
> Кэширует **выходы задач (outputs)**, ключ — хэш **входов (inputs)** задачи (исходники, classpath, аргументы компилятора, версия тулчейна). Если задача с такими же входами уже выполнялась — её результат **берётся из кэша**, а не пересчитывается. Это работает поверх обычной incremental-логики (up-to-date checks).

```properties
org.gradle.caching=true
```

| Тип | Где живёт | Кто использует |
| --- | --- | --- |
| **Local build cache** | `~/.gradle/caches/build-cache-1` | один разработчик между сборками/ветками |
| **Remote build cache** | общий узел (Develocity/Gradle Enterprise, HTTP-node, S3) | вся команда + CI |

> [!important] Remote build cache — ключевая идея для команды
> CI собирает ветку, **публикует** outputs задач в общий кэш (push). Когда разработчик или другой CI-джоб собирает тот же код (те же входы), он **скачивает** готовые результаты вместо локальной компиляции (cache hit). Типичный сценарий: запулил main, который уже собрал CI → большинство модулей подтянулось из кэша, локально пересобираются только твои изменения.
> Обычно: **CI пишет** в remote cache, **разработчики только читают** (push с локальных машин отключают, чтобы не засорять).

> [!warning] Условия корректности remote cache
> • Задача должна быть **cacheable** (помечена `@CacheableTask`; не все таковы).
> • Outputs должны быть **relocatable** и **reproducible** — не зависеть от абсолютных путей, времени, имени машины. Иначе хэши не совпадут (нет хитов) или, хуже, прилетит чужой неверный результат.
> • Единая **версия Gradle/JDK/плагинов** в команде и на CI — иначе ключи входов разные, кэш не попадает.

## Прочие рычаги (быстрый чек-лист)

> [!tip] Что ещё включают
> • **`org.gradle.parallel=true`** — модули без зависимостей собираются параллельно (работает в паре с [[Модуляризация|модуляризацией]]).
> • **Gradle Daemon** — держит JVM прогретой между сборками (по умолчанию включён).
> • **`org.gradle.jvmargs`** — поднять heap/metaspace демону (нехватка → долгие GC при сборке).
> • **File system watching** (`org.gradle.vfs.watch=true`) — Gradle отслеживает изменения ФС, быстрее up-to-date проверки.
> • **KSP вместо kapt** — `kapt` запускает генерацию через APT поверх Java-стабов (медленно); **KSP** работает напрямую с Kotlin (кратно быстрее). Актуально для Room/Dagger/Hilt/Moshi (см. [[Hilt]], [[Dagger 2]]).
> • **K2-компилятор Kotlin** — ускоряет компиляцию.
> • **Version catalogs + convention plugins** — меньше дублирующей конфигурации, чище инвалидцация.
> • **Non-transitive R class**, `nonFinalResIds` — меньше пересборок R-классов.
> • Избегать **dynamic versions** (`1.+`) — они ломают воспроизводимость и кэш.

## Как измерять (не на глаз)

> [!note] Инструменты
> • **`--profile`** — HTML-отчёт по времени фаз и задач.
> • **Build Scan** (`--scan`, Develocity) — детальный разбор: что не закэшировалось, почему промахи, timeline параллелизма.
> • **`gradle-profiler`** — воспроизводимые бенчмарки сценариев сборки (как [[Performance. Рендеринг, jank и Macrobenchmark|Macrobenchmark]], но для билда).
> • Сравнивать **clean build**, **incremental** (изменил одну строку) и **abi/non-abi change** — разные сценарии узких мест.

> [!tip] Ответ на собесе в одну фразу
> «Configuration cache переиспользует граф задач (фаза configuration), build cache — выходы задач по хэшу входов (фаза execution); remote build cache шарит эти выходы между CI и командой, давая cache hits на неизменённый код. Плюс parallel, daemon, KSP вместо kapt, модуляризация для параллелизма и инкрементальности, а узкие места ищут через build scan / --profile.»
