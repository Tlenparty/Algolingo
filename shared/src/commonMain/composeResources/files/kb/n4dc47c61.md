# SOLID

Пять принципов проектирования (Роберт Мартин). Цель — гибкий, расширяемый и тестируемый код.

## S — Single Responsibility Principle (Единственная ответственность)

**Принцип:** у класса должна быть только одна причина для изменения — он отвечает за одну задачу.

**Нарушение:**

```kotlin
class User {
    var name: String = ""
    var email: String = ""

    fun saveToDatabase() { /* сохранение в БД */ }
    fun sendEmail() { /* отправка письма */ }
}
```

`User` отвечает и за хранение, и за отправку писем — две разные ответственности.

**Исправление:**

```kotlin
class User(var name: String, var email: String)

class UserRepository {
    fun saveToDatabase(user: User) { /* сохранение в БД */ }
}

class EmailService {
    fun sendEmail(user: User) { /* отправка письма */ }
}
```

> В Android классический нарушитель — `Context`: он отвечает за слишком многое.

## O — Open/Closed Principle (Открытость/закрытость)

**Принцип:** классы открыты для расширения, но закрыты для модификации.

**Нарушение** — для каждой новой фигуры приходится менять `AreaCalculator`:

```kotlin
class AreaCalculator {
    fun calculateArea(rectangle: Rectangle): Double =
        rectangle.width * rectangle.height.toDouble()

    fun calculateArea(circle: Circle): Double =
        Math.PI * circle.radius * circle.radius
}
```

**Исправление** — выносим поведение в абстракцию:

```kotlin
interface Shape {
    fun calculateArea(): Double
}

class Rectangle(val width: Int, val height: Int) : Shape {
    override fun calculateArea(): Double = width * height.toDouble()
}

class Circle(val radius: Int) : Shape {
    override fun calculateArea(): Double = Math.PI * radius * radius
}

class AreaCalculator {
    fun calculateArea(shape: Shape): Double = shape.calculateArea()
}
```

Новая фигура → новый класс, реализующий `Shape`; `AreaCalculator` менять не нужно.

**Пример из Android** — `when` по типу элемента в адаптере нарушает OCP:

```kotlin
override fun getItemViewType(position: Int): Int = when (items[position]) {
    is TextItem -> 0
    is ImageItem -> 1
    // новый тип → правим этот when и onCreateViewHolder
}
```

Исправление — делегаты (AdapterDelegates), где новый тип = новый делегат:

```kotlin
class MyAdapter : ListDelegationAdapter<List<Item>>() {
    init {
        delegatesManager.addDelegate(textItemDelegate())
        delegatesManager.addDelegate(imageItemDelegate())
    }
}
```

## L — Liskov Substitution Principle (Подстановка Лисков)

**Принцип:** объект базового типа можно заменить объектом производного типа, и программа продолжит работать корректно.

> Если программа работает с родительским классом, она должна продолжить корректно работать и с дочерним.

**Классический контрпример — квадрат и прямоугольник.** Если сделать `Square` наследником `Rectangle`, он меняет поведение: задавая одну сторону, неявно меняет вторую → код, рассчитывающий на независимые `width`/`height`, ломается.

> В Android нарушение — тема: `Application` context не применяет тему и не работает с UI, в отличие от `Activity` context. Подставить один вместо другого нельзя.

## I — Interface Segregation Principle (Разделение интерфейсов)

**Принцип:** клиент не должен зависеть от методов, которые он не использует.

**Нарушение** — `Robot` вынужден реализовать `eat()`:

```kotlin
interface Worker {
    fun work()
    fun eat()
}

class Robot : Worker {
    override fun work() = println("Robot working")
    override fun eat() = throw UnsupportedOperationException("Robot doesn't eat")
}
```

**Исправление** — разбиваем на мелкие интерфейсы:

```kotlin
interface Workable { fun work() }
interface Eatable { fun eat() }

class Robot : Workable {
    override fun work() = println("Robot working")
}

class Human : Workable, Eatable {
    override fun work() = println("Human working")
    override fun eat() = println("Human eating")
}
```

> В Android нарушение — `TextWatcher`: заставляет переопределять `beforeTextChanged`/`onTextChanged`/`afterTextChanged`, хотя обычно нужен один.

## D — Dependency Inversion Principle (Инверсия зависимостей)

**Принцип:** модули верхнего уровня не зависят от модулей нижнего уровня — оба зависят от абстракций. Абстракции не зависят от деталей; детали зависят от абстракций.

> Класс не должен сам конфигурировать свои зависимости — он получает их готовыми извне (см. [[DI VS SERVICE LOCATOR]]).

**Нарушение** — `Switch` жёстко завязан на `LightBulb`:

```kotlin
class Switch {
    private val bulb = LightBulb()
    fun operate() = bulb.turnOn()
}
```

**Исправление** — зависимость от абстракции:

```kotlin
interface Switchable {
    fun turnOn()
    fun turnOff()
}

class LightBulb : Switchable {
    override fun turnOn() = println("LightBulb on")
    override fun turnOff() = println("LightBulb off")
}

class Fan : Switchable {
    override fun turnOn() = println("Fan on")
    override fun turnOff() = println("Fan off")
}

class Switch(private val device: Switchable) {
    fun operate() = device.turnOn()
}
```

Теперь `Switch` работает с любым `Switchable` — устройство легко заменить.

> [!tip] Шпаргалка одной строкой
> - **S** — один класс = одна ответственность.
> - **O** — расширяем через новые классы, а не правкой существующих.
> - **L** — наследник не ломает контракт родителя.
> - **I** — много маленьких интерфейсов лучше одного «толстого».
> - **D** — зависим от абстракций, зависимости получаем извне (DI).
>
> **DIP ≠ DI:** DIP — это принцип (зависеть от абстракций), DI — техника его реализации (передавать зависимости извне).
