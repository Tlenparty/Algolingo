# 12 Наблюдаемость

Наблюдаемость (observability) — способность понять по внешним сигналам, что происходит внутри системы: почему запрос медленный, где ошибка, кого задело. Три опоры — логи, метрики и трейсы, плюс алерты, которые будят дежурного. На SD-собесе это обязательная часть ответа «как узнаем, что сломалось».

> [!tip] Аналогия из Android
> Логи — это Logcat, только со всех серверов в одном поиске. Метрики — это Android Vitals: crash rate, ANR rate, время старта по перцентилям. Трейс — это Perfetto/System Trace: дорожка времени, где видно, какой участок съел время, только не внутри приложения, а через несколько сервисов.

## Логи

- **Структурные:** JSON с полями, а не произвольная строка. Тогда можно искать «все ошибки userId=42 за час».
- Уровни: ERROR (нужно внимание), WARN, INFO (бизнес-события), DEBUG (выключен на проде).
- **Correlation / request id:** клиент генерирует `X-Request-Id` (UUID) на каждый запрос, шлюз пробрасывает его во все сервисы, каждая строка лога содержит его. Пользователь пишет в поддержку — по id из приложения находим всю цепочку.
- Сбор: сервисы пишут в stdout, агент отправляет в хранилище (ELK/OpenSearch, Loki), там поиск.
- Никаких токенов, паролей, номеров карт и лишних персональных данных в логах.

```text
{"ts":"...","level":"ERROR",
 "requestId":"7f3c...",
 "userId":42,"route":"/orders",
 "status":500,"ms":812,
 "error":"db timeout"}
```

## Метрики

Числа во времени, дёшево хранить и строить графики. Типовой стек: сервис отдаёт метрики, **Prometheus** их собирает (scrape), **Grafana** рисует дашборды и алерты.

- Типы: counter (растёт: число запросов), gauge (текущее значение: размер очереди), histogram (распределение: время ответа).
- **RED** — для сервисов (запросов): **R**ate — запросов в секунду, **E**rrors — доля ошибок, **D**uration — время ответа.
- **USE** — для ресурсов (CPU, диск, пул соединений): **U**tilization — загрузка, **S**aturation — очередь ожидания, **E**rrors — ошибки.
- Метки (labels) — `route`, `status`. Не класть в метки userId или requestId: каждая уникальная комбинация — отдельный временной ряд, Prometheus захлебнётся (high cardinality).

### Почему p99, а не среднее

```text
100 запросов:
 98 × 50 мс, 2 × 5000 мс
 среднее ≈ 149 мс  «всё ок»
 p50 = 50 мс, p99 = 5000 мс
```

Среднее прячет хвост. p99 — 99% запросов быстрее этого значения, а 1% медленнее. Экран, который делает 10 запросов, упрётся хотя бы в один медленный заметно чаще, чем в 1% случаев. А медленный хвост часто приходится на самых активных пользователей с большими данными.

## Трейсинг

```text
trace 7f3c (GET /feed) 420 мс
├ gateway            420
│ ├ auth              15
│ └ feed-service     390
│   ├ redis get        2
│   ├ db posts       310 ◄
│   └ users-service   60
```

- **Trace** — путь одного запроса через все сервисы; **span** — один участок (вызов сервиса, запрос в БД) с началом, длительностью и родителем.
- Контекст трейса передаётся в заголовке `traceparent` (стандарт W3C), его можно начать прямо в приложении.
- **OpenTelemetry** — стандартный SDK и протокол; бэкенды — Jaeger, Tempo, Zipkin, коммерческие APM.
- Трейсить всё дорого — пишут выборку (sampling), но ошибки и медленные запросы стараются сохранять.

## Алерты и SLO

- Алертить по **симптомам**, которые видит пользователь (растут ошибки, p99 выше порога), а не по причинам (CPU 80%): высокий CPU без влияния на пользователей — не повод будить ночью.
- **SLI** — измеряемая метрика (доля успешных запросов). **SLO** — цель (99.9% успешных за 30 дней). **Error budget** — допустимые 0.1%: бюджет тратится — тормозим релизы и чиним надёжность.
- Каждый алерт должен требовать действия и иметь runbook; шумные алерты игнорируют, и настоящий пропустят.

## Мобильная сторона

- **Crashlytics** (Firebase) или Sentry: краши и non-fatal ошибки со стектрейсом, версией, устройством. Для обфусцированных сборок нужен mapping-файл R8.
- **ANR** и время старта: Android Vitals в Play Console, свои метрики через Firebase Performance.
- **Breadcrumbs:** последние действия перед крашем (открыл экран, нажал кнопку, ответ 500).
- Клиентские метрики сети: время запроса, доля ошибок по версиям приложения и операторам; requestId в логах приложения для связи с сервером.
- Release health: crash-free users по версии, поэтапная выкатка и остановка релиза, если показатель упал.

## Когда применять в SD-задаче

Сигналы: «как узнаете, что сервис деградировал», «пользователь жалуется, что медленно», «как выкатывать безопасно», «SLA 99.9%», в конце любого дизайна — «что будем мониторить».

Фраза на собес: «Каждый запрос несёт X-Request-Id из приложения; структурные логи с ним, метрики RED по эндпоинтам в Prometheus и Grafana с алертами по p99 и доле ошибок относительно SLO, распределённый трейсинг через OpenTelemetry; на клиенте — Crashlytics, ANR и время старта по версиям».

> [!warning] Грабли
> - Смотреть на среднее время ответа — хвост p99 не виден.
> - userId или URL с id в метках метрик — взрыв кардинальности и падение Prometheus.
> - Токены и персональные данные в логах — утечка через систему логирования.
> - Алерты на всё подряд — дежурный привыкает игнорировать.
> - Нет request id — запрос пользователя невозможно найти среди миллионов строк.
> - Логи только на диске сервера: под в Kubernetes пересоздан — логи исчезли.

> [!question]- Чем логи, метрики и трейсы отличаются и зачем все три?
> Метрики — дешёвые агрегаты во времени: быстро показывают, что что-то не так (выросли ошибки, p99). Трейсы показывают, где именно в цепочке сервисов теряется время для конкретного запроса. Логи дают детали конкретного события: текст ошибки, параметры. Обычно путь такой: алерт по метрике → трейс медленного запроса → логи по его requestId.

> [!question]- Почему перцентили, а не среднее время ответа?
> Среднее размывается: 98 быстрых и 2 очень медленных запроса дают «нормальное» среднее. p99 показывает, что испытывает 1% худших запросов, а у активного пользователя с множеством запросов на экран шанс попасть в хвост намного выше 1%. Поэтому SLO и алерты строят по p95/p99, причём перцентили считают из гистограмм, а не усредняют между серверами.

> [!question]- Пользователь жалуется, что лента грузится 10 секунд. Как будете искать причину?
> Найду его запросы по userId или X-Request-Id, который приложение пишет в свои логи и отправляет на сервер; открою трейс — какой span занял время (БД, внешний сервис, очередь); посмотрю метрики RED этого эндпоинта — проблема массовая или у одного пользователя; проверю клиентскую часть — сеть, время на клиенте, версию приложения. Если массовая — сверю с последними релизами.
