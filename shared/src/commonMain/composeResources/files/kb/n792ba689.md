### **До Java 8 (Связный список)**

Предположим, у нас есть несколько ключей с одинаковым `hashCode`, например, `key1`, `key2` и `key3`. В этом случае все ключи будут храниться в виде связного списка (`LinkedList`) в одном ведре (bucket).

Новые элементы добавлялись в **начало** списка (head insertion).
Поиск/вставка/удаление в таком ведре — **O(n)**, потому что приходится проходить весь список и для каждого узла вызывать `equals()`.

```kotlin
bucket[i] -> [key1|val1] -> [key2|val2] -> [key3|val3] -> null
```

---

### **После Java 8 (Связный список → Красно-чёрное дерево)**

Начиная с Java 8, ведро может **динамически превращаться** из связного списка в **сбалансированное красно-чёрное дерево** (`TreeNode`), когда коллизий становится слишком много. Это спасает от деградации производительности при «атаке хэшами» или плохой хэш-функции.

**Когда происходит treeification (превращение в дерево):**

1. Количество элементов в одном ведре достигает `TREEIFY_THRESHOLD = 8`, **И**
2. Общий размер таблицы (количество корзин) `>= MIN_TREEIFY_CAPACITY = 64`.

> Если корзин меньше 64 — вместо построения дерева HashMap сначала делает **resize()** (увеличивает массив), потому что увеличение таблицы дешевле и часто само разносит коллизии по разным ведрам.

**Обратное превращение (untreeify):**
Если при удалении элементов размер ведра падает до `UNTREEIFY_THRESHOLD = 6`, дерево снова сворачивается в связный список. Зазор между 8 и 6 (гистерезис) не даёт структуре «дёргаться» туда-сюда на границе.

**Производительность:**

| Структура ведра      | Поиск/вставка |
| -------------------- | ------------- |
| Связный список       | O(n)          |
| Красно-чёрное дерево | O(log n)      |

```
bucket[i]  ──treeify──>        (key2)
(список из 8+)                 /      \
                          (key1)    (key3)   ← красно-чёрное дерево
```

**Важные нюансы:**

- Внутри дерева узлы упорядочиваются сначала по `hash`, затем (при равенстве хэшей) по сравнению через `Comparable` (если ключ его реализует), иначе — по порядку вставки / сравнению идентичности (`System.identityHashCode`). При этом `equals()` всё равно используется, чтобы найти именно нужный ключ.
- Дерево не отменяет `equals()`: оно лишь ускоряет навигацию, а финальное определение «тот ли это ключ» всегда идёт через `hashCode` + `equals`.
- См. также [[Как сравниваются ключи в HashMap при одинаковом hashCode]] и [[Как работает HashMap]].

**Константы (из `java.util.HashMap`):**

```java
static final int TREEIFY_THRESHOLD     = 8;
static final int UNTREEIFY_THRESHOLD   = 6;
static final int MIN_TREEIFY_CAPACITY  = 64;
```
