# 06 Redis

Redis — key-value хранилище в оперативной памяти: ответ за доли миллисекунды против единиц-десятков миллисекунд у БД на диске. В SD-задачах это универсальный «быстрый слой»: кеш, сессии, счётчики для rate limit, лидерборды, простой pub/sub.

> [!tip] Аналогия из Android
> Redis — это общий для всех серверов `LruCache`. Обычный `LruCache` живёт в памяти одного процесса; Redis — отдельный процесс, к которому по сети ходят все N экземпляров сервера, поэтому кеш и счётчики у них общие. И так же, как `LruCache`, он вытесняет старое, когда память кончается.

## Как работает

Команды выполняются в одном потоке по очереди, поэтому каждая отдельная команда атомарна — `INCR` от двух серверов одновременно не потеряет инкремент.

### Структуры данных

| Тип | Пример | Для чего |
| --- | --- | --- |
| string | `SET user:42:name "Ann"` | кеш JSON, флаги, счётчики (`INCR`) |
| hash | `HSET user:42 name Ann age 30` | объект с полями |
| list | `LPUSH feed:42 post:9` | ленты, простые очереди |
| set | `SADD likes:post:9 42` | уникальные значения, «лайкнул ли» |
| sorted set | `ZADD top 1500 user:42` | рейтинги, лидерборды, окна по времени |

Ещё есть Streams (журнал сообщений с consumer group), bitmap, HyperLogLog (приблизительный счёт уникальных).

### TTL

У любого ключа есть срок жизни: `SET session:abc 42 EX 3600` — исчезнет через час. Для кеша TTL обязателен: даже если инвалидация где-то забыта, данные устареют максимум на TTL.

### Стратегии кеширования

```text
Cache-aside (lazy):
 app ─get─► Redis ─hit─► ответ
   │ miss
   └─► DB ─► SET key EX ttl ─► ответ
 запись: UPDATE DB, затем DEL key

Write-through:
 app ─► Redis + DB (синхронно)

Write-behind:
 app ─► Redis ─(позже, пачкой)─► DB
```

- **Cache-aside** — самый частый. Приложение само читает кеш, при промахе идёт в БД и кладёт результат. При записи обновляет БД и **удаляет** ключ (не обновляет — меньше гонок). Кеш содержит только то, что реально читают.
- **Write-through** — пишем сразу и в кеш, и в БД. Кеш всегда свежий, но запись медленнее и кеш забит тем, что, возможно, не читают.
- **Write-behind (write-back)** — пишем в кеш, в БД сбрасываем асинхронно пачками. Очень быстрая запись (счётчики просмотров, лайки), но при падении Redis несброшенные данные теряются.

### Счётчики и rate limit

```text
key = rl:{userId}:{минута}
n = INCR key
if n == 1: EXPIRE key 60
if n > 100: ответ 429
```

Это fixed window. Чтобы `INCR` и `EXPIRE` не разъехались при сбое, их выполняют атомарно (Lua-скрипт или `MULTI`). Точнее — sliding window на sorted set или token bucket.

### Pub/Sub

`PUBLISH chat:7 "hi"` → все, кто сейчас `SUBSCRIBE chat:7`, получат сообщение. Fire-and-forget: подписчик, который был отключён, сообщение потерял навсегда. Подходит, чтобы разослать событие по всем WebSocket-серверам; для надёжной доставки нужны Redis Streams или Kafka.

### Память, вытеснение, надёжность

- При достижении `maxmemory` работает политика вытеснения: `allkeys-lru`/`allkeys-lfu` для чистого кеша, `volatile-*` — только ключи с TTL. По умолчанию `noeviction` — запись просто начнёт падать с ошибкой.
- Персистентность есть (RDB-снимки, AOF-журнал), но с `appendfsync everysec` при падении теряется до ~секунды записей; репликация асинхронная — при failover последние записи могут пропасть.
- Масштаб: реплики для чтения, Redis Cluster шардирует ключи по 16384 слотам.

### Когда НЕ Redis

- Источник истины для денег, заказов, всего, что нельзя потерять, — это БД с транзакциями.
- Данные больше памяти или нужны сложные запросы, JOIN, поиск по полям — это БД / поисковый движок.
- Надёжная очередь с повторной обработкой и хранением истории — Kafka/RabbitMQ.
- Данные, которые нужны одному серверу, — хватит локального in-memory кеша.

## Когда применять в SD-задаче

Сигналы: «много чтений, мало записей», «популярная лента/профиль», «нужно отвечать быстро», «rate limit», «сессии для многих серверов», «топ-100», «онлайн-статус».

Фраза на собес: «Горячие данные кладу в Redis по схеме cache-aside с TTL и инвалидацией удалением ключа при записи; там же атомарные счётчики для rate limit и сессии, чтобы серверы оставались stateless; источник истины — БД».

> [!warning] Грабли
> - **Cache stampede:** популярный ключ истёк, и тысяча запросов одновременно идут в БД. Лечится блокировкой на перестроение (`SET lock NX EX`), ранним фоновым обновлением, разбросом TTL (jitter).
> - Гонка в cache-aside: старое чтение может положить в кеш устаревшее значение после `DEL` — спасает TTL как страховка.
> - Без TTL и без `maxmemory`-политики Redis растёт до упора.
> - Большие ключи (список в миллион элементов) блокируют единственный поток — все остальные запросы ждут.
> - Redis как единственное хранилище «потому что быстро» — потеря данных при падении.

> [!question]- Почему Redis такой быстрый, если он однопоточный?
> Данные в памяти, без дисковых чтений; простые структуры с O(1)/O(log n) операциями; один поток выполнения без блокировок и переключения контекста; мультиплексированный сетевой ввод-вывод (epoll), а с Redis 6 сетевой I/O может идти в отдельных потоках. Узкое место обычно сеть, а не CPU.

> [!question]- Cache-aside, write-through, write-behind — в чём разница?
> Cache-aside: приложение читает кеш, при промахе — БД и заполняет кеш; при записи обновляет БД и удаляет ключ. Write-through: каждая запись синхронно идёт и в кеш, и в БД — кеш свежий, запись медленнее. Write-behind: запись только в кеш, в БД — асинхронно пачками; быстро, но при падении кеша данные теряются. По умолчанию выбирают cache-aside.

> [!question]- Как реализовать rate limiter на Redis для нескольких серверов?
> Счётчик в Redis общий для всех экземпляров. Fixed window: ключ `rl:{user}:{минута}`, `INCR`, при первом инкременте `EXPIRE 60`, больше лимита — 429. Атомарность — через Lua-скрипт. Fixed window пропускает всплеск на стыке окон; точнее sliding window (sorted set с timestamp и `ZREMRANGEBYSCORE`) или token bucket.

> [!question]- Можно ли использовать Redis Pub/Sub для доставки сообщений чата?
> Только как транспорт «онлайн»: разослать событие по всем WebSocket-серверам, у которых сейчас подключены участники. Pub/Sub не хранит сообщения — офлайн-получатель их не увидит. Само сообщение сначала сохраняется в БД (или Kafka), а пропущенное клиент дочитывает при переподключении.
