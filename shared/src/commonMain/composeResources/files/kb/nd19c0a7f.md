
**Inline-функции** в Kotlin — это функции, ==код которых вставляется (или “встраивается”) ==непосредственно ==в место их вызова во время компиляции==. ==Это позволяет уменьшить накладные расходы на вызов функции==, поскольку компилятор заменяет вызов функции её реализацией, а не выполняет стандартный механизм вызова (с передачей управления, создание нового стека вызовов и т.д.).

**Почему это важно?**

В обычных функциях в Kotlin, при их вызове создается новый стек вызовов, передаются параметры и выполняются другие механизмы, связанные с вызовом функции. Для маленьких функций это может привести к дополнительным накладным расходам. В случае **inline**-функций компилятор заменяет эти вызовы “телом” функции, таким образом исключая накладные расходы на создание нового стека вызова.

```kotlin
inline fun logMessage(message: String) {
    println(message) //Теперь каждый вызов logMessage("Hello, World!") будет заменен непосредственно на println(message) в компилированном коде.
}
```
**Преимущества inline-функций:**

1. **Снижение накладных расходов**: Встраивание кода функции непосредственно в место вызова может уменьшить затраты на выполнение, особенно для небольших функций.

2. **Поддержка лямбда-выражений**: Одно из наиболее популярных применений inline-функций — это использование лямбда-выражений, где их ==код вставляется непосредственно в место вызова, а не передается как объект==.

3. **Улучшение производительности**: Особенно это полезно при использовании высокоуровневых операций, таких как обработка коллекций или обработка событий, где каждый вызов функции может быть дорогим.

**Пример использования inline с лямбда-выражениями:**

Когда вы передаете лямбду в обычную функцию, она передается как объект. Для этого нужно создать объект лямбды, что может привести к дополнительным накладным расходам. Однако, если вы используете **inline-функцию**, то лямбда будет вставлена непосредственно в код, избегая создания лишних объектов.

```kotlin
inline fun <T> myForEach(list: List<T>, action: (T) -> Unit) {
    for (item in list) {
        action(item) // Вставляется лямбда в код
    }
}

fun main() {
    val list = listOf(1, 2, 3, 4, 5)
    
    // Вызов inline-функции с лямбдой
    myForEach(list) { println(it) }
}
```

При вызове myForEach(list) { println(it) }, компилятор **вставляет** тело лямбды прямо в тело функции myForEach. Это позволяет избежать создания дополнительного объекта лямбды.

**Когда использовать inline-функции?**

• **Маленькие функции, часто вызываемые**: Inline-функции могут быть полезны для небольших функций, которые часто вызываются, так как их встраивание помогает сэкономить время на вызовы.

• **Лямбда-выражения**: Когда функция принимает лямбда-выражение, использование inline может значительно улучшить производительность, так как лямбда-выражение будет встраиваться в код, избегая создания объектов.

• **Коллекции и операции с функциями высшего порядка**: В Kotlin есть множество операций с коллекциями, таких как map, filter, и forEach, которые могут быть реализованы как inline-функции.


**Ограничения и моменты, которые нужно учитывать:**

1. **Размер встраиваемого кода**: Если функция слишком большая или содержит большое количество кода, её встраивание может привести к увеличению размера конечного приложения, так как код будет повторяться в местах каждого вызова функции.

2. **Рекурсивные inline-функции**: Inline-функции не могут быть рекурсивными, потому что компилятор не может корректно встраивать рекурсивные вызовы.

3. **Инлайн-лямбды**: Важно помнить, что лямбды, передаваемые в inline-функции, также могут иметь ограничения на количество использования памяти, так как они могут быть инлайнены в код.
4. Однако **локальные inline-функции** не поддерживаются, потому что их **нельзя эффективно инлайнить

```kotlin
fun click() {  
	// Так нельзя. Надо вынести на уровень класса
    inline fun kek(){  
          
    }  
}
```


**Пример с более сложной inline-функцией и лямбдами:**

```kotlin
inline fun <T> doSomethingWithList(list: List<T>, action: (T) -> Unit) {
    println("Start processing...")
    for (item in list) {
        action(item)
    }
    println("End processing...")
}

fun main() {
    val numbers = listOf(1, 2, 3, 4, 5)

    // Передача лямбды в inline-функцию
    doSomethingWithList(numbers) { number ->
        println("Processing number: $number")
    }
}
```

**Заключение**
**Inline-функции** — это мощный инструмент в Kotlin для оптимизации производительности и упрощения работы с лямбда-выражениями. Использование **inline** помогает снизить накладные расходы на вызов функции и повысить производительность в случае частых вызовов небольших функций или работы с лямбдами. Однако, важно учитывать, что чрезмерное использование inline-функций с большими функциями или большими лямбдами может привести к увеличению размера кода и потенциальным проблемам с памятью.

>Если сделать **все функции** в Android проекте **inline**, то это может привести к нескольким проблемам и недостаткам. Вот основные:

**3️⃣ Проблемы с дебаггингом**

## noinline

В Kotlin, ключевое слово ==noinline== используется для ==**отмены инлайнинга**== лямбд, передаваемых в функции, которые помечены как inline. Оно ==позволяет вам использовать лямбды в inline-функциях, но исключить их из инлайнинга==, что может быть полезно в ситуациях, когда лямбда ==не должна быть вставлена в код, а должна передаваться как обычный объект==.

**Зачем нужно noinline?**

==Когда функция помечена как inline, все лямбды, передаваемые ей, по умолчанию становятся тоже инлайнены (встраиваются в тело функции). Однако, бывают ситуации, когда вы хотите, чтобы только некоторые лямбды были инлайнены, а другие — нет.== В таких случаях используется noinline, чтобы исключить конкретные лямбды из инлайнинга, оставив их в виде обычных объектов.

**Как это работает?**
Допустим, у вас есть функция, которая принимает несколько лямбд. Если вы хотите, чтобы одна из них была инлайнена, а другая оставалась как обычный объект, то для этой второй лямбды используйте noinline.

**Пример с использованием noinline:**

Предположим, у нас есть функция, которая принимает две лямбды: одну мы хотим инлайнить, а другую нет.

```kotlin
inline fun doSomething(action1: () -> Unit, noinline action2: () -> Unit) {
    // action1 будет инлайнена, а action2 — нет
    println("Before action1")
    action1()
    println("Before action2")
    action2()  // action2 передается как обычный объект
}

fun main() {
    val action1 = { println("Action 1") }
    val action2 = { println("Action 2") }

    doSomething(action1, action2)
}
```

**Объяснение:**

1. `action1` будет инлайнена — её код вставляется непосредственно в место вызова.
2. `action2` не будет инлайнена, а передастся как обычный объект лямбды (создаётся объект, представляющий лямбду).

**Когда использовать noinline?**

noinline полезен, когда вы хотите смешать инлайнинг и обычные лямбды в одной функции. Например:

• ==**Передача лямбды как аргумента в другой контекст**==. Лямбда, помеченная как noinline, будет передаваться как объект, и её код не будет инлайнен.

• **==Использование лямбд в callback-функциях или в других местах**==, где лямбда не может быть инлайнена, например, в случаях, когда она должна быть выполнена позже или передана другим компонентам.

## crossinline

*crossinline* — это ключевое слово в Kotlin, которое используется в контексте **inline-функций**. Оно предназначено для того, чтобы ==запретить возврат из лямбды, передаваемой в inline-функцию==, или, точнее, ==предотвратить использование оператора return внутри этой лямбды==.

**Зачем нужно crossinline?**

При передаче лямбды в inline-функцию в Kotlin, иногда может возникнуть ситуация, когда внутри лямбды используется оператор return. Если лямбда передается в функцию, которая имеет как inline-поведение, то использование return может привести к неожиданным результатам. В частности, это может привести к возвращению из внешней функции, а не только из самой лямбды.

Чтобы избежать таких случаев, используется crossinline, которое запрещает использование оператора return внутри лямбды.

**Пример использования crossinline:**

```kotlin
inline fun doSomething(action: () -> Unit, crossinline onComplete: () -> Unit) {
    println("Before action")
    action()  // Вызываем первую лямбду

    // Код, который не связан с лямбдой
    println("Doing some other work...")

    // Нельзя использовать return в onComplete, так как она помечена crossinline
    onComplete()  // Вызываем вторую лямбду
}

fun main() {
    doSomething(
        action = { println("Action executed") },
        onComplete = { 
            println("Complete executed")
            // return  // Ошибка! return нельзя использовать внутри crossinline лямбды
        }
    )
}
```

**Объяснение:**

1. В функции doSomething у нас есть две лямбды: action и onComplete.
2. Лямбда onComplete помечена как crossinline.
3. crossinline не позволяет использовать оператор return внутри лямбды onComplete. Например, если бы вы попытались использовать return в onComplete, компилятор вызвал бы ошибку, потому что лямбда передается в inline-функцию, и её выполнение будет частью более широкой логики.

**Когда использовать crossinline?**

1. **Когда нужно запретить использование** `return` **в лямбде**, передаваемой в inline-функцию, чтобы избежать ошибок с неожиданным выходом из внешней функции.

2. **Когда лямбда выполняется не напрямую, а в другом контексте** (вложенная лямбда, отложенный вызов) — компилятор требует `crossinline`, потому что non-local return оттуда невозможен.

**1️⃣ Без crossinline:**
```kotlin
inline fun testFunction(block: () -> Unit) {
    println("Before block")
    block()  // Вызов лямбды
    println("After block")
}

fun main() {
    testFunction {
        println("Inside block")
        return  // Возврат из main
    }
    println("This will never be printed")
}
```

**2️⃣ С crossinline:**
```kotlin
inline fun testFunction(crossinline block: () -> Unit) {
    println("Before block")
    block()  // Вызов лямбды
    println("After block")
}

fun main() {
    testFunction {
        println("Inside block")
        // return  // Ошибка! Нельзя использовать return, так как block помечен как crossinline
    }
    println("This will be printed")
}
```

**3️⃣ return@label для правильного возврата:**

```kotlin
inline fun testFunction(block: () -> Unit) {
    println("Before block")
    block()  // Вызов лямбды
    println("After block")
}

fun main() {
    testFunction {
        println("Inside block")
        return@testFunction  // Возврат из testFunction, а не из main
    }
    println("This will be printed")
}
```

**4️⃣ Может ли return@ сделать правильный ретерн без crossinline?**
Да, с помощью return@label можно **правильно выполнить возврат** из инлайн-функции, даже если лямбда не помечена как crossinline. Это позволяет избежать необходимости использовать crossinline, если вам нужно контролировать, из какой функции нужно выходить.

```kotlin
inline fun testFunction(block: () -> Unit) {
    println("Before block")
    block()  // Вызов лямбды
    println("After block")
}

fun main() {
    testFunction {
        println("Inside block")
        return@testFunction  // Возврат из testFunction
    }
    println("This will be printed")
}
```

## reified

**reified** — это ключевое слово в Kotlin, которое используется для работы с **типами** в **generic-функциях**. ==В обычных дженериках типы стираются при компиляции (процесс называется **type erasure**), что означает, что в рантайме мы не можем получить информацию о конкретных типах. Однако, с помощью reified можно сохранить информацию о типе на момент выполнения и использовать её внутри функции.== 

**Зачем нужно reified?**
Когда вы используете **generic-функции**, вы теряете доступ к типу параметра во время выполнения. Это ограничивает возможности, например, когда вы хотите выполнить проверку типа или создать экземпляр объекта на основе типа параметра. reified позволяет получить доступ к реальному типу параметра внутри generic-функции.

**Как это работает?**

> Для того, чтобы использовать reified, функция должна быть помечена как inline. Это связано с тем, что при использовании inline-функций компилятор вставляет код функции прямо в место её вызова, что позволяет сохранить информацию о типе в процессе компиляции и передать её в тело функции.

**Пример использования reified:**
```kotlin
inline fun <reified T> printType() {
    println("Тип T: ${T::class.java}")
}

fun main() {
    printType<String>()  // Вывод: Тип T: class java.lang.String
    printType<Int>()     // Вывод: Тип T: int
}
```

В этом примере:

• Функция printType использует reified для сохранения информации о типе параметра T в момент выполнения.
• Мы можем обратиться к типу с помощью T::class.java, чтобы вывести его на экран.

**Основные особенности reified:**

1. **Доступ к типу во время выполнения**: Без reified мы не могли бы получить доступ к типу T в рантайме (он был бы “стерт” при компиляции), но с reified это становится возможным.

2. **Использование только в inline-функциях**: reified можно использовать только внутри **inline-функций**, так как только в них информация о типе сохраняется после компиляции.

3. **Преимущества при работе с generics**: Это особенно полезно в ситуациях, когда вам нужно:

• Проверить тип в рантайме.
• Создавать экземпляры объектов с типом, который передан в качестве параметра.
• Применять операции, зависящие от типа (например, приведение типов).

**Пример создания объектов с reified:**

```kotlin
inline fun <reified T> createInstance(): T {
    // newInstance() устарел; современный вариант:
    return T::class.java.getDeclaredConstructor().newInstance()
}

fun main() {
    val stringInstance: String = createInstance()
    println(stringInstance::class.java)  // Вывод: class java.lang.String
}
```

Здесь:

• Мы создаем экземпляр типа T, используя T::class.java.newInstance().

• Благодаря reified мы можем создавать объект с типом, который передан в generic-функцию.

Пример с проверкой типа 
```kotlin
inline fun <reified T> isInstance(obj: Any): Boolean {
    return obj is T
}

fun main() {
    val result = isInstance<String>("Hello, Kotlin!")
    println(result)  // Вывод: true
    
    val result2 = isInstance<Int>("Hello, Kotlin!")
    println(result2)  // Вывод: false
}
```

Здесь мы используем reified для того, чтобы выполнить проверку типа (obj is T) во время выполнения. Это было бы невозможно в обычных generic-функциях без использования reified.

**Стирание типов** (type erasure) в Kotlin (и в других языках программирования, таких как Java) означает, что информация о типах параметров обобщённых (generic) классов и функций теряется на момент выполнения программы. Это делается для того, чтобы сэкономить место и обеспечить совместимость с более старыми версиями JVM, которые не поддерживают дженерики в том виде, как это делают современные языки.
Когда мы используем **дженерики** в Kotlin, информация о типе, переданном в качестве параметра, исчезает после компиляции. То есть, на момент выполнения программа “забывает”, какие именно типы были переданы в обобщённый тип или функцию.

**Пример стирания типов**

Предположим, у нас есть простая функция с дженериком
```kotlin
fun <T> printType(value: T) {
    println(value)
}
```

Когда мы компилируем этот код, параметр T является **дженериком**, и в момент компиляции он может быть подставлен конкретным типом, например, Int или String. Однако, когда программа запускается, тип T “стирается” и становится просто Object (или его аналог, в зависимости от реализации), и мы не можем получить доступ к исходному типу.
```kotlin
fun main() {
    val list = listOf("apple", "banana", "cherry")
    
    // Функция с дженериком:
    val firstElement = list.first()
    
    // В рантайме тип T уже "стерт", и мы не можем узнать его тип напрямую:
    println(firstElement::class)  // Это всегда будет Class<String>, потому что в Kotlin List<String> компилируется как List<Any>
}
```
На этапе компиляции в ``List<String>`` мы можем увидеть, что тип элемента — это String, но в рантайме это будет общее представление типа Any. Мы не можем напрямую работать с типом String в коде, поскольку информация о типе будет утеряна при компиляции.


### **Как работает стирание типов в Kotlin?**

1. **Только исходный тип параметра сохраняется в компилированном коде**:

После компиляции в JVM, все типы, такие как ``List<String>``, становятся эквивалентными ``List<Any>``. То есть параметр типа String в ``List<String>`` становится просто Any в байт-коде, и мы теряем информацию о точном типе.

2. **Отсутствие поддержки типовой информации в рантайме**:

На уровне JVM информация о конкретных типах исчезает, и все дженерики в коде становятся базовыми типами, как Any или Object, в зависимости от языка.

3. **Это влияет на работу с типами во время выполнения**:

Без использования reified или рефлексии вы не сможете узнать точный тип параметра, переданного в дженерики. Это ограничение накладывает определённые ограничения на использование дженериков.

**Пример с ограничением на типы (базовые классы и интерфейсы)**
```kotlin
fun <T> printClassName(value: T) {
    println(value::class.simpleName)  // Это работает и будет выводить имя класса
}

fun main() {
    val myString = "Hello, World"
    val myInt = 42
    
    printClassName(myString)  // Вывод: String
    printClassName(myInt)     // Вывод: Int
}
```

Здесь мы использовали ::class.simpleName, чтобы узнать тип объекта во время выполнения. Однако в случае с дженериками в **обычных функциях**, как показано ниже, мы не можем сделать то же самое:
```kotlin
fun <T> printType(value: T) {
    println(T::class.java)  // Ошибка компиляции, так как T стирается на этапе компиляции
}
```

Если бы в Java был механизм, аналогичный reified, компилятор должен был бы сохранять типы в байт-коде, что противоречит принципам стирания типов в языке. В Java, например, метод getClass() работает только с реальными типами объектов, но он не может извлечь информацию о параметризованном типе, как это можно сделать в Kotlin.

> [!tip] Связка inline + reified на собесе
> - **`reified` работает только в `inline`-функциях** — потому что тело инлайнится в место вызова, и компилятор подставляет туда **конкретный** тип, обходя стирание типов (type erasure).
> - Без `reified`: `T::class`, `obj is T`, `obj as T` — **ошибка компиляции**. С `reified` — работают.
> - Типичное применение в Android: `inline fun <reified T> Gson.fromJson(json) = fromJson(json, T::class.java)`, `inline fun <reified T : Activity> Context.startActivity()`.
> - Минусы inline помни тоже: раздувает байткод (тело копируется в каждый вызов), нельзя рекурсию, усложняет стектрейсы. Поэтому `inline` ставят на функции с **лямбда-параметрами** или **reified**, а не на всё подряд.
