# 🟠 Уровень 6 — Надёжный сервис

Цель уровня: защитные механизмы сервиса написаны руками, а не только названы на схеме.

## 6.1 Token bucket
Напиши ограничитель запросов «ведро токенов»: ведро вмещает `capacity` токенов и пополняется на `refillPerSec` токенов в секунду. Запрос в момент `nowMs` проходит, если в ведре есть целый токен, и забирает его. Так выглядит rate limiter из System Design (`sd1.2`) в коде.

- 🎯 **Тренируем:** состояние с временем, ленивое пополнение «сколько прошло × скорость», ограничение сверху.
- ⏱ **Цель:** 5 минут.

> [!question]- 💡 Подсказка 1
> Не нужен таймер. При каждом запросе посчитай, сколько секунд прошло с прошлого раза, и долей `elapsed * refillPerSec` токенов — но не выше `capacity`.

> [!question]- 💡 Подсказка 2
> Токены дробные (`Double`): за 500 мс при 1 токене/с наливается 0.5. Пропускать можно, только когда `tokens >= 1.0`, и тратить ровно один.

> [!success]- ✅ Решение
> ```kotlin
> // Случай 1: ведро 2, 1 токен/с: 0 мс → true, 0 мс → true, 0 мс → false
> // Случай 2: ведро 1, 1 токен/с: 0 мс → true, 500 мс → false, 1000 мс → true
> // Случай 3: ведро 1, 2 токена/с: 0 мс → true, 500 мс → true
> class TokenBucket(private val capacity: Int, private val refillPerSec: Double) {
>     // токенов в ведре сейчас (дробно)
>     private var tokens = capacity.toDouble()
>     // когда доливали в последний раз, мс
>     private var lastMs = 0L
>
>     // долить за прошедшее время
>     private fun refill(nowMs: Long) {
>         // сколько секунд прошло
>         val elapsed = (nowMs - lastMs) / 1000.0
>         // долив, но не выше ёмкости
>         tokens = minOf(capacity.toDouble(), tokens + elapsed * refillPerSec)
>         lastMs = nowMs
>     }
>
>     // пропустить запрос в момент nowMs?
>     fun allow(nowMs: Long): Boolean {
>         // сначала долить
>         refill(nowMs)
>         // меньше токена — отказ
>         if (tokens < 1.0) return false
>         // тратим один токен
>         tokens -= 1.0
>         return true
>     }
> }
> ```
> **Сложность:** O(1) / O(1).
> **Почему работает:** ведро — это «долг времени». Пока запросов нет, время копится в токены до потолка `capacity`; всплеск до `capacity` запросов проходит разом, а дальше ровно `refillPerSec` в секунду. Пополнение ленивое: считается в момент запроса, поэтому ни таймеров, ни фоновых потоков.
> ⚠️ **Грабли:** `tokens <= 1.0` откажет при ровно одном токене — ведро на 1 токен не пропустит ничего; `tokens == 0.0` вместо `< 1.0` пропустит запрос на дробном остатке; забыть `minOf(capacity, …)` — после долгой паузы ведро «накопит» тысячи токенов и лимит исчезнет; считать `elapsed` в миллисекундах — долив в тысячу раз быстрее; на одном инстансе в памяти лимит не общий — за балансером ×N, общий счётчик живёт в Redis (`sd1.2`).
> 🔁 **Вариации:** leaky bucket (ровный поток вместо всплесков); sliding window log (точный, но хранит время каждого запроса); лимит на пользователя — `Map<UserId, TokenBucket>` с выселением неактивных; общий лимит на N инстансов — `INCR` + `EXPIRE` в Redis.
