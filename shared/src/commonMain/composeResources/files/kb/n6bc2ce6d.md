# 10 Real-time

Как доставить клиенту событие, которое произошло на сервере: новое сообщение, лайк, смена статуса заказа. HTTP устроен «клиент спросил — сервер ответил», поэтому для обратного направления есть несколько приёмов с разной ценой по трафику, батарее и сложности сервера.

> [!tip] Аналогия из Android
> Polling — это `while (true) { load(); delay(30_000) }` в корутине. WebSocket — это открытый `Flow` от сервера, который вы `collect`-ите, пока экран жив. Push через FCM — это `BroadcastReceiver`, который система разбудит, даже когда приложение не запущено.

## Варианты

```text
Polling:   C─?─►S  C─?─►S  C─?─►S
           (каждые N секунд)
Long poll: C─?─►S ...ждёт... ◄─data
           C─?─►S ...
SSE:       C─GET─►S
           ◄─ev ◄─ev ◄─ev (один поток)
WebSocket: C◄═══════►S (оба направления)
Push:      S─►FCM/APNs─►устройство
```

**Polling** — запрос раз в N секунд.
- Плюс: проще всего, обычный HTTP, кешируется.
- Минус: задержка до N секунд, большинство запросов пустые, тратит батарею и сервер.
- Когда: данные меняются редко, свежесть не критична (статус заказа раз в минуту).

**Long polling** — сервер держит запрос открытым, пока не появятся данные (или таймаут ~30 с), клиент сразу шлёт следующий.
- Плюс: почти мгновенно, работает через любые прокси.
- Минус: соединение на каждого ожидающего, переоткрытие после каждого события.

**SSE (Server-Sent Events)** — один долгий HTTP-ответ `text/event-stream`, сервер дописывает события.
- Плюс: обычный HTTP, у событий есть `id`, и при переподключении клиент шлёт `Last-Event-ID` — сервер дошлёт пропущенное.
- Минус: только сервер → клиент; клиент пишет обычными запросами.
- Когда: лента, котировки, прогресс задачи, стриминг ответа LLM.

**WebSocket** — после HTTP-рукопожатия (`Upgrade: websocket`) соединение становится двунаправленным каналом сообщений.
- Плюс: минимальная задержка в обе стороны, мало накладных расходов на сообщение.
- Минус: сервер держит состояние на соединение (sticky, своя балансировка), нужен свой протокол сообщений, ack и heartbeat (ping/pong).
- Когда: чат, совместное редактирование, игры, «печатает…».

**Push (FCM на Android, APNs на iOS)** — сервер шлёт событие через инфраструктуру Google/Apple, ОС доставляет его даже в фоне.
- Плюс: работает, когда приложение закрыто, одно системное соединение на все приложения — бережёт батарею.
- Минус: доставка не гарантирована и не мгновенна, размер payload ограничен (около 4 КБ), порядок не гарантирован.
- Правило: push — это сигнал «есть новое», а данные приложение дочитывает по API.

## Что выбрать

- **Чат:** WebSocket, пока приложение на экране; push, когда в фоне; после переподключения — дочитать историю по API с последнего известного id.
- **Лента:** обычно pull-to-refresh и плашка «новые посты» через SSE или polling раз в минуту; real-time для ленты редко нужен.
- **Уведомления:** push (FCM/APNs) плюс список уведомлений по API.
- **Статус заказа/такси:** SSE или WebSocket на экране отслеживания, push для ключевых смен статуса.

## Переподключение

Мобильная сеть рвётся постоянно: лифт, метро, смена Wi-Fi на LTE.

```text
обрыв ─► ждём 1с±jitter ─► connect
  fail ─► 2с±j ─► 4с ─► ... ≤ 60с
  ok ─► resume(lastEventId)
     ─► сервер шлёт пропущенное
```

- **Экспоненциальный backoff + jitter:** иначе после сбоя сервера миллион клиентов переподключится в одну и ту же секунду и снова его положит (thundering herd).
- **Resume:** клиент помнит id последнего полученного события и просит «всё после него». Для этого сервер хранит события (БД, Kafka), а не только рассылает онлайн.
- Слушать `ConnectivityManager.NetworkCallback`: сеть вернулась — переподключаемся сразу, без ожидания backoff.
- **Heartbeat:** ping каждые 20–30 с, чтобы обнаружить «мёртвое» соединение (NAT и мобильные операторы молча рвут простаивающие TCP).

## Батарея на мобильном

- Каждое пробуждение радиомодуля стоит дорого: после передачи радио ещё секунды остаётся в активном состоянии. Частый polling в фоне быстро сажает батарею.
- Android ограничивает фон (Doze, App Standby): своё долгое соединение в фоне будет убито. Для фона — FCM, для отложенной синхронизации — WorkManager.
- WebSocket держим только пока экран виден (`repeatOnLifecycle(STARTED)`), уходим в фон — закрываем.

## Когда применять в SD-задаче

Сигналы: «чат», «уведомить пользователя», «показывать в реальном времени», «статус доставки», «кто онлайн», «совместное редактирование».

Фраза на собес: «На открытом экране — WebSocket с heartbeat и переподключением по экспоненциальному backoff с jitter и resume по lastEventId; в фоне — push через FCM как сигнал, данные дочитываем по REST; источник истины — история на сервере, а не сокет».

> [!warning] Грабли
> - Считать WebSocket надёжной доставкой: сообщения в момент обрыва теряются, нужны ack и дочитка истории.
> - Переподключение без jitter: после сбоя сервер добивают синхронные реконнекты.
> - Держать сокет в фоне: Android всё равно его убьёт, а батарея пострадает.
> - Класть данные в push: payload ограничен, push может не дойти или прийти дважды.
> - WebSocket-серверы за обычным балансировщиком: нужно знать, на каком сервере сокет получателя, — рассылка через Redis Pub/Sub или брокер.

> [!question]- WebSocket, SSE или long polling — как выбрать?
> Если нужна двусторонняя связь с малой задержкой (чат, совместное редактирование) — WebSocket. Если события идут только от сервера (лента, прогресс, котировки) — SSE: это обычный HTTP, проще балансировать, есть встроенный resume через Last-Event-ID. Long polling — запасной вариант, когда долгие соединения режут прокси. Если свежесть не критична — обычный polling раз в минуту.

> [!question]- Как доставить сообщение в чат, если приложение закрыто?
> Сообщение сначала сохраняется на сервере. Получателю отправляется push через FCM/APNs: высокоприоритетное уведомление показывается сразу, data-push будит приложение ненадолго. При открытии чата клиент дочитывает пропущенные сообщения по API с последнего известного id и подключает WebSocket для новых.

> [!question]- Как правильно переподключаться после потери связи?
> Экспоненциальный backoff с ограничением сверху и случайным jitter, чтобы клиенты не ломились одновременно; сразу переподключаться по событию «сеть появилась» от ConnectivityManager; после подключения запрашивать события после последнего полученного id; heartbeat, чтобы замечать «мёртвые» соединения; операции отправки — идемпотентные, с client-generated id, чтобы повтор не создал дубль.
