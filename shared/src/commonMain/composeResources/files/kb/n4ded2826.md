Как уйти от race condition ? Синхронизация? 
```kotlin
var unreadMessageCount = 0

val scope = CoroutineScope(Dispatchers.IO)

suspend fun updateUnreadReviews() {
    println("do API reviews request")
    Thread.sleep(Random.nextLong(100, 2000))
    val reviewsResponse = Random.nextInt(5, 10)
    unreadMessageCount = reviewsResponse
}

suspend fun updateUnreadComplains() {
    println("do API complains request")
    Thread.sleep(Random.nextLong(500, 1500))
    val complainsResponse = Random.nextInt(5, 10)
    unreadMessageCount = complainsResponse
}

fun main(): Unit = runBlocking {
    val job = scope.launch {
        updateUnreadComplains()
        updateUnreadReviews()
    }

    job.join()
    println(unreadMessageCount)
}
```

Синхронизация с Mutex
```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

var unreadMessageCount = 0
private val mutex = Mutex()

suspend fun updateUnreadReviews() {
    println("do API reviews request")
    delay(Random.nextLong(100, 2000))
    val reviewsResponse = Random.nextInt(5, 10)
    mutex.withLock {
        unreadMessageCount = reviewsResponse
    }
}

suspend fun updateUnreadComplains() {
    println("do API complains request")
    delay(Random.nextLong(500, 1500))
    val complainsResponse = Random.nextInt(5, 10)
    mutex.withLock {
        unreadMessageCount = complainsResponse
    }
}
```

Через Channel 
```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.channels.Channel
import kotlin.random.Random

var unreadMessageCount = 0

val scope = CoroutineScope(Dispatchers.IO)

suspend fun updateUnreadReviews(channel: Channel<Int>) {
    println("do API reviews request")
    delay(Random.nextLong(100, 2000))  // Используем delay вместо Thread.sleep для работы в корутинах
    val reviewsResponse = Random.nextInt(5, 10)
    channel.send(reviewsResponse)  // Отправляем результат в канал
}

suspend fun updateUnreadComplains(channel: Channel<Int>) {
    println("do API complains request")
    delay(Random.nextLong(500, 1500))  // Используем delay вместо Thread.sleep для работы в корутинах
    val complainsResponse = Random.nextInt(5, 10)
    channel.send(complainsResponse)  // Отправляем результат в канал
}

fun main() = runBlocking {
    val channel = Channel<Int>()  // Канал для передачи результатов

    val job = scope.launch {
        updateUnreadComplains(channel)  // Запускаем функцию с каналом
        updateUnreadReviews(channel)    // Запускаем функцию с каналом
    }

    // Получаем данные из канала и обновляем unreadMessageCount
    launch {
        repeat(2) {
            unreadMessageCount += channel.receive()  // Добавляем значение, полученное из канала
        }
        job.join()
        println("Final unreadMessageCount: $unreadMessageCount")
    }
}
```

fun <T> filterList(list: List<Any>, action: () -> Unit): List<T> {
    val resultList = mutableListOf<T>()
    for (element in list) {
        if (element is T) {
            resultList.add(element)
        } else {
            saveResult(action)
        }
    }
    return resultList
}

fun saveResult(action: () -> Unit) {
    action.invoke()

Кеш из апи

```kotlin
interface BackendApi {
    suspend fun apiCall(): String // very long call
}

// Сделать код-ревью и рефакторинг по необходимости
class Repository(private val backendApi: BackendApi) {
    private var cache: String? = null

    suspend fun apiCallOrCache(): String {
        if (cache != null) {
            return cache!!
        }

        val apiResponse = backendApi.apiCall() // very long call
        cache = apiResponse
        return apiResponse
    }
}
```


```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

class Repository(private val backendApi: BackendApi) {
    private var cache: String? = null
    private val mutex = Mutex()

    suspend fun apiCallOrCache(): String {
        return mutex.withLock {
            cache ?: backendApi.apiCall().also { cache = it }
        }
    }
}
```

> [!warning] Race condition: `Thread.sleep` в `suspend` — отдельная ошибка
> В первом варианте обе функции пишут общий `var unreadMessageCount` без синхронизации (последний выигрывает) и используют **`Thread.sleep`** внутри `suspend` — это **блокирует поток диспетчера**, а не приостанавливает корутину. В корутинах всегда `delay` (как в исправленных вариантах). Здесь функции к тому же вызываются **последовательно** в одном `launch`, так что реальной гонки в этом `main` нет — она появится, если запускать их параллельно (`async`/отдельные `launch`).

> [!note] Три способа и что они на самом деле дают
> • **`Mutex`** — сериализует доступ к `unreadMessageCount`. Но «гонка» тут не в атомарности присваивания ссылки (оно и так атомарно), а в **логике** «кто записал последним» — `Mutex` её не меняет, лишь убирает чересполосицу при инкрементах.
> • **`Channel`** — правильный «корутинный» подход: вместо общего мутабельного состояния данные **передаются** в одну корутину-агрегатор (`+= channel.receive()`), которая владеет состоянием единолично. `job.join()` стоит **после** цикла `receive` — логичнее вынести его раньше/в `main`.

> [!warning] inline + reified (вопрос про `is T`)
> `if (element is T)` **не скомпилируется**: `fun <T>` не `inline`, тип `T` стёрт на рантайме. Нужно `inline fun <reified T>`. Дополнительно: `action` передаётся в **не-inline** `saveResult(action)` — внутри inline-функции лямбда по умолчанию тоже inline и так напрямую не передаётся; параметр нужно пометить **`noinline`** (или `crossinline`, если важно запретить нелокальный return):
> ```kotlin
> inline fun <reified T> filterList(list: List<Any>, noinline action: () -> Unit): List<T> { … }
> ```

> [!tip] Кеш через `Mutex`: что улучшено и что ещё можно
> Исходный `apiCallOrCache` подвержен гонке: два конкурентных вызова оба видят `cache == null` и оба дёргают долгий API. Версия с `Mutex` это чинит — второй ждёт и берёт готовое. Минус: лок держится на **всё время** запроса, поэтому даже когда значение уже закэшировано, вызовы сериализуются на входе в `withLock`. Альтернатива без этого минуса — кэшировать **`Deferred`** (один `async` на все ожидающие) или `lazy`-подобную обёртку, тогда после первого вычисления блокировка не нужна.
