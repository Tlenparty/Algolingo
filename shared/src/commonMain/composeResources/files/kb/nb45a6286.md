# 09 Docker и Kubernetes

Docker упаковывает сервис со всеми зависимостями в образ, который одинаково запускается на ноутбуке и на проде. Kubernetes запускает много таких контейнеров на кластере машин: держит нужное число копий, перезапускает упавшие, выкатывает новые версии без простоя. На SD-собесе это уровень «как сервис деплоится и масштабируется».

> [!tip] Аналогия из Android
> Docker-образ — это APK для сервера: собран один раз, внутри код и всё нужное для запуска, ставится одинаково на любую машину. Registry — это Google Play для образов. Kubernetes — что-то вроде системы, которая сама ставит APK на парк устройств, следит, чтобы приложение работало на нужном числе устройств, и выкатывает обновление поэтапно, как staged rollout.

## Контейнер vs виртуальная машина

```text
   VM                 контейнеры
┌─────┬─────┐       ┌─────┬─────┐
│ app │ app │       │ app │ app │
│ libs│ libs│       │ libs│ libs│
│ OS  │ OS  │       └─────┴─────┘
├─────┴─────┤       Docker engine
│ hypervisor│       ядро хост-ОС
└───────────┘       └───────────┘
```

- **VM** эмулирует целую машину со своим ядром ОС: сильная изоляция, но гигабайты и запуск за минуты.
- **Контейнер** — обычный процесс хост-ОС, изолированный средствами ядра Linux (namespaces — свой вид на процессы, сеть, файлы; cgroups — лимиты CPU и памяти). Ядро общее, поэтому контейнер весит мегабайты и стартует за секунды.
- Изоляция у контейнера слабее, чем у VM. В облаке контейнеры обычно и так работают внутри VM.

## Образ, контейнер, registry

- **Image (образ)** — неизменяемый слепок: файловая система из слоёв + команда запуска. Собирается из Dockerfile.
- **Container** — запущенный экземпляр образа. Из одного образа можно запустить сколько угодно контейнеров. Файлы внутри контейнера пропадают вместе с ним — данные хранят в volume или во внешней БД.
- **Registry** (Docker Hub, GitHub Container Registry, ECR) — хранилище образов с тегами версий: `app:1.4.2`.

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY build/libs/app.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

Каждая инструкция даёт слой; неизменившиеся слои берутся из кеша, поэтому редко меняющееся (зависимости) кладут выше, а код — ниже.

## docker-compose: локальное окружение

Чтобы поднять бэкенд с Postgres и Redis на ноутбуке одной командой `docker compose up`:

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: dev
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
  redis:
    image: redis:8
    ports: ["6379:6379"]
volumes:
  pgdata:
```

Пароль `dev` — только для локальной разработки; на проде секреты передают через секреты окружения или Kubernetes Secrets, а не в файле в репозитории.

## Зачем Kubernetes

Один сервер с `docker run` не решает: что делать, если машина умерла; как запустить 20 копий на 5 машинах; как обновить версию без простоя. Это делает оркестратор, стандарт — Kubernetes (k8s).

```text
Deployment app: replicas=3
 ├ Pod app-1 (node A)
 ├ Pod app-2 (node B)
 └ Pod app-3 (node C)
Service app ─► балансирует
 на живые поды
```

- **Pod** — минимальная единица: один или несколько контейнеров с общей сетью. Поды смертны, у них меняются IP.
- **Deployment** — описание «хочу 3 пода версии 1.4.2». Контроллер постоянно приводит реальность к желаемому: под упал — создаётся новый.
- **Service** — стабильный адрес и балансировка трафика на живые поды. **Ingress** — вход снаружи (HTTP-маршруты, TLS), по сути reverse proxy.
- **Probes:** liveness (жив ли — иначе перезапуск), readiness (готов ли принимать трафик — иначе не слать запросы).
- **HPA (Horizontal Pod Autoscaler)** — меняет число подов по метрике (CPU, RPS): нагрузка выросла — подов стало больше.
- **Rolling update** — новая версия выкатывается по одному поду, старые гасятся, когда новые готовы (readiness). Что-то пошло не так — `kubectl rollout undo` возвращает прошлую версию.
- Конфиги и секреты — ConfigMap и Secret, а не зашитые в образ значения.

## Когда применять в SD-задаче

Сигналы: «как масштабировать сервис», «пиковая нагрузка вечером», «выкатить без простоя», «сервис упал — что будет», «несколько окружений (dev, stage, prod)».

Фраза на собес: «Сервис stateless, упакован в Docker-образ и развёрнут в Kubernetes как Deployment с HPA по CPU и RPS; за Service и Ingress, обновления — rolling update с readiness-пробами и быстрым откатом, состояние — во внешних БД и Redis».

> [!warning] Грабли
> - Хранить данные внутри контейнера: перезапуск — и данных нет. Нужен volume или внешняя БД.
> - Секреты в образе или в Dockerfile: образ лежит в registry, его может скачать кто угодно с доступом.
> - Тег `latest` на проде: непонятно, что запущено, откатиться некуда. Нужны конкретные версии.
> - Нет readiness-пробы: rolling update шлёт трафик в под, который ещё прогревается, — всплеск ошибок.
> - Stateful-сервис (сессии в памяти) за балансировщиком: при переезде пода пользователь разлогинен. Сессии — в Redis.
> - Kubernetes для одного маленького сервиса: часто хватает managed-платформы (Cloud Run, App Engine).

> [!question]- Чем контейнер отличается от виртуальной машины?
> VM виртуализирует железо и запускает своё ядро ОС поверх гипервизора: сильная изоляция, но тяжело и долго стартует. Контейнер — изолированный процесс на общем ядре хоста (namespaces для изоляции, cgroups для лимитов ресурсов): лёгкий, стартует за секунды, но изоляция слабее. Поэтому контейнеры удобны для упаковки и плотного размещения сервисов.

> [!question]- Что такое под, деплоймент и сервис в Kubernetes?
> Pod — минимальная единица запуска, один или несколько контейнеров с общей сетью, смертный и с меняющимся IP. Deployment описывает желаемое состояние (образ, число реплик) и сам поддерживает его, а также выкатывает обновления. Service даёт стабильное имя и балансирует трафик между живыми подами, которые выбирает по меткам.

> [!question]- Как выкатить новую версию без простоя?
> Rolling update: Kubernetes поднимает новые поды по одному, ждёт, пока readiness-проба скажет «готов», переключает на них трафик и гасит старые. Важно, чтобы API и схема БД были обратно совместимы — какое-то время работают обе версии. При ошибках — rollout undo. Альтернативы: blue-green (два окружения, переключение трафика целиком) и canary (сначала малый процент трафика).
