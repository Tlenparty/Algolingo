## ☕ Kotlin / Java

### [[ООП]]
Четыре принципа: **инкапсуляция** (объединение данных+методов, сокрытие реализации), **наследование** (переиспользование через иерархию), **полиморфизм** (единый интерфейс для разных типов), **абстракция** (выделение сути через абстрактный класс/интерфейс).
- Абстракция vs инкапсуляция (часто путают): инкапсуляция — *сокрытие как сделано* (прячем поля); абстракция — *выделение что делает, а не как*.
- SOLID не противоречит ООП, а дополняет (5 принципов чистого кода в рамках ООП).
- Инкапсуляция по-котлиновски: не пары get/set-методов, а свойства + модификаторы видимости (`private set`).

### [[Abstract class vs Interface,  Полиморфизм]]
- Абстрактный класс: хранит состояние (поля, конструктор), но наследоваться можно только от **одного**; интерфейс: только контракт, `val` без backing field, можно реализовать **много**.
- Интерфейс может объявить **абстрактный `var`** (без backing field — хранение реализует класс), но не может сам хранить состояние.
- Полиморфизм: ad-hoc (перегрузка), подтипов (override + `open`), интерфейсов; работает через позднее связывание (late binding) — вызов зависит от реального типа объекта.
- Diamond problem: два одинаковых default-метода → компилятор заставляет override с явным `super<Interface>.method()`.
- Правило: начинай с интерфейса; абстрактный класс — когда нужны общее состояние/конструктор/`protected`.

### [[Композиция vs наследование]]
Наследование — связь **is-a** (жёсткая, хрупкий базовый класс, изменение родителя ломает потомков); композиция — **has-a** (гибче, тестируемее, класс содержит другой как поле и делегирует).
- В Kotlin классы **по умолчанию `final`** — язык подталкивает к композиции (для наследования нужен `open`).
- **Делегирование интерфейса через `by`** — композиция без бойлерплейта: `class LoggingRepository(delegate) : Repository by delegate` перекладывает всю работу на вложенный объект, переопределяя только нужное.
- Принцип «композиция вместо наследования»; наследование — только для настоящих is-a и шаблонных методов.

### [[Модификаторы доступа и их видимость]]
Четыре модификатора: `public` (по умолчанию, везде), `internal` (в пределах модуля), `protected` (класс + наследники), `private` (класс/файл).
- Отличия от Java: по умолчанию `public` (в Java — package-private); в Kotlin **нет package-private** (ближайший — `internal`, но модуль ≠ пакет).
- `protected` в Kotlin **строже**: только класс + наследники, НЕ тот же пакет (в Java `protected` = наследники + пакет).
- `private` на top-level = видно только в этом файле; `internal` — основа модульности (api/impl).

### [[Типы данных, отличие const val от val, есть ли в Котлин примитивы]]
В Kotlin нет примитивов «в привычном смысле» — всё классы (`Int`, `Double`, `Char`), но компилятор оптимизирует в примитивы JVM под капотом.
- **`val`** — значение вычисляется в рантайме, любой тип, любой контекст; **`const val`** — compile-time константа, только примитивы/String, только top-level или `companion object`, без геттера.
- **Boxing/unboxing**: `Int?`/дженерики/коллекции упаковывают в `Integer` (heap). Задача: `Int? = 10` → `===` true (Integer-кэш −128…127), `10000` → false (разные объекты). Для `Int` (не nullable) оба true. Сравнивать значения через `==`.
- Размеры: Byte 8, Short 16, Int 32, Long 64, Float 32, Double 64, Char 16 бит.

### [[Any,Nothing,Unit]]
`Any` — корень иерархии (аналог `Object`, но только 3 метода: `equals`/`hashCode`/`toString`), `Unit` — синглтон-объект (аналог `void`, ровно одно значение), `Nothing` — тип без значений (функция никогда не завершается нормально — throw или бесконечный цикл).
- `Nothing` — **подтип любого типа**, поэтому `throw`/`return`/`TODO()` можно ставить в правую часть elvis (`?:`) и в ветки `when`.
- Иерархия: `Nothing` — на дне (подтип всех), `Any?` — на вершине (надтип всех).
- `Unit` vs `void`: `Unit` — полноценный тип/объект, его можно использовать как аргумент дженерика, `void` — нельзя.

### [[Object]]
Методы `java.lang.Object`: `equals()`, `hashCode()`, `toString()`, `getClass()`, `clone()`, `notify()`/`notifyAll()`/`wait()`.
- Kotlin `Any` объявляет **только три**: `equals`, `hashCode`, `toString`. Остальных нет: `wait/notify` убраны намеренно (используют корутины/`Mutex`), `getClass()` → `obj::class`/`obj.javaClass`, `clone()` → `copy()` у data class.
- Под JVM `Any` ложится на `Object`, поэтому `(obj as Object).wait()` возможен, но это антипаттерн.

### [[Data class]]
Класс для хранения данных, автогенерирует `equals()`, `hashCode()`, `toString()`, `copy()`, `componentN()`. Требует ≥1 параметр в первичном конструкторе (все `val`/`var`), класс `final`.
- **Нельзя наследовать** — сгенерированные методы строятся по полям и наследование сломало бы контракт; расширять через композицию.
- `equals`/`hashCode`/`toString`/`copy` учитывают **только свойства первичного конструктора** — поля в теле класса игнорируются.
- `copy()` — **поверхностная** (shallow): вложенные объекты копируются по ссылке.
- `var` опасен: объект-ключ «потеряется» в `HashMap`, если после вставки изменить поле (сменится `hashCode`). Предпочитать `val` + `copy()`.

### [[Sealed class vs enum]]
`enum` — конечный набор **однотипных** констант; `sealed` — конечный набор **разнотипных** наследников (каждый со своими данными).
- `sealed class` компилируется в `abstract class`, все наследники известны на компиляции → нельзя создать инстанс базового.
- Главная польза обоих — **исчерпывающий `when`** (без `else`); добавил вариант → компилятор заставит обработать везде.
- С Kotlin 1.5 наследники sealed — в любом файле **того же модуля и пакета**; из другого модуля — нельзя.
- **`sealed interface`** часто предпочтительнее: множественная реализация, нет конструктора.
- enum: `values()`/`entries`, `valueOf()`, `name`, `ordinal`.

### [[object и companion object]]
В Kotlin нет `static`; заменяют top-level функции, `object`, `companion object`, `const val`/`@JvmStatic`.
- `static` в Java: член класса, нет `this`, вызов через `invokestatic` (без vtable → нет полиморфизма, дёшево). Не переопределяется — только method hiding.
- **`object`** — потокобезопасный ленивый синглтон (поле `INSTANCE`, вызовы `invokevirtual`).
- **`companion object`** — **не совсем static**: реальный объект-синглтон в поле `Companion`; для настоящей static нужна `@JvmStatic`. Может иметь имя, реализовывать интерфейсы, быть фабрикой.
- `const val` — настоящее `static final`, значение инлайнится в места использования.

### [[Nested class vs inner class]]
В Kotlin вложенный класс **по умолчанию static-nested** (нет доступа к внешнему классу); `inner` даёт доступ к outer через `this@Outer`.
- Nested: создаётся как `Outer.Nested()`, без ссылки на outer. Inner: `Outer().Inner()`, хранит **неявную ссылку** на внешний объект.
- Противоположно Java (там по умолчанию inner) — в Kotlin static по умолчанию **ради безопасности**.
- `inner`-класс, живущий дольше внешнего (Activity), → **утечка памяти** (классика: `Handler`/`Runnable` как inner в Activity). Решение: nested + `WeakReference`.

### [[Вторичный конструктор]]
- Обязан вызвать первичный конструктор (`: this(...)`) прямо или косвенно; если есть родитель — `super(...)`.
- **Нельзя** объявлять `val`/`var` в его параметрах, задавать default-значения; нельзя в `data class`.
- **Порядок инициализации**: `init {}`-блоки и инициализаторы свойств выполняются в составе первичного конструктора → сначала делегирование первичному → `init` → потом **тело** вторичного.
- В Kotlin нужен редко — обычно заменяют параметрами по умолчанию первичного; для сложного создания — фабричный метод в `companion object`.

### [[Backing Field в Kotlin]]
Скрытое поле для хранения значения свойства, доступное через `field` **только** внутри кастомных `get`/`set`.
- Прямое присваивание свойству в сеттере (`name = value`) → рекурсия → `StackOverflowError`; нужно `field = value`.
- **Backing property** — главный паттерн: скрыть mutable-тип, наружу отдать read-only (`private val _state = MutableStateFlow(...)` + `val state: StateFlow = _state.asStateFlow()`).
- Если backing field не нужен (вычисляемое свойство `val full get() = ...`), Kotlin его не генерирует.

### [[Inline class, value class, typealias, infix]]
- **inline class** (устарел) → **value class** (`@JvmInline`): типобезопасная обёртка над **одним** значением без оверхеда (`UserId(Long)` ≠ `OrderId(Long)`). В Compose так сделаны `Dp`, `Color`, `TextUnit`.
- **value class боксируется**, когда используется как nullable (`Email?`), как супертип/интерфейс или в дженерике/коллекции — выигрыш теряется.
- **typealias** — лишь псевдоним типа, новый тип **не создаёт** (нет type-safety), только для читаемости.
- **infix** — инфиксный вызов без скобок (`a isOlderThan b`); функция-член/extension, один параметр, не `private`.

### [[Делегаты.  Lateinit and Lazy]]
Делегирование свойств через `by` (делегат реализует `getValue`/`setValue`). Встроенные: `lazy`, `observable`, `vetoable`.
- **`lateinit var`** — отложенная инициализация **снаружи** (DI, `onCreate`); только не-nullable **ссылочные** типы; обращение до инициализации → `UninitializedPropertyAccessException`; проверка `::x.isInitialized`.
- **`val by lazy`** — вычисляется **само** при первом обращении и кэшируется; потокобезопасно по умолчанию (`SYNCHRONIZED`; ещё `PUBLICATION`, `NONE`).
- `lateinit` часто «зло»: требует `var`, краш при раннем доступе, `lateinit var binding` во фрагментах → утечки. Альтернатива — nullable-поле с проверкой.

### [[Кто поддерживает деструктуризацию в Kotlin ?]]
Деструктуризация (`val (a, b) = obj`) работает через `operator fun componentN()`.
- Поддерживают: `data class`, обычные классы (при ручном `componentN()`), `Pair`/`Triple`, `List` (до 5 элементов), `Map.Entry`.
- **Позиционна, а не по имени**: `val (age, name) = person` молча присвоит `age = person.name`. Важен порядок свойств, не имена переменных.
- Опасна для однотипных полей: перестановка полей тихо ломает деструктуризацию. Пропуск компонента через `_`.

### [[Лямбда]]
Анонимная функция в `{}`. **Захват** (capture) — использование переменных из окружения (замыкание).
- В Kotlin можно захватывать и **изменять `var`** — компилятор оборачивает в `Ref.IntRef` → скрытая аллокация обёртки.
- **Лямбда без захвата** → синглтон (без аллокаций); **с захватом** → новый объект при каждом создании (давит на GC в циклах).
- В `inline`-функции лямбда встраивается — объекта нет вообще (поэтому `forEach`/`map`/`let` помечены `inline`).
- `fun interface` (SAM) — передача лямбды туда, где ожидается интерфейс с одним методом.

### [[Функциональные типы в Kotlin]]
Функциональный тип `(A, B) -> C` представляет функцию как объект.
- Под капотом компилируется в интерфейс `FunctionN` (`Function2<A,B,C>` с методом `invoke`); лямбда — объект, реализующий `invoke`.
- **Оператор `invoke`**: `obj()` ≡ `obj.invoke()`. Класс может наследоваться от `() -> Unit` и вызываться как функция.
- **Receiver-тип** `A.(B) -> C` — функция с приёмником (как `apply`/`buildString`), `this` = `A`; основа DSL.
- **`suspend`-функциональные типы** `suspend (A) -> B` — для suspend-лямбд в корутинах.

### [[Reference function]]
Ссылка на функцию через `::` — функции как первоклассные объекты.
- **Unbound** (`User::introduce`) — первым параметром принимает приёмник, тип `(User) -> Unit`; удобно в `list.map(User::name)`.
- **Bound** (`person::introduce`) — приёмник привязан, тип `() -> Unit`.
- Применение: передать существующую функцию вместо лямбды (`setOnClickListener(::onClick)`) — читаемее, не плодит объект.

### [[Extension функции]]
Добавление функций к классам без изменения их кода. Под капотом — **статическая функция** с receiver'ом первым параметром.
- **Разрешаются статически** (по объявленному типу переменной) — **нет полиморфизма**, нельзя переопределить в наследниках.
- **Член класса всегда побеждает** extension с той же сигнатурой.
- Нет доступа к `private`/`protected` — только публичный API.
- Extension-свойства не могут хранить состояние (только геттер/сеттер).

### [[let, apply,  with, run, also]]
Мнемоника: **возвращают объект** → `apply`/`also`; **возвращают результат блока** → `let`/`run`/`with`. Контекст **`it`** → `let`/`also`; **`this`** → `run`/`with`/`apply`.
- `let` — nullable (`?.let`), трансформация; `apply` — конфигурация/инициализация; `also` — побочные эффекты (логи) в цепочке; `run` — блок вычислений; `with` — несколько операций (не extension).
- Ловушка: `apply {}` возвращает **тот же** receiver; результат вызова внутри отбрасывается.

### [[Inline, Noinline, cross inline, reified]]
`inline`-функция встраивает своё тело (и тело лямбд) в место вызова — убирает создание объекта лямбды.
- Минусы: раздувает байткод, нельзя рекурсию, усложняет стектрейсы. Ставят на функции с лямбда-параметрами или `reified`.
- **`noinline`** — отменить инлайнинг конкретной лямбды (передать её как объект дальше).
- **`crossinline`** — запретить non-local `return` из лямбды (когда она вызывается в другом контексте).
- **`reified`** — доступ к типу в рантайме (обход type erasure); **только в inline**. Без него `T::class`, `obj is T`, `obj as T` — ошибка компиляции. Применение: `Gson.fromJson<T>`, `startActivity<T>`.

### [[Spread operator и vararg]]
`vararg` — переменное число аргументов (внутри — массив: `IntArray` для примитивов, `Array<T>` для объектов). `*` (spread) распаковывает готовый массив.
- `*` создаёт **поверхностную копию** массива — лишняя аллокация для больших массивов.
- В функции только **один** `vararg`-параметр, обычно последний.
- Комбинируется: `printNumbers(0, *nums, 4)`; `listOf(*a, *b)`.

### [[Generic]]
Обобщённые типы (`Box<T>`). Главное — вариантность:
- **`out T` (ковариантность)** — тип только **производит/отдаёт** (Producer); `Box<Int>` можно передать как `Box<Any>`. Нельзя записывать.
- **`in T` (контравариантность)** — тип только **потребляет/принимает** (Consumer); `Box<Any>` можно передать как `Box<Int>`. Нельзя читать.
- **PECS**: Producer-Extends (`out`), Consumer-Super (`in`).
- Declaration-site (Kotlin, `class Box<out T>`) vs use-site (`List<out T>`, Java `? extends T`).
- `*` (star-projection) — `List<*>`: читать как `Any?`, добавлять нельзя.
- Типы стираются в рантайме (type erasure) — обход через `reified`.

### [[EQUALS, HASHCODE]]
- Если `a.equals(b)` → `a.hashCode() == b.hashCode()` (обязательно). Обратное неверно (коллизия). `equals` рефлексивен, симметричен, транзитивен, консистентен.
- Классический баг: переопределили `equals`, забыли `hashCode` → объект теряется в `HashMap`/`HashSet`. `data class` генерирует оба согласованно.
- В Kotlin `==` вызывает `equals()`, `===` сравнивает ссылки; `==` с `null` не бросает NPE.
- В коллекциях сначала сравнивают дешёвый `hashCode` (int), при совпадении — дорогой `equals`.
- **String Pool**: литералы интернируются (`==` даёт true). **Integer cache** −128…127.

### [[HashMap vs HashSet]]
`HashSet` — это `HashMap` под капотом: элемент множества хранится как **ключ**, значение — заглушка `PRESENT`.
- Уникальность обеспечивается тем же механизмом `hashCode`/`equals`.
- Требование: элементы/ключи корректно реализуют `equals`/`hashCode` и неизменяемы по полям хэша.
- Сложность `add`/`contains`/`get` — в среднем **O(1)**, в худшем — **O(log n)** (с Java 8 бакет → дерево при ≥8 элементах).

### [[Stream vs Collection vs Sequence]]
- **Collection (eager)**: каждая операция сразу создаёт новую коллекцию и проходит **все** элементы. Для маленьких коллекций — нормально.
- **Sequence (lazy)**: операции выполняются **поэлементно по цепочке** только при терминальной операции; без промежуточных коллекций. Выгодно на больших данных, длинных цепочках, раннем выходе (`first`, `take`); поддерживает бесконечные (`generateSequence`).
- **Java Stream** — конвейер (Source→Intermediate→Terminal), ленивый, одноразовый, `parallelStream()` (ForkJoinPool).
- Не оборачивай маленькие списки в `asSequence()` — только накладные расходы.

### [[String]]
`String` неизменяем и хранится в **String Pool** (литералы интернируются); `new String()`/конкатенация создают новый объект в heap.
- Неизменяемость даёт: безопасность, потокобезопасность, работу пула, кэш `hashCode`. Минус: сенситивные данные держат в `CharArray`/`ByteArray`.
- Сравнивать через `==` (это `equals`), `===` — только осознанно.
- Конкатенация в цикле через `+` — O(n²); использовать `StringBuilder`/`buildString {}` (O(n)); для списков — `joinToString`.

### [[Побитовое сравнение]]
В Kotlin побитовые операции — **инфиксные функции** (не символы `&`/`|` как в Java): `and`, `or`, `xor`, `inv()`, `shl`, `shr`, `ushr`.
- Применение: флаги в одном `Int` (`READ or WRITE`, проверка `and WRITE != 0`).
- В Android: `Intent`-флаги, `View.SYSTEM_UI_FLAG_*`; распаковка ARGB (`(color shr 16) and 0xFF`); `x and 1 == 0` — чётность; `shl`/`shr` — умножение/деление на 2.

### [[Heap & Stack]]
**Stack** (на поток, LIFO, локальные переменные + ссылки + адреса возврата, автоосвобождение) и **Heap** (общая, сами объекты, очистка GC).
- `val p = Person()` — объект `Person` в heap, ссылка `p` в stack. Static-поля — в **Metaspace**.
- Heap медленнее stack: аллокатор+GC vs сдвиг указателя, хуже кэшируется, фрагментация, синхронизация (общий на потоки).
- Переполнение stack → `StackOverflowError` (рекурсия), нехватка heap → `OutOfMemoryError`.
- Примитивы-локальные — в стеке; при боксинге (`Int?`, дженерики) уезжают в кучу.

### [[Аллокация в jvm]]
Аллокация — выделение памяти в **heap** под новый объект; позже GC удаляет объекты без ссылок.
- **TLAB** (Thread-Local Allocation Buffer) — свой кусок Eden на поток, bump-the-pointer без блокировок.
- **Escape analysis**: если объект не «убегает» из метода, JIT может не аллоцировать его в куче (scalar replacement).
- Новые объекты — в Eden (Young), пережившие → Old.
- Лишние аллокации: автобоксинг (`Int?`, дженерики), лямбды с захватом, промежуточные коллекции.

### [[GC, Виды ссылок, GC roots]]
Сборщик мусора JVM: находит недостижимые от GC Roots объекты (mark-and-sweep), поколенческая модель (Young: Eden+Survivor / Old / Metaspace).
- **Виды ссылок**: Strong (не удалится), Soft (при нехватке памяти — кэш), Weak (при первой сборке — `WeakHashMap`), Phantom (пост-финализация).
- **GC Roots**: static-поля, активные потоки, JNI, загруженные классы, локальные переменные метода. Объект жив, пока достижим от Root.
- JVM собирает **циклические ссылки** (через достижимость, не reference counting).
- **Android ≠ HotSpot**: ART использует concurrent copying GC; `System.gc()` — лишь подсказка.
- Утечки в Android = что-то из GC Roots (static, поток, Handler, inner class) держит strong-ссылку на `Activity`/`Context`.

### [[Структуры данных]]
Обзор коллекций: `Array` (фиксированный размер, O(1) доступ), `List`/`ArrayList` (на массиве), `Set` (`setOf`→LinkedHashSet), `Map`.
- **HashMap под капотом**: `capacity` 16 (степень 2), `loadFactor` 0.75 → при превышении массив удваивается + рехеширование. Коллизии — chaining (список, с Java 8 → красно-чёрное дерево при >8).
- Задача: 5 объектов с `hashCode()==1` без `equals` → **5 элементов** (разные ссылки, один бакет, поиск деградирует до O(n)).
- Big-O: `ArrayList` доступ O(1)/вставка в середину O(n); `LinkedList` доступ O(n)/вставка O(1); `HashMap` O(1)*; `TreeMap` O(log n).

## 🧵 Многопоточность

### [[Процессы и потоки]]
Процесс — экземпляр приложения в изолированном адресном пространстве (общение через IPC — `Binder`, `ContentProvider`, AIDL); поток — легковесная единица внутри процесса, потоки делят общую память (отсюда нужна синхронизация).
- У каждого процесса минимум один поток — главный (UI thread), долгая работа в нём → ANR.
- Приоритеты процессов Android: Foreground → Visible → Service → Cached/Background (LRU) → Empty (убивается первым).
- Все процессы порождаются `fork()` от `Zygote` (copy-on-write — быстрый старт и экономия памяти).

### [[Синхронные и асинхронные операции]]
Синхронные операции блокируют поток до завершения; асинхронные не блокируют вызывающий поток, результат приходит через колбэк / `Future` / suspend-функцию.
- Ключевое: асинхронность ≠ параллельность — конкурентность про структуру (переключение задач, возможно на одном потоке), параллельность про физически одновременное выполнение на нескольких ядрах.
- Асинхронность для I/O-bound, параллельность для CPU-bound; корутины дают конкурентность, параллельность — диспетчеры с пулом (`Dispatchers.Default`).

### [[Handler и Looper]]
Механизм очереди сообщений (`MessageQueue`) в потоке для межпоточной коммуникации и отложенных задач.
- `Looper` крутит event-loop и держит очередь; один `Looper` на поток (`Looper.prepare()` + `Looper.loop()`). Главный поток под капотом крутится на `Looper`.
- `Handler` привязан к `Looper` и кладёт `Runnable`/`Message` (`post`, `postDelayed`).
- Типичный кейс — вернуть результат в UI: `Handler(Looper.getMainLooper()).post { }`.
- Подводный камень — утечки: нестатический `Handler` держит ссылку на `Activity` → чистить `removeCallbacksAndMessages(null)` в `onDestroy`. На проде — `HandlerThread` (не забыть `quitSafely()`); в современном коде вытеснен корутинами.

### [[Volatile & Synchronized, Atomic]]
- `synchronized` — видимость + атомарность (взаимное исключение) через захват монитора; нестатический метод блокирует `this`, статический — класс; монитор освобождается даже при исключении.
- `volatile` (`@Volatile`) — только видимость, без атомарности: `counter++` теряет обновления. Для флагов (`isRunning`).
- `Atomic` (`AtomicInteger`) — видимость + атомарность отдельных операций без блокировок через CAS (compare-and-swap, lock-free). Для счётчиков.
- Выбор: флаг → `@Volatile`; счётчик → `AtomicInteger`; сложная критическая секция → `synchronized`/`ReentrantLock`; в корутинах → `Mutex.withLock`.

### [[Happens before]]
Гарантии видимости и порядка операций между потоками (JMM). Это НЕ про «раньше по времени», а про гарантию: если A happens-before B, результат A виден в B.
- `synchronized`: выход из блока happens-before следующего входа на том же мониторе.
- `volatile`: запись happens-before последующего чтения другим потоком.
- `Thread.start()` — видно всё, записанное до старта; `Thread.join()` — видны результаты завершившегося потока.
- `Lock`: `unlock()` happens-before следующего `lock()`; `java.util.concurrent`: `countDown()`→`await()`, `put()`→`take()` и т.п.

### [[Правила семантики в jvm]]
Виды формальной семантики JVM: операционная (исполнение байт-кода), синхронизации (JMM), исключений (поиск `catch` + unwinding), типов, безопасности (Bytecode Verifier), памяти. На собеседовании почти всегда спрашивают только семантику синхронизации/памяти — happens-before и JMM.

### [[ReentrantLock, Semaphore и CyclicBarrier]]
- `ReentrantLock` — гибкая замена `synchronized`: `tryLock()`, таймауты, `lockInterruptibly()`, реентрантность; `unlock()` в `finally`.
- `Semaphore` — ограничивает число потоков с ресурсом (`acquire()`/`release()`); пул соединений.
- `CyclicBarrier` — все потоки ждут друг друга в общей точке, затем отпускаются разом; переиспользуемый.
- `CountDownLatch` — ждём завершения нескольких задач; одноразовый.
- Подводный камень: `java.util.concurrent.Semaphore.acquire()` блокирует поток — в корутинах брать `kotlinx.coroutines.sync.Semaphore` (`withPermit`) или `Mutex`.

### [[Как работает CountDownLatch]]
Синхронизатор-счётчик: инициализируется числом N, потоки вызывают `countDown()`, ждущие на `await()` разблокируются при счётчике 0. Одноразовый (для повторного использования — `CyclicBarrier`). `await()` блокирует поток (в корутинах вместо этого `Job.join()`/`awaitAll()`); есть перегрузка с таймаутом.

### [[Structured Concurrency]]
Асинхронные задачи образуют дерево, привязанное к скоупу родителя; родитель не завершится, пока не завершатся дети, а отмена/ошибка распространяются иерархически.
- `coroutineScope` — не вернёт управление, пока не отработают все дети; падение любого отменяет остальных и пробрасывает ошибку вверх.
- `supervisorScope` — падение одного ребёнка НЕ отменяет соседей (независимые задачи).
- Антипаттерн, ломающий SC, — `GlobalScope.launch`: живёт вне дерева, никто не отменит → утечки. Использовать `viewModelScope`/`lifecycleScope`.

### [[SharedFlow vs Flow vs StateFlow]]
- `Flow` — холодный, без кеша: тело перезапускается для каждого подписчика. Для источников данных (сеть, Room).
- `SharedFlow` — горячий, много подписчиков получают одно значение; при `replay = 0` без подписчиков теряется. Для одноразовых событий (тост, навигация).
- `StateFlow` — горячий, всегда хранит одно последнее значение (`.value`); новый подписчик сразу получает актуальное; дедуплицирует по `equals`. Для состояния UI (аналог `LiveData`).
- Под капотом `StateFlow` = `SharedFlow(replay = 1, onBufferOverflow = DROP_OLDEST)`. Холодный → горячий через `.stateIn()`/`.shareIn()`.

### [[BackPressure в Flow что это и как решается]]
Backpressure — когда Producer эмитит быстрее, чем Consumer обрабатывает. В Kotlin Flow из коробки решается приостановкой: `emit()` — suspend, при отставании Consumer'а Producer ждёт (данные не теряются). Операторы, когда ожидание не устраивает:
- `buffer()` — разносит по разным корутинам, буфер + `onBufferOverflow` (`SUSPEND`/`DROP_OLDEST`/`DROP_LATEST`).
- `conflate()` — хранит только последнее значение.
- `collectLatest()` — отменяет незавершённую обработку предыдущего элемента.
- `sample(time)` — значение раз в интервал; `debounce(time)` — эмит после паузы во входе (поиск).

## 🌀 Корутины и Flow

### [[Coroutines]]
Корутины — легковесная неблокирующая многопоточность, выглядящая как синхронный код.
- `CoroutineContext` — дерево элементов (Компоновщик): `Job`, `CoroutineDispatcher`, `CoroutineName`, `CoroutineExceptionHandler`; комбинируются `+`. `suspend` компилируется в state machine через CPS.
- Билдеры: `launch` (fire-and-forget, `Job`), `async` (результат через `Deferred.await()`), `runBlocking` (блокирует поток, тесты/`main`), `withContext` (смена контекста).
- Диспетчеры: `Main` (UI), `IO` (лимит max(64, ядра)), `Default` (max(2, ядра), CPU); `IO` и `Default` делят общий пул. `Unconfined` — только тесты.
- Потокобезопасность: `Mutex.withLock` (приостанавливает, не реентрантный → дедлок при повторном lock), atomic, thread confinement, `Channel`, `StateFlow`. `stateFlow.value += 1` не атомарно — нужен `update { it + 1 }`.
- Scope: `GlobalScope` (не рекомендуется), `lifecycleScope`, `viewModelScope`, `coroutineScope` (ждёт детей, всё-или-ничего), `supervisorScope` (изолирует падение прямых детей).

### [[Обработка ошибок в корутинах]]
Два механизма: отмена (`CancellationException`, не ошибка) и распространение обычных исключений по дереву `Job`.
- Отмена кооперативна: реально прерывает на suspend-точке или ручном `isActive`/`ensureActive()`. `CancellationException` при ловле `Exception` обязательно перебрасывать (`throw e`). Очистка в `finally`; suspend-работа там — через `withContext(NonCancellable)`.
- Дерево: отмена родителя идёт только вниз; ошибка обычного `Job` идёт вверх и каскадом отменяет соседей. `SupervisorJob`/`supervisorScope` рвут распространение ошибки вверх/вбок, но не отмену вниз.
- `SupervisorJob` изолирует дерево, но не обрабатывает исключение — без `CoroutineExceptionHandler` необработанное исключение всё равно может уронить процесс.
- `CoroutineExceptionHandler` — только для `launch`, на root-scope, не ловит `CancellationException`. У `async` исключение всплывает через `await()`.

### [[Coroutines. Вопрос ответ]]
Практические мини-вопросы: ленивый старт `CoroutineStart.LAZY`, один поток через `newSingleThreadContext` (обязательно `close()`; лучше `limitedParallelism(1)`).
- Дождаться корутину: `async` + `await()` (нужен результат), `launch` + `join()` (результат не нужен), `withContext` (сменить контекст и вернуть результат).
- Маппинг: сеть на `Dispatchers.IO`, тяжёлый CPU-маппинг на `Dispatchers.Default`; suspend-Retrofit сам уходит с главного потока.

### [[Coroutines + callback]]
Как обернуть callback-API в suspend: `suspendCoroutine` (без отмены) и `suspendCancellableCoroutine` (с отменой, предпочтительно).
- `Continuation` возобновляют вручную: `resume(value)` при успехе, `resumeWithException(e)` при ошибке.
- `suspendCancellableCoroutine` реагирует на отмену через `invokeOnCancellation` — там отменяют реальный запрос (OkHttp `Call`).
- Профит: асинхронный код читается как синхронный, ошибки через `try-catch`, поддержка отмены.

### [[FLOW]]
`Flow<T>` — асинхронный поток многих значений во времени (`emit`). Операторы объединения:
- `combine` — берёт последние значения потоков, реагирует на изменение любого (состояние экрана из нескольких источников).
- `zip` — соединяет строго парами по порядку; короче/пустой один → завершается.
- `merge` — сливает потоки по мере поступления, без пар.
- `flatMapLatest` — при новом элементе отменяет предыдущий внутренний поток (поиск); `flatMapConcat` — последовательно; `flatMapMerge` — параллельно.

### [[Задачи на корутины]]
- Дерево корутин: `scope.launch` на отдельном `CoroutineScope(SupervisorJob())` не привязан к `runBlocking` — `main` выходит мгновенно; исключение поднимается вверх по дереву `Job` до первого supervisor'а. Привязать правильно: `supervisorScope`, `SupervisorJob(parent=...)` + `complete()`, или `joinAll`.
- Отмена: корутина с `Thread.sleep` в `while(true)` не отменится — отмена кооперативна; чинится `delay`, `while(isActive)` или `ensureActive()`.
- Рефакторинг Compose: не передавать `Context` в `ViewModel`, не создавать VM руками в `onCreateView`, сайд-эффекты в `LaunchedEffect`, `collectAsStateWithLifecycle`.

## 🎨 Jetpack Compose

### [[Compose]]
Декларативный UI-фреймворк на Kotlin без XML; композиция строится `Composer`, `@Composable` обрабатывает Compose Compiler Plugin (`startRestartGroup()`/`endRestartGroup()` + битовая карта `$changed`).
- Три фазы кадра: Composition (какой UI) → Layout (measure + placement) → Drawing (`Canvas` поверх Skia); фазы могут пропускаться.
- Правила: composable вызывается только из composable; с большой буквы — рендерит `Unit`; порядок параметров — обязательные, потом дефолтные, `Modifier` первым из опциональных, trailing-лямбда последней.
- Тот же рантайм работает в Compose Multiplatform (меняется лишь бэкенд отрисовки).

### [[Compose. Recomposition]]
Рекомпозиция — точечное обновление UI: при изменении состояния Compose помечает зависимые узлы invalidated и через Slot Table перерисовывает только их.
- **Чтение** состояния подписывает функцию на изменения, **запись** сама по себе — нет; чтение+запись в одной области → бесконечная рекомпозиция.
- Приём defer reads: выносить чтение ниже по дереву, передавать вниз `State` или лямбду.
- При скролле `derivedStateOf` предпочтительнее `snapshotFlow` + `collect`.
- Нестабильные значения, захваченные лямбдой, оборачивать в `rememberUpdatedState`.

### [[Compose. Remember]]
`remember` кэширует значение на время жизни композиции и не пересчитывает лямбду при рекомпозиции; при изменении `keys` пересоздаётся, при выходе из дерева — сбрасывается.
- `rememberSaveable` дополнительно переживает смену конфигурации и смерть процесса через `Bundle`/`Saver`.
- Частая ошибка — забытый `key`: значение «залипает» на старом параметре.
- Эфемерное UI-состояние → `remember`/`rememberSaveable`; бизнес-состояние → `ViewModel`.

### [[Compose. Effect Handlers]]
Три эффекта: `LaunchedEffect` (корутина в скоупе композиции, перезапуск при смене `key`), `DisposableEffect` (подписки с обязательным `onDispose`), `SideEffect` (синхронизация с не-Compose на каждой рекомпозиции).
- `LaunchedEffect(Unit)` — запуск один раз. Для запуска по событию (клик) — `rememberCoroutineScope`, а не `LaunchedEffect`.
- `produceState` — асинхронно производит `State<T>`; `derivedStateOf` — вычисляемое состояние, эмитит только при изменении результата лямбды.
- `rememberUpdatedState` — чтобы долгая корутина видела «свежее» значение без перезапуска.

### [[Compose. Composition Local]]
Механизм передачи данных вниз по дереву в обход параметров (тема, локаль, плотность, `NavController`); создаётся `compositionLocalOf`/`staticCompositionLocalOf`, задаётся `CompositionLocalProvider`, читается через `.current`.
- `compositionLocalOf` — чтения **отслеживаются** (рекомпозируются только читающие).
- `staticCompositionLocalOf` — чтения **не отслеживаются** (при смене рекомпозируется всё поддерево, зато чтение дешевле). Для почти неизменных (`LocalContext`, `LocalDensity`).
- Подводный камень: это неявная зависимость (Service Locator для UI) — злоупотреблять нельзя.

### [[Compose. Composer and Snapshot]]
`Composer` управляет композицией (регистрирует и выполняет `@Composable`, отслеживает зависимости, запускает рекомпозицию), а `Snapshot` — слой состояния, фиксирующий изменения `mutableStateOf`. Одной фразой: Snapshot = «что изменилось», Composer = «что с этим делать в UI»; связь через `SnapshotObserver`.

### [[Compose. Snapshot]]
Основной механизм управления состоянием — транзакционная система, отслеживающая «что изменилось» и «кто зависит»; `mutableStateOf` создаёт `StateRecord` в глобальном Snapshot.
- Чтение `.value` внутри `@Composable` регистрирует подписку → рекомпозиция.
- Оптимизации: группировка через `withMutableSnapshot { }`, откат через `takeSnapshot`/`restore`, отложенное применение через `apply()`.
- Работает в связке со Slot Table. Аналогия для собеса: MVCC-подобная (как в БД) система версий — отсюда потокобезопасность `mutableStateOf`.

### [[Compose. Snapshot 1]]
Дополнение с акцентом на **Copy-on-Write** и многопоточность: изменение создаёт локальную приватную копию снапшота, которая при `apply()` атомарно сливается с глобальным.
- Несколько потоков меняют `MutableState` в своих снапшотах; конфликт разрешается стратегией Last Write Wins.
- `Snapshot.withMutableSnapshot { }` группирует изменения атомарно; `takeSnapshot()` + `restore()` даёт откат.

### [[Compose. Slot api]]
Паттерн публичного API: передача `@Composable`-лямбд внутрь компонента как слотов (по сути «Стратегия»/«Композиция»). Примеры: `Scaffold` (`topBar`, `floatingActionButton`), `TopAppBar`, `Surface`, `Box`. Не путать со Slot Table.

### [[Compose. Slot table]]
Внутренняя линейная структура runtime, хранящая порядок вызовов `@Composable`, их параметры и состояния (`remember`) — обеспечивает частичную рекомпозицию.
- Структура **позиционная**: состояние идентифицируется по позиции вызова, а не по содержимому.
- Отсюда — нельзя условно «сдвигать» порядок вызовов (для этого `key(id) { }`), а в `LazyColumn` обязателен `items(list, key = { it.id })`, иначе состояние «прилипнет» не к тому элементу.

### [[Compose. SubcomposeLayout]]
Низкоуровневый layout с отложенной композицией в **две фазы**: сначала измеряет одни элементы, затем докомпозирует другие с учётом размеров.
- Дороже обычного `Layout` — применять только когда размер одного элемента реально зависит от измерения другого.
- Заметка разбирает также кастомный `Layout` (`measure` → `place`) и **интринзики** (`minIntrinsicWidth` и т.п.).
- Под капотом используют: `LazyColumn`, `ConstraintLayout`, `BoxWithConstraints`, `Pager`.

### [[Compose. Анимации]]
Уровни: `animate*AsState()` (простые значения), `updateTransition()` (несколько параметров), `Animatable` (ручное/жестовое), `animateItem()` (списки), `rememberInfiniteTransition()` (бесконечные).
- `Modifier.animateItemPlacement()` устарел → `animateItem()`; нужен стабильный `key` в `items`.
- Ещё спрашивают: `AnimatedVisibility`, `Crossfade`, `AnimatedContent`.
- Производительность: анимировать `alpha`/`scale`/`translation` через `Modifier.graphicsLayer { }` — меняется только фаза Draw.

### [[Compose. Стабильность]]
Стабильный тип — предсказуемый, с корректным `equals`, позволяет Compose пропускать рекомпозицию (`@StabilityInferred`, поле `$stable`).
- Стабильны: примитивы, `String`, лямбды, классы со всеми `val`-полями стабильных типов, `enum`, помеченные `@Immutable`/`@Stable`.
- Нестабильны: классы с `var`-полем и всё из модулей без Compose-компилятора — `List`/`Set`/`Map` (это интерфейсы!), `Flow`, `LocalDate`; лечится `kotlinx.collections.immutable`, обёртками, аннотациями.
- Лямбды с захватом нестабильной/`var`-переменной пересоздаются → рекомпозиция даже skippable-функции.
- `@Immutable` = неизменяемый; `@Stable` = может меняться, но сам оповещает.

### [[Compose. Оптимизация]]
- Главные принципы: defer reads (читать состояние ниже по дереву); Compose пропускает рекомпозицию только для стабильных параметров (проверять compiler metrics: `stable`/`skippable`).
- Частые изменения и анимации выносить на фазы Layout/Draw (`graphicsLayer`, `drawBehind`).
- Не создавать объекты (лямбды/списки) в теле composable без `remember`.
- `key()` в списках и стабильные `key` в `LazyColumn` — для переиспользования узлов.

### [[KPI]]
Шпаргалка по стабильности/рекомпозиции: списки стабильных/нестабильных типов, `@Immutable`/`@Stable`, `List` стабильным через `@JvmInline value class`, инструменты диагностики.
- **Strong Skipping Mode** включён по умолчанию с Kotlin 2.0.20+ — функции с нестабильными параметрами тоже становятся skippable (сравнение по ссылке), лямбды с захватом оборачиваются в `remember` автоматически.
- `rememberUpdatedState` принимает **значение**, а не лямбду; нужен, чтобы долгоживущий эффект видел актуальное значение без перезапуска.
- Best practice: выносить часто меняющиеся поля из больших стейтов; не оборачивать дешёвые вычисления в `remember`.

## 🤖 Android

### [[Android]]
Архитектура ОС слоями: ядро Linux → HAL → нативные библиотеки → **ART** → Application Framework → приложения. Сборка: Kotlin/Java → `.class` → `.dex` (D8) → минификация/обфускация (R8) → APK → подпись → zipalign.
- **ART**: AOT-компиляция (`dex2oat`) + JIT + профилирование; раньше Dalvik (только JIT). Процессы из **Zygote** (copy-on-write).
- **APK vs AAB:** в Play публикуют App Bundle, Play генерирует оптимизированные APK под устройство. D8 — дексер, R8 — дексер + минификатор.

### [[Activity и Fragment]]
ЖЦ `Activity` (`onCreate`→`onStart`→`onResume`→`onPause`→`onStop`→`onDestroy`) и `Fragment` схожи, но у фрагмента два ЖЦ — собственный и ЖЦ его View (`onCreateView`…`onDestroyView`), поэтому подписки на UI вешают на `viewLifecycleOwner`.
- При повороте оба пересоздаются → состояние держи в `ViewModel`/`SavedStateHandle`.
- У фрагмента должен быть **публичный пустой конструктор** (иначе краш при восстановлении).
- `onDestroy` может не вызваться: убийство процесса, Force Stop, `finish()` в `onCreate`.
- Современно — single-Activity + фрагменты/Compose. Флаги (`FLAG_ACTIVITY_NEW_TASK`, `CLEAR_TOP`, `SINGLE_TOP`) управляют стеком.

### [[Activity, Service,  Broadcast Receiver,  Content Provider]]
`Activity` — экран UI; `Service` — фоновая работа без UI (started/bound/foreground); `BroadcastReceiver` — реакция на события (`onReceive` на главном потоке, коротко); `ContentProvider` — общий доступ к данным через `ContentResolver`/URI.
- Все, кроме `Application`, регистрируются в манифесте и являются точками входа под управлением системы.
- `onStartCommand` возвращает `START_STICKY`/`START_NOT_STICKY`/`START_REDELIVER_INTENT` и работает на **главном потоке**.
- Foreground service требует `startForeground` + `foregroundServiceType` (обязателен с Android 14) + рантайм-разрешение.
- Устарели: `JobIntentService`, `LocalBroadcastManager` — замена WorkManager и `Flow`.

### [[Context]]
Абстрактный класс — доступ к ресурсам, системным сервисам, компонентам, файлам/БД. Правило: **UI → Activity-контекст, всё долгоживущее → Application-контекст**.
- Хранение `Activity`-контекста в синглтоне/static = **утечка**.
- Для `Toast`, `Dialog`, `LayoutInflater`, `startActivity` без `NEW_TASK` — Activity-контекст (несёт тему и окно). Для Room/DataStore — `applicationContext`.
- Наследники: `ContextWrapper`, `ContextThemeWrapper` (от него `Activity`), `Application`, `Service`. В домен/VM `Context` не таскать — за `ResourceProvider` + DI.

### [[Intent]]
Объект-намерение для запуска компонентов и передачи данных. **Явный** — указан класс (навигация внутри приложения); **неявный** — указано действие (`ACTION_VIEW`) + данные, систему просим найти обработчик по `intent-filter`.
- Составляющие: Action, Data (URI), Category, Extras, Component, Flags.
- С Android 11+ для неявных нужен `<queries>` в манифесте; `startActivity` может бросить `ActivityNotFoundException`.
- **`PendingIntent`** с Android 12+ **обязательно** требует `FLAG_IMMUTABLE` или `FLAG_MUTABLE`.

### [[Что такое Manifest]]
`AndroidManifest.xml` — обязательный конфигурационный файл: объявляет компоненты, разрешения (`uses-permission`), тему/иконку, точку входа (`intent-filter` с `MAIN`/`LAUNCHER`), фичи устройства.
- `<permission>` объявляет своё разрешение, `<uses-permission>` запрашивает существующее.
- **`android:exported` обязателен с API 31** для компонентов с `intent-filter` (иначе не соберётся; незакрытый exported — дыра безопасности).
- Manifest merging склеивает манифесты app+библиотек+флейворов. Runtime-разрешения объявляют в манифесте, но запрашивают в рантайме.

### [[Jetpack Navigation]]
Один `NavController` управляет переходами и **единым back stack** по объявленному графу (`NavGraph`), отображаемому в `NavHost`.
- Fragment-навигация — граф в XML + Safe Args; Navigation Compose — граф в коде, маршруты строками.
- **Type-safe navigation (2.8+)** на `@Serializable`-классах — компилятор проверяет типы аргументов.
- Аргументы идут через `Bundle` — передавать id, а не тяжёлые модели. В KMP — Decompose/Voyager.

### [[Передача данных между фрагментами]]
Способы: `Bundle` через `arguments` (аргументы при создании), **Fragment Result API** (`setFragmentResult`/`setFragmentResultListener` — замена `startActivityForResult`), **shared ViewModel** через `by activityViewModels()`.
- Лимит транзакции Binder ~1 МБ — тяжёлые данные через Bundle не передавать (передавать id).
- Антипаттерны: каст `requireActivity() as MainActivity` (жёсткая связанность) и SharedPreferences.

### [[AndroidViewModel vs ViewModel]]
`ViewModel` — по умолчанию, не знает про `Context` (проще тестировать); `AndroidViewModel` даёт `Application`-контекст (не течёт).
- Даже `AndroidViewModel` — не лучшая практика: `Context`/ресурсы прячут за репозиторием + DI.
- Шаринг между фрагментами — `by activityViewModels()`; хранить VM синглтоном в `Application` — антипаттерн (нет `onCleared`, утечки).

### [[ViewModel, SaveStateHandle, SavedStateRegistryOwner]]
Три уровня сохранения: **ViewModel** переживает поворот (через `ViewModelStore`), но НЕ смерть процесса; **SavedStateHandle** = ViewModel + переживание смерти процесса (под капотом `SavedStateRegistry` → `Bundle`); **`onSaveInstanceState`/`SavedStateRegistry`** — низкоуровневый механизм-основа.
- `ViewModelProvider(this)` берёт `ViewModelStore`; при финальном уничтожении → `onCleared()`.
- Современно: `by viewModels()` сам даёт `SavedStateHandle`; с Hilt — `@HiltViewModel` + `@Inject constructor(SavedStateHandle)`.

### [[Сохранение состояние в android и Bundle]]
`Bundle` — контейнер пар ключ(String)-значение; сериализуется, живёт в RAM, не для больших данных (`TransactionTooLargeException`).
- Эталон: **эфемерное UI → SavedInstanceState/rememberSaveable; состояние экрана → ViewModel; пережить смерть процесса → SavedStateHandle; навсегда → Room/DataStore**.
- **SharedPreferences: `apply()` = async (рекомендуется), `commit()` = sync с `Boolean`** — частая путаница.
- `configChanges` отключает пересоздание (ломает подмену ресурсов, оправдан для видеоплеера/WebView).

### [[Parcelable vs Serializable]]
`Serializable` — Java-интерфейс-маркер через **рефлексию** (медленно, мусор → нагрузка на GC), кросс-платформенный. `Parcelable` — Android-интерфейс для IPC через Binder, быстрый (прямая запись в память), но требует бойлерплейта.
- На практике `Parcelable` пишут через плагин **`@Parcelize`**, а не руками.
- В `Bundle`/`Intent`/Navigation — предпочтительно `Parcelable`.

### [[Custom view]]
Три фазы: `onMeasure` (обязательно `setMeasuredDimension`) → `onLayout` (расставить детей, только `ViewGroup`) → `onDraw` (`Canvas`).
- **MeasureSpec** = режим + размер в одном `Int`. Режимы: `EXACTLY` (`match_parent`/dp), `AT_MOST` (`wrap_content`), `UNSPECIFIED`.
- `invalidate()` → перерисовка (`onDraw`); `requestLayout()` → пересчёт размеров — не путать.
- Производительность `onDraw`: не создавать `Paint`/`Path`/`Bitmap` внутри. Утечки — отписка в `onDetachedFromWindow()`. Атрибуты — `obtainStyledAttributes(...).recycle()`, `@JvmOverloads`.

### [[EditText]]
`EditText` автоматически сохраняет текст при пересоздании через встроенные `onSaveInstanceState`/`onRestoreInstanceState`.
- **Работает только при наличии `android:id`** (он ключ в `Bundle`); при дублирующихся id ломается.
- Не сохраняет при обычном закрытии экрана. Бизнес-данные (черновик) держи в `ViewModel`/`SavedStateHandle`.

### [[RecyclerView, Diff Utils, List Adapter]]
`RecyclerView` переиспользует `ViewHolder` (паттерн ViewHolder убирает повторный `findViewById`). Части: ViewHolder, Adapter, LayoutManager, Recycler.
- **`notifyDataSetChanged()` — плохо**; лучше `ListAdapter` + `submitList` (diff в фоне) или точечные `notifyItemXxx`.
- **DiffUtil**: `areItemsTheSame` (по стабильному id) + `areContentsTheSame`. Не путать `DiffUtil.ItemCallback` (для `ListAdapter`) и `DiffUtil.Callback` (для ручного `calculateDiff`).
- Не оборачивать в `ScrollView` (теряется переработка); для смешанного контента — `ConcatAdapter`/несколько viewType.

### [[Recycler. ViewPool, PayLoads]]
`RecycledViewPool` **шарит пул `ViewHolder` между несколькими RecyclerView**, можно `setMaxRecycledViews`. **Payloads** — частичное обновление одного поля item через `getChangePayload` + `onBindViewHolder(holder, position, payloads)`.
- Несколько типов — через `getItemViewType` либо библиотека **AdapterDelegate** (каждый тип = свой делегат).
- **`setHasFixedSize(true)`** НЕ про одинаковый размер элементов, а про то, что габариты RecyclerView не зависят от контента (экономит `requestLayout`); нельзя при `wrap_content`.

### [[Анимации в Android]]
Три семейства: **View Animation** (XML scale/rotate/alpha) — анимирует только «обманку», реальные свойства и тач-зоны не двигает (устарело); **Property Animation** (`ObjectAnimator`/`ValueAnimator`/`ViewPropertyAnimator`) — меняет реальные свойства (стандарт); **Transitions/MotionLayout**.
- Ключевое: View Animation vs Property Animation (обманка vs реальное движение).
- `ViewPropertyAnimator` (`view.animate()`) — удобнее для одной View (через RenderThread). В Compose иначе.

### [[Choreographer, SurfaceFlinger]]
`Choreographer` синхронизирует рендеринг UI с VSYNC (`postFrameCallback`/`doFrame`); `SurfaceFlinger` — системный сервис композитинга слоёв через Hardware Composer.
- Конвейер: **VSYNC → Choreographer → UI Thread (measure/layout/draw → DisplayList) → RenderThread (GPU) → BufferQueue → SurfaceFlinger + HWC → дисплей**.
- **Jank** = не успели за период VSYNC (>16 мс при 60 Гц); причины — тяжёлый UI-поток, лишние measure/layout, аллокации в `onDraw`.

### [[Render Thread]]
Отдельный поток для рендеринга графики (с Android 4.0+): UI-поток строит **DisplayList**, а RenderThread превращает его в команды GPU, разгружая главный поток.
- Некоторые анимации (`ViewPropertyAnimator`, `RippleDrawable`) идут плавно, даже если UI-поток занят.
- Связка: Choreographer → UI Thread → RenderThread → SurfaceFlinger.

### [[Вызов в потоке UI]]
UI можно трогать только из главного потока (иначе `CalledFromWrongThreadException`). Способы: `Handler(Looper.getMainLooper()).post{}` (legacy), `runOnUiThread{}` (в Activity), `View.post{}` (ещё и после layout — для размеров).
- Современно — корутины: `withContext(Dispatchers.Main)`, `lifecycleScope`/`viewModelScope`, `Flow.collect` на главном потоке.

### [[Плотность экрана в Android]]
Плотность меряется в `dpi` (пикселей на дюйм); чтобы UI выглядел одинаково на разных экранах, размеры задают в `dp` (density-independent pixels), а не `px`.
- Baseline — `mdpi` (160 dpi), где `1 dp = 1 px`; формула `px = dp * (dpi / 160)` = `dp * density`.
- Корзины (множитель к mdpi): `ldpi` 0.75 · `mdpi` 1.0 · `hdpi` 1.5 · `xhdpi` 2.0 · `xxhdpi` 3.0 · `xxxhdpi` 4.0 (ресурсы иконок в соотношении 3:4:6:8:12:16).
- На практике берут `displayMetrics.density` (реальный множитель, точнее «корзины» `densityDpi/160`). Текст — в `sp` (dp с учётом `fontScale`).
- В Compose `dp`/`sp` — единицы первого класса (`16.dp`, `14.sp`), перевод прячется за `LocalDensity.current`.

### [[Coil]]
Coroutine Image Loader — Kotlin-библиотека загрузки картинок на корутинах (замена Glide/Picasso), с Coil 3 мультиплатформенная; интегрируется с Compose (`AsyncImage`).
- **Downsampling** (декод под размер View) — главная защита от OOM.
- Двухуровневый кэш: memory (`LruCache` bitmap) + disk (закодированные байты).
- Отменяет незавершённую загрузку при переиспользовании `ViewHolder`/уходе composable.

### [[Exo player]]
Медиаплеер от Google (адаптивный стриминг HLS/DASH, DRM, кэширование). Живёт теперь в **`androidx.media3`** (старый `com.google.android.exoplayer2` не развивается).
- Обязательно `player.release()` в `onStop`/`onDestroy` (или `DisposableEffect`) — иначе утечка и удержание аудио-фокуса.
- Компоненты: `ExoPlayer`, `MediaItem`, `MediaSource`, `TrackSelector`, `PlayerView`. Фон — `MediaSessionService` + `MediaSession`.

### [[Retrofit]]
Библиотека REST-запросов: API описываешь интерфейсом с аннотациями (`@GET`), `retrofit.create()` через **Java Dynamic Proxy** генерирует реализацию, запрос выполняет **OkHttp**, ответ конвертирует Converter (Gson/Moshi/kotlinx.serialization).
- Современно — **suspend-функции** (`suspend fun getData(): MyResponse` или `Response<T>`), Retrofit сам уводит с главного потока.
- Таймауты, логирование, авторизация, повторы — **OkHttp-интерцепторы** (`addInterceptor`), а не Retrofit.

### [[Room]]
ORM поверх SQLite: `@Database` (наследует `RoomDatabase`, сущности + версия), `@Entity` (таблица), `@Dao` (интерфейс доступа).
- Главное преимущество над голым SQLite — **проверка SQL на этапе компиляции** + автогенерация бойлерплейта.
- `suspend`-функции DAO выполняются вне главного потока; `Flow<List<T>>` — реактивный (эмитит при изменении таблицы).
- **Миграции:** поднимаешь `version` + `Migration`, иначе `fallbackToDestructiveMigration()` сотрёт данные. `@Transaction`, `@TypeConverters`.

### [[Room or SharedPreferences]]
**Room** — структурированные/большие данные, связи, запросы, кэш API; **SharedPreferences** — простые пары ключ-значение (настройки, флаги, токен).
- `SharedPreferences` устарел → **DataStore**. Проблемы старого: `commit()` блокирует, `apply()` может терять данные при краше, нереактивность.
- Большие файлы/медиа — файловое хранилище, не БД.

### [[DataStore]]
Современная замена `SharedPreferences`: полностью асинхронный (корутины + `Flow`), безопасен на main, транзакционные `suspend`-записи. Два вида: **Preferences** (ключ-значение) и **Proto** (типизированный объект по protobuf).
- Чинит боли SharedPreferences: `commit()` блокирует, `apply()` может терять данные, блокировка main при первом чтении, нереактивность.
- Грабли: один экземпляр на файл; это не БД (для больших данных — Room); синхронно не прочитать, только через `Flow`/`first()`.

### [[WorkManager]]
Jetpack-библиотека для **гарантированной** отложенной/фоновой работы, переживающей перезапуск (состояние в Room, под капотом JobScheduler/AlarmManager). Для deferrable + guaranteed задач, НЕ для «прямо сейчас» (корутины) и не для realtime-трекинга (foreground service).
- `Result`: `success`/`failure`/`retry` (с `BackoffPolicy`). Constraints (сеть, зарядка). Периодическая — минимум **15 минут**. Цепочки, уникальность (`enqueueUniqueWork`).
- В Doze/Standby откладывается; вендорские «убийцы» батареи могут убивать фон. `CoroutineWorker.doWork()` — suspend; DI — `HiltWorker`.

### [[Standby Bucket + Doze Mode]]
**App Standby Bucket** (Android 9) распределяет **приложение** по 5 категориям (Active/Working Set/Frequent/Rare/Restricted) по частоте использования; **Doze Mode** (Android 6) срабатывает, когда **устройство** неактивно — откладывает фон/сеть/AlarmManager/WakeLock до «окон обслуживания».
- Обход для важного: **Foreground Service**, **FCM high-priority**, `setExactAndAllowWhileIdle`, whitelist оптимизации батареи.
- Практический вывод: надёжный фон — **WorkManager**, срочная доставка — FCM, длительная работа — foreground service.

### [[Приоритеты процессов]]
Процессы по убыванию приоритета (система убивает снизу вверх): **Foreground** (видимый активный) → **Visible** (`Activity` в `onPause`, foreground-сервис) → **Service** (`startService`) → **Cached/Background** (все `Activity` в `onStop`) → **Empty**.
- Канонически выделяют 5 уровней; чем выше приоритет, тем позже убьют.

### [[Dagger 2]]
Compile-time DI: генерирует код и проверяет граф зависимостей **на этапе компиляции**. Ключевое: `@Module`/`@Provides`, `@Component`, `@Inject`, `@Binds`, `@Scope`/`@Singleton`, `@Qualifier`.
- **`@Binds` vs `@Provides`:** `@Binds` (абстрактный, связывает интерфейс↔реализацию) генерирует меньше кода; `@Provides` — когда объект нужно сконструировать руками.
- `@Scope` (`@Singleton`) — один экземпляр в пределах компонента. `@Qualifier` — различать биндинги одного типа.
- Сейчас поверх Dagger обычно **Hilt**.

### [[Hilt]]
Официальная DI-библиотека Google поверх Dagger 2: готовые компоненты, привязанные к ЖЦ Android (`@HiltAndroidApp`, `@AndroidEntryPoint`, `@HiltViewModel`), убирает ручное `@Component`/`inject()`.
- Компоненты/скоупы: `SingletonComponent`/`@Singleton`, `ViewModelComponent`/`@ViewModelScoped`, `ActivityComponent`/`@ActivityScoped`. Модули — через `@InstallIn`.
- Compile-time проверка графа (в отличие от Koin — рантайм). Только JVM/Android (для общего KMP-кода не подходит). Воркеры — `@HiltWorker`.

### [[Свой DI на коленке]]
Как написать простейший DI-контейнер на `MutableMap`: регистрируешь (`register`) и достаёшь по типу (`resolve`); улучшенные версии добавляют ленивую инициализацию через provider-лямбды и авто-инъекцию через делегат (`inline`+`reified` + `by inject`).
- Важный нюанс: строго говоря это **Service Locator**, а не DI — объект сам «вытягивает» зависимость из контейнера (скрытая зависимость, сложнее тестировать). Настоящий DI передаёт зависимости снаружи через конструктор.
- Подводные камни: `as T` — unchecked cast из-за стирания типов; `mutableMapOf` не потокобезопасен (нужен `ConcurrentHashMap`); нет скоупов и управления жизненным циклом.
- В проде: Dagger/Hilt (кодогенерация, compile-time) или Koin (рантайм, по духу как раз такой «DI на коленке»).

### [[BuildType, BuildFlavour, BuildVariant]]
`BuildType` (как собирать: debug/release), `BuildFlavor` (варианты приложения: free/paid, dev/prod), `BuildVariant = BuildType × Flavor`.
- Код/ресурсы под флейвор/тип кладут в `src/<flavor>/`, `src/<buildType>/` — мёржатся поверх `src/main/`.
- `buildConfigField`/`BuildConfig` в AGP 8+ требуют `buildFeatures { buildConfig = true }`. `flavorDimensions` обязателен. `minifyEnabled`/`shrinkResources` обычно только в release.

### [[Gradle build-оптимизация]]
Три фазы сборки: **initialization → configuration** (выполняет build-скрипты, строит граф задач) **→ execution**. **Configuration cache** ускоряет фазу configuration, **build cache** — фазу execution (кэширует выходы по хэшу входов) — это разные кэши.
- **Remote build cache** шарит выходы между CI и командой.
- Прочие рычаги: `org.gradle.parallel`, Gradle Daemon, **KSP вместо kapt**, K2-компилятор, модуляризация, version catalogs. Измерять — `--profile`, Build Scan.

### [[R8, ProGuard, обфускация]]
При release `minifyEnabled` включает **R8** (заменил ProGuard, всё за один проход): shrinking (tree shaking), optimization, obfuscation, desugaring. Правила — `proguard-rules.pro`.
- **Keep-правила** нужны для классов через рефлексию/имена строк (модели сериализации, JNI, манифест) — иначе R8 удалит/переименует.
- Обфускация ломает стектрейсы → хранить **`mapping.txt`** (каждая сборка своя). Обфускация — не шифрование, не защита секретов.

### [[Безопасность в Android]]
Модель: каждое приложение — отдельный Linux-UID со своей песочницей, IPC только через явные механизмы, permissions ограничивают доступ.
- **Хранение секретов:** ключи — в **Android Keystore** (ключ не покидает TEE/StrongBox), токены — `EncryptedSharedPreferences`/зашифрованный DataStore, гейт — `BiometricPrompt`.
- **Нельзя:** хардкодить API-ключи в коде/`BuildConfig` (APK декомпилируется), хранить токены в обычных SharedPreferences, доверять клиенту.
- **Сеть:** certificate/public-key pinning от MITM; с Android 9 cleartext HTTP запрещён по умолчанию. Play Integrity, `FLAG_SECURE`, осознанный `android:exported`.

### [[Разница в SDK]]
`minSdk` — минимальная версия запуска; `targetSdk` — версия, под поведение которой заточено приложение (определяет behavior changes); `compileSdk` — против какого SDK компилируем.
- Повышение `targetSdk` = про **behavior changes**: `POST_NOTIFICATIONS` (33), Scoped Storage (11), mutable/immutable `PendingIntent` (12), обязательные foreground service types (14–15), edge-to-edge (16).
- Google Play обязывает поднимать `targetSdk` (обычно «текущая −1») для публикации обновлений.

### [[ML Kit Barcode Scanning в Android]]
Локальное (офлайн) сканирование штрих/QR-кодов от Google: захват через CameraX/Camera2 → `InputImage` → `BarcodeScanning.getClient().process()` → `barcode.rawValue`.
- В CameraX-анализаторе **обязателен `imageProxy.close()`**, иначе конвейер кадров зависнет.
- Ограничивай форматы через `BarcodeScannerOptions` (`FORMAT_QR_CODE`). Готовый сканер без своего UI — `play-services-code-scanner`.

## 🏛 Архитектура

### [[SOLID]]
Пять принципов проектирования для гибкого и тестируемого кода.
- `S` — один класс = одна ответственность (антипример `Context`).
- `O` — расширяем через новые классы, а не правку существующих (`AdapterDelegates` вместо `when` по типу).
- `L` — наследник не ломает контракт родителя («квадрат/прямоугольник»).
- `I` — много маленьких интерфейсов лучше одного «толстого» (антипример `TextWatcher`).
- `D` — зависим от абстракций, зависимости получаем извне. `DIP` — принцип, `DI` — техника его реализации.

### [[Чистая архитектура]]
Разделение на слои для тестируемости: `Presentation` (Activity/Fragment/ViewModel), `Domain` (Use Cases, бизнес-логика), `Data` (Repositories, remote/local).
- Главное — правило зависимостей (Dependency Rule): зависимости направлены только внутрь, к домену; `Domain` не знает ни о ком.
- Интерфейс репозитория объявлен в `Domain`, реализация — в `Data` (развёрнутая стрелка = `DIP`); у каждого слоя свои модели (`UserDto` ↔ `User` ↔ `UserUi`) с мапперами.
- Подводные камни: `UseCase` иногда опускают на простых экранах (VM → Repository напрямую); для маленьких приложений вся Clean Architecture — оверкилл.

### [[Отличия MVI от MVVM,  MVC]]
- `MVC` — Controller в Android сливается с View (`Activity`/`Fragment`), отсюда «God Activity»; поток двунаправленный.
- `MVVM` — ViewModel не знает о View, отдаёт состояние через `StateFlow`/`LiveData`; минус — состояние размазано по нескольким полям → рассинхрон.
- `MVI` — развитие MVVM: единый неизменяемый `State` + `reducer` (чистая функция), строго однонаправленный поток `Intent → State → View`; минус — бойлерплейт.
- Ловушки: `launchWhenStarted` устарел (`repeatOnLifecycle`), `viewModelFactory { initializer {} }`.

### [[UDF (Unidirectional Data Flow)]]
Однонаправленный поток данных — принцип, лежащий в основе MVI и рекомендованного Google подхода к Compose.
- Два правила: `State` течёт вниз (UI только отображает), события текут вверх; `UI = f(state)`.
- Выгоды: single source of truth, предсказуемость, тестируемость, естественная укладка на рекомпозицию.
- Антипаттерны: мутабельный state в публичном API (`MutableStateFlow` наружу), состояние размазано по View, логика в composable.
- `MVI` реализует UDF строже всего; `MVVM` может быть UDF (один `StateFlow<UiState>`) или нет.

### [[MVI библиотеки]]
Готовые MVI-решения, когда самописный `StateFlow` + `onEvent` перерастает себя, с акцентом на `KMP`.
- Библиотеки: `Decompose` (компоненты + навигация), `MVIKotlin` (классический Store), `Orbit MVI` (лёгкий), `Ballast` (time-travel) — все мультиплатформенны.
- Тонкость: `State` идемпотентен, а одноразовые события (навигация, тост) нельзя класть в state — иначе повторятся при повороте; для них отдельный канал (`Label`/`Channel`).
- Частая связка в KMP: `Decompose` + `MVIKotlin`. Не тащить библиотеку на простом экране.

### [[Модуляризация]]
Разбиение приложения на независимые Gradle-модули — ключевая тема на Senior.
- Выгоды: скорость сборки (кэш и параллелизм), изоляция и чистые границы, переиспользование, разделение между командами.
- Стратегии: by layer (плохо масштабируется), by feature, рекомендуемый гибрид (feature-модули + `:core_*`).
- Паттерн `API/IMPL`: фичи зависят от контракта (`:feature_x_api`), а не от реализации — это `DIP` на уровне модулей.
- Нюансы: `implementation` не протекает транзитивно (в отличие от `api`), version catalogs, convention plugins; избегать циклов и God-модуля.

### [[DI VS SERVICE LOCATOR]]
Оба — частные случаи `IoC`.
- `Service Locator` — объект сам «вытягивает» (pull) зависимость из глобального локатора; `DI` — зависимости «проталкивают» (push) извне через конструктор.
- Главный минус Service Locator: скрытые зависимости — по сигнатуре не видно, что нужно классу.
- Сегодня Service Locator считают антипаттерном; `DI` предпочтительнее.
- В Android: `Hilt`/`Dagger` (compile-time) vs `Koin` (Service-Locator-подобный, рантайм).

### [[Отличия между Service Locator и Dependency injection.]]
Краткий дубль темы DI vs Service Locator (подробно — [[DI VS SERVICE LOCATOR]]).
- Три вида DI: конструктор (предпочтительный), сеттер/свойства, интерфейс; DI — реализация принципа `IoC`.
- Ключевой тезис: DI делает зависимости явными, Service Locator их скрывает.

### [[Паттерны]]
Обзор паттернов GoF.
- Классификация: порождающие (Фабрика, Строитель, Синглтон), структурные (Компоновщик, Декоратор, Адаптер, Фасад, Прокси), поведенческие (Стратегия, Наблюдатель, Команда).
- Часто спрашивают: Компоновщик, Декоратор (соблюдает `OCP`), Фабрика (`SRP`), Строитель, Стратегия (убирает `if/when`).
- Где в Android: Строитель — `AlertDialog.Builder`; Фабрика — `ViewModelProvider.Factory`; Декоратор — `ContextWrapper`; Стратегия — `Comparator`; Компоновщик — дерево `View`/`ViewGroup`.

### [[Примеры декораторов]]
Кэширующий репозиторий поверх сетевого: `CachedUserRepository` оборачивает `NetworkUserRepository` (тот же интерфейс), добавляя `LruCache`: сначала кэш, сеть только при промахе.
- Декоратор vs наследование: добавляет поведение в рантайме, комбинируется (`Logging(Cache(Network()))`) без комбинаторного взрыва подклассов, соблюдает `OCP`. По этому принципу устроен `ContextWrapper`.

### [[Примеры стратегии]]
Выбор поведения в рантайме: стратегии авторизации (Google/Email/Facebook через `AuthStrategy`), загрузки изображений (Glide/Picasso/Coil), контекст хранит ссылку на стратегию и меняет через сеттер.
- Идиома Kotlin: при одном методе стратегию задают функциональным типом (лямбдой), а не интерфейсом — та же Стратегия без бойлерплейта; интерфейс нужен при нескольких методах или состоянии.

## ⚡ Performance

### [[Performance. Обзор и метрики]]
На Senior спрашивают не «что тормозит», а как измерить. Главное правило — сначала измерь, потом оптимизируй.
- Три кита: запуск (startup), плавность (rendering/`jank`), память.
- Типы запуска: cold (нет процесса, самый дорогой), warm (Activity пересоздаётся), hot (Activity в памяти).
- Метрики запуска: `TTID` (до первого кадра), `TTFD` (до готового контента, `reportFullyDrawn()`); цель cold start < 500 мс.
- `jank`: бюджет кадра 60 fps ≈ 16.6 мс, 120 fps ≈ 8.3 мс; Play Console штрафует slow frames (>16 мс) и frozen frames (>700 мс).
- Инструменты: Android Studio Profiler, `Perfetto`, `Macrobenchmark`, `LeakCanary`, Android Vitals. Lab data (CI) vs Field data (реальные юзеры).

### [[Performance. Рендеринг, jank и Macrobenchmark]]
Цель — уложить каждый кадр в бюджет (60 fps → 16.6 мс, 120 fps → 8.3 мс).
- Путь кадра: Input → Animation → Measure/Layout → Draw → Sync → RenderThread (GPU) → Display; `VSYNC` синхронизирует через `Choreographer`, `SurfaceFlinger` композитит слои.
- Причины `jank`: тяжёлая работа на главном потоке, overdraw, лишние рекомпозиции, аллокации в горячем цикле, синхронный `inflate`, декодирование bitmap на UI-потоке.
- `Macrobenchmark` — воспроизводимые замеры startup/scroll «снаружи» через UiAutomator, для CI; метрики `StartupTimingMetric`, `FrameTimingMetric` (P50/P90/P99).
- `Macrobenchmark` (целое приложение снаружи) vs `Microbenchmark` (изолированная «горячая» функция). Причину регрессии ищут в `Perfetto`; разметка `trace("MySection") { }`.

### [[Performance. Память и утечки]]
Утечка — когда ненужный объект удерживается цепочкой сильных ссылок от GC root; ведёт к росту памяти, частым GC (паузы → `jank`) и `OutOfMemoryError`.
- Топ причин: `Activity` в долгоживущем объекте (лечится `applicationContext`); `inner`/анонимные классы и колбэки (`Handler`); неотписанные подписки; корутины в `GlobalScope`; ссылки на `View`/`Fragment` во ViewModel.
- `LeakCanary` (debug): держит `WeakReference` после `onDestroy`, запускает GC, при живом объекте снимает heap dump и строит leak trace.
- Аллокации в горячих местах (`onDraw`, `onBindViewHolder`, draw-фаза Compose) избегать. Bitmap — главный пожиратель (ширина×высота×4 байта для ARGB_8888); `largeHeap` — симптом, не лечение.

### [[Performance. Оптимизация Compose]]
Перформанс Compose = минимум лишних рекомпозиций + дешёвые фазы Layout/Draw. Читать `State` как можно позже.
- Три фазы: Composition → Layout → Draw. Лямбда-версии (`Modifier.offset { }`, `graphicsLayer { }`) читают state в Layout/Draw, минуя рекомпозицию.
- Сокращают рекомпозиции: стабильные типы, `key` в `LazyColumn`, `derivedStateOf`, стабильные лямбды, вынос часто меняющегося параметра из большого `data class`.
- Измерение: Layout Inspector, Compose Compiler Reports, `Macrobenchmark` + `FrameTimingMetric`.
- Подводный камень: НЕ мерить перформанс в debug — только release (`R8` + `Baseline Profile`).

### [[Performance. Baseline и Startup Profiles]]
`Baseline Profile` (`baseline-prof.txt`) — список важных для запуска классов/методов, которые `ART` компилирует в нативный код (`AOT`) при установке, минуя медленный старт «интерпретация + `JIT`».
- Эффект: до ~30% ускорения холодного старта и меньше `jank` в первых прокрутках; профиль пакуется в APK/AAB.
- Генерируется тестом с `BaselineProfileRule` в модуле `:baselineprofile`.
- `Startup Profiles` — подмножество для старта; `Cloud Profiles` от Play агрегируют профили реальных юзеров.
- Подводный камень: НЕ уменьшает работу при старте (если в `Application.onCreate()` грузится «полмира» — нужен ленивый `App Startup`). Проверка эффекта — `Macrobenchmark` (`CompilationMode.None()` vs `Partial()`).

## 📱 KMP

### [[KMP]]
Технология JetBrains для переиспользования Kotlin-кода между платформами при сохранении **нативного UI и интеграции**; стабильна с **Kotlin 1.9.20 (ноябрь 2023)**.
- Делим логику (сеть, парсинг, бизнес-логику, модели, use-case'ы, БД, репозитории, часто ViewModel), не делим UI; UI шарится опционально через Compose Multiplatform.
- Компиляция: Kotlin/JVM (Android), Kotlin/Native через LLVM (`.framework`/XCFramework для iOS), Kotlin/JS и Wasm (web).
- Платформенные различия — `expect`/`actual`. Новый memory manager без `freeze()` с Kotlin 1.7.20.
- За: нативный UX, постепенное внедрение. Против: iOS-разработчику нужно вникнуть в Kotlin, CMP на iOS молод.

### [[KMP. expect-actual]]
`expect`/`actual` — объявление в `commonMain` API-контракта без тела, у которого в каждом таргете (`androidMain`/`iosMain`) своя `actual`-реализация; «мультиплатформенный интерфейс».
- Нет `actual` хотя бы в одном таргете → проект **не соберётся**.
- Работает для функций, свойств, классов, объектов; частый приём — `actual typealias` на платформенный тип (`Throwable`, `Parcelable`).
- Ловушка: не для всего. Когда есть несколько реализаций или нужна подмена в тестах — чище интерфейс в `commonMain` + DI. `expect/actual` оправдан для единого типа/функции без полиморфизма.

### [[KMP. Source sets и Gradle]]
**Source set** — набор исходников под конкретный набор таргетов. `commonMain` компилируется во все таргеты и видит только мультиплатформенные API + `expect/actual`, не видит `android.*` и `platform.UIKit.*`.
- Три iOS-таргета: `iosArm64` (устройства), `iosSimulatorArm64`, `iosX64`; обычно собирают в один **XCFramework**.
- **Default Hierarchy Template**: Kotlin Gradle Plugin сам строит промежуточный `iosMain` (раньше — руками через `dependsOn`).
- Движки кладут в свой source set: `ktor-client-okhttp` → `androidMain`, `ktor-client-darwin` → `iosMain`. Android-зависимость в `commonMain` ломает iOS-сборку.

### [[KMP. Compose Multiplatform]]
Фреймворк JetBrains для шаринга не только логики, но и **UI** поверх Jetpack Compose; надстройка над KMP.
- Не путать: **KMP** = шаринг логики (UI нативный); **CMP** = шаринг UI (можно не использовать).
- Статус: Android/Desktop — Stable, **iOS — Stable с 2025**, Web (Wasm) — Alpha/Beta.
- На iOS CMP **рисует сам** через Skia (Skiko) — не нативные UIKit-контролы (ближе к Flutter). Интероп: `UIKitView { }`, `ComposeUIViewController { App() }`.
- Подводные камни: iOS-UX (скролл-физика, жесты, accessibility), размер бинаря, стартовое время — поэтому многие шарят логику, а UI на iOS оставляют SwiftUI.

### [[KMP. iOS interop и корутины]]
Как Kotlin потребляется из Swift и что с `suspend`/`Flow` на границе.
- Мост на iOS идёт через **рантайм Objective-C**, поэтому API «огрубляется»: `Int`/`Long` боксятся, `sealed class` теряет исчерпывающность, дженерики искажаются.
- `suspend`-функция становится в Swift **`async`** (`try await`). `Flow` из коробки теряет дженерик.
- **SKIE** (Touchlab) — генератор Swift-обёрток: `Flow` → `AsyncSequence`, `suspend` → `async` с отменой, `sealed` → Swift `enum`. Альтернатива — **KMP-NativeCoroutines**.
- Память: с Kotlin 1.7.20 новый memory manager **без freezing** (`freeze()` — история).

### [[KMP. Библиотеки экосистемы]]
Карта замен Android-библиотек: Retrofit → **Ktor**, Gson/Moshi → **kotlinx.serialization**, Room → **SQLDelight** (или Room KMP), Dagger/Hilt → **Koin**, java.time → **kotlinx-datetime**, SharedPreferences → **multiplatform-settings**, Coil → **Coil 3**.
- Ktor: клиент в `commonMain`, движок per-target (OkHttp — Android, Darwin — iOS).
- Koin вместо Hilt, потому что Hilt/Dagger завязаны на JVM-кодогенерацию.
- Ловушка: чисто-JVM-библиотеки (Retrofit, Gson, Hilt) скомпилируются под Android, но сломают iOS-сборку.

### [[KMP. Сборка и доставка iOS-приложения]]
AS с KMP-плагином лишь **оркеструет**, а реальная компиляция/подпись/установка делается toolchain'ом Apple (Xcode + iOS SDK + `codesign`), только на **macOS**.
- **Без Mac собрать iOS-приложение нельзя** (требование Apple, не KMP).
- Конвейер: Kotlin/Native компилирует общий код (Kotlin → LLVM IR → Mach-O ARM64 → `.framework`); Xcode линкует Swift с Kotlin-framework через ObjC-заголовки; `codesign` подписывает.
- Задачи: `linkDebugFrameworkIos*`, `embedAndSignAppleFrameworkForXcode`, `assembleXCFramework`. **Bitcode** deprecated с Xcode 14.

### [[KMP. Вопросы с собеса]]
Шпаргалка «вопрос → короткий ответ».
- Отличие от Flutter/RN: KMP не несёт свой UI и рантайм, делится только логика, UI нативный, внедрение постепенное.
- `commonMain` компилируется несколькими бэкендами: Kotlin/JVM (Android), Kotlin/Native (iOS), Kotlin/JS и Wasm (web).
- `suspend` → Swift `async`, `Flow` через SKIE; «заморозка» — легаси до Kotlin 1.7.20.
- KMP стабилен с **Kotlin 1.9.20**, в проде у McDonald's, Netflix, Forbes, 9GAG.
- Что шарить: сеть, парсинг, БД, бизнес-логику; оставлять нативным: UI (без CMP), разрешения, платформенные SDK.

## ⚠️ Исключения

### [[Иерархия]]
Корень `Throwable` делится на `Error` (системные сбои JVM — `OutOfMemoryError`, `StackOverflowError`, ловить не нужно) и `Exception`.
- `Exception` → `RuntimeException` (unchecked: `NullPointerException`, `IllegalArgumentException`) и checked (`IOException`, `SQLException`, `InterruptedException`).
- Отличие: checked требует обработки компилятором Java (try/throws), unchecked — на усмотрение.
- Ключевой факт: в Kotlin ВСЕ исключения unchecked — компилятор никогда не требует try-catch/`throws`. Причина отказа — checked ведут к «глушению» ошибок и захламлению сигнатур.
- Глобальный перехват — `Thread.setDefaultUncaughtExceptionHandler` в `Application`.

### [[Как перехватить все исключения в run time]]
Три уровня: локально через try-catch, для потока через `setUncaughtExceptionHandler`, глобально во всём процессе через `Thread.setDefaultUncaughtExceptionHandler`.
- Порядок поиска обработчика JVM: хендлер потока → его `ThreadGroup` → default-обработчик.
- В Android глобальный хендлер ставят в `Application.onCreate()`.
- Важно: глобальный обработчик НЕ предотвращает краш — только логирует. При Crashlytics нужно сохранить предыдущий обработчик и вызвать его в конце своего.
- Исключения корутин туда могут не дойти — там `CoroutineExceptionHandler`, а `CancellationException` — штатная отмена.

## 🎯 Общие вопросы и задачи

### [[HTTP]]
- Протокол прикладного уровня клиент-сервер поверх TCP (порт 80/443), модель запрос-ответ.
- Методы: `GET`/`POST`/`PUT`/`PATCH`/`DELETE`/`HEAD`/`OPTIONS`; коды 1xx-5xx.
- Безопасные: `GET`, `HEAD`, `OPTIONS`; идемпотентные: `GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS` — `POST` и `PATCH` НЕ идемпотентны (важно для ретраев).
- Версии: 1.0 (соединение на запрос), 1.1 (keep-alive), 2 (мультиплексирование, HPACK), 3 (поверх QUIC/UDP). HTTPS = HTTP поверх TLS.

### [[WebSocket для чего]]
- Полнодуплексный постоянный канал для real-time: чаты, игры, котировки, уведомления, совместное редактирование.
- Начинается как HTTP-запрос с `Upgrade: websocket` (handshake, код `101`), затем переключается; схемы `ws://`/`wss://`. Сервер может слать данные сам.
- На проде: reconnect с backoff (OkHttp сам не делает), heartbeat ping/pong, `readTimeout(0)`, коды закрытия (`1000` норма).
- Когда избыточен: если данные только сервер→клиент, проще SSE; long-polling — легаси-фоллбэк.

### [[Атомарность и Транзакции]]
- Атомарная операция — целиком или никак, над одной переменной, без rollback (`AtomicInteger.incrementAndGet()`).
- Транзакция — группа операций «всё или ничего», с rollback, обычно в БД.
- `AtomicInteger` — через CAS (Compare-And-Swap), lock-free.
- Атомарность отдельных операций ≠ атомарность комбинации: `check-then-act` (`if get==0 set 1`) — гонка; нужен `compareAndSet`/`updateAndGet`.
- В БД атомарность — буква A из ACID; на Android — `@Transaction`/`runInTransaction` в Room, в корутинах — `Mutex.withLock`.

### [[Fragment transaction]]
- `FragmentTransaction` — атомарный набор операций (`add`/`replace`/`remove`), создаётся `beginTransaction()`.
- `commit()` — асинхронный, кидает `IllegalStateException` после `onSaveInstanceState`; `commitAllowingStateLoss()` подавляет, но теряет транзакцию.
- `commitNow()` — синхронный, но НЕ совместим с `addToBackStack`.
- Современно навигацию ведёт Navigation Component; ручные транзакции — для legacy/собеса.

### [[Метод main в Android]]
В Android нет своего `main()` в коде приложения — точка входа `ActivityThread.main()` внутри фреймворка: готовит главный `Looper` (`prepareMainLooper`), запускает `Looper.loop()`. Поэтому главный поток не завершается — крутится в цикле обработки сообщений. Процесс порождается из Zygote.

### [[Могут ли объекты перемещаться в памяти]]
Да, объекты в JVM перемещает GC (Eden→Survivor→Old, компактинг в G1/ZGC/Shenandoah). Identity hash (`System.identityHashCode`) НЕ адрес — вычисляется лениво и хранится в заголовке объекта (mark word), поэтому при перемещении не меняется (иначе `HashMap` бы ломался). JIT объекты не перемещает — это escape-анализ/scalar replacement. На Android — ART с Concurrent Copying GC.

### [[Приватный конструктор]]
Приватный конструктор запрещает создание объекта извне — для Singleton, Factory Method, инкапсуляции. Ловушка: `getInstance()` с `if (instance == null)` НЕ потокобезопасен (гонка, два экземпляра); в Kotlin синглтон — через `object` или `by lazy` (`SYNCHRONIZED`). Приватный конструктор в Kotlin чаще в фабриках `companion object` и sealed-иерархиях.

### [[Создание своего Executer]]
Кастомный `Executor` на `ThreadPoolExecutor` + `HandlerThread`/`Handler`. Ключевой вопрос — неинтуитивная логика: сначала до `corePoolSize`, потом в очередь, и только при ПЕРЕПОЛНЕННОЙ очереди — сверх core до `maximumPoolSize`. С неограниченной `LinkedBlockingQueue` `maximumPoolSize` бесполезен (риск OOM). `DiscardPolicy` молча теряет задачи. Сегодня почти не нужен — корутины.

### [[CodeReview]]
Ревью `ViewModel` с `Flow`. Красные флаги: `GlobalScope.launch` вместо `viewModelScope` (утечка + держит `Context`), прямой `Context` во ViewModel (за `TextProvider`), публичный `MutableLiveData` наружу, `lateinit`-поля как общее состояние между эмиссиями (гонки). Плюс `var`→`val`, магическое `42` в константу, `async` для параллельной загрузки.

### [[Способы передачи геолокации в фоновом режиме]]
Три способа: (1) **Foreground Service** — лучший для real-time трекинга, но жрёт батарею и требует `ACCESS_BACKGROUND_LOCATION`; (2) **WorkManager** — периодически (минимум 15 мин), экономит батарею; (3) **AlarmManager + BroadcastReceiver** — ненадёжен (откладывается в Doze). Отдельная боль — эволюция разрешений (Android 10/11/12/14) и `FLAG_IMMUTABLE` для `PendingIntent`.

### [[Передача точной геолокации с интервалом времени]]
Через `FusedLocationProviderClient` + `LocationRequest` (`interval`, `priority`) + `LocationCallback`. Замечания: старый `LocationRequest.create()`/`PRIORITY_*` deprecated → `LocationRequest.Builder` и класс `Priority`; старт/стоп привязывать к `onResume`/`onPause`, для фона — Foreground Service.

### [[Вопросы с WB]]
Сборник задач: (1) уход от race condition на общем `var` — через `Mutex.withLock` или `Channel` (корутина-агрегатор); `Thread.sleep` в `suspend` блокирует поток (нужен `delay`); (2) `inline`+`reified` — `if (element is T)` не скомпилируется без `reified`, лямбда в не-inline требует `noinline`; (3) кеш из API подвержен гонке — фикс `Mutex.withLock`, лучше кешировать `Deferred`.

### [[Задача на flow от Совкомбанка]]
«В каком диспетчере выполнится каждый оператор». Ключ: `flowOn` меняет контекст только для upstream (операторов ВЫШЕ себя до следующего `flowOn`). `map`→IO, `filter`→Default, терминальный `single()`→контекст коллектора (Main).

### [[Корутины от Альфы]]
«Что выведется» на structured concurrency. Ключ: `coroutineScope` не вернёт управление, пока не завершатся ВСЕ дети, а `launch` из `runBlocking` живёт параллельно. Порядок: `coroutine scope` (~100), `runBlocking` (~200), `nested launch` (~500), `Coroutine scope is over` (~500).

### [[Задача на оптимизацию Compse кода c WB]]
Оптимизация Compose-списка. Проблемы: самодельный `remember { CoroutineScope }` не отменяется (нужен `rememberCoroutineScope()`); `forEach { item {} }` вместо `items(list, key = { it.id })`; `messages.sorted()` в композиции (выносить в VM); `Message` нестабилен из-за `LocalDateTime` (нужен `@Immutable`); `Modifier.composed {}` устарел (использовать `Modifier.Node`).

### [[Задача на рефакторинг от Т-Банка]]
Рефакторинг `Formula1DataSource`. Баги: `for (i in 0..engines.size)` → `IndexOutOfBoundsException` (нужно `until`); двойное добавление; `car` в `companion object` — глобальное мутабельное состояние; `saveCar` игнорирует `name`. Рефакторинг: `@Synchronized`→`Mutex.withLock`, инкапсуляция `cars` в репозитории, `suspend`-доступ.

### [[Задача от VK на лайвкодинг]]
Скобочная последовательность из `(`, `{`, `[`: достроить до правильной добавлением символов в конец или вернуть `null`. Решение стеком за O(n): на закрывающую скобку сверять вершину; в конце дописать закрывающие для оставшихся открытых.

### [[Задача по легенде с Я. Кеш и Mutex]]
`LoadUrlUseCase` с кешированием, лимитом одновременных запросов и порядком ответов. Решение: `ConcurrentHashMap<URL, Deferred<Data>>` + `computeIfAbsent` (атомарный get-or-create → дедупликация in-flight) + `Semaphore(limit).withPermit` + `urls.map { async }.awaitAll()` (сохраняет порядок). Инсайт: начать с минимума (~15 строк), самому назвать слабости, усложнять по запросу.

### [[Задача с Авито]]
(1) `data class User` — `val id = Random()` в теле НЕ входит в `equals`/`hashCode` (только параметры первичного конструктора); (2) `filterIsInstance` требует `reified`; (3) утечка — `inner class` держит сильную ссылку на Activity, `WeakReference` бесполезен (делать не-`inner`); (4) `CountDownLatch(1)` НЕ гарантирует «1 1» — нужен барьер `CountDownLatch(2)`.

### [[Пиздец от Яндекса]]
Часть 1: гонка на общем `Counter.count++` из 1000 параллельных `async`, `try` не ловит тело `async`, `runBlocking` на Main (ANR). Часть 2 (главная ловушка): голый `return` из `inline`-лямбды `forEvery` — нелокальный, завершает `main`; итерация по `reversed()` печатает `7`, `5`, на `3` выходит → остальное недостижимо.

### [[CityDrive]]
Из списка `User` убрать ВСЕХ, чей email встречается более одного раза (не «оставить уникальные»). Решение через `groupingBy { it.email }.eachCount()` + `filter { count == 1 }` за O(n); ловушка — `distinctBy` тут не подходит (оставит первого).

### [[Х5]]
Мини-задачи на язык: (1) модификаторы доступа + `Nested` vs `inner`; (2) `when` как выражение требует `else`, ветки с `println` дают `Unit`; (3) `private` в конструкторе ломает top-level extension; (4) параметры вторичного конструктора не могут иметь `val`/`var`; (5) scope-функции: `apply`/`also` возвращают receiver, `let`/`run` — результат лямбды; (6) structured concurrency — ранняя отмена спасает от исключения.
