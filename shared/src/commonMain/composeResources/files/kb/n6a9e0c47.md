В Android разработке **Activity**, **Service**, **Broadcast Receiver** и **Content Provider** — это четыре ключевых компонента приложения, которые обеспечивают взаимодействие с пользователем, выполнение фоновых задач, обмен данными и работу с системой. Давайте рассмотрим их функции, отличия и основные аспекты.

## **1. Activity**
	Activity представляет собой экран пользовательского интерфейса в приложении. Это точка взаимодействия пользователя с приложением. (Для отображения интерфейса и обработки действий пользователя.)

**Основные особенности:**
• Это основной компонент для работы с UI.
• Каждое приложение обычно содержит несколько Activity, между которыми можно переключаться.
• Activity управляется системой через **жизненный цикл**, который включает методы:
	• onCreate() — инициализация Activity.
	• onStart(), onResume() — активность становится видимой и доступной для взаимдействия.
	• onPause(), onStop() — активность перестает быть видимой или активной.
	• onDestroy() — активность уничтожается.

## **2. Service**
	В Android сервисы (Service) — это компоненты, которые позволяют выполнять долгосрочные фоновые операции без пользовательского интерфейса. Они используются для задач, которые должны продолжаться, даже если пользователь закрывает приложение. Сервисы могут работать в двух основных режимах: **запущенные** и **привязанные**. Давайте подробнее разберем, какие бывают сервисы и для чего они нужны.
### **Типы сервисов в Android**

1. **По способу запуска:**
	• **Started Service** (Запущенный сервис)
	• **Bound Service** (Привязанный сервис)
2. **По продолжительности работы:**
	• **Foreground Service** (Сервис переднего плана)
	• **Background Service** (Сервис фонового режима)

### **1. Started Service**
Запущенный сервис начинает выполнять свою работу после вызова метода startService(). Он продолжает работать, даже если пользователь покинул приложение.

**Основные особенности:**
• Выполняется до тех пор, пока не вызван метод ``stopSelf()`` или ``stopService()``.
• Используется для выполнения задач в фоновом режиме, которые не требуют взаимодействия с пользователем.

**Пример использования:**
• Загрузка файла.
• Отправка данных на сервер.

```kotlin
class MyStartedService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // Выполнение задачи
        Thread {
            // Выполнение длительной операции
            stopSelf() // Завершение сервиса после выполнения задачи
        }.start()
        return START_STICKY
    }

    override fun onBind(intent: Intent?): IBinder? = null
}
```

### **2. Bound Service**

Привязанный сервис предоставляет клиентам интерфейс для взаимодействия через метод ``bindService()``. Такие сервисы прекращают работу, как только все клиенты разрывают соединение.

**Основные особенности:**

• Позволяет другим компонентам (Activity, Fragment) взаимодействовать с сервисом. Через service connection.
• Используется для тесной интеграции между компонентами приложения.

**Пример использования:**

• Воспроизведение музыки с управлением через UI.
• Работа с базой данных, предоставляя доступ из разных компонентов приложения.

```kotlin

class MyBoundService : Service() {
    private val binder = LocalBinder()

    inner class LocalBinder : Binder() {
        fun getService(): MyBoundService = this@MyBoundService
    }

    override fun onBind(intent: Intent?): IBinder = binder

    fun performTask() {
        // Реализация задачи
    }
}
```

**✅ Простой Bound Service через IBinder (Kotlin)**

**1️⃣ Создаём Bound Service**

```kotlin
class MyBoundService : Service() {

    private val binder = LocalBinder()

    inner class LocalBinder : Binder() {
        fun getService(): MyBoundService = this@MyBoundService
    }

    override fun onBind(intent: Intent?): IBinder {
        return binder
    }

    // Метод, который можно вызвать из Activity
    fun getHelloMessage(): String {
        return "Привет от Bound Service!"
    }
}
```

**2️⃣ Связываем Activity с сервисом**
```kotlin
class MainActivity : AppCompatActivity() {

    private var myService: MyBoundService? = null
    private var isBound = false

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
            val binder = service as MyBoundService.LocalBinder
            myService = binder.getService()
            isBound = true

            // Теперь можно вызывать методы сервиса
            val message = myService?.getHelloMessage()
            Toast.makeText(this@MainActivity, message, Toast.LENGTH_SHORT).show()
        }

        override fun onServiceDisconnected(name: ComponentName?) {
            isBound = false
        }
    }

    override fun onStart() {
        super.onStart()
        val intent = Intent(this, MyBoundService::class.java)
        bindService(intent, connection, Context.BIND_AUTO_CREATE)
    }

    override fun onStop() {
        super.onStop()
        if (isBound) {
            unbindService(connection)
            isBound = false
        }
    }
}
```

### **3. Foreground Service**

Сервис переднего плана выполняет задачи с высоким приоритетом и отображает уведомление в статусной строке, чтобы информировать пользователя о своей работе.

**Основные особенности:**

• Требует отображения уведомления с помощью startForeground() (с Android 8.0+ это обязательно).
• Используется для задач, которые пользователь должен знать и контролировать.
**Пример использования:**
• Воспроизведение музыки.
• Навигация и GPS-трекинг.
• Умные часы или фитнес-приложения.
• Отображают уведомление в статус-баре, показывая пользователю, что задача выполняется.
• Используются для задач, требующих постоянного выполнения, таких как воспроизведение музыки или запись геолокации.
• Запускаются с помощью startForeground(), уведомление обязательно.

```kotlin

class MyForegroundService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = NotificationCompat.Builder(this, "CHANNEL_ID")
            .setContentTitle("Foreground Service")
            .setContentText("Service is running...")
            .setSmallIcon(R.drawable.ic_notification)
            .build()
        startForeground(1, notification)

        // Выполнение фоновой задачи
        return START_STICKY
    }

    override fun onBind(intent: Intent?): IBinder? = null
}
```

### **4. Background Service**

Фоновые сервисы работают без взаимодействия с пользователем. С Android 8.0 (API 26) использование фоновых сервисов ограничено из-за оптимизации батареи.
**Особенности:**
• Для выполнения фоновых задач рекомендуется использовать WorkManager или JobIntentService.
• Если задача требует выполнения после закрытия приложения, используйте **Foreground Service**.

```kotlin

class DownloadService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // Выполнение фоновой загрузки
        Thread {
            // Скачивание файла
            stopSelf()
        }.start()
        return START_NOT_STICKY
    }

    override fun onBind(intent: Intent?): IBinder? = null
}
```


**Краткое сравнение**

| Тип сервиса            | Продолжительность работы            | Взаимодействие с пользаком | Пример                       |
| ---------------------- | ----------------------------------- | -------------------------- | ---------------------------- |
| Started service        | Работает до вызова stop self        | нет                        | Загрузка данны,синхронизация |
| Bound service          | Работает пока есть активные клиенты | Да                         | Музыка                       |
| Foreground service     | Работает до явного завершения.      | Через уведомление          | GPS-навигация, плеер.        |
| **Background Service** | Завершается системой автоматически  | Нет                        | Устаревший                   |
### **Альтернативы сервисам**

С появлением новых API Google рекомендует использовать более оптимальные способы выполнения фоновых задач:
• WorkManager — для задач, которые должны выполняться гарантированно (даже после перезагрузки устройства).
• JobScheduler — для задач, зависящих от условий (например, подключение к Wi-Fi).
• Handler/Thread — для выполнения коротких задач в рамках UI.
Сервисы остаются мощным инструментом, но их использование требует понимания, как они влияют на производительность и батарею устройства.

## **WorkManager** и **JobScheduler** 

**WorkManager** и **JobScheduler** — это инструменты Android для выполнения фоновых задач. Они обеспечивают гибкое и надежное выполнение задач с учетом ограничений, таких как состояние устройства, подключение к сети и заряд батареи.
### **WorkManager** 

**WorkManager** — это библиотека Jetpack, которая управляет планированием и выполнением фоновых задач, которые гарантированно должны быть выполнены, даже если приложение закрыто или устройство перезагружается.

**Ключевые особенности:**
• Подходит для долгосрочных и отложенных задач.
• Работает независимо от версии Android (заменяет устаревшие JobScheduler, AlarmManager и Firebase JobDispatcher).
• Может учитывать ограничения:
• Требование подключения к сети.
• Уровень заряда батареи.
• Подключение к источнику питания и т.д.
• Поддерживает повторяющиеся задачи.
• Обеспечивает гарантию выполнения задач (включая повторное выполнение в случае неудачи).

**Как работает?**
1. Создайте задачу, унаследовавшись от класса Worker.
2. Определите ограничения и расписание задачи.
3. Запланируйте задачу с помощью WorkManager.

```kotlin
class MyWorker(context: Context, params: WorkerParameters) : Worker(context, params) {
    override fun doWork(): Result {
        // Выполнение задачи
        return Result.success()
    }
}

// Запуск задачи
val workRequest = OneTimeWorkRequestBuilder<MyWorker>()
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED) // Требуется подключение к сети
            .build()
    )
    .build()

WorkManager.getInstance(context).enqueue(workRequest)
```

**Когда использовать?**
• Для задач, которые гарантированно должны быть выполнены.
• Примеры:
• Загрузка данных в фоновом режиме.
• Отправка аналитики.
• Синхронизация с сервером.

### **2. JobScheduler**

JobScheduler — это системный API Android, доступный с API 21 (Lollipop). Он позволяет планировать выполнение задач в фоне с учетом состояния устройства.

**Ключевые особенности:**
• Позволяет планировать задачи, зависящие от ограничений, таких как:
	• Состояние сети.
	• Заряд батареи.
	• Источник питания.
	• Система может объединять задачи для оптимизации расхода ресурсов.
	• Задачи выполняются только тогда, когда ограничения выполнены.

**Как работает?**
1. Создайте задачу, унаследовавшись от JobService.
2. Зарегистрируйте задачу через JobScheduler.

```kotlin

class MyJobService : JobService() {
    override fun onStartJob(params: JobParameters?): Boolean {
        // Выполнение задачи
        Thread {
            // Выполнение операции
            jobFinished(params, false) // Завершение задачи
        }.start()
        return true // Задача выполняется асинхронно
    }

    override fun onStopJob(params: JobParameters?): Boolean {
        // Обработка отмены задачи
        return true
    }
}

// Планирование задачи
val jobScheduler = getSystemService(Context.JOB_SCHEDULER_SERVICE) as JobScheduler
val jobInfo = JobInfo.Builder(1, ComponentName(this, MyJobService::class.java))
    .setRequiredNetworkType(JobInfo.NETWORK_TYPE_UNMETERED) // Требуется Wi-Fi
    .setRequiresCharging(true) // Устройство должно быть подключено к зарядке
    .build()

jobScheduler.schedule(jobInfo)
```

### **ПЕРЕЗАПУСК СЕРВИСА** И ОСТАНОВКА

- Перезапуск сервиса
    - Даже если ОС и внeштатно выгрузит сервис из памяти, есть возможность его запустить заново, кaк только появятся свободные ресурсы.
    - Метод ``onStartCommand`` возвращает переменную, указывaющую ОС, как следует поступить с сервисом, если он был принудительно остановлен. Существует три варианта того, как ОС может поступить с сервисом, если он был принудительно завершен:
        - `START_NOT_STICKY` — не будет перезапущен системой, и все останется так, как есть. Подходит для случая, когда он выпoлняет не самые важные задачи, и приложение может позже при необходимости самостоятельно его перезапустить.
        - `START_STICKY` — будет запущен заново, но в Intent, который ОС создаст для его запуска, не будет никаких параметров. Такой вариант работает с аудиоплеерами — он должен быть активным в фоне, но не обязательно при этом автоматически начинать проигрывать песни.
        - `START_REDELIVER_INTENT` — сервис будет запущен с теми же параметрами, которые были при его последнем старте. Это удобно, когда в фоне загружается большой файл и его загрузка была прервана.

- Остановка сервиса
    - Сервис, создaнный с помощью одноименного класса, будет жить, пока его принудительно не остановят. Сделать это можно либо откуда-то снаружи методом stopService, с указанием интента, которым он был запущен, либо внутри самого сервиса методом stopSelf.
    - Как узнать, что сервис уже все сделал, особенно если мы поставили перед ним сразу несколько задач? В этом нам поможет параметр startId у метода onstartcommand — это порядковый номер каждого вызова сервиса, который увеличивается на единицу при каждом запуске.
    - Создав новый поток, разумно завeршать его методом stopSelf, указывая startId в качестве параметра. С таким параметром ОС не будет сразу завершать сервис, а сравнит переданный идентификатор с тем, который был выдан при последнем запуске onStartCommand. Если они не равны, значит, в очередь была добавлена новая задача и сервис остановлен не будет.

## ЖЦ Сервиса

![[i3f7d2941.png]]


>Метод onStartCommand() в Service Android вызывается в главном потоке (UI-потоке) приложения.

• onStartCommand() вызывается, когда сервис запускается с помощью метода startService().
• В отличие от метода onCreate(), который вызывается при создании сервиса, onStartCommand() используется для обработки запросов на запуск сервиса.

**❗ Что это значит для многозадачности?**

• Поскольку onStartCommand() вызывается в **главном потоке**, вам нужно быть осторожным, чтобы не блокировать его длительными операциями (например, сетевыми запросами или долгими вычислениями).

• Если вы выполняете долгие операции в onStartCommand(), они могут **заморозить UI**, что приведет к **неприятному пользовательскому опыту**.


## **Фоновая работа в Android** 

**1 WorkManager** - Можем запустить работу 1 раз, можно с периодичностью метод doWork(). Работает с условиями выполнения работы (например достаточно сети), хватает памяти. JobScheduler под капотом у work manager. Можно выстраивать chain, минимум можно запускать раз в 15 минут. Работа ограничивается app standby и doze mode

**2 DownloadManger** для загрузки данных из сети, нельзя закинуть доп безопасность по мимо сертификата HTTPS, нельзя загрузить в приватную папку. 

**3 JobIntentService** -  Создаёт и работает в собственном потоке, выполняет работу из метода onHandleIntent(), после чего останавливается. Операции в **onHandleIntent()** не могут быть прерваны, связь с основным потоком отсутствует

**4 Сервисы** Запущенные -> запустил работу и приостановил **stopSelf()** или привязанные сервисы. Привязанные -> живет пока на него подписаны. В методе onBind() возвращается не null, а реальное значение 

**5 Foreground** -> Показываем Notification, **обязательно указываем `foregroundServiceType`** (location, mediaPlayback, dataSync и т.д.) + соответствующее разрешение в манифесте. С Android 14 (API 34) тип сервиса **обязателен**, и каждый тип требует своего рантайм-разрешения. Использовать можно только по назначению. 

**6 AlarmManager** - Нужно задать работу по точному времени. Отправляет Intent во время срабатывания.

## **Content Provider**
**Content Provider** — это компонент Android, который предоставляет общий интерфейс для управления данными приложения и позволяет другим приложениям получать к ним доступ. 

**Основные функции Content Provider**
1. **Предоставление доступа к данным**:
• Данные могут храниться в базе данных SQLite, файлах, в сети или других структурах.
• Другие приложения или компоненты могут запрашивать эти данные через ==ContentResolver.==
1. **Обеспечение безопасности**:
• Доступ к данным регулируется через разрешения (permissions), указанные в манифесте.
2. **Стандартизированный доступ к данным**:
• Использует **URI** (Uniform Resource Identifier) для идентификации данных.
• Операции чтения, записи, обновления и удаления выполняются через стандартные методы.

**Когда использовать Content Provider?**
3. Для предоставления данных другим приложениям:
• Пример: приложение “Контакты” предоставляет доступ к контактам через Content Provider.
4. Для унифицированного доступа к данным внутри приложения:
• Пример: компоненты одного приложения могут использовать Content Provider для взаимодействия.

***Основные методы Content Provider***

| Метод     | Описание                                                                |
| --------- | ----------------------------------------------------------------------- |
| query()   | Чтение данных, возвращает Cursor                                        |
| insert()  | Добавление данных возвращет Uri                                         |
| update()  | Обновление существующих данных. Возвращает количество изменённых строк. |
| delete()  | Удаление данных. Возвращает количество удалённых строк.                 |
| getType() | Возвращает MIME-тип данных для заданного URI.                           |
**Как работает Content Provider?**

5. **Клиент отправляет запрос через** ContentResolver:

• Это стандартный API Android для взаимодействия с Content Provider.
• Пример: context.getContentResolver().query(uri, ...).

6. **Content Provider обрабатывает запрос**:

• Выполняет операцию (например, чтение или запись данных) и возвращает результат клиенту.

7. **Использование URI для идентификации данных**:

• Каждый Content Provider имеет уникальный URI, который включает:
• **Authority** — уникальный идентификатор провайдера.
• **Path** — путь к данным (таблица, коллекция или конкретный элемент).
• **ID** — уникальный идентификатор элемента (опционально).

Пример

```kotlin
val uri = Uri.parse("content://com.example.myprovider/my_table")
val cursor = contentResolver.query(uri, null, null, null, null)
while (cursor?.moveToNext() == true) {
    val data = cursor.getString(cursor.getColumnIndex("column_name"))
    println(data)
}
cursor?.close()
```

### Cursor vs InputStream

Cursor и InputStream — это два разных способа получения данных из **Content Provider**, и их использование зависит от того, как вы хотите работать с данными.

**Когда использовать Cursor?**

Cursor используется, когда вы хотите запросить несколько строк данных из **Content Provider**. Он работает с **табличными данными**, такими как контакты, изображения, видео и другие записи в базе данных, которые возвращаются как набор строк (записей). Cursor позволяет вам перемещаться по этим строкам и извлекать данные по столбцам.

Например, если вы хотите получить **список всех контактов**, **список изображений**, или другие коллекции данных, Cursor идеально подходит для этого, потому что он работает с коллекциями данных (несколько записей) и предоставляет удобные методы для перебора и извлечения информации.

**Когда использовать InputStream?**
InputStream используется, когда вам нужно работать с **большими или бинарными данными**, такими как изображения, аудио, видео или другие файлы. Это полезно, когда вам нужно **загрузить конкретный файл**, например, изображение, и работать с ним как с потоком байтов.

InputStream позволяет читать данные **постепенно** (по мере необходимости), что особенно полезно, если файл может быть слишком большим, чтобы загружать его целиком в память.

## **Broadcast Receiver**

**Broadcast Receiver** — это компонент Android, который позволяет принимать и обрабатывать сообщения (broadcasts), отправленные системой или другими приложениями. Broadcast Receiver часто используется для реакции на события, такие как изменения состояния устройства, получение push-уведомлений или ответы от других компонентов.

**Основные функции**

1. **Реакция на системные события**:

• Пример: изменение уровня заряда батареи, подключение к сети, загрузка устройства и т.д.

2. **Обработка сообщений от других приложений**:

• Пример: получение push-уведомлений от Firebase.

3. **Обмен данными внутри приложения**:

• Пример: отправка локальных сообщений между компонентами приложения.

### **Как работает Broadcast Receiver?**

4. **Отправка сообщения**:

• Используется объект Intent, который содержит информацию о событии.

5. **Приём сообщения**:

• Broadcast Receiver регистрируется для прослушивания определённых событий через фильтр (IntentFilter).

6. **Обработка события**:

• Приёмник обрабатывает сообщение в методе onReceive().

### **Типы Broadcasts**

7. **Системные Broadcasts**:

• Отправляются системой при наступлении определённых событий.
• Примеры:
• ACTION_BATTERY_LOW — низкий заряд батареи.
• ACTION_BOOT_COMPLETED — загрузка устройства завершена.

8. **Пользовательские Broadcasts**:

• Отправляются приложением для уведомления других компонентов или приложений.
• Пример: локальные события внутри приложения.

```kotlin
class MyBroadcastReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        when (intent.action) {
            "android.net.conn.CONNECTIVITY_CHANGE" -> {
                // Реакция на изменение состояния сети
                Toast.makeText(context, "Сеть изменилась", Toast.LENGTH_SHORT).show()
            }
        }
    }
}
```

**2. Динамическая регистрация** (Local broadcast)
Используется для временного прослушивания событий.
**Пример:**

```kotlin

class MainActivity : AppCompatActivity() {
    private val myReceiver = MyBroadcastReceiver()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        val filter = IntentFilter("android.intent.action.AIRPLANE_MODE")
        registerReceiver(myReceiver, filter)
    }

    override fun onDestroy() {
        super.onDestroy()
        unregisterReceiver(myReceiver) // Обязательно нужно удалять регистрацию
    }
}
```

**Отправка Custom Broadcast**
Приложение может отправлять собственные Broadcast сообщения.

**Пример отправки:**
```kotlin
val intent = Intent("com.example.MY_CUSTOM_BROADCAST")
intent.putExtra("data", "Hello, World!")
sendBroadcast(intent)
```

Прием
```kotlin
class MyCustomReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        val data = intent.getStringExtra("data")
        Toast.makeText(context, "Получено: $data", Toast.LENGTH_SHORT).show()
    }
}
```

**Особенности и ограничения**

9. **Контекст BroadcastReceiver**:

• onReceive() выполняется в главном потоке, поэтому нельзя выполнять длительные операции.

• Для долгих задач используйте WorkManager или запускайте сервис.

10. **Ограничения в Android 8.0+**:

• Статическая регистрация ограничена для большинства событий.
• Для задач, требующих постоянного фона, используйте JobScheduler или WorkManager.

11. **Эффективность**:

• Используйте локальные Broadcast (через LocalBroadcastManager) для внутренних сообщений, чтобы избежать лишнего потребления ресурсов.

**Когда использовать BroadcastReceiver**
12. **Для системных событий**:
• Реакция на заряд батареи, загрузку устройства, изменения состояния сети и т.д.
13. **Для локальных сообщений**:
• Уведомление компонентов внутри приложения о событиях (например, обновление UI).
14. **Для глобальных сообщений**:
• Отправка и получение уведомлений между приложениями.

### **1️⃣ Разница между регистрацией в манифесте и программной регистрацией**

| **Функция**                               | **В манифесте (**AndroidManifest.xml**)**            | **Программно (**registerReceiver()**)**  |
| ----------------------------------------- | ---------------------------------------------------- | ---------------------------------------- |
| **Живёт после закрытия приложения?**      | ✅ Да (если не **Android 8+**)                        | ❌ Нет (удаляется при закрытии)           |
| **Работает после перезагрузки?**          | ✅ Да (если есть BOOT_COMPLETED)                      | ❌ Нет, нужно регистрировать снова        |
| **Контекст регистрации**                  | application (глобальный)                             | activity / service (локальный)           |
| **Может обрабатывать системные события?** | ✅ Да (например, BOOT_COMPLETED, CONNECTIVITY_CHANGE) | 🔹 Да, но только если приложение открыто |
| **Может быть безопаснее (локальный)?**    | ❌ Нет (приёмник глобальный)                          | ✅ Да (работает только внутри приложения) |
| **Удаление ресивера**                     | ❌ Нет, удаляется только при удалении приложения      | ✅ Можно вызвать unregisterReceiver()     |

**Итог**
Broadcast Receiver — это простой и эффективный способ реагировать на события в системе или между приложениями. При правильном использовании он помогает создавать приложения, которые взаимодействуют с системой или другими компонентами, минимизируя использование ресурсов.

## Почему Application не компонент приложения?? 
 
🔹 **А вот** Application **— НЕ компонент, потому что:**

> • **НЕ регистрируется в** AndroidManifest.xml **как компонент**, хотя его можно указать в 
```xml
<application android:name="MyApplication">.
```

>• **Не является точкой входа** — система создаёт объект Application автоматически, а не по требованию пользователя или системы.

>• **Не управляется** ActivityManager — в отличие от Activity или Service, система не может “убить” или “перезапустить” Application как компонент.

>• **Живёт столько же, сколько и процесс приложения**, а не управляется через стандартные Intent-механизмы.

> [!important] Что устарело (проверь актуальность)
> - **`JobIntentService` — deprecated** (удалён). Замена — **WorkManager** (для гарантированной фоновой работы) или короткие задачи через корутины + foreground service.
> - **`LocalBroadcastManager` — deprecated.** Для коммуникации внутри приложения используйте `LiveData`/`StateFlow`/`SharedFlow` или прямой observer-паттерн.
> - **Фоновые `Service` сильно ограничены** с Android 8 (нельзя стартовать из фона) — почти всегда нужен **WorkManager** или **foreground service**.
> - **`onReceive` нельзя стартовать foreground service напрямую** на новых версиях из фонового состояния — используйте WorkManager.
> - С Android 13 (API 33) для нотификаций нужно рантайм-разрешение `POST_NOTIFICATIONS` — без него foreground-уведомление не покажется.

> [!tip] Четыре компонента — одной строкой (на собес)
> - **Activity** — экран UI.
> - **Service** — фоновая работа без UI (started / bound / foreground).
> - **BroadcastReceiver** — реакция на системные/кастомные события (`onReceive` на главном потоке, коротко).
> - **ContentProvider** — общий доступ к данным между приложениями через `ContentResolver`/URI.
> Все, кроме `Application`, регистрируются в манифесте и являются «точками входа», которыми управляет система. WorkManager — не компонент, а библиотека поверх них.
