# 05 nginx, reverse proxy, load balancer, API Gateway

Между приложением и серверами с кодом почти всегда стоит «вахтёр»: принимает соединения, снимает TLS, раскидывает запросы по серверам, отбрасывает лишнее. Это одна и та же идея в трёх ролях — reverse proxy, load balancer, API Gateway — и часто один и тот же софт (nginx, Envoy, HAProxy, облачный LB).

> [!tip] Аналогия из Android
> nginx — это OkHttp-interceptor на стороне сервера. Как interceptor добавляет заголовки, логирует, ретраит и может ответить из кеша, не дойдя до сети, так и reverse proxy перехватывает каждый запрос до бизнес-кода: проверяет, переписывает, распределяет или отвечает сам.

## Как работает

### Forward vs reverse proxy

```text
Forward proxy (на стороне клиента):
 [клиенты]─►[proxy]─►интернет
 скрывает клиентов (VPN, корп. прокси)

Reverse proxy (на стороне сервера):
 интернет─►[proxy]─►[app1][app2][app3]
 скрывает серверы, клиент видит 1 адрес
```

Клиент ходит на `api.example.com` и не знает, сколько серверов за ним и где они.

### Что делает reverse proxy

- **TLS-терминация.** Сертификат и рукопожатие живут на прокси ([[03 HTTPS, TLS, SSL]]); внутрь сети идёт обычный HTTP (или новый TLS, если сеть недоверенная). Серверы не тратят CPU на шифрование, сертификат обновляется в одном месте.
- **Статика и кеш.** Отдаёт файлы и кешированные ответы, не трогая приложение.
- **Сжатие** (gzip/brotli), лимиты на размер тела, таймауты.
- **Rate limiting.** Ограничение частоты запросов по IP/ключу (в nginx — `limit_req`, алгоритм leaky bucket), лишние получают 429.

### Балансировка нагрузки

```text
          ┌──► app1  ✓
[LB] ─────┼──► app2  ✓
          └──► app3  ✗ (health check)
```

Алгоритмы:

- **Round robin** — по очереди; просто, хорошо при одинаковых запросах и серверах. Есть weighted-вариант для разных по мощности машин.
- **Least connections** — тому, у кого меньше активных соединений; лучше при запросах разной длительности (WebSocket, тяжёлые отчёты).
- **IP hash / consistent hashing** — один и тот же клиент или ключ всегда на один сервер (sticky). Нужен, когда у сервера есть локальное состояние или кеш; consistent hashing при добавлении узла перемещает только малую часть ключей.

**Health checks.** LB регулярно дёргает `/health` у каждого узла и выкидывает из ротации тех, кто не отвечает. Пассивный вариант — считать ошибки на живом трафике.

**L4 vs L7.** L4-балансировщик видит только TCP/UDP (IP и порт) — быстрый, не смотрит внутрь. L7 понимает HTTP: может роутить по пути (`/api` → одни серверы, `/img` → другие), по заголовкам, делать TLS-терминацию и rate limit по пользователю.

### API Gateway

Это L7-прокси с бизнес-обязанностями, единая точка входа в микросервисы:

```text
         ┌─► /users  ─► user-svc
app ─►[GW]─► /orders ─► order-svc
         └─► /feed   ─► feed-svc
 auth · rate limit · логи · метрики
```

- **Аутентификация:** проверяет JWT один раз на входе ([[04 Авторизация]]), сервисам передаёт уже `userId`.
- **Маршрутизация** по пути и версии API (`/v1`, `/v2`).
- **Throttling/квоты** по пользователю или API-ключу.
- **Агрегация** (BFF — backend for frontend): один запрос от мобилки → несколько внутренних вызовов → один ответ. Меньше RTT по медленной сети.
- Сквозные вещи: логирование, `X-Request-Id`, метрики, CORS.

Отличие от простого LB: LB решает «на какой из одинаковых серверов», Gateway — «в какой сервис и можно ли вообще».

## Когда применять в SD-задаче

Сигналы: «сервис должен выдержать рост нагрузки», «несколько серверов», «микросервисы», «защита от спама/DDoS», «мобилке нужно меньше запросов».

Фраза на собес: «Перед stateless-серверами ставлю L7-балансировщик с TLS-терминацией и health checks; для микросервисов — API Gateway, который проверяет токен, применяет rate limit и роутит по сервисам, а для мобилки может агрегировать ответы как BFF».

> [!warning] Грабли
> - Сам балансировщик — единая точка отказа: нужны минимум два и переключение (облачные LB это уже делают).
> - Sticky sessions мешают масштабированию: упал узел — его пользователи потеряли сессии. Лучше stateless-серверы + сессии в общем Redis ([[06 Redis]]).
> - После прокси сервер видит IP прокси, а не клиента — реальный адрес передают в `X-Forwarded-For`; без этого rate limit по IP режет всех сразу.
> - Таймаут на прокси меньше, чем у долгого запроса, — клиент получит 504, хотя сервер работу доделал (опасно для неидемпотентных операций).
> - Долгоживущие соединения (WebSocket) с round robin распределяются неравномерно — нужен least connections.

> [!question]- Чем reverse proxy отличается от load balancer и API Gateway?
> Reverse proxy — общий принцип: стоит перед серверами, принимает запросы от их имени (TLS, кеш, сжатие). Load balancer — reverse proxy, задача которого распределить нагрузку по одинаковым экземплярам с health checks. API Gateway — L7-прокси перед микросервисами с аутентификацией, маршрутизацией по сервисам, квотами и агрегацией. nginx умеет все три роли.

> [!question]- Какие алгоритмы балансировки знаешь и когда какой?
> Round robin (и weighted) — одинаковые короткие запросы. Least connections — запросы разной длительности и долгие соединения. IP hash / consistent hashing — когда нужно, чтобы клиент или ключ стабильно попадал на один узел (локальный кеш, шардинг); consistent hashing минимизирует перераспределение при изменении числа узлов.

> [!question]- Где делать rate limiting и что вернуть клиенту?
> На входе: в API Gateway или nginx, чтобы лишний трафик не дошёл до приложения; при нескольких экземплярах шлюза счётчики держат в общем Redis. Лимит — по пользователю/API-ключу, а не только по IP (NAT у мобильных операторов). Ответ — 429 Too Many Requests с `Retry-After`; клиент делает backoff, а не долбит повтором.
