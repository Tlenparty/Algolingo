# MVI библиотеки

Когда MVI/[[UDF (Unidirectional Data Flow)|UDF]] перерастает «самописный `StateFlow` + `onEvent`», берут готовые библиотеки. На Senior полезно знать ландшафт и компромиссы — особенно в контексте [[KMP]].

## Зачем библиотека, если MVI пишется руками

> [!info] Что дают готовые решения
> Самописный MVI быстро упирается в повторяющийся бойлерплейт: reducer, обработка side-effects, восстановление состояния после смены конфигурации, навигация, склейка дерева компонентов. Библиотеки стандартизируют это и часто **мультиплатформенны** (общий презентационный слой для Android + iOS).

## Ландшафт

| Библиотека | Кратко | KMP |
| --- | --- | --- |
| **Decompose** | компонентная архитектура + навигация, lifecycle-aware, state переживает конфигурацию | ✅ да |
| **MVIKotlin** | классический MVI: Store (Intent → Executor → Reducer → State) + side-effects | ✅ да |
| **Orbit MVI** | лёгкий, container-based, минимум бойлерплейта, дружит с корутинами/Flow | ✅ да |
| **Ballast** | MVI с акцентом на отладку (time-travel, логирование) | ✅ да |

## Ключевые понятия (на примере MVIKotlin Store)

```text
Intent ──► Executor ──► (suspend работа) ──► Message ──► Reducer ──► State
                              └──────────────────────────► Label (side-effect)
```
- **Intent** — намерение пользователя/системы.
- **Executor** — обрабатывает Intent, дёргает репозитории, шлёт Message.
- **Reducer** — чистая функция `(State, Message) -> State`.
- **Label** — одноразовый side-effect (навигация, тост) — то, что **не** часть state.

> [!important] Главная тонкость MVI: state vs one-time events
> `State` — то, что можно отрендерить в любой момент (идемпотентно). А навигация, тосты, «показать снекбар» — **одноразовые события**, их нельзя класть в state (иначе повторятся при рекомпозиции/повороте). В библиотеках это отдельный канал (`Label`/side-effect/`Channel`). Частый вопрос: «как в MVI показать одноразовое сообщение» → через эффекты, не через state.

> [!tip] Decompose — почему его любят в KMP
> Decompose даёт **дерево компонентов** с собственным lifecycle и **навигацией, переживающей смену конфигурации**, полностью в общем коде — то, чего «ванильный» Navigation в KMP пока не закрывает (см. [[KMP. Compose Multiplatform]], [[Jetpack Navigation]]). Часто связку берут как «Decompose (навигация/компоненты) + MVIKotlin (логика стора)».

> [!warning] Когда НЕ тащить библиотеку
> На простом экране самописный `StateFlow<UiState>` + `onEvent` достаточно и понятнее. Библиотека оправдана при: мультиплатформе, сложных графах навигации, большой команде с потребностью в единых правилах, требовании отлаживаемости (time-travel). Иначе — оверинжиниринг.

> [!note] Связь с базой
> Все они — реализация [[UDF (Unidirectional Data Flow)|UDF]] поверх [[Coroutines|корутин]] и [[SharedFlow vs Flow vs StateFlow|StateFlow/SharedFlow]]. Понимание базового MVI важнее знания конкретной либы — её синтаксис учится за день.
