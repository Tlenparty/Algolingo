# 11 Файлы, CDN, S3

Картинки, видео и документы не хранят в БД и не гоняют через API-сервер. Файлы лежат в объектном хранилище (S3 и аналоги), раздаются через CDN рядом с пользователем, а загружаются клиентом напрямую в хранилище по presigned URL. API-сервер хранит только метаданные и выдаёт разрешения.

> [!tip] Аналогия из Android
> CDN — это дисковый кеш Coil/Glide, только общий для всех пользователей региона и стоящий в дата-центре рядом с ними. Как и в Coil, ключ кеша — URL, поэтому новая версия картинки должна получать новый URL, иначе все будут видеть старую.

## Объектное хранилище (S3)

- S3 (AWS), GCS (Google), MinIO (своё) — хранилище «ключ → файл» (объект) в бакете: `photos/u42/9f3a.jpg`. Не файловая система: нет настоящих папок, объект перезаписывается целиком.
- Почти бесконечный объём, высокая надёжность (копии в нескольких дата-центрах), дёшево за гигабайт.
- В БД — только метаданные: id, владелец, ключ в бакете, размер, MIME, статус («загружается», «готов»).
- Бакет приватный. Доступ — через presigned URL или CDN, а не публичный листинг.

## Загрузка по presigned URL

```text
1 C ─POST /uploads(size,type)─► API
2 API проверяет права, лимиты
  ◄─ presigned PUT URL (TTL 15м)
3 C ─PUT файл───────────► S3
4 S3 ─событие─► обработчик
  (превью, проверка, статус)
5 C ─POST /uploads/id/done─► API
```

- **Presigned URL** — ссылка на конкретный объект с подписью и сроком действия, сгенерированная сервером своими ключами. Клиент **никогда** не получает ключи от бакета; с этой ссылкой он может сделать ровно одну операцию (PUT этого ключа) до истечения срока.
- Сервер разгружен: гигабайты не идут через API, только маленькие JSON-запросы.
- Ключ объекта генерирует сервер (UUID), а не клиент — иначе можно перезаписать чужой файл.
- Лимиты размера и типа задаются в условиях подписи; после загрузки содержимое проверяют (реальный MIME, антивирус).

## Большие файлы: multipart и докачка

- **Multipart upload:** файл режется на части (в S3 от 5 МБ), каждая грузится своим presigned URL, параллельно; в конце сервер вызывает «собрать». Упала часть — повторяем только её.
- **Докачка (resumable):** клиент помнит, какие части уже загружены, и после обрыва продолжает с места. Протокол tus — то же для своего сервера.
- На Android загрузку запускают через WorkManager с ограничением по сети: переживает уход приложения в фон и перезапуск.
- Скачивание больших файлов — HTTP Range-запросы (`Range: bytes=1000000-`), тоже с докачкой.

## Превью и ресайз

```text
S3 original ─event─► queue
  ─► worker: resize 160/480/1080,
     webp/avif, strip EXIF
  ─► S3 thumbs/ ─► CDN
```

- Оригинал не отдают в ленту: генерируют несколько размеров, клиент запрашивает тот, что подходит под экран.
- Обработка асинхронная через очередь; пока превью нет — показываем плейсхолдер или blurhash.
- Удаление EXIF — это ещё и приватность: там бывают координаты съёмки.
- Альтернатива — ресайз «на лету» на CDN/image-сервисе по параметрам URL с кешированием результата.

## CDN

```text
user(МСК) ─► edge МСК ─hit─► файл
               │ miss
               └─► origin (S3)
```

- **CDN** — сеть edge-серверов по миру. Первый запрос в регионе идёт в origin, ответ кешируется на edge, следующие пользователи получают его за миллисекунды.
- Что кешировать и сколько, CDN берёт из `Cache-Control` ответа.
- **Статика с хешем в имени** (`app.3f9a1c.js`, `photos/9f3a.jpg`): `Cache-Control: public, max-age=31536000, immutable` — кешируем навсегда, новая версия = новый URL.
- **Инвалидация (purge)** — принудительно сбросить кеш на edge. Работает, но медленно и ограниченно; правильный путь — версионированные URL.
- Приватный контент через CDN — signed URL/cookies на уровне CDN с коротким сроком.

## Когда применять в SD-задаче

Сигналы: «пользователи загружают фото/видео», «аватарки», «вложения в чате», «лента с картинками», «скачивание обновлений», «пользователи по всему миру».

Фраза на собес: «Файлы в S3, в БД только метаданные; клиент получает presigned URL и грузит напрямую, большие — multipart с докачкой через WorkManager; событие загрузки запускает асинхронную генерацию превью, раздача через CDN с версионированными URL и долгим Cache-Control».

> [!warning] Грабли
> - Загрузка файлов через API-сервер: потоки заняты гигабайтами, сервер падает от нескольких видео.
> - Ключи доступа к бакету в приложении: их вытащат из APK за минуту. Только presigned URL.
> - Публичный бакет с предсказуемыми именами: чужие файлы перебираются.
> - Перезапись файла по тому же URL при наличии CDN и долгого кеша: пользователи видят старую версию.
> - Отдавать оригинал 12 МП в ленту: трафик, память, OOM при декодировании на телефоне.
> - Не чистить незавершённые multipart-загрузки и «брошенные» объекты: платите за хранение мусора (lifecycle-правила бакета).

> [!question]- Как организовать загрузку фото в мобильном приложении?
> Клиент запрашивает у API разрешение на загрузку, сервер проверяет права и лимиты, генерирует ключ объекта и presigned URL с коротким сроком. Клиент загружает файл напрямую в S3 (большие — multipart, с докачкой через WorkManager), затем сообщает API о завершении. Событие хранилища запускает в очереди проверку и генерацию превью; файлы раздаются через CDN.

> [!question]- Что такое presigned URL и чем он безопасен?
> Это URL к конкретному объекту, подписанный ключом сервера, с ограниченным сроком действия и разрешённой операцией (GET или PUT). Клиент не получает учётные данные хранилища и не может сделать ничего, кроме этой операции с этим объектом. Сервер контролирует, кому и что выдавать, и может ограничить размер и тип файла.

> [!question]- Как обновить картинку, которая закеширована в CDN?
> Лучший способ — не обновлять, а выдать новый URL: имя файла с хешем содержимого или версией, тогда старый кеш просто перестаёт использоваться, а у ресурса можно держать max-age на год. Purge (инвалидация) на CDN существует, но он медленный, ограничен по количеству и не трогает кеши клиентов.
