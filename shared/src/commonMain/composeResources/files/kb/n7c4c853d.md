# 22 Партиционирование и шардирование

Партиции — разделение таблицы внутри одной базы. Шарды — распределение данных между узлами. Оба механизма полезны только тогда, когда границы данных совпадают с операциями приложения. Размер таблицы сам по себе не доказывает необходимость ни того, ни другого.

> [!tip] Аналогия из Android
> Партиционирование — как Room с таблицей `messages`, где индекс по `(chatId, createdAt)` даёт читать только нужный чат, а старые чаты чистятся одним `DELETE WHERE createdAt < …`. Шардирование — как разные файлы базы на разные аккаунты: быстро внутри одного аккаунта, но «найти сообщение по тексту во всех аккаунтах» — обход всех файлов.

## Партиционирование

Одна логическая таблица, строка попадает в свою партицию, общие CPU, память и диск. Учебный пример: 500 млн заказов, 2 ТБ, частый диапазон чтения 30 дней, хранение 24 месяца.

```text
orders (логическая таблица)
├── orders_2026_01
├── orders_2026_02  ← WHERE date ≥ 01.02 AND date < 01.03
└── orders_2026_03     читаем только февраль
```

**Способы разделения** выбирают по запросам и жизненному циклу: range (месяцы, интервалы дат или значений), list (явные группы регионов или категорий), hash (группы по хешу ключа).

**Условие запроса должно раскрывать границы.** `WHERE created_at >= '2026-02-01' AND created_at < '2026-03-01'` читает одну партицию. Поиск по `id` без условия по дате может затронуть все партиции. Партиция и индекс работают на разных уровнях: сначала выбираются партиции по фильтру, потом локальный индекс ищет внутри.

**Историю удобно обслуживать целыми частями.** Создать партицию месяца заранее → принимать данные → читать активное → отсоединить старую (DETACH) → архив или удаление. Никакого `DELETE` по 100 млн строк.

**Цена:** много партиций — больше объектов и работы планировщика; в PostgreSQL ключ партиции входит в UNIQUE; пределы CPU и диска остаются общими.

## Шардирование

Теперь части данных живут на разных узлах: каждый шард хранит часть данных на своих CPU, RAM и диске, нагрузка распределяется, репликация нужна каждому шарду отдельно.

Порядок проектирования: нагрузка → частые запросы → граница данных → ключ → размещение. Поле ключа и алгоритм распределения выбирают отдельно.

**Хороший ключ:** кардинальность (много разных значений), распределение (баланс объёма и запросов), локальность (частые операции в одном шарде), стабильность (значение редко меняется). Универсально лучшего ключа нет: `customer_id` держит историю клиента в одном шарде; `order_id` хорош для точечных операций по заказу; `created_at` диапазоном собирает все новые записи в одном месте.

- **Range (`0 ≤ id < 1 млн` → шард 1)** — Соседние значения рядом, range-запросы. Новые id попадают в последний диапазон: горячий хвост.
- **Hash (`hash(customer_id) % N`)** — Много ключей распределяются ровнее. Теряется локальность диапазона; смена N переносит почти всё (нужен consistent hashing).

**Равные объёмы не значат равную нагрузку.** Один активный ключ («на этом шарде Тейлор Свифт», 1M rps против 1K на остальных) хеш сохраняет на одном шарде. Смотрим QPS и p99 по каждому узлу. Горячую нагрузку делят по её причине: горячее чтение — кеш и реплики; крупный клиент — выделенное размещение и лимиты; горячая запись — более дробный ключ, цена — больше чтений и координации.

**Cross-shard.** Глобальный запрос («10 популярных постов») уходит всем шардам, координатор объединяет ответы (scatter-gather): хвост задержки становится важнее — ответ не быстрее самого медленного шарда.

**Локальность (colocation).** Связанные таблицы с общим ключом (`customer 42`, `orders 42`, `items 42`) на одном шарде: соединения локальны, частые транзакции остаются в шарде. Данные на разных шардах — нужна координация.

**Транзакции между шардами** требуют явной модели: локальная (внутри шарда), распределённая (общий commit с сетевой координацией, 2PC), сага (шаги и компенсации бизнес-процесса). Сага не равна атомарному откату.

**Resharding.** Перенос данных: копия → догнать изменения → проверить → переключить маршрут → завершить. В каждый момент понятен владелец записи и способ восстановления.

**Эксплуатация.** По каждому шарду: QPS, p99, CPU, диск, размер. Актуальная карта маршрутизации и повторы. Реплики, backup, восстановление. Запас на рост и миграции. Продукт управляет механикой, ключ выбираем мы: PostgreSQL — локальные партиции, Citus — распределение поверх PostgreSQL, MongoDB — ключ, роутеры и балансировка.

## Вместе

Два ключа: `hash(customer_id)` определяет шард, `created_at` — месяц внутри шарда, реплика копирует данные шарда. Ключ клиента выбирает шард, дата выбирает партицию.

## Когда применять в SD-задаче

Сигналы партиций: «таблица на миллиарды строк», «читаем последние 30 дней», «удалять старше двух лет». Сигналы шардов: «не влезает на один сервер», «запись упёрлась в один primary», «данные за 5 лет». Сначала партиции (одна база, просто), потом шарды (отдельная операционная сложность).

Фраза на собес: «Таблицу постов партиционирую по месяцу создания: лента читает последние недели, посты старше двух лет отсоединяю партицией в архив. Если запись упрётся в один сервер, шардирую по `author_id`: посты автора и его лента в одном шарде, раскладка хешем, с consistent hashing. Ленту «популярное» строю заранее, а не scatter-gather по всем шардам».

> [!warning] Грабли
> - Партиции без условия по ключу партиции в запросах: читаются все части, выигрыша нет.
> - Ждать от партиций ускорения вместо индекса: они не заменяют индексы.
> - Шард по `created_at`: вся запись в один «сегодняшний» шард.
> - `hash % N` без consistent hashing: добавил узел — переехало всё.
> - Равномерный объём при неравномерной нагрузке: hot shard от одного клиента.
> - Транзакция через два шарда «как раньше»: либо 2PC с его ценой, либо сага, но явно.
> - Шардировать до того, как попробованы индексы, кеш, реплики и партиции.

> [!question]- Чем партиционирование отличается от шардирования?
> Партиционирование делит таблицу внутри одной базы: читаем только нужную часть, обслуживаем историю целыми частями, но CPU и диск общие. Шардирование раскладывает данные по разным узлам с независимыми ресурсами: масштабирует запись и объём, но приносит cross-shard запросы, горячие шарды, распределённые транзакции и миграции.

> [!question]- Как выбрать ключ шардирования?
> От частых запросов и транзакций: ключ должен держать их внутри одного шарда (локальность), иметь много значений (кардинальность), давать ровное распределение объёма и нагрузки и редко меняться. Проверить отдельно равномерность хранения и равномерность нагрузки: один горячий ключ ломает ровный хеш.

> [!question]- Как удалить посты старше двух лет из таблицы на 100 млн строк?
> Партиционировать по месяцу создания и отсоединять старые партиции целиком (DETACH → архив или DROP). Построчный DELETE на десятки миллионов строк — блокировки, раздувание таблицы и часы работы.
