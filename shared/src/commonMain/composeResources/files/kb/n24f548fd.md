# Задачи на корутины

## Задача 1. Какой результат будет выведен?

```kotlin
fun main() {
    runBlocking {
        val scope = CoroutineScope(SupervisorJob())

        // Этот scope не должна уронить ошибка
        scope.launch {
            launch { delay(1000); println("11") }
            launch { delay(1000); println("12") }
        }

        // Этот scope уронит ошибка
        scope.launch {
            launch { delay(1000); println("21") }
            launch {
                delay(1000)
                launch {
                    println("22")
                    throw RuntimeException()
                }
            }
        }
    }
}
```

### Разбор

**Шаг 0. Строим дерево корутин — с него начинается любая такая задача.**

Вопрос к каждому `launch`: **на каком scope он вызван?** От этого зависит, кто его родитель.

```text
runBlocking (Job A)          ← своё дерево, детей НЕТ
scope (SupervisorJob)        ← ОТДЕЛЬНОЕ дерево, к runBlocking не привязано
├── scope.launch №1          ← прямой ребёнок supervisor'а
│   ├── launch → "11"
│   └── launch → "12"
└── scope.launch №2          ← прямой ребёнок supervisor'а
    ├── launch → "21"
    └── launch (B)
        └── launch → "22" + throw   ← внук №2
```

Ключевое наблюдение: `scope.launch` вызван на **своём** `scope`, а не на `this` из `runBlocking`. Значит, оба верхних `launch` — дети `SupervisorJob`, а у `runBlocking` детей **ноль**. Два дерева никак не связаны.

**Шаг 1. Кого ждёт `runBlocking`?**

`runBlocking` блокирует поток до завершения **своей** джобы, а джоба завершается, когда завершились её **дети**. Детей нет → тело выполнилось (мгновенно: оба `scope.launch` только *запустили* корутины и вернулись) → `runBlocking` отпускает поток → `main()` завершается.

**Шаг 2. Ответ: ничего не выведется.**

`CoroutineScope(SupervisorJob())` без диспетчера работает на `Dispatchers.Default` — его потоки **daemon**, JVM их не ждёт. `main` вернулся на ~0 мс, а первые `println` были бы на ~1000 мс. JVM вышла — корутины умерли молча.

**Шаг 3. «А если дождаться?» — вопрос, который зададут следующим.**

Чиним ожидание (собираем джобы и `joinAll()`, либо пишем `runBlocking { ... }` вокруг `scope.coroutineContext[Job]!!.children`) — и теперь работает вторая половина задачи, про исключение. Трассируем путь `RuntimeException` **снизу вверх по дереву**:

1. ~1000 мс: печатаются `21` и `22` (и `11`, `12` из первого блока — все на одной отметке, порядок между ними недетерминирован).
2. Внук №2 бросает `RuntimeException` → падает сам и **сообщает родителю** (launch B).
3. B — обычный `Job`, не supervisor → падает и сообщает выше, в `scope.launch №2`. Тот **отменяет остальных своих детей** (корутину с `21` — но она уже успела напечатать: обе были на отметке 1000 мс, а исключение летит уже *после* неё).
4. Исключение доходит до `scope.launch №2` → он падает и сообщает в `SupervisorJob`. **Вот здесь распространение останавливается**: supervisor по контракту не падает от ошибки ребёнка и **не трогает других детей** → `scope.launch №1` c `11`/`12` живёт как ни в чём не бывало.
5. Раз исключение никем не обработано — оно уходит в `CoroutineExceptionHandler` (если задан) или в uncaught handler потока → в консоли стектрейс.

Итог гипотетического сценария: `11`, `12`, `21`, `22` (порядок между блоками недетерминирован) + стектрейс.

**Шаг 4. Как правильно привязать корутины к дереву `runBlocking` — три способа:**

1. **`supervisorScope` (идиоматично)** — не создавать отдельный scope вообще:

```kotlin
runBlocking {
    supervisorScope {                    // ребёнок runBlocking
        launch { /* 11, 12 */ }          // прямые дети supervisor'а — изолированы
        launch { /* 21, 22, throw */ }
    }
}
```

`supervisorScope` — suspend-функция: не вернётся, пока не завершатся все её дети → `runBlocking` автоматически всё дождётся. Одно дерево, structured concurrency, изоляция прямых детей сохранена.

2. **`SupervisorJob(parent = ...)`** — вживить свой scope в дерево:

```kotlin
val supervisor = SupervisorJob(parent = coroutineContext.job)
val scope = CoroutineScope(supervisor)
scope.launch { /* ... */ }
supervisor.complete()   // ← без этого runBlocking повиснет НАВСЕГДА
```

Ловушка: `SupervisorJob()` — «вечный» `CompletableJob`, сам не завершается никогда. Обязателен `complete()`: «завершаюсь — дожидаюсь детей». Забыть — дедлок.

3. **`joinAll(j1, j2)`** — деревья остаются раздельными, просто ждём вручную. `join` — «дождаться», а не «усыновить»: отмена `runBlocking` эти корутины не отменит, исключения к нему не полетят. Не structured — годится для тестов/`main`, не для прода.

**Частые ошибки в ответе:**

- «SupervisorJob защитит и вложенные launch» — нет. Supervisor изолирует **только прямых детей** (`scope.launch №1` от `№2`). Внутри блока №2 вся цепочка `внук → B → №2` — обычные джобы, они падают по цепочке. Комментарии в коде («этот scope не уронит / этот уронит») именно про это.
- «try/catch вокруг launch поймает» — не поймает: исключение из `launch` идёт **по дереву джоб**, а не по стеку вызовов.
- Ответить про supervisor, не заметив, что программа вообще ничего не печатает — задача-матрёшка: сначала «кто кого ждёт», и только потом «кто кого роняет».

> [!tip] Вывод
> Две идеи на одной задаче: (1) `runBlocking` ждёт только **свои дочерние** корутины — чужой scope ему никто; (2) исключение поднимается по дереву джоб до первого supervisor'а: он спасает **соседей упавшей ветки**, но не тех, кто внутри неё. Алгоритм решения: нарисовать дерево → понять, кто кого ждёт → провести исключение снизу вверх до supervisor'а.

## Задача 2. Отменится ли корутина?

```kotlin
fun main() {
    runBlocking {
        val job = launch {
            while (true) {
                Thread.sleep(1000) // блокирует поток
                println("Loading progress")
            }
        }
        launch(Dispatchers.IO) {
            delay(5000)
            job.cancel()
        }
    }
}
```

### Разбор

**Нет, корутина не отменится** — будет печатать `Loading progress` бесконечно.

Отмена в корутинах **кооперативная**: `cancel()` лишь помечает джобу как отменяемую, а реально прерывание происходит только в **точках приостановки** (`delay`, `yield`, `ensureActive()`). Здесь:

- `Thread.sleep(1000)` — блокирующий вызов, **не** точка приостановки.
- `while (true)` никогда не приостанавливается и не проверяет `isActive`.

**Как починить:**

```kotlin
// Вариант 1: delay вместо Thread.sleep (бросит CancellationException)
while (true) {
    delay(1000)
    println("Loading progress")
}

// Вариант 2: проверять активность джобы
while (isActive) {
    Thread.sleep(1000)
    println("Loading progress")
}

// Вариант 3: явная проверка
while (true) {
    ensureActive()
    Thread.sleep(1000)
}
```

## Задача 3. Отрефакторить код

```kotlin
class ProductFragment : Fragment() {

    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        val productModel: ProductViewModel by lazy {
            ProductViewModel(
                id = requireArguments().getInt(ARG_PRODUCT_ID),
                context = requireContext()
            )
        }

        return ComposeView(requireContext()).apply {
            setContent {
                ProductScreen(viewModel = productModel)
            }
        }
    }
    // ...
}

@Composable
fun ProductScreen(viewModel: ProductViewModel) {
    val context = LocalContext.current
    val scope = rememberCoroutineScope()
    val product by viewModel.product.collectAsState(initial = null)
    val inCartCount by viewModel.inCartCount.collectAsState(initial = 0)

    scope.launch {
        viewModel.sendLog("Widget was composed ${product?.id}")
    }

    LaunchedEffect(inCartCount) {
        delay(CART_ANIMATION_DELAY_MS)
    }

    Column(modifier = Modifier.fillMaxSize().background(Color.Blue)) {
        ProductContent(context = context, product = product, inCartCount = inCartCount)
    }
}
```

### Что не так

1. **`ViewModel` создаётся вручную и с `context`.** `ProductViewModel(... context = requireContext())` хранит ссылку на Activity-контекст → **утечка памяти**, ViewModel живёт дольше View. Создавать нужно через `by viewModels { factory }`, а контекст в VM не передавать (нужен ресурс — брать `Application` или прокинуть строку/репозиторий).
2. **`by lazy` как локальная переменная в `onCreateView`.** ViewModel пересоздаётся при каждом пересоздании View и **не переживает поворот экрана**. Должна храниться делегатом `viewModels()`/`activityViewModels()`.
3. **`scope.launch { ... }` прямо в теле `@Composable`.** Это запускается на **каждой рекомпозиции** → новая корутина каждый раз. Сайд-эффект нужно вынести в `LaunchedEffect` с правильным ключом.
4. **`rememberCoroutineScope()` для логирования** — лишний; для эффекта при появлении используем `LaunchedEffect`.
5. **`context` прокидывается в `ProductContent` и в VM** — UI не должен раздавать `Context`; это связывает слои.
6. **`collectAsState`** не учитывает жизненный цикл — лучше `collectAsStateWithLifecycle()`.
7. **`Color.Blue` хардкодом** — цвета из темы (`MaterialTheme.colorScheme`).

### Решение (эскиз)

```kotlin
class ProductFragment : Fragment() {

    private val viewModel: ProductViewModel by viewModels {
        ProductViewModel.factory(
            productId = requireArguments().getInt(ARG_PRODUCT_ID)
        )
    }

    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?
    ): View = ComposeView(requireContext()).apply {
        setViewCompositionStrategy(DisposeOnViewTreeLifecycleDestroyed)
        setContent {
            AppTheme {
                ProductScreen(viewModel = viewModel)
            }
        }
    }
    // ...
}

@Composable
fun ProductScreen(viewModel: ProductViewModel) {
    val product by viewModel.product.collectAsStateWithLifecycle()
    val inCartCount by viewModel.inCartCount.collectAsStateWithLifecycle()

    // лог — один раз при смене id, а не на каждой рекомпозиции
    LaunchedEffect(product?.id) {
        product?.id?.let { viewModel.sendLog("Widget was composed $it") }
    }

    LaunchedEffect(inCartCount) {
        delay(CART_ANIMATION_DELAY_MS)
        // анимация
    }

    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(horizontal = 16.dp)
            .background(MaterialTheme.colorScheme.background)
    ) {
        ProductContent(product = product, inCartCount = inCartCount)
    }
}
```

> [!tip] Что подсветить на собесе
> Главные грехи: **передача `Context` в `ViewModel`** (утечка) и **запуск корутины прямо в теле `@Composable`** (на каждой рекомпозиции). Сайд-эффекты в Compose — только через `LaunchedEffect`/`rememberCoroutineScope` с обработчиком события, и с осмысленным ключом.
