## **Garbage Collector (GC)**

**Garbage Collector (GC)** — это механизм управления памятью в JVM, который автоматически освобождает память, занятую неиспользуемыми объектами. Основная цель GC — предотвратить утечку памяти, автоматически очищая память от объектов, на которые больше не существует ссылок.

### **Как работает Garbage Collector в JVM?**
Garbage Collector работает по принципу отслеживания ссылок между объектами и использования этой информации для освобождения памяти. Его основная задача — найти объекты, которые больше не используются в программе, и освободить их память.

### GC выполняет несколько шагов:

1. **Определение “достижимости” объектов:**
• **Достижимыми** считаются объекты, на которые существуют активные ссылки, т.е. на которые можно попасть через цепочку ссылок, начиная с корня (например, из стека, статических переменных и т.д.).
• **Недостижимыми** являются объекты, на которые больше нет ссылок. Эти объекты можно считать “мусором” и их память можно освобождать.

2. **Алгоритмы сборки мусора:**
В JVM используется несколько алгоритмов для сборки мусора, наиболее известные из которых:

• **Mark-and-Sweep (Пометить и очистить):**
1. **Mark** — все объекты, которые достижимы (есть ссылка на объект), помечаются как “активные”.
2. **Sweep** — затем проходят по всем объектам, удаляя те, которые не были помечены как активные.

### **Generational Garbage Collection (Поколенческая сборка мусора):**

JVM делит кучу на несколько областей (поколений), что помогает улучшить производительность:
• **Молодое поколение (Young Generation):** объекты, которые недавно созданы.
• **Старое поколение (Old Generation):** объекты, которые существуют долго и перемещаются сюда после того, как пережили несколько сборок мусора в молодом поколении.
• **Сборка мусора в молодом поколении:** происходит чаще, потому что объекты в этом поколении обычно “короткоживущие” (например, временные объекты).
• **Сборка мусора в старом поколении:** реже, так как объекты в старом поколении живут дольше.

### **Фазы сборки мусора:**
Сборка мусора в JVM обычно делится на несколько фаз:
• **Minor GC (Маленькая сборка мусора):** происходит в молодом поколении. Это более быстрый процесс, потому что обычно освобождается меньше памяти.
• **Major GC или Full GC (Полная сборка мусора):** происходит в старом поколении. Это более затратный процесс, так как приходится проверять все объекты в куче и освободить их память.

### **Как работает Generational Garbage Collection?**

JVM использует **поколенческую модель** для оптимизации работы сборщика мусора. В этой модели куча разделена на несколько частей:

1. **Young Generation:**
• Состоит из:
• **Eden Space:** новое место для объектов.
• **Survivor Spaces (S0 и S1):** два пространства, куда перемещаются объекты, пережившие первую сборку мусора.
• Объекты, создаваемые в Eden, обычно очень быстро становятся ненужными. Те объекты, которые “выживают” несколько циклов сборки, перемещаются в Survivor Spaces и в дальнейшем могут быть перемещены в старое поколение.

2. **Old Generation:**
• Это область памяти для долгоживущих объектов.
• Сюда попадают объекты, которые пережили несколько циклов сборки мусора в Young Generation.

3. **Permanent Generation (в старых версиях Java до Java 8) или Metaspace (в Java 8 и позже):**

• Это область памяти, где хранятся метаданные, например, информация о классах и методах.

### **Типы Garbage Collection в JVM:**

1. **Serial Garbage Collector:**
• Используется для однопоточных приложений.
• Все фазы GC выполняются в одном потоке, что делает его медленным для многозадачных приложений.

2. **Parallel Garbage Collector:**
• Использует несколько потоков для параллельной обработки сборки мусора в молодом поколении.
• Это повышает производительность, особенно на многозадачных машинах.

3. **CMS (Concurrent Mark-Sweep) Garbage Collector:**

• Пытается уменьшить время, когда приложение не может работать, выполняя часть работы параллельно с потоками приложения.
• Работает в два этапа: метка (Mark) и очистка (Sweep).

4. **G1 (Garbage First) Garbage Collector:**

• Современный сборщик мусора, предназначенный для серверных приложений с большим объемом памяти.
• Разбивает кучу на несколько “регионов”, что позволяет более эффективно управлять сборкой мусора в разных частях памяти.

**Когда и как часто происходит сборка мусора?**
• **Когда:** Сборка мусора происходит, когда:
• Процессор не может найти достаточно свободной памяти.
• Количество доступной памяти на куче становится слишком низким.
• Память в старом поколении исчерпана.
• **Частота:**
• Для младшего поколения (Young Generation) сборка мусора выполняется часто, так как объекты в этом поколении часто уничтожаются.
• Для старшего поколения (Old Generation) сборка мусора происходит реже.

> Можно ли самим запустить GC ? 
> - Да. System.gc() или Runtime.getRuntime().gc().

Пример очистки Weakreference и вызова GC
   
```kotlin
fun main() {  
    val weakRefList = mutableListOf<WeakReference<MyClass>>()  
  
    // Создание объектов и добавление их в коллекцию как слабые ссылки  
    for (i in 1..5) {  
        val obj = MyClass(i)  
        val weakRef = WeakReference(obj)  
        weakRefList.add(weakRef)  
    }  
  
    // Удаление сильных ссылок на объекты  
    System.gc()  
  
    // Печать объектов, которые еще не были собраны сборщиком мусора  
    for (weakRef in weakRefList) {  
        val obj = weakRef.get()  
        if (obj != null) {  
            println("Object: ${obj.value}")  
        } else {  
            println("Object has been garbage collected")  
        }  
    }  
}  
  
data class MyClass(val value: Int)
```

### **Виды ссылок**

В языке Java (и Kotlin, который работает на JVM) существуют разные виды ссылок, каждая из которых имеет свои особенности в отношении управления памятью и сборки мусора. Это важные концепции для эффективного использования памяти и управления объектами.

**Типы ссылок в Java (и Kotlin):**

1. **Strong Reference (Сильная ссылка)**
2. **Weak Reference (Слабая ссылка)**
3. **Soft Reference (Мягкая ссылка)**
4. **Phantom Reference (Фантомная ссылка)**


**1. Strong Reference (Сильная ссылка)**

• **Сильная ссылка** — это стандартная ссылка, которую мы используем в коде для создания объектов. Объект, на который есть сильная ссылка, **не будет удален сборщиком мусора**, пока существует эта ссылка.
```kotlin
fun main() {
    val person = Person("John")  // сильная ссылка на объект
    println(person.name)
}
```
**Как работает:**

• Пока объект person существует и на него есть сильная ссылка, он не будет удален сборщиком мусора.
• Сильные ссылки — это нормальные ссылки, которые мы используем ежедневно

**2. Weak Reference (Слабая ссылка)**

• **Слабая ссылка** — это ссылка, которая ==**не препятствует удалению объекта**== сборщиком мусора, если на объект больше нет сильных ссылок.
• Когда на объект остаются только слабые ссылки, объект будет удален при следующем запуске сборщика мусора.

**Пример:

```kotlin
import java.lang.ref.WeakReference

fun main() {
    val person = Person("John")
    val weakRef = WeakReference(person)  // создаем слабую ссылку на объект

    println(weakRef.get()?.name)  // выводит "John"
    
    // Если после этого объект person больше не будет использоваться, то он будет удален сборщиком мусора
    System.gc()  // запускаем сборщик мусора вручную

    println(weakRef.get()?.name)  // может быть null, если объект был удален
}
```

**Как работает:**

• Если объект больше ==не имеет сильных ссылок, а только слабые, то сборщик мусора удалит его==.
• Слабая ссылка полезна, когда вам нужно поддерживать ссылку на объект, но не препятствовать его удалению при нехватке памяти (==например, кэш==).

**3. Soft Reference (Мягкая ссылка)**

• **Мягкая ссылка** — это ссылка, которая, как и слабая ссылка, не предотвращает удаление объекта сборщиком мусора.
• Однако сборщик мусора будет **удалять объект с мягкими ссылками** ==только в том случае, если **память на устройстве ограничена**==.
• Мягкие ссылки полезны для реализации кэширования, так как объект может быть удален только в случае нехватки памяти

```kotlin
import java.lang.ref.SoftReference

fun main() {
    val person = Person("John")
    val softRef = SoftReference(person)  // создаем мягкую ссылку на объект

    println(softRef.get()?.name)  // выводит "John"

    // После этого объект может быть удален только если система испытывает дефицит памяти
}
```

**Как работает:**
• Сборщик мусора удаляет объект с мягкой ссылкой ==**только при нехватке памяти**==, что делает его полезным для кэширования, когда вы хотите, чтобы объекты оставались в памяти, если есть достаточно ресурсов.

**4. Phantom Reference (Фантомная ссылка)**

• **Фантомная ссылка** — это наиболее сложный тип ссылки. Он используется для того, ==чтобы узнать, когда объект **приближается к удалению**==.

• Фантомная ссылка не может быть использована напрямую для получения объекта. Ее основное предназначение — это способ получения уведомления, когда объект стал кандидатом на удаление, но еще не был удален.

**Пример:**

```kotlin
import java.lang.ref.PhantomReference
import java.lang.ref.ReferenceQueue

fun main() {
    val referenceQueue = ReferenceQueue<Person>()
    val person = Person("John")
    val phantomRef = PhantomReference(person, referenceQueue)  // создаем фантомную ссылку на объект

    println(phantomRef.get())  // всегда возвращает null

    // Фантомная ссылка используется, чтобы отслеживать объекты, которые скоро будут удалены.
    // Она не позволяет получить доступ к объекту, но помогает отслеживать момент его удаления.
}
```

**Как работает:**

• ==**Фантомная ссылка** не позволяет получить доступ к объекту напрямую.==
• ==Она используется для более низкоуровневого управления памятью и для уведомлений, когда объект будет удален.==
• Это наиболее сложная ссылка и используется редко, например, для реализации некоторых типов очистки ресурсов.

### **Как использовать ссылки в различных сценариях?**

• **Сильные ссылки** являются наиболее распространенным способом создания и работы с объектами.
• **Слабые ссылки** полезны в ситуациях, когда вы хотите, чтобы объект мог быть удален, но хотите избежать его удаления, если на него существует хотя бы одна сильная ссылка (например, кэш, к которому должны быть слабые ссылки).
• **Мягкие ссылки** обычно используются для **кэширования объектов**, которые могут быть удалены только при нехватке памяти.
• **Фантомные ссылки** используются в сценариях, где нужно получить уведомление о том, что объект будет удален, но сам объект уже не доступен для работы.

**1. Пример использования WeakReference в Android**

**WeakReference** часто используется для хранения объектов, на которые не нужно удерживать жесткие ссылки. Например, когда вы хотите избежать утечек памяти при использовании слушателей событий, обработчиков или адаптеров.

**Пример: Использование WeakReference для хранения ссылки на Activity**

Одним из типичных случаев использования WeakReference является избежание утечек памяти в Activity или Fragment при работе с асинхронными задачами или обработчиками.
```kotlin
import android.os.Bundle
import android.os.Handler
import android.widget.TextView
import androidx.appcompat.app.AppCompatActivity
import java.lang.ref.WeakReference

class MyActivity : AppCompatActivity() {

    private lateinit var myTextView: TextView

    // Сильная ссылка на Handler
    private val handler = Handler()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        myTextView = findViewById(R.id.myTextView)

        // Создаем слабую ссылку на Activity
        val weakActivity = WeakReference(this)

        // Выполняем задачу с задержкой
        handler.postDelayed({
            // Проверяем, что Activity всё ещё существует, перед доступом к UI
            weakActivity.get()?.let {
                it.myTextView.text = "Задача выполнена!"
            }
        }, 2000)
    }

    override fun onDestroy() {
        super.onDestroy()
        // Освобождаем слабую ссылку, чтобы избежать утечек памяти
    }
}
```

**Что происходит:**

• В данном примере мы используем WeakReference для хранения ссылки на Activity. Если Activity будет уничтожена (например, пользователь перейдет на другую активность), сборщик мусора сможет освободить память, даже если у нас есть слабая ссылка.
• Это помогает предотвратить утечки памяти, когда асинхронная задача или обработчик удерживает ссылку на объект Activity после ее уничтожения.

**2. Пример использования SoftReference в Android**

**SoftReference** используется, когда объекты могут быть удалены сборщиком мусора, если в системе не хватает памяти. Это полезно для кэширования данных, например, изображений или других ресурсов, которые можно восстановить при необходимости, но не критичны для приложения.

**Пример: Использование SoftReference для кэширования изображений**

Предположим, что у вас есть приложение, которое загружает изображения. Чтобы избежать постоянной загрузки изображений и экономить память, можно использовать **SoftReference** для кэширования изображений.

```kotlin
import android.graphics.Bitmap
import android.os.Bundle
import android.widget.ImageView
import androidx.appcompat.app.AppCompatActivity
import java.lang.ref.SoftReference

class ImageCachingActivity : AppCompatActivity() {

    private lateinit var imageView: ImageView
    private var softBitmapRef: SoftReference<Bitmap>? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_image_caching)

        imageView = findViewById(R.id.imageView)

        // Попытка получить изображение из кэша
        val cachedBitmap = softBitmapRef?.get()
        if (cachedBitmap != null) {
            imageView.setImageBitmap(cachedBitmap)
        } else {
            // Если изображения нет в кэше, загружаем его
            val bitmap = loadImage()  // Функция для загрузки изображения
            softBitmapRef = SoftReference(bitmap)
            imageView.setImageBitmap(bitmap)
        }
    }

    // Пример функции для загрузки изображения (можно использовать библиотеку, например, Picasso)
    private fun loadImage(): Bitmap {
        // Загрузить изображение (например, из сети или ресурсов)
        // Для примера просто создадим пустой Bitmap
        return Bitmap.createBitmap(100, 100, Bitmap.Config.ARGB_8888)
    }
}
```

**Что происходит:**

• В данном примере мы создаем SoftReference для изображения (Bitmap), чтобы кэшировать изображение.
• Когда память становится низкой, объект с мягкой ссылкой может быть удален сборщиком мусора, что помогает избежать перегрузки памяти.
• Если изображение было удалено, оно будет загружено заново.

### **GC Roots**

**GC Roots** — это объекты, которые служат начальной точкой для процесса сборки мусора (garbage collection) в **Java** и **Android**. Эти объекты гарантированно остаются в памяти, пока они не будут удалены. Сборщик мусора начинает обходить все объекты, начиная с GC roots, и помечает те, которые достижимы. Все объекты, которые не достижимы от GC roots, считаются **мусором** и могут быть удалены.

## Вот основные **виды GC Roots**, которые используются в Java (и Android):

**✅ 1. Статические поля (Static Fields)**

• **Описание**: Все объекты, которые сохраняются в статических полях классов, являются GC roots, так как они существуют на протяжении всего времени работы программы. Эти объекты могут быть как примитивами, так и ссылками на другие объекты.

• **Пример**:

```java
public class MyClass {
    public static MyObject staticObject = new MyObject(); // staticObject - это GC root
}
```

**✅ 2. Активные потоки (Active Threads)**

• **Описание**: Все объекты, которые принадлежат активным потокам, являются GC roots. Каждый поток может иметь локальные переменные, и все эти переменные могут быть использованы в процессе сборки мусора.

• **Пример**:

• Переменные в **потоке** (например, в методах или локальных переменных) могут стать GC roots.

```java
Thread thread = new Thread() {
    public void run() {
        MyObject obj = new MyObject(); // obj будет GC root
    }
};
thread.start();
```

**✅ 3. Регистрированные объекты JNI (Java Native Interface)**

• **Описание**: Взаимодействие с нативным кодом (через JNI) также может служить GC root. Например, если объект передается в нативный код и сохраняется там, то он будет удерживаться в памяти до тех пор, пока не будет освобожден нативным кодом.

• **Пример**:

• Взаимодействие с нативным кодом через JNI, где объекты передаются между Java и C/C++ кодом.

  
**✅ 4. Контексты классов (Class Loaders)**

• **Описание**: Каждый загруженный класс является GC root. Контексты классов (Class Loaders) сами по себе могут содержать ссылки на объекты, что делает их корнями для сборщика мусора.

• **Пример**:

• Если класс загружен с помощью ClassLoader, то объект этого загрузчика также будет считаться GC root.

  
**✅ 5. Локальные переменные и параметры метода**

• **Описание**: Локальные переменные и параметры метода (в процессе исполнения текущего метода) являются GC roots, так как они доступны в текущем контексте выполнения.

• **Пример**:

```java
public void someMethod() {
    MyObject obj = new MyObject(); // obj - это GC root, пока метод выполняется
}
```

**✅ 6. Статические ссылки через Reflection**

• **Описание**: Использование **Reflection** может позволить ссылаться на объекты, которые также становятся GC roots. Это важно для динамического доступа к объектам и их методам.

**✅ 7. Ссылки на объект в процессе вычислений или операций в Java Virtual Machine (JVM)**

• **Описание**: В процессе вычислений объекты, которые временно используются в стеке вызовов JVM, также могут быть GC roots.

**🔥 Основные типы GC Roots**

1. **Статические поля** (static fields)
2. **Активные потоки** (active threads)
3. **JNI объекты** (связанные с нативным кодом)
4. **Загруженные классы** (class loaders)
5. **Локальные переменные и параметры методов**
6. **Reflection ссылки** и другие динамические ссылки


**🚀 Как это работает в процессе GC?**

• **GC (сборщик мусора)** начинает свою работу с проверки всех **GC roots**. Все объекты, которые достижимы через эти корни, считаются «живыми» и не подлежат удалению.
• Все объекты, которые не достижимы от GC roots, считаются «мусором» и могут быть удалены.

**❗ Важно:**

Процесс идентификации достижимых объектов требует, чтобы GC roots не были “заблокированы”. Например, если объект хранится в статическом поле и ссылка на него не меняется, то он будет оставаться в памяти.



## **📌 Что такое родительский объект в Java/Kotlin?**

В **Java/Kotlin** родительский объект (**Parent Object**) — это объект, который **содержит ссылки** на другие объекты (**дочерние объекты, Child Objects**).

Пример

```kotlin
class Parent {
    val child = Child()  // Родитель держит ссылку на Child
}

class Child

fun main() {
    val parent = Parent() // Создаём объект Parent (и он создаёт Child)
}
```

📌 **В этом случае** Parent **— родительский объект**, так как он **хранит ссылку на** Child.

**🚀 Как работает Garbage Collector (GC) со Strong References?**

**Garbage Collector (GC)** в **JVM (Java Virtual Machine)** использует **систему ссылок**, чтобы определить, какие объекты **ещё нужны**, а какие можно **удалить**.

**🔗 Strong Reference (Сильная ссылка)**

Если у объекта есть **strong reference (обычная ссылка,** val **или** var**)**, **GC не может его удалить**.

```kotlin
class Parent {
    val child = Child()  // strong reference
}

fun main() {
    val parent = Parent() // Parent создаёт Child
    // Пока 'parent' в памяти, 'child' тоже не удаляется
}
```
🔹 **GC НЕ удалит** child**, пока** parent **существует.**

**🔥 Когда GC удаляет объект со strong reference?**

GC удаляет объект **только если на него больше нет ссылок**.

**Пример 1: Убираем ссылку**
```kotlin
fun main() {
    var parent: Parent? = Parent()  // Создаём объект
    parent = null  // Теперь у объекта нет ссылок → GC удалит его!
}
```

✅ **Теперь объект** Parent **недоступен → GC удаляет** Parent **и** Child**!**

**Пример 2: Циклические ссылки и GC**

Если два объекта **ссылаются друг на друга**, но нет **внешней ссылки** — GC их удалит!
```kotlin
class A {
    var b: B? = null
}

class B {
    var a: A? = null
}

fun main() {
    val objA = A()
    val objB = B()
    
    objA.b = objB  // A ссылается на B
    objB.a = objA  // B ссылается на A

    // Объекты ссылаются друг на друга, но мы убираем внешнюю ссылку:
    objA.b = null
    objB.a = null

    // Теперь на них никто не ссылается → GC удалит их!
}
```

✅ **JVM GC умеет находить и удалять такие “циклы”!**


## Как GC может почистить объекты которые ссылаются на Context ? Как GC может до них дотянуться? 

**Как работает сборщик мусора (GC) в Java/Android?**

Сборщик мусора очищает объекты, которые:

1. ==**Недостижимы:** на них нет активных ссылок.==
2. ==**Не имеют пути от GC Roots:** объект должен быть достижим от корневого объекта.==

**Что такое GC Roots?**

GC Roots — это объекты, которые **никогда не могут быть очищены** сборщиком мусора.

**🧠 Примеры GC Roots:**

1. **Threads:** активные потоки (Main Thread).
2. **Static объекты:** любые static переменные.
3. **Activity & Application Context:** пока Activity не завершена или Application жив.
4. **Local переменные методов:** объекты в стеке выполнения метода.
5. **Active View Hierarchy:** все виджеты, которые привязаны к активному окну (Window).


**Когда объект с Context может быть очищен GC?**

1. **Activity или Fragment завершены:**

• Если Activity вызвала finish(), все её View становятся недостижимыми.
• Сборщик мусора может очистить их, если на них нет активных ссылок.

1. **Объект вне GC Roots:**

• Если объект с Context не сохраняется в static, Thread, или других GC Roots, он может быть очищен.

1. **При onDestroy():**

• Если Context использовался в Service, BroadcastReceiver или Fragment, и они завершены.

---

**🚨 Когда объект с Context НЕ может быть очищен? (Memory Leak)**

**1. Static ссылки:**

```kotlin
object Singleton {
    var context: Context? = null
}

// ❌ Memory Leak
Singleton.context = activity
```

• Так как Singleton — это GC Root, Activity останется в памяти, даже если она завершена.

---

**2. Долгоживущие объекты (Thread, Handler, Timer):**
```kotlin
class MyThread(context: Context) : Thread() {
    private val contextRef = context

    override fun run() {
        Thread.sleep(10000) // Долгое выполнение
        println(contextRef.packageName)
    }
}
```

• Пока поток активен, он удерживает ссылку на Context, препятствуя сбору мусора.

---
**3. Inner class в Activity:**

```kotlin
class MyActivity : AppCompatActivity() {

    private val runnable = Runnable {
        // Использование ссылки на Activity
        println(this.packageName)
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Handler(Looper.getMainLooper()).postDelayed(runnable, 10000)
    }
}
```


• Вложенный класс (inner class) неявно содержит ссылку на внешний класс (Activity).
• Пока Runnable ожидает выполнения, Activity не может быть очищена.

🛠 **Решение:** Использовать WeakReference или static class.

> [!important] Важно для Android-собеса: ART ≠ HotSpot JVM
> Описанные выше сборщики (Serial, Parallel, **CMS**, **G1**) и `PermGen`/`Metaspace` — это про **HotSpot JVM** (десктоп/сервер). На Android код исполняет **ART (Android Runtime)** со **своим** GC:
> - ART использует **concurrent copying GC** (большая часть работы — параллельно с приложением, минимизируя паузы).
> - Куча тоже делится на пространства (в т.ч. для молодых/старых объектов), но названия и алгоритмы отличаются от HotSpot.
> - `System.gc()` на Android — лишь **подсказка**, ART вправе её проигнорировать; вызывать в проде не нужно.
> Поэтому на собесе по Android: общие принципы (достижимость от GC Roots, mark-and-sweep, поколения) — верны, но не приписывай Android именно G1/CMS.

> [!tip] Сводка по видам ссылок
> | Ссылка    | GC удалит объект, когда...                          | Применение                         |
> | --------- | -------------------------------------------------- | ---------------------------------- |
> | **Strong**  | никогда (пока есть ссылка)                         | обычные ссылки                     |
> | **Soft**    | при нехватке памяти                               | кэш (картинки), который не жалко   |
> | **Weak**    | при первой же сборке (нет strong-ссылок)          | избегание утечек (listener, ключи `WeakHashMap`) |
> | **Phantom** | объект уже почти удалён; нельзя получить (`get()=null`) | пост-финализация, очистка ресурсов |
>
> Утечки в Android = когда что-то из **GC Roots** (static, поток, активный Handler) держит **strong**-ссылку на `Activity`/`Context`. Лечится: `applicationContext`, `WeakReference`, отвязка колбэков в `onDestroy`.
