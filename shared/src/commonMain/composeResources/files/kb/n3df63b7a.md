
**Где хранится String в JVM?**
 
В JVM строковые значения хранятся в специальной области памяти, называемой **String Pool** (строковый пул). Это область памяти в куче (heap), которая используется для оптимизации работы со строками.

**Особенности:**

1. **String Pool:**

• Если строка создаётся как литерал (например, val str = "Hello"), JVM сначала проверяет, существует ли эта строка в пуле.
• Если строка уже существует, JVM вернёт ссылку на неё.
• Если строки нет, она будет добавлена в пул.

2. **Heap Memory:**

• Когда строки создаются с помощью конструктора String (например, val str = String("Hello".toCharArray())), они помещаются вне пула, в обычную область кучи, что требует больше памяти.

3. **Интернирование строк:**

• Метод ==String.intern()== позволяет вручную добавить строку в пул или получить ссылку на существующую строку из пула.

### **Почему String в Java и Kotlin является неизменяемым (immutable)?**

String в JVM неизменяем, и это дизайн-решение было сделано по нескольким причинам:

**1. Безопасность:**

• Изменяемые строки могут представлять угрозу безопасности. Например, строки используются для хранения конфиденциальных данных, таких как пароли, URL, ключи и т.д. Если строки были бы изменяемыми, злоумышленник мог бы изменить содержимое без изменения ссылки.

**2. Потокобезопасность:**

• Иммутабельность делает строки безопасными для многопоточной среды. Разные потоки могут одновременно использовать одну строку, не вызывая конфликтов или необходимости синхронизации.

**3. Эффективность работы с пулом строк:**

• Если строки были бы изменяемыми, использование строкового пула стало бы невозможным или крайне неэффективным. Ссылки на строки в пуле могли бы изменить значение, что привело бы к непредсказуемому поведению.


**4. Кэширование хэша:**

• String в JVM кеширует свой хэш-код после первой его вычисления. Если строка была бы изменяемой, хэш-код мог бы устаревать при изменении содержимого.


**5. Оптимизация:**

• Иммутабельность упрощает оптимизацию компилятором и виртуальной машиной. Например, строковые литералы могут быть объединены и переиспользованы.

Хранение стрингов не безопасно так как чтобы очистить ее из памяти, то для этого нужен GC. Надо хранить в массиве байтов. Это кейс если речь про сенситив данные.

### Какие есть способы конкатинации строк?

**1️⃣ Конкатенация с помощью оператора +**
```kotlin
val firstName = "John"
val lastName = "Doe"
val fullName = firstName + " " + lastName
println(fullName) // John Doe
```

⏳ **Минусы:** неоптимально, так как строки неизменяемы (immutable), и при каждом `+` создаётся новая строка. В **цикле** это даёт сложность **O(n²)** — каждая конкатенация копирует всю накопленную строку.

**2️⃣ Интерполяция строк (String Templates) ✅**
```kotlin
val firstName = "John"
val lastName = "Doe"
val fullName = "$firstName $lastName"
println(fullName) // John Doe
```

**3️⃣ StringBuilder (Лучший вариант для циклов) 🔥**

📌 **Если нужно динамически объединять много строк в цикле, лучше использовать** StringBuilder.
```kotlin
val sb = StringBuilder()
sb.append("Hello")
sb.append(" ")
sb.append("World")
println(sb.toString()) // Hello World
```

✅ **Плюсы** StringBuilder**:**

• **Эффективность:** Не создает новую строку в памяти на каждом шаге.
• **Гибкость:** Можно добавлять/изменять строки.

🚀 **Лучший вариант для циклов!**

**4️⃣ joinToString() для списков ✅**

📌 **Оптимальный способ объединить элементы списка в строку.**
```kotlin
val list = listOf("apple", "banana", "cherry")
val result = list.joinToString(", ") // Объединяем через запятую
println(result) // apple, banana, cherry
```

**5️⃣ buildString {} — Современный аналог StringBuilder 🔥**

📌 **Использует** StringBuilder **под капотом, но с Kotlin DSL.**

```kotlin
val result = buildString {
    append("Hello")
    append(" ")
    append("World")
}
println(result) // Hello World
```

## **📌 Почему third === first + second → false?**

**🔍 Разбираем строки в Kotlin**


В Kotlin (как и в Java) **строки являются неизменяемыми (immutable) и интернированными (interned)**. Это значит, что:


1️⃣ ==**Литералы строк (**"abc"**) хранятся в пуле строк (String Pool)** и могут ссылаться на один и тот же объект.==
2️⃣ ==**Операции со строками (**+**) создают новый объект, а не изменяют существующий.**==

**📌 Разбираем код шаг за шагом**

**🔹 1. first === second → true**

```kotlin
first = "abc"
second = "abc"
```

• Оба значения "abc" **являются литералами** и хранятся в String Pool.
• **Так как строки неизменяемые, обе переменные ссылаются на один и тот же объект в памяти.**
• Поэтому first === second → true (они ссылаются на один и тот же объект).

**🔹 2. third === first + second → false**

```kotlin
third = "abcabc"
println(third === first + second) // false
```

📍 Что делает first + second?
```kotlin
first + second  // "abc" + "abc" -> создаётся новый объект String
```

• ==При **конкатенации строк (**+**) создаётся новый объект в куче (Heap), а не в String Pool!**==
• Новый объект **не совпадает с литералом** "abcabc"**, который хранится в String Pool.**

**📌 Разные объекты в памяти**

**Ситуация в памяти:**
```kotlin
"abc"  --->  [String Pool]  <--- "abc"
"abcabc" ---> [String Pool]
"abcabc" ---> [Heap]  (создан new String)
```

Чтобы строки не попадали в **стринг-пул** (и === вернул false), нужно создать **новые объекты строк**, а не использовать существующие строки из пула. Это можно сделать разными способами:

Чтобы поместить строки в heap можно этот пример переписать на вот так: 

```kotlin
fun main() {
    var first = String("abc".toCharArray()) // Новый объект строки
    var second = String("abc".toCharArray()) // Новый объект строки

    // false, так как ссылки разные
    println(first === second)
}
```

> [!tip] Главное про строки на собесе
> - **Сравнивай строки через `==`** (в Kotlin это `equals`), а `===` — только когда осознанно проверяешь идентичность ссылок.
> - **String Pool** хранит литералы; `+`-конкатенация и `String(charArray)` создают новый объект в куче → `===` даёт `false`.
> - **Неизменяемость** даёт потокобезопасность, кэш hashCode и работу пула — но для сенситивных данных (пароли) это минус: строку нельзя «затереть», она живёт в памяти до GC. Поэтому пароли держат в `CharArray`/`ByteArray` и обнуляют вручную.
> - **Для конкатенации в цикле** — `StringBuilder` / `buildString {}` (O(n) вместо O(n²)); для списков — `joinToString`.
