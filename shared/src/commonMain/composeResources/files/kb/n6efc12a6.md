# 21 Репликация БД

Несколько копий одного состояния: primary принимает все записи, реплики получают журнал и обслуживают чтение. Три эффекта: масштабируют чтение, повышают отказоустойчивость, дают резерв. Но хорошая репликация определяется не количеством копий, а тем, какие чтения куда идут, когда запись считается подтверждённой и кто становится владельцем записи при отказе.

> [!tip] Аналогия из Android
> Replication lag — это экран после `POST`, который перечитал список с сервера и не нашёл только что созданную запись: ты прочитал с реплики, куда изменение ещё не доехало. Лечится так же, как на клиенте: «свои» данные показываем из того места, куда писали (read-after-write), остальное может чуть отставать.

## Как работает

```text
Клиенты ─ запись ─→ Primary
                      │ WAL / binlog
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Replica A   Replica B   Replica C
       чтение      чтение      отчёты
```

Путь одной транзакции:

1. Клиент отправляет изменение на primary.
2. Primary проверяет ограничения, меняет страницы, формирует запись журнала (WAL в PostgreSQL, binlog в MySQL).
3. Primary отвечает клиенту COMMIT.
4. Процесс отправки передаёт журнал на реплики.
5. Реплика сохраняет поток и применяет изменения к своей копии. Только после применения чтение на реплике увидит новое состояние.

**Lag = очередь передачи + очередь применения.** Реплика может получить журнал, но ещё не применить.

**Физическая или логическая.** Физическая копирует страницы: полная близкая копия, удобный standby, но зависит от формата хранения и версии. Логическая передаёт изменения строк: можно выбирать таблицы, делать миграции и интеграции, но сложнее DDL, ключи и порядок событий.

## Синхронно или асинхронно

Терминология: **RPO** (Recovery Point Objective) — сколько данных можно потерять; **RTO** (Recovery Time Objective) — сколько можно восстанавливаться; **ACK** — где запись считается надёжной; **quorum** — сколько копий ждём.

| Режим | ACK | RPO | Latency записи |
| --- | --- | --- | --- |
| Синхронный | после реплики | ближе к 0 | выше, зависит от копий |
| Асинхронный | сразу после primary | хвост можно потерять | ниже |
| Полусинхронный | после одной из N реплик | промежуточно | промежуточно |

Момент подтверждения определяет компромисс. RPO и RTO задают для каждого класса данных, а не для «базы вообще»: заказы — синхронно, лайки — асинхронно.

## Какие чтения куда

| Класс запроса | Маршрут | Гарантия |
| --- | --- | --- |
| Запись | primary | единственный порядок изменений |
| Критичное чтение | primary | read-after-write |
| Обычное чтение | реплика | допустима ограниченная устарелость |
| Тяжёлый отчёт | выделенная реплика | согласованный срез, изоляция нагрузки |

Хорошо переносятся на реплики: поиск и каталог, ленты, исторические данные и отчёты, фоновые задачи. Требуют primary: статус заказа сразу после создания, проверка баланса перед изменением, проверка уникальности, шаги одного бизнес-процесса, где результат предыдущей записи должен быть виден немедленно, любые решения, влияющие на запись.

Маршрутизация должна знать lag: реплика с лагом выше порога выводится из ротации чтения (health check по lag).

## Топологии

- **Один leader и реплики** — базовая для большинства транзакционных систем.
- **Каскадная** — часть реплик получает журнал через промежуточную копию, разгружает primary от отправки.
- **Multi-leader** — несколько узлов принимают записи, обычно в разных регионах; нужна разрешение конфликтов.
- **Leaderless с кворумами** — клиент или координатор пишет W копий и читает R копий; W + R > N даёт согласованность (Cassandra, DynamoDB).

Репликация решает не каждую проблему: чтение распределяется, но запись остаётся на одном primary; ошибочный DELETE копируется на реплики, так что это не backup.

## Практический алгоритм

1. Опишите профиль нагрузки: доля чтения и записи, пиковый поток, тяжёлые запросы.
2. Задайте RPO и RTO для каждого класса данных.
3. Выберите точку подтверждения записи и число обязательных копий.
4. Спроектируйте routing, health check и поведение при превышении lag.
5. Проведите нагрузочный тест и game day: потеря primary, сети, одной реплики.

Пример курса, интернет-магазин: изменение товара → primary (единый порядок записи); каталог и поиск → реплики (небольшое отставание допустимо); создание заказа → primary (жёсткий RPO); статус сразу после создания → primary (корректность процесса); отчёты → выделенная реплика (изоляция тяжёлого чтения).

Что проверить на испытании: сколько чтений реально ушло с primary; что видит пользователь сразу после записи при искусственном lag; как растёт p95/p99 чтения при потере одной реплики; соответствует ли потеря хвоста заявленному RPO.

## Когда применять в SD-задаче

Сигналы: «чтений на порядок больше», «база должна пережить отказ сервера», «пользователь не видит то, что только что сохранил», «отчёты мешают заказам». Ответ: primary + реплики, таблица маршрутов, режим подтверждения по классам данных, порог lag.

Фраза на собес: «Один primary на запись, N реплик на чтение. Каталог и ленты читаю с реплик, свои данные после записи и всё, что влияет на запись, — с primary. Заказы подтверждаю синхронно хотя бы одной репликой, лайки асинхронно. Реплику с лагом больше 5 секунд вывожу из ротации. Отчёты на выделенной реплике».

> [!warning] Грабли
> - Все чтения на реплики: статус заказа «не найден» сразу после создания.
> - Считать реплику бэкапом: `DELETE` без `WHERE` доехал до всех копий за секунду.
> - Синхронная репликация на все реплики: одна зависла — запись встала.
> - Failover без ответа «кто теперь владелец записи»: два primary, split brain.
> - Балансировщик не знает lag: отставшая реплика отдаёт данные часовой давности.
> - Думать, что реплики снимают предел записи. Для записи — шардирование.

> [!question]- Пользователь сохранил профиль и после обновления видит старые данные. Почему и что делать?
> Запись ушла на primary, чтение — на реплику, куда журнал ещё не применился (replication lag). Решение: read-after-write — свои данные после записи читать с primary (например, N секунд после записи или по маркеру сессии), либо ждать подтверждения применения, либо показать оптимистично на клиенте.

> [!question]- Синхронная или асинхронная репликация?
> Зависит от RPO класса данных. Синхронная: потеря подтверждённой записи недопустима (платежи, заказы), цена — задержка записи и зависимость от реплики. Асинхронная: задержка меньше, но при отказе primary хвост теряется (лайки, логи, аналитика). Полусинхронная — подтверждение одной из N реплик.

> [!question]- Что такое RPO и RTO?
> RPO — сколько данных можно потерять при отказе (измеряется временем: «последние 5 секунд»). RTO — сколько времени можно восстанавливаться. Их задают на каждый класс данных отдельно и из них выводят режим репликации и план failover.
