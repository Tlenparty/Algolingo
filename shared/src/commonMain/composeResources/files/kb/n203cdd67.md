При построении архитектуры приложения используют **наследование (inheritance)** и **композицию (composition)**. Разберёмся, чем они отличаются и где что лучше применять.

## 1. Наследование (Inheritance)

Наследование означает, что класс получает поведение от другого класса — через `extends` (Java) или `:` (Kotlin).

### Пример: наследование `View`

```kotlin
class CustomButton(context: Context, attrs: AttributeSet?) : Button(context, attrs) {
    init {
        setBackgroundColor(Color.BLUE)
        setTextColor(Color.WHITE)
    }
}
```

- 🔹 `CustomButton` наследует `Button` и автоматически получает все его методы.
- 🔹 **Проблема** — жёсткая связность: `CustomButton` зависит от всей реализации `Button`.

### Пример: наследование `Activity`

```kotlin
open class BaseActivity : AppCompatActivity() {
    fun showToast(msg: String) {
        Toast.makeText(this, msg, Toast.LENGTH_SHORT).show()
    }
}

class MainActivity : BaseActivity() {
    fun showMessage() {
        showToast("Привет!")
    }
}
```

- 🔹 **Плюс**: упрощает код — `BaseActivity` содержит общий функционал для всех экранов.
- 🔹 **Минус**: если изменится `BaseActivity`, **все потомки могут сломаться** (проблема хрупкого базового класса).

## 2. Композиция (Composition)

Композиция означает, что один класс содержит другой ==как поле== и делегирует ему логику.

### Пример: композиция `View`

```kotlin
// CustomView не наследует Button, а хранит его как поле (has-a)
class CustomView(context: Context, attrs: AttributeSet?) : FrameLayout(context, attrs) {
    private val button = Button(context).apply {
        setBackgroundColor(Color.BLUE)
        setTextColor(Color.WHITE)
    }

    init {
        addView(button) // важно: без addView вложенный Button не попадёт в иерархию и не отрисуется
    }

    fun setText(text: String) {
        button.text = text
    }
}
```

- 🔹 `CustomView` **не является** `Button`, а **содержит** его внутри.
- 🔹 **Гибкость**: внутренний виджет — деталь реализации. Заменить `Button` на, например, `TextView` можно, не меняя публичный API класса (`setText`).

### Пример: композиция вместо наследования (`Activity`)

```kotlin
class MessageHelper(private val context: Context) {
    fun showToast(msg: String) {
        Toast.makeText(context, msg, Toast.LENGTH_SHORT).show()
    }
}

class MainActivity : AppCompatActivity() {
    private val messageHelper = MessageHelper(this)

    fun showMessage() {
        messageHelper.showToast("Привет!")
    }
}
```

- 🔹 Вместо базового класса — вынесенный помощник. Тот же `MessageHelper` можно переиспользовать в любом экране, не завязываясь на общего родителя.

## Композиция vs наследование: коротко

| Фактор            | Наследование                          | Композиция                            |
| ----------------- | ------------------------------------- | ------------------------------------- |
| Связанность       | Жёсткая (класс зависит от базового)   | Гибкая (можно заменять компоненты)    |
| Гибкость          | Плохо (сложно менять родителя)        | Хорошо (поведение меняется в рантайме) |
| Переиспользование | Только внутри иерархии                | В любом классе                        |
| Связь             | «is-a» (`CustomButton` **является** `Button`) | «has-a» (`CustomView` **содержит** `Button`) |

## Делегирование в Kotlin (`by`)

Kotlin даёт композиции синтаксический сахар — **делегирование интерфейса** через `by`. Класс реализует интерфейс, но всю работу перекладывает на вложенный объект, не дублируя методы:

```kotlin
interface Repository {
    fun load(): String
}

class NetworkRepository : Repository {
    override fun load() = "data from network"
}

// LoggingRepository "содержит" Repository и делегирует ему всё,
// переопределяя только нужное
class LoggingRepository(
    private val delegate: Repository
) : Repository by delegate {
    override fun load(): String {
        println("loading...")
        return delegate.load()
    }
}
```

Это композиция без бойлерплейта: не нужно вручную писать «прокидывающие» методы.

> [!tip] Принцип «композиция вместо наследования»
> - **Наследование — связь «is-a»** (`CustomButton` **является** `Button`). Хрупкое: изменение родителя ломает потомков (проблема хрупкого базового класса), нарушается инкапсуляция.
> - **Композиция — связь «has-a»** (`MainActivity` **имеет** `MessageHelper`). Гибче, тестируемее, нет жёсткой иерархии.
> - В Kotlin классы **по умолчанию `final`** — язык сам подталкивает к композиции (чтобы наследоваться, нужно явно `open`). Наследование оправдано для настоящих «is-a» отношений и шаблонных методов; в остальных случаях — композиция/делегирование.
