# 08 Базы данных

БД — источник истины сервиса: всё, что нельзя потерять, живёт здесь, а кеши и очереди только ускоряют работу вокруг неё. На SD-собесе ждут, что вы выберете тип БД под паттерн доступа, назовёте ключ шардирования и объясните, что будет с консистентностью при репликации.

> [!tip] Аналогия из Android
> Серверная PostgreSQL — это тот же Room/SQLite: таблицы, индексы, транзакции, `@Transaction`. Разница в том, что к ней одновременно ходят тысячи клиентов, данные не помещаются на один диск, а сервер может упасть. Отсюда всё новое: уровни изоляции, реплики, шарды, CAP.

## SQL vs NoSQL

**Реляционные (PostgreSQL, MySQL)** — таблицы, схема, JOIN, транзакции. Выбор по умолчанию: пользователи, заказы, платежи, всё со связями и требованиями к целостности.

NoSQL — общее название для разных моделей:
- **Документные (MongoDB)** — JSON-документы с гибкой схемой. Когда объект читается целиком (профиль, карточка товара), а связей мало.
- **Key-value (Redis, DynamoDB)** — get/put по ключу, очень быстро. Сессии, кеш, корзина.
- **Wide-column (Cassandra, ScyllaDB, HBase)** — строки по ключу партиции, отсортированные внутри. Огромные объёмы записи: сообщения чата, лента, телеметрия, история событий.
- **Графовые (Neo4j)** — узлы и связи. Друзья друзей, рекомендации, когда запросы ходят по связям на много уровней.
- **Поисковые (Elasticsearch, OpenSearch)** — полнотекстовый поиск, фильтры, ранжирование. Обычно вторичный индекс рядом с основной БД.

Правило собеса: начинайте с PostgreSQL и переходите к NoSQL, когда называете конкретную причину (масштаб записи, гибкая схема, тип запросов).

## Индексы

```text
SELECT * FROM users
 WHERE email = 'a@example.com'

без индекса: перебор всех строк O(n)
B-tree индекс:     [m]
                  /   \
               [d,h]  [r,w]
               дерево → O(log n)
```

- **B-tree** — стандартный индекс: равенство, диапазоны, сортировка. Составной индекс `(user_id, created_at)` работает для запросов по `user_id` и по `user_id + диапазон дат`, но не по одному `created_at` (правило левого префикса).
- Индекс не бесплатен: каждая вставка и обновление пишет и в индекс, индексы занимают место. Индексируют поля из `WHERE`, `JOIN`, `ORDER BY` горячих запросов, а не всё подряд.
- Проверка — `EXPLAIN ANALYZE`: видно, идёт ли запрос по индексу или полным сканом.

## Транзакции и ACID

- **Atomicity** — всё или ничего: списали с одного счёта и зачислили на другой, либо ничего.
- **Consistency** — после транзакции соблюдены ограничения (unique, foreign key, check).
- **Isolation** — параллельные транзакции не видят полуготовых данных друг друга (в меру уровня изоляции).
- **Durability** — после COMMIT данные переживут падение (журнал WAL на диске).

Уровни изоляции (от слабого к строгому):
- **Read uncommitted** — видны чужие незакоммиченные изменения (dirty read). В PostgreSQL фактически не бывает.
- **Read committed** — видны только закоммиченные данные, но два чтения в одной транзакции могут дать разное. Дефолт PostgreSQL.
- **Repeatable read** — внутри транзакции данные как снимок на её начало. Дефолт MySQL InnoDB.
- **Serializable** — результат как при последовательном выполнении; конфликтующие транзакции откатываются, их надо повторять.

Для «списать остаток, если хватает» на read committed используют `SELECT ... FOR UPDATE` (блокировку строки) или атомарный `UPDATE ... SET balance = balance - 10 WHERE balance >= 10`.

## Репликация

```text
 write ─► primary ──WAL──► replica 1
                    └────► replica 2
 read  ─► replica (может отставать)
```

- Primary принимает записи, реплики копируют журнал и обслуживают чтения. Масштабирует чтение и даёт failover.
- Асинхронная репликация → **replication lag**: пользователь сохранил профиль, обновил экран, а чтение пошло на отстающую реплику — данные «откатились».
- **Read-your-writes:** свои данные после записи читаем с primary (например, N секунд после записи или для экрана «мой профиль»), чужие — с реплик.
- Синхронная репликация убирает потерю данных при падении primary, но замедляет каждую запись.

## Шардирование

Данных больше, чем тянет один сервер, — делим их по **ключу шардирования** между несколькими БД.

- **Ключ** выбирают по главному запросу: чат — `chat_id` (все сообщения чата на одном шарде), профиль — `user_id`. Запрос без ключа шарда идёт на все шарды (scatter-gather) — дорого.
- **Hash-шардирование** равномерно распределяет данные; **range** (по дате, алфавиту) удобно для диапазонов, но новые данные бьют в один шард.
- **Hot shard:** знаменитость с миллионами подписчиков перегружает свой шард. Лечат дроблением ключа, кешем, отдельной обработкой «горячих».
- Перешардирование болезненно; consistent hashing уменьшает объём переносимых данных.
- Транзакции и JOIN между шардами — сложно и медленно; схему проектируют так, чтобы они были не нужны.

## CAP на пальцах

При сетевом разделении (P — partition, сеть между узлами порвалась) распределённая система выбирает:
- **C (consistency)** — отказать в ответе, чтобы не отдать устаревшие данные. Банк, остатки на складе.
- **A (availability)** — ответить тем, что есть, возможно устаревшим, и потом сойтись (eventual consistency). Лайки, лента, счётчик просмотров.

Пока сеть цела, выбирать не нужно; CAP — про поведение при сбое. На собесе говорите: «для платежей — CP, для ленты — AP с eventual consistency».

## Когда применять в SD-задаче

Сигналы: «сколько данных через 5 лет», «соотношение чтение/запись», «нужны транзакции/деньги», «поиск», «миллионы сообщений в день», «данные пользователя видны сразу».

Фраза на собес: «Источник истины — PostgreSQL с индексом под главный запрос; чтение масштабирую репликами с read-your-writes для своих данных, при росте шардирую по userId; сообщения чата — в Cassandra с партицией по chatId».

> [!warning] Грабли
> - Запрос без индекса на большой таблице: всё работает в тестах и падает на проде.
> - Индекс на каждое поле — запись становится медленной.
> - Чтение с реплики сразу после записи — пользователь не видит своих изменений.
> - Ключ шарда, который не совпадает с главным запросом: каждый запрос идёт на все шарды.
> - «Возьмём MongoDB, потому что NoSQL масштабируется» без причины — потом нужны транзакции и JOIN.
> - Read-modify-write без блокировки или атомарного UPDATE — потерянное обновление (lost update).

> [!question]- Когда SQL, а когда NoSQL?
> SQL — по умолчанию: связи, транзакции, целостность, гибкие запросы (пользователи, заказы, платежи). NoSQL — под конкретный паттерн: wide-column (Cassandra) для огромного потока записей по ключу (чат, события), документная — для объектов с гибкой схемой, читаемых целиком, KV — для быстрого get/put по ключу, графовая — для обхода связей. Часто используют обе: PostgreSQL как источник истины плюс специализированное хранилище.

> [!question]- Что такое ACID и уровни изоляции?
> Atomicity — всё или ничего; Consistency — ограничения соблюдены; Isolation — параллельные транзакции не мешают друг другу; Durability — закоммиченное переживёт сбой. Уровни изоляции: read uncommitted (видны чужие незакоммиченные данные), read committed (только закоммиченные, дефолт PostgreSQL), repeatable read (снимок на начало транзакции), serializable (как будто транзакции шли по очереди).

> [!question]- Пользователь сохранил профиль, а после обновления видит старые данные. Почему?
> Скорее всего, чтение ушло на асинхронную реплику, которая ещё не догнала primary (replication lag). Решения: read-your-writes — читать свои данные с primary какое-то время после записи; привязка пользователя к реплике, которая не отстаёт от его последней записи; на клиенте — оптимистично показать сохранённое значение, не дожидаясь перечитывания.

> [!question]- Как выбрать ключ шардирования для мессенджера?
> По главному запросу: «последние сообщения чата» — значит chat_id, тогда весь чат лежит на одном шарде и читается одним запросом. Hash от chat_id даёт равномерность. Риск — огромный групповой чат как hot shard. Список чатов пользователя — отдельная таблица с ключом user_id.
