# 03 HTTPS, TLS, SSL

HTTPS = обычный HTTP внутри зашифрованного TLS-канала. TLS решает три задачи: **шифрование** (никто не прочитает), **целостность** (никто незаметно не изменит) и **аутентификация сервера** (ты говоришь именно с `api.example.com`, а не с подставным Wi-Fi).

> [!tip] Аналогия из Android
> TLS — это как подпись APK плюс зашифрованный канал. Подпись доказывает, что APK собрал владелец ключа; сертификат сервера доказывает, что на том конце владелец домена. А CA — это как Google Play, которому все заранее доверяют и который «ручается» за подпись.

## Как работает

### SSL vs TLS

SSL — старое название протокола от Netscape. SSL 2.0/3.0 давно взломаны и выключены (POODLE, 2014). TLS 1.0 и 1.1 официально устарели (RFC 8996, 2021). Живые версии — **TLS 1.2** и **TLS 1.3** (2018). «SSL-сертификат» — просто историческое название, на деле это X.509-сертификат для TLS.

### Два вида шифрования

- **Асимметричное** (пара ключей: публичный + приватный; RSA, ECDSA, ECDHE). Медленное. Используется только в рукопожатии: подписать и проверить сертификат, договориться об общем секрете.
- **Симметричное** (один общий ключ; AES-GCM, ChaCha20-Poly1305). Быстрое. Им шифруются все данные после рукопожатия.

Схема: асимметрикой безопасно получаем общий секрет → дальше всё шифруем симметрично.

### Рукопожатие TLS 1.3 (1 RTT)

```text
Клиент                       Сервер
  │── ClientHello ─────────────►│
  │   версии, шифры, SNI,       │
  │   key_share (ECDHE)         │
  │◄──────────── ServerHello ───│
  │   key_share (ECDHE)         │
  │   {Certificate}             │
  │   {CertificateVerify}       │
  │   {Finished}                │
  │── {Finished} + GET /feed ──►│
  │◄═══════ зашифрованный HTTP ═│
{...} — уже зашифровано
```

1. Клиент сразу шлёт свою половину обмена ключами (ECDHE, обычно X25519) — поэтому TLS 1.3 укладывается в 1 RTT, а TLS 1.2 требовал 2.
2. Сервер отвечает своей половиной; обе стороны независимо вычисляют один и тот же секрет, сам секрет по сети не передаётся.
3. Сервер присылает сертификат и подписывает рукопожатие своим приватным ключом (CertificateVerify) — это доказывает, что ключ у него.
4. Обмен эфемерный → **forward secrecy**: утечка приватного ключа сервера завтра не расшифрует перехваченный сегодня трафик. В TLS 1.3 обмен без forward secrecy (RSA key transport) убран совсем.
5. При повторном подключении возможен **0-RTT** (данные сразу в первом пакете), но такие данные можно переиграть (replay) — годится только для идемпотентных GET.

### Сертификаты и цепочка CA

```text
Root CA (в хранилище ОС)
  └ подписал Intermediate CA
      └ подписал api.example.com
```

Клиент проверяет: подписи по цепочке до доверенного корня, имя домена совпадает с сертификатом (SAN), срок действия не истёк. Корневые CA лежат в системе Android; с Android 7 (targetSdk 24+) приложения по умолчанию **не доверяют пользовательским** CA — поэтому Charles/mitmproxy без доп. настройки не видят трафик.

### Что защищено, а что видно

- **Защищено:** путь и query (`/feed?user=42`), заголовки (включая `Authorization`, cookies), тело.
- **Видно наблюдателю:** IP-адреса и порт, **SNI** — имя хоста в ClientHello (шифрует только ECH, пока редкость), DNS-запрос (если не DoH/DoT), размеры и тайминги пакетов.

### Certificate pinning

Pinning = приложение доверяет не любому сертификату от любого CA, а только заранее известному публичному ключу (хэш SPKI). Защищает от MITM через скомпрометированный или подсунутый CA. На Android — через Network Security Config:

```xml
<network-security-config>
 <domain-config>
  <domain>example.com</domain>
  <pin-set expiration="2027-06-01">
   <pin digest="SHA-256">AAAA...=</pin>
   <pin digest="SHA-256">BBBB...=</pin>
  </pin-set>
 </domain-config>
</network-security-config>
```

Подключается в манифесте `android:networkSecurityConfig="@xml/network_security_config"`. Альтернатива в коде — `CertificatePinner` в OkHttp. Там же через `<debug-overrides>` можно доверять пользовательским CA только в debug-сборке.

## Когда применять в SD-задаче

Сигналы: платежи, банкинг, медицинские данные, «как защитить трафик», «что если пользователь в публичном Wi-Fi». Pinning — для приложений с высоким риском; для обычного контент-приложения достаточно стандартной проверки TLS.

Фраза на собес: «Весь трафик по HTTPS с TLS 1.2+, асимметрика только для рукопожатия, дальше симметричный AES; для чувствительных данных добавлю pinning по публичному ключу с запасным пином и датой expiration, чтобы ротация сертификата не убила приложение».

> [!warning] Грабли
> - Pinning может «окирпичить» приложение: сервер сменил ключ, а старые версии APK у пользователей знают только старый пин — все запросы падают с `SSLPeerUnverifiedException`, а обновиться люди не успели. Обязательно: **пинить публичный ключ (не сертификат), держать запасной пин** и ставить `expiration`.
> - Pinning не защищает от того, у кого рут/Frida на своём устройстве — это защита канала, а не секретов в APK.
> - Самописный `TrustManager`, который «принимает всё» (часто для отладки), — дыра; Google Play такие приложения отклоняет.
> - Неверное время на телефоне ломает проверку срока сертификата → `SSLHandshakeException` у отдельных пользователей.

> [!question]- Чем отличается SSL от TLS и какую версию использовать?
> SSL — предшественник, все версии взломаны и отключены. TLS 1.0/1.1 устарели. Использовать TLS 1.3 (1 RTT, только шифры с forward secrecy, нет устаревших алгоритмов), TLS 1.2 — как минимум для совместимости. «SSL» сегодня — просто бытовое название.

> [!question]- Как устроено рукопожатие TLS 1.3 и зачем там асимметричное шифрование?
> ClientHello с поддерживаемыми шифрами, SNI и ключевой долей ECDHE → ServerHello со своей долей, сертификат, подпись рукопожатия, Finished → Finished клиента и сразу данные. Асимметрика нужна, чтобы договориться об общем секрете по открытой сети и доказать подлинность сервера. Все данные потом шифруются симметричным ключом — он быстрый.

> [!question]- Видит ли провайдер, какие запросы делает приложение по HTTPS?
> Видит IP сервера, порт, имя хоста (SNI в ClientHello и обычно DNS-запрос), объём и время трафика. Не видит путь, параметры, заголовки, токены и тело — они внутри TLS. То есть «приложение ходит на api.bank.com» — видно, «переводит 1000 ₽ Пете» — нет.

> [!question]- Что такое certificate pinning и чем он опасен?
> Приложение принимает только заранее известный публичный ключ сервера, даже если CA подписал другой сертификат, — защита от MITM через поддельный CA. Опасность: при ротации ключа старые версии приложения перестают работать. Митигация: пин публичного ключа, запасной ключ заранее в списке, `expiration` у pin-set, удалённый kill switch через конфиг.
