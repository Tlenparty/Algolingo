# 02 HTTP

HTTP — язык, на котором клиент и сервер договариваются: «что сделать» (метод), «с чем» (путь), «как» (заголовки) и «чем кончилось» (код ответа). На SD-собесе от тебя ждут не синтаксис, а понимание идемпотентности, кодов и того, чем HTTP/2 и HTTP/3 лучше для мобилки.

> [!tip] Аналогия из Android
> Аннотации Retrofit — это и есть HTTP: `@GET("feed")` — метод и путь, `@Header`/`@Headers` — заголовки, `@Body` — тело, `@Query` — параметры, а `Response<T>.code()` — код ответа. Retrofit просто превращает интерфейс в текстовый HTTP-запрос.

## Как работает

Запрос и ответ — это стартовая строка, заголовки, пустая строка и (не всегда) тело:

```text
GET /v1/feed?cursor=abc HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJ...
Accept: application/json
If-None-Match: "v42"

HTTP/1.1 304 Not Modified
ETag: "v42"
Cache-Control: max-age=60
```

### Методы и идемпотентность

Идемпотентный = повтор того же запроса оставляет сервер в том же состоянии, что и один вызов. Безопасный = вообще ничего не меняет. Именно идемпотентность решает, можно ли автоматически повторить запрос после таймаута.

| Метод | Зачем | Безопасный | Идемпотентный |
| --- | --- | --- | --- |
| GET | прочитать | да | да |
| HEAD | только заголовки | да | да |
| PUT | заменить ресурс целиком | нет | да |
| DELETE | удалить | нет | да |
| PATCH | частично изменить | нет | не гарантирован |
| POST | создать / действие | нет | нет |

POST не идемпотентен: повтор «создать заказ» создаст второй заказ. Решение — заголовок `Idempotency-Key: <uuid>`: клиент генерирует UUID один раз на действие и шлёт его при каждом ретрае, сервер запоминает ключ и на повтор отдаёт сохранённый результат вместо нового заказа.

### Коды ответа

- **2xx — успех:** 200 OK, 201 Created (создано, обычно с `Location`), 204 No Content (успех без тела).
- **3xx — перенаправление:** 301 Moved Permanently, 304 Not Modified (кеш актуален, тела нет).
- **4xx — ошибка клиента, повторять бессмысленно:** 400 Bad Request, 401 Unauthorized (нет/протух токен — обнови и повтори), 403 Forbidden (токен валиден, но прав нет), 404 Not Found, 409 Conflict (конфликт версий, см. [[Конфликты состояний с backend]]), 429 Too Many Requests (смотри `Retry-After`).
- **5xx — ошибка сервера, можно повторить с backoff:** 500 Internal Server Error, 502 Bad Gateway (прокси не получил нормальный ответ от сервера), 503 Service Unavailable (перегружен / на обслуживании), 504 Gateway Timeout.

### Ключевые заголовки

- `Content-Type` / `Accept` — формат тела (`application/json`).
- `Authorization: Bearer <token>` — кто я ([[04 Авторизация]]).
- `Cache-Control`, `ETag`, `If-None-Match`, `Last-Modified` — кеширование, подробно в [[Кеширование через заголовки]].
- `Content-Encoding: gzip` — сжатие; OkHttp сам добавляет `Accept-Encoding: gzip` и распаковывает.
- `Retry-After` — когда можно повторить после 429/503.
- `Idempotency-Key`, `X-Request-Id` — защита от дублей и сквозной id для поиска в логах.

### REST на пальцах

Ресурсы — существительные в пути, действия — методы: `GET /orders/42`, `POST /orders`, `DELETE /orders/42`. Сервер stateless: всё нужное для обработки (токен, курсор) есть в самом запросе. Ответы кешируемы через заголовки. Пагинация ленты — курсором (`?cursor=...`), а не `offset`, чтобы новые элементы не сдвигали страницы.

### HTTP/1.1 vs HTTP/2 vs HTTP/3

```text
HTTP/1.1: 1 запрос за раз на соединение
  conn1: [req A]──[req B]──[req C]
HTTP/2: потоки в одном TCP
  conn:  [A][B][C][A][C][B]...
HTTP/3: потоки поверх QUIC (UDP)
  потеря пакета A не тормозит B и C
```

- **HTTP/1.1** — текстовый, keep-alive, но в одном соединении запросы идут по очереди (head-of-line blocking), поэтому клиенты открывали по 6 соединений на хост.
- **HTTP/2** — бинарный, мультиплексирование многих потоков в одном TCP-соединении, сжатие заголовков (HPACK). Но потеря одного TCP-пакета тормозит все потоки — HOL-блокировка уровня TCP.
- **HTTP/3** — поверх **QUIC** (UDP): потоки независимы, рукопожатие транспорта и TLS 1.3 объединены (1 RTT, при повторе возможен 0-RTT), соединение переживает смену сети Wi-Fi → LTE (connection ID вместо IP:порт). Для мобилки это главный плюс.

OkHttp поддерживает HTTP/2 из коробки (через ALPN при TLS); HTTP/3 в OkHttp пока нет, его дают Cronet или нативный стек на iOS.

## Когда применять в SD-задаче

Сигналы: проектирование API («какие эндпоинты?»), «платёж ушёл дважды», «что делать при таймауте», «как не качать ленту заново», «медленно на плохой сети».

Фраза на собес: «GET/PUT/DELETE идемпотентны и их можно ретраить, для POST я добавляю Idempotency-Key; 4xx не ретраю, 5xx и 429 — с backoff и учётом Retry-After; ленту кеширую через ETag и пагинирую курсором; транспорт — HTTP/2, а на плохих сетях выигрывает HTTP/3».

> [!warning] Грабли
> - OkHttp сам молча повторяет запрос при некоторых сбоях соединения (`retryOnConnectionFailure = true` по умолчанию) — включая POST. Без Idempotency-Key это возможный дубль.
> - 401 и 403 путают: на 401 надо обновить токен, на 403 — нет, повтор не поможет.
> - Ошибка в теле с кодом 200 (`{"error": ...}`) ломает ретраи, кеш и мониторинг — коды должны быть честными.
> - `offset`-пагинация на живой ленте даёт дубли и пропуски элементов.

> [!question]- Что такое идемпотентность и какие методы идемпотентны?
> Повторный одинаковый запрос даёт тот же эффект на сервере, что и один. GET, HEAD, PUT, DELETE — идемпотентны; POST — нет; PATCH — не гарантированно. Важно для ретраев: идемпотентный запрос после таймаута можно смело повторить, неидемпотентный — только с `Idempotency-Key`, который сервер дедуплицирует.

> [!question]- Чем 401 отличается от 403, а 502 от 503?
> 401 — «не знаю, кто ты»: токена нет или он протух, клиент обновляет токен и повторяет. 403 — «знаю, но нельзя»: прав нет, повтор бесполезен. 502 — прокси/балансировщик получил от сервера плохой ответ или разрыв. 503 — сервис сам говорит, что временно недоступен (перегрузка, деплой), часто с `Retry-After`.

> [!question]- Зачем HTTP/2, если есть keep-alive, и что даёт HTTP/3?
> Keep-alive переиспользует соединение, но запросы в нём идут по очереди. HTTP/2 мультиплексирует много потоков в одном соединении и сжимает заголовки — меньше соединений и задержек. HTTP/3 переносит это на QUIC поверх UDP: потеря пакета не блокирует остальные потоки, рукопожатие короче, соединение переживает смену сети — заметный выигрыш на мобильном интернете.
