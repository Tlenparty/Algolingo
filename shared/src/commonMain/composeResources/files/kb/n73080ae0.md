**🔧 Как рекомпозиция работает под капотом?**

1. **Состояние изменилось** (**mutableStateOf** или **remember**)
2. **Compose помечает часть UI как “устаревшую” (invalidated)**
3. **Вызывает** @Composable **функции, которые зависят от изменённого состояния**
4. **Перерисовывает только изменённые элементы (используя** Slot Table**)**
5. **Не затрагивает неизменённые части UI**


📌 **Ключевая особенность** — Jetpack Compose использует Slot Table, чтобы эффективно отслеживать, какие элементы нужно обновить.  [[Compose. Slot table]]

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) } // State хранится в Slot Table
    Button(onClick = { count++ }) {
        Text("Clicked $count times") // Только этот элемент будет обновляться
    }
}
```

**🔍 Что происходит при нажатии на кнопку?**
1. remember **сохраняет объект** mutableStateOf(0) **в** Slot Table, чтобы он не пересоздавался при рекомпозиции.
2. mutableStateOf(0) **создаёт наблюдаемое состояние** (observable state), используя SnapshotState.
3. **При изменении** count.value **Compose получает сигнал об обновлении** и вызывает рекомпозицию.
4. count++ изменяет mutableStateOf(0) → mutableStateOf(1)
5. Compose **определяет**, что Text("Clicked $count times") зависит от count
6. **Рекомпозиция происходит только для** Text**, а** Button **остаётся неизменным!**

**🔥 Почему изменение mutableStateOf вызывает рекомпозицию?**

🔹 **1.** mutableStateOf **— это** SnapshotState**, который отслеживает изменения.**

Когда значение изменяется, Compose **“помечает” все** @Composable**, которые используют это состояние как “устаревшие” (invalidated).**

🔹 **2. Compose автоматически запускает рекомпозицию только тех элементов, которые используют изменённое состояние.**

Если count.value используется только в Text, то **только этот элемент будет рекомпозирован**.


> [!note] `@NonRestartableComposable`
> Аннотация `@NonRestartableComposable` отключает кодогенерацию restart-группы: для функции **не генерируется код перезапуска/рекомпозиции**, она не может рекомпозироваться независимо (рекомпозируется только вместе с родителем). Применяют как микрооптимизацию для мелких функций, которые и так всегда вызываются заново родителем — экономит на служебном коде. Использовать осознанно: для функции, читающей состояние, это сломает обновление.

### Чтение vs запись состояния

- **Запись** в состояние сама по себе **не** вызывает рекомпозицию.
- **Чтение** состояния внутри composable «подписывает» эту функцию на изменения → вызывает рекомпозицию.
- Если в одной области и **читаем, и пишем** — получаем **бесконечную рекомпозицию**.

![[i88d3cb68.png]]

Чтобы избежать, выносят чтение в промежуточные `@Composable`-функции и передают вниз либо `State`, либо лямбду (отложенное чтение — defer reads).

> [!tip] Пример с большим списком
> Для списка из 20–30 элементов отслеживание состояния каждого может стоить дороже самих расчётов. Иногда дешевле передать значение всем явно или через `CompositionLocal`, чем заставлять Compose отслеживать множество мелких подписок.

Чтобы увидеть опасность лишней рекомпозиции, удобнее работать через свойство `.value` (явное чтение видно в коде).

LaunchedEffect vs derivedStateOf при скролле..
```kotlin
val isScrolled = remember {
    derivedStateOf { lazyListState.firstVisibleItemIndex > 5 }
}
```

🔹 **Почему лучше?**

• **Минимальные перерисовки** → derivedStateOf триггерит **только при изменении состояния (false → true или true → false)**.

• **Не использует корутины** → работает **быстрее и проще**.

• **Оптимально для UI** → идеально подходит для вычисления **локального состояния**.

```kotlin
LaunchedEffect(lazyListState) {
    snapshotFlow { lazyListState.firstVisibleItemIndex }
        .collect { index ->
            val newState = index > 5
            if (newState != isScrolled) { 
                isScrolled = newState
            }
        }
}
```

🔹 **Почему хуже?**

• **Запускает корутину** → лишняя нагрузка на систему.
• **Использует** snapshotFlow() **+** collect {} → постоянное отслеживание и обновление состояния.
• **Не нужен поток для простых UI-изменений** → derivedStateOf делает то же самое **без корутин**.
