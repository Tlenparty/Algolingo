# KMP. Source sets и Gradle

## Source set — что это

**Source set** — это набор исходников, скомпилированных под конкретный набор таргетов со своим набором зависимостей. Каждый таргет связан с одним или несколькими source sets.

```text
commonMain   → компилируется во ВСЕ таргеты, видит только мультиплатформенные API
   ↑
androidMain  → видит commonMain + весь Android/JVM SDK
iosMain      → видит commonMain + Kotlin/Native + Apple-фреймворки (platform.*)
   ↑
iosArm64Main / iosSimulatorArm64Main / iosX64Main → конкретные ABI
```

`commonMain` **не видит** ни `android.*`, ни `platform.UIKit.*` — только общие библиотеки (`kotlinx.coroutines`, `kotlinx.serialization`, Ktor и т.п.) и то, что объявлено через [[KMP. expect-actual|expect/actual]].

## Минимальный `build.gradle.kts`

```kotlin
plugins {
    kotlin("multiplatform")
    id("com.android.library")
}

kotlin {
    androidTarget()                 // Android (Kotlin/JVM)
    iosArm64()                      // реальные устройства
    iosSimulatorArm64()             // симулятор на Apple Silicon
    iosX64()                        // симулятор на Intel

    sourceSets {
        commonMain.dependencies {
            implementation(libs.kotlinx.coroutines.core)
            implementation(libs.ktor.client.core)
        }
        androidMain.dependencies {
            implementation(libs.ktor.client.okhttp)   // движок Ktor под Android
        }
        iosMain.dependencies {
            implementation(libs.ktor.client.darwin)    // движок Ktor под iOS
        }
    }
}
```

> [!info] Default Hierarchy Template
> Раньше иерархию source sets (`iosMain` → `iosArm64Main`/`iosSimulatorArm64Main`/`iosX64Main`) приходилось описывать руками через `dependsOn`. Теперь Kotlin Gradle Plugin **создаёт иерархию автоматически** (default hierarchy template): достаточно объявить таргеты, а промежуточный `iosMain` появляется сам. Это частый «а как раньше делали» вопрос.

> [!tip] Зачем три iOS-таргета
> `iosArm64` — реальные iPhone; `iosSimulatorArm64` — симулятор на маках с Apple Silicon (M1+); `iosX64` — симулятор на старых Intel-маках. Все три обычно собирают в один **XCFramework**, чтобы один артефакт работал и на устройстве, и на симуляторе.

## Как iOS-проект подключает общий модуль

Три способа отдать Kotlin-код в Xcode:
1. **Прямой framework** — Gradle-задача собирает `.framework`, путь прописывается в Xcode (или через скрипт сборки).
2. **CocoaPods-плагин** (`kotlin("native.cocoapods")`) — общий модуль публикуется как Pod, Xcode тянет его через `Podfile`. Долго был стандартом.
3. **XCFramework / SPM** — собрать `XCFramework` и подключить через Swift Package Manager. Прямой Swift export пока **экспериментальный**.

> [!warning] commonMain не должен «протекать» платформенными зависимостями
> Если случайно положить Android-зависимость в `commonMain`, проект перестанет собираться под iOS (там нет JVM-классов). Поэтому платформенные движки/драйверы (`ktor-client-okhttp`, SQLDelight `android-driver`/`native-driver`) кладут строго в `androidMain`/`iosMain`, а в `commonMain` — только их общий API.

> [!note] Где обычно лежит KMP-модуль
> В типовом проекте: `shared/` (или `core/`) — мультиплатформенный модуль; `androidApp/` — обычное Android-приложение, зависящее от `shared`; `iosApp/` — Xcode-проект, подключающий framework из `shared`. Android-команда работает в Android Studio, iOS — в Xcode.
