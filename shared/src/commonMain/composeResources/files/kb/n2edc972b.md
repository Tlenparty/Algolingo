# 07 Kafka и очереди

Очередь (брокер сообщений) развязывает «кто сделал событие» и «кто его обработал»: сервис кладёт сообщение и сразу отвечает клиенту, а тяжёлая работа идёт асинхронно. Kafka — самый частый ответ на собесе, когда звучит «поток событий», «нагрузка пиками» или «несколько потребителей одного события».

> [!tip] Аналогия из Android
> Kafka — это `SharedFlow` с огромным `replay`, который хранится на диске и переживает перезапуск. Каждый подписчик (consumer group) читает в своём темпе и помнит, где остановился, а новый подписчик может прочитать историю с начала. Обычная очередь вроде RabbitMQ ближе к `Channel`: элемент получает один потребитель, и после обработки он исчезает.

## Зачем асинхронность

- **Сглаживание пиков:** 10 000 заказов за минуту распродажи ложатся в очередь, а обработчики разбирают их со своей скоростью.
- **Развязка сервисов:** сервис заказов не знает про почту, аналитику и склад — он публикует «OrderCreated», остальные подписываются.
- **Надёжность:** если обработчик упал, сообщение не потеряно, оно дождётся в брокере.
- **Быстрый ответ клиенту:** 202 Accepted сразу, результат — позже (push, polling, WebSocket).

## Как работает Kafka

```text
producer ─► topic "orders"
 ┌ partition 0: m0 m1 m2 m3 ...
 ├ partition 1: m0 m1 m2 ...
 └ partition 2: m0 m1 ...
       (offset = номер в разделе)

group "billing": c1←p0  c2←p1,p2
group "email":   c1←p0,p1,p2
```

- **Topic** — именованный журнал событий. Делится на **partition** — упорядоченные append-only журналы на диске, разнесённые по брокерам и реплицированные.
- **Offset** — порядковый номер сообщения внутри партиции. Сообщения не удаляются после чтения, а живут по retention (например, 7 дней) или compaction (остаётся последнее значение по ключу).
- **Consumer group** — набор экземпляров одного сервиса. Каждая партиция в группе читается ровно одним consumer, поэтому параллелизм группы ≤ числу партиций. Разные группы читают топик независимо — каждая получает все сообщения.
- Consumer сам коммитит offset: «обработал до сюда». После падения он продолжит с последнего закоммиченного.
- **Порядок гарантирован только внутри партиции.** Сообщения с одним ключом (например, `orderId`) попадают в одну партицию (hash(key) % N) — так события одного заказа идут по порядку.

## Семантика доставки

- **At-most-once** — закоммитили offset, потом обработали. Упали посередине — сообщение потеряно. Годится для метрик, где потеря не страшна.
- **At-least-once** — обработали, потом закоммитили. Упали между ними — сообщение придёт ещё раз. Это стандартный выбор.
- **Exactly-once** — в Kafka есть идемпотентный producer и транзакции, но это гарантия внутри Kafka (читаем топик → пишем топик). Как только обработчик пишет во внешнюю БД или шлёт письмо, на практике делают at-least-once + **идемпотентный consumer**.

Идемпотентный consumer: у сообщения есть уникальный id, обработчик хранит обработанные id (таблица с unique-ключом) или делает операцию, которую безопасно повторить (`UPSERT`, «установить статус», а не «прибавить»).

## Kafka vs RabbitMQ

**Kafka** — распределённый журнал:
- сообщения хранятся, их можно перечитать (replay);
- огромная пропускная способность, много независимых групп;
- порядок внутри партиции;
- для потоков событий, аналитики, event sourcing, CDC.

**RabbitMQ** — классический брокер очередей:
- сообщение удаляется после ack;
- гибкая маршрутизация (exchanges, routing keys), приоритеты, TTL сообщений;
- для «задач» (отправить письмо, сделать превью), где нужен один исполнитель и не нужна история.

Ещё варианты: AWS SQS/SNS, Google Pub/Sub (облачные, без своей инфраструктуры), Redis Streams (лёгкий журнал на Redis).

## Outbox, DLQ, retry

**Проблема двойной записи:** сервис сохраняет заказ в БД и публикует событие в Kafka. Если одно прошло, а другое нет — система рассинхронизирована.

```text
Transactional outbox:
 BEGIN
  INSERT orders(...)
  INSERT outbox(event)
 COMMIT
 relay ─чтение outbox─► Kafka
       └─ помечает отправленным
```

Событие пишется в ту же транзакцию, что и данные. Отдельный relay (или CDC вроде Debezium) читает таблицу outbox и публикует. Доставка at-least-once — потребители идемпотентны.

- **Retry с backoff:** временная ошибка (таймаут внешнего API) — повторяем через 1 с, 2 с, 4 с… с jitter, ограниченное число раз.
- **DLQ (dead letter queue):** «ядовитое» сообщение, которое падает всегда (битый JSON), после N попыток уходит в отдельный топик. Иначе оно блокирует партицию — consumer крутится на нём вечно. DLQ мониторят и разбирают руками.

## Когда применять в SD-задаче

Сигналы: «отправить уведомление после заказа», «обработать загруженное видео», «пиковая нагрузка», «одно событие нужно нескольким сервисам», «лента / fan-out», «аналитика событий», «нельзя потерять».

Фраза на собес: «Запись подтверждаю синхронно, а побочные действия публикую событием в Kafka через outbox; партиционирую по userId, чтобы сохранить порядок, consumer идемпотентный с дедупликацией по eventId, ошибки — retry с backoff и DLQ».

> [!warning] Грабли
> - Рассчитывать на глобальный порядок по всему топику — его нет, только внутри партиции.
> - Партиций меньше, чем consumer в группе: лишние экземпляры простаивают. Увеличить число партиций можно, но при этом меняется hash(key) % N, и порядок по ключу на стыке ломается.
> - Горячий ключ: все события популярного аккаунта в одной партиции — она перегружена.
> - Auto-commit offset до реальной обработки — тихая потеря сообщений.
> - Неидемпотентный обработчик при at-least-once: двойное списание денег, два одинаковых пуша.
> - Нет DLQ: одно битое сообщение останавливает обработку партиции.

> [!question]- Как Kafka гарантирует порядок сообщений?
> Только внутри одной партиции: это append-only журнал, и одну партицию в группе читает один consumer. Чтобы события одной сущности шли по порядку, их отправляют с одним ключом (например, orderId) — producer кладёт их в одну партицию. Глобального порядка по топику нет; если он нужен, топик с одной партицией, но тогда нет параллелизма.

> [!question]- At-least-once, at-most-once, exactly-once — что выберете?
> At-most-once теряет сообщения при сбое, at-least-once может дублировать. Exactly-once в Kafka работает внутри Kafka (транзакции read-process-write), а при внешних эффектах (БД, письма, платежи) на практике выбирают at-least-once плюс идемпотентного consumer: уникальный id события и дедупликация, либо операции, которые безопасно повторить.

> [!question]- Что такое transactional outbox и зачем он нужен?
> Он решает проблему двойной записи в БД и брокер. Событие пишется в таблицу outbox в той же транзакции, что и бизнес-данные, а отдельный процесс (relay или CDC) читает outbox и публикует в Kafka. Если сервис упал после коммита — событие всё равно уйдёт; если транзакция откатилась — события нет.

> [!question]- Чем Kafka отличается от Redis Pub/Sub?
> Pub/Sub в Redis — fire-and-forget: кто не подписан в момент публикации, сообщение потерял, истории нет. Kafka хранит сообщения на диске по retention, каждая группа помнит свой offset, офлайн-consumer дочитает пропущенное, можно перечитать историю. Redis Pub/Sub — для «разослать онлайн», Kafka — для надёжной доставки.
