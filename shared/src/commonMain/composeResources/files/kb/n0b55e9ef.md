# Handler и Looper

В Android **Handler** и **Looper** — это инструменты для управления очередью сообщений (message queue) и выполнения задач в потоке, когда требуется взаимодействие между разными потоками или обработка задач в асинхронном режиме.

## 1. Looper

**Looper** управляет циклом обработки сообщений в потоке. Каждый поток может иметь один объект `Looper`, который держит **MessageQueue** (очередь сообщений) и обрабатывает эти сообщения в порядке их поступления.

**Основные функции:**

- Управляет очередью сообщений, в которую можно класть задачи (`Runnable`) или сообщения (`Message`).
- Обеспечивает цикл обработки сообщений в потоке (event loop).

**Пример работы Looper:**

```kotlin
class MyThread : Thread() {
    lateinit var looper: Looper

    override fun run() {
        Looper.prepare()              // инициализирует Looper для текущего потока
        looper = Looper.myLooper()!!
        Looper.loop()                 // запускает цикл обработки сообщений
    }
}
```

## 2. Handler

**Handler** позволяет отправлять сообщения или задачи в очередь, управляемую `Looper`. Он работает в связке с `Looper` и выполняет операции на том потоке, с которым связан.

**Основные функции:**

- Отправка задач (`Runnable`) или сообщений (`Message`) в очередь.
- Выполнение кода в конкретном потоке через связанный `Looper`.
- Упрощение асинхронных операций и межпоточной коммуникации.

**Пример использования Handler:**

```kotlin
val handler = Handler(Looper.getMainLooper()) // Handler для главного потока

handler.post {
    println("Эта задача выполнится в главном потоке")
}
```

## 3. Как Looper и Handler работают вместе

1. **Looper** создаёт `MessageQueue` и цикл обработки событий в потоке.
2. **Handler** связывается с `Looper` и добавляет задачи (`Runnable`) или сообщения (`Message`) в очередь.
3. **Looper** достаёт сообщения из очереди по мере поступления и передаёт их обратно в `Handler` для выполнения.

## 4. Практическое применение

### 4.1. Результат фоновой работы в главный поток

Когда задачу выполняем в фоне, а результат отправляем в UI-поток:

```kotlin
val backgroundThread = Thread {
    Thread.sleep(2000) // имитация долгой операции
    Handler(Looper.getMainLooper()).post {
        println("Обновление UI из главного потока")
    }
}
backgroundThread.start()
```

### 4.2. Собственный поток с очередью сообщений

Если нужен свой поток, принимающий задачи в очередь:

```kotlin
class MyLooperThread : Thread() {
    lateinit var handler: Handler

    override fun run() {
        Looper.prepare()                      // инициализация Looper
        handler = Handler(Looper.myLooper()!!)
        Looper.loop()                         // запуск цикла обработки
    }
}

val looperThread = MyLooperThread()
looperThread.start()

looperThread.handler.post {
    println("Выполняется в пользовательском потоке")
}
```

> [!tip] Так делать на проде не надо
> Ручной `Looper.prepare()` / `loop()` подвержен гонкам (поле `handler` может быть ещё не инициализировано к моменту использования). В Android для этого есть готовый **`HandlerThread`** — он сам поднимает `Looper`:
> ```kotlin
> val thread = HandlerThread("worker").apply { start() }
> val handler = Handler(thread.looper)
> handler.post { /* работа в фоновом потоке */ }
> // ...
> thread.quitSafely() // не забыть остановить
> ```

## 5. Почему это важно в Android

- **Потокобезопасность UI.** UI можно обновлять только из главного потока. Handler/Looper позволяют передать задачу из фонового потока в главный.
- **Асинхронные задачи.** Управление задачами в других потоках без блокировки основного.
- **Очередь сообщений.** Удобный способ выполнять задачи в порядке поступления (в т.ч. отложенно — `postDelayed`).

## 6. Недостатки и ограничения

1. **Ручное управление.** Свой `Looper` нужно инициализировать и завершать (`Looper.quit()` / `quitSafely()`), иначе поток не остановится.
2. **Перегрузка очереди.** Слишком много задач в очереди → задержки в обработке.
3. **Низкоуровневость.** В современном коде предпочитают более высокоуровневые инструменты: **Coroutines (`Dispatchers.Main`)**, **WorkManager**, реже RxJava. Но под капотом главный поток Android по-прежнему крутится на `Looper`.

> [!warning] Утечки памяти
> `Handler` как нестатический внутренний класс / лямбда держит ссылку на внешний объект (например, Activity). Отложенное сообщение в очереди не даст его собрать GC. Решение: убирать колбэки в `onDestroy` через `handler.removeCallbacksAndMessages(null)`.
