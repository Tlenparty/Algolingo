# 20 Масштабирование БД: где узкое место

Приложение размножить легко, состояние — сложно. Поэтому база становится общей точкой нагрузки раньше всего остального. Заметка о том, как диагностировать ограничение и выбрать следующий шаг: не «поставить шарды», а самый простой шаг, снимающий давление.

> [!tip] Аналогия из Android
> Это профилирование jank: низкая загрузка CPU не значит, что всё хорошо, кадр может ждать блокировку или диск. Сначала трейс и поиск самого дорогого участка, потом оптимизация именно его. Ускорять то, что не на критическом пути, бесполезно. С базой так же: `EXPLAIN ANALYZE` вместо «добавим реплику».

## Почему база — узкое место

База — точка схождения: хранит состояние, обеспечивает транзакции и ограничения, одна на многие сервисы, партнёров и фоновые задачи. Горизонтальное масштабирование приложения усиливает конкуренцию за базу: больше экземпляров — одно общее состояние.

```text
Клиент → Балансировщик → App ×N → Пул → База ×1
                         больше      одно
                         экземпляров состояние
```

## Как растёт нагрузка

Четыре измерения, каждое давит по-своему:

| Растёт | Что давит на базу |
| --- | --- |
| Пользователи (больше сессий) | соединения, конкуренция |
| Данные (больше строк и индексов) | объём чтения, обслуживание, индексы не влезают в память |
| Запросы (частота и сложность) | CPU, I/O |
| Транзакции (больше одновременно) | очереди, блокировки, конфликты |

Одинаковый рост трафика создаёт совершенно разные узкие места. И одинаковый QPS стоит по-разному: полное сканирование — много, поиск по индексу — мало. Стоимость задают план запроса, объём данных и ожидания, а не только число запросов.

## Где запрос теряет время

Задержка = работа + ожидания + очередь.

- **Работа**: CPU (план и вычисления), RAM (буферный кеш), диск (страницы данных, WAL).
- **Ожидания**: соединение из пула, I/O, блокировки.
- **Очередь**: запрос ждёт, пока освободится ресурс.

Ускорение одного этапа не поможет, если ограничивает другой.

**Высокий CPU** обычно указывает на дорогую работу: full scan, тяжёлые JOIN, лишние сортировки, лишние или неиспользуемые индексы. Первые действия: найти запросы с наибольшим суммарным временем и проверить их планы через `EXPLAIN ANALYZE`.

**Растёт I/O**, когда working set не помещается в RAM: горячие страницы вытесняются, промахи буфера идут на диск. Важно не сколько данных хранится, а какая часть активно читается прямо сейчас.

**Низкий CPU не исключает высокую задержку.** Транзакция A захватила строку, B ждёт (lock wait), CPU простаивает. Дедлок — частный случай циклического ожидания, который база разрывает откатом одной транзакции.

## Почему деградация нелинейна

До порога задержка растёт плавно. После точки насыщения очередь растёт быстрее нагрузки: задержка → таймауты → повторные запросы → ещё больше нагрузки → очередь. Повторы усиливают перегрузку: клиент воспринимает таймаут как временную ошибку и шлёт снова.

Практический вывод: нельзя проектировать постоянную работу на 100% ресурса. Запас мощности нужен для пиков, фоновых операций, отказа узла и неточности прогнозов.

## Лестница стратегий

Сначала дешёвый шаг. Стратегии подключаются по мере появления конкретного ограничения:

1. **Запросы и индексы** — часто решает всё.
2. **Кеширование** — снимает повторное чтение.
3. **Репликация** — разгружает чтение, даёт резерв.
4. **Партиционирование** — локализует данные и обслуживание в одной базе.
5. **Шардирование** — распределяет запись и объём по узлам.

Три последние снимают разное давление и не взаимоисключают друг друга: каждый шард может быть партиционирован по времени и иметь собственные реплики.

## Когда применять в SD-задаче

Сигналы: «база тормозит», «ответ стал 2 секунды», «рост ×3 за год», «что делать с базой при масштабировании». Ответ: сначала диагностика (какое из четырёх измерений выросло, где теряется время), потом самый дешёвый шаг лестницы.

Фраза на собес: «Сначала смотрю, где теряется время: планы самых дорогих запросов, помещается ли working set в память, есть ли lock wait. Потом по лестнице: индексы, кеш, реплики на чтение, партиции по дате, и только для записи и объёма — шарды. И закладываю запас: при насыщении деградация нелинейна, а повторы её усиливают».

> [!warning] Грабли
> - Шардировать до индексов. 90% проблем решает план запроса.
> - Судить по среднему CPU: низкий CPU при lock wait.
> - Масштабировать App при узком месте в базе: стало хуже, больше соединений.
> - Ретраи без лимита при перегрузке: каждая ошибка превращается в два запроса.
> - Планировать базу на 100% ресурса: нет запаса на пик и отказ узла.
> - Пул соединений больше, чем база может обслужить: очередь переехала внутрь базы.

> [!question]- База стала узким местом. С чего начнёте?
> С диагностики: какое измерение выросло (пользователи, данные, запросы, транзакции) и где теряется время (CPU, I/O, блокировки, очередь на соединение). `EXPLAIN ANALYZE` самых дорогих по суммарному времени запросов. Потом дешёвый шаг: индексы и запросы, затем кеш, реплики, партиции, шарды.

> [!question]- Почему при росте нагрузки на 10% задержка выросла в 5 раз?
> Прошли точку насыщения: очередь растёт быстрее нагрузки, а таймауты вызывают повторы, которые добавляют нагрузку. Нужен запас мощности и ограничение повторов (backoff, circuit breaker), иначе система не выйдет из перегрузки сама.

> [!question]- Чем репликация, партиционирование и шардирование отличаются?
> Репликация копирует данные целиком и разгружает чтение, даёт резерв. Партиционирование делит таблицу на части внутри одной базы, локализует чтение и обслуживание, но ресурсы сервера общие. Шардирование раскладывает части данных по разным узлам, распределяет запись и объём. Их комбинируют.
