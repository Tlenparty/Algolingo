# 01 Путь запроса

Что на самом деле происходит между `api.getFeed()` в приложении и JSON в ответе. Сквозная картина нужна, чтобы на SD-собесе рисовать схему слева направо и по любой ошибке из логов понимать, на каком звене она случилась.

> [!tip] Аналогия из Android
> Это как цепочка OkHttp-interceptor'ов, только растянутая по сети: каждое звено (DNS, TLS, балансировщик, сервер, кеш) может обработать запрос, изменить его, ответить само или упасть. Ошибка в логе — это «на каком interceptor'е оборвалось».

## Как работает

```text
Приложение (Retrofit/OkHttp)
  │ 1. DNS: api.example.com → IP
  ▼
  │ 2. TCP: SYN / SYN-ACK / ACK
  ▼
  │ 3. TLS: рукопожатие, ключи
  ▼
  │ 4. HTTP: GET /feed + заголовки
  ▼
Load balancer / nginx
  │ 5. TLS-терминация, выбор узла
  ▼
App-сервер (один из N)
  │ 6. auth, бизнес-логика
  ▼
Redis (кеш) ──miss──► БД
  │ 7. данные
  ▼
Ответ: 200 + JSON обратно по цепочке
```

По шагам:

1. **DNS.** Имя `api.example.com` превращается в IP. Ответ кешируется по TTL: в ОС, у провайдера, в OkHttp-пуле соединений (живое соединение повторно не резолвится).
2. **TCP.** Трёхстороннее рукопожатие — один round trip (RTT). На мобильной сети RTT легко 100–300 мс, поэтому каждое новое соединение дорогое.
3. **TLS.** Проверка сертификата сервера и согласование ключей. В TLS 1.3 это +1 RTT (подробно — [[03 HTTPS, TLS, SSL]]).
4. **HTTP.** Сам запрос: метод, путь, заголовки, тело ([[02 HTTP]]). На HTTP/2 по одному соединению идут параллельно много запросов.
5. **Балансировщик / reverse proxy.** Принимает TLS, выбирает живой экземпляр сервера, может ограничить частоту запросов ([[05 nginx, reverse proxy, load balancer, API Gateway]]).
6. **App-сервер.** Проверяет токен, выполняет логику. Сервер stateless — любой из N экземпляров может обработать запрос.
7. **Кеш и БД.** Сначала Redis ([[06 Redis]]), при промахе — база данных, результат кладётся в кеш.
8. **Ответ** идёт обратно той же цепочкой. Клиент парсит JSON и кладёт в локальную БД / показывает.

Почему повторное соединение так ценно: шаги 1–3 стоят 2+ RTT ещё до первого байта ответа. Поэтому OkHttp держит пул соединений (keep-alive), а HTTP/2 мультиплексирует всё в одно соединение.

## Что где ломается

| Этап | Что сломалось | Как видно в приложении |
| --- | --- | --- |
| DNS | нет сети, имя не резолвится | `UnknownHostException` |
| TCP | сервер недоступен, порт закрыт | `ConnectException`, `SocketTimeoutException` (connect) |
| TLS | просрочен сертификат, pinning, неверное время на телефоне | `SSLHandshakeException`, `SSLPeerUnverifiedException` |
| HTTP (клиент) | неверный запрос, нет токена | 400, 401, 403, 404, 422 |
| LB / proxy | все узлы лежат, узел не ответил | 502, 503, 504 |
| App | исключение в коде | 500 |
| Кеш / БД | медленный запрос, перегрузка | долгий ответ → `SocketTimeoutException` (read) |
| Лимиты | слишком часто | 429 + `Retry-After` |

Правило для ретраев: сетевые ошибки до отправки запроса (DNS, connect) и 502/503/504 — повторять с экспоненциальной задержкой; 4xx — не повторять, это ошибка клиента; 500 на неидемпотентный POST — повторять только с Idempotency-Key.

## Когда применять в SD-задаче

Сигналы: «спроектируй ленту/чат/загрузку», «приложение медленно открывается», «как обработать ошибки сети». Начинай схему именно с этой цепочки, потом углубляйся в звено, о котором спрашивают.

Фраза на собес: «Запрос проходит DNS, TCP, TLS, затем балансировщик раскидывает его по stateless-серверам, которые читают из кеша и БД; на клиенте я переиспользую соединения и ретраю только идемпотентные запросы и 5xx/таймауты».

> [!warning] Грабли
> - Таймауты по умолчанию в OkHttp — 10 с на connect/read/write; для медленной сети нужен ещё и `callTimeout` на весь вызов, иначе запрос может висеть очень долго.
> - Ретрай без backoff и jitter после падения сервера даёт «шторм»: миллион клиентов одновременно добивают поднимающийся сервер.
> - `SSLHandshakeException` у части пользователей часто означает неправильное время на устройстве или корпоративный прокси, а не баг сервера.
> - DNS тоже может быть точкой отказа: ответ закеширован по TTL, и переключение на новый IP доходит до клиентов не сразу.

> [!question]- Что происходит, когда в приложении вызывается GET api.example.com/feed?
> DNS-резолв имени в IP → TCP-рукопожатие → TLS-рукопожатие (проверка сертификата, общий ключ) → HTTP-запрос по зашифрованному каналу → балансировщик (TLS-терминация, выбор живого узла) → app-сервер (auth, логика) → кеш, при промахе БД → ответ обратно. Повторные запросы идут по уже открытому соединению из пула, без шагов DNS/TCP/TLS.

> [!question]- Пользователи жалуются на долгий первый запрос, а последующие быстрые. Почему?
> Первый запрос платит за DNS + TCP + TLS — это 2–3 RTT, на мобильной сети сотни миллисекунд. Дальше соединение живёт в пуле OkHttp. Лечится: один общий `OkHttpClient` на всё приложение, HTTP/2, preconnect к API при старте, TLS 1.3 (меньше RTT), а на сервере — CDN/edge ближе к пользователю.

> [!question]- Как по ошибке понять, на чьей стороне проблема?
> `UnknownHostException`/`ConnectException` — сеть или DNS, до сервера не дошли. `SSLHandshakeException` — сертификат, время или pinning. 4xx — сервер ответил, ошибка в запросе клиента. 502/503/504 — балансировщик жив, а сервер за ним нет. 500 — баг в коде сервера. Read-timeout — сервер принял запрос, но долго думает (часто БД).
