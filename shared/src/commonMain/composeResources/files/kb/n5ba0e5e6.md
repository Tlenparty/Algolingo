# 23 OLTP и OLAP

Покупатель спрашивает «где мой заказ № 700?», аналитик — «как менялись продажи за год?». Первое — OLTP (Online Transaction Processing), операции приложения: точечно, по ключу, маленький ответ. Второе — OLAP (Online Analytical Processing), анализ множества операций: миллионы строк, несколько столбцов, агрегаты. Разница в характере запросов, объёме работы и требованиях к результату, и смешивать их в одной базе — путь к тому, что утренний отчёт кладёт заказы.

> [!tip] Аналогия из Android
> OLTP — `SELECT * FROM orders WHERE id = ?` в Room для экрана заказа. OLAP — Firebase Analytics и BigQuery: события улетают в отдельное хранилище, и никто не считает DAU по таблице в Room на телефоне пользователя. Приложение пишет факты, аналитика считает их в другом месте и с другой свежестью.

## Два запроса

```sql
-- OLTP: точечное чтение
SELECT status, total_amount
FROM orders
WHERE order_id = 700;
-- доступ по ключу, индекс на order_id, одна строка

-- OLAP: агрегация
SELECT month, region, SUM(paid_amount)
FROM fact_paid_orders
WHERE paid_at >= DATE '2025-01-01'
  AND paid_at <  DATE '2026-01-01'
GROUP BY month, region;
-- много строк, мало столбцов
```

| | OLTP | OLAP |
| --- | --- | --- |
| Запрос | по ключу, одна сущность | фильтр и группировка периода |
| Строк | единицы | миллионы |
| Столбцов | все поля объекта | 3–4 |
| Хранение | построчное | колоночное |
| Свежесть | немедленно | минуты или часы допустимы |
| Пример | PostgreSQL, MySQL | ClickHouse, BigQuery, Greenplum |

**Построчное и колоночное хранение.** Строка удобна для полей одного объекта: один заказ целиком. Столбец удобен для значений многих объектов: сумма по миллиону заказов читает только столбец `amount`, а не всю строку с адресом и комментарием. Выбор зависит от запросов.

## Паттерн в системах

Тяжёлый отчёт конкурирует с заказами: агрегации занимают CPU и память, большое чтение меняет рабочий набор в кеше (вытесняет горячие страницы заказов). Реплика разгружает primary, но сохраняет свой предел: это та же построчная база, отчёт на ней всё равно часы.

Путь данных в аналитическое хранилище:

```text
OLTP база ─→ передача изменений ─→ преобразование ─→ OLAP ─→ отчёт
             (пакет раз в час       (витрины,          (колоночное)
              или CDC из WAL)        агрегаты)
```

Пакетная загрузка или CDC — по требованиям к свежести: отчёту «за вчера» хватит ночного пакета, дашборду «за последний час» нужен поток через CDC и Kafka.

Порядок проектирования: сначала описать запросы и цели по задержке и свежести; затем выбрать модель данных, способ хранения и степень изоляции ресурсов; при выделении аналитического контура отдельно проверить доставку изменений и смысл метрик (одинаково ли считается «опубликованный пост» в приложении и в отчёте).

## Когда применять в SD-задаче

Сигналы: «аналитики строят отчёт», «дашборд», «посчитать за год», «проверить гипотезу по продажам», «отчёт мешает пользователям». Ответ: отдельный контур, колоночное хранилище, доставка пакетом или CDC по свежести.

Фраза на собес: «Отчёт за 12 месяцев — OLAP-нагрузка, её нельзя гонять по базе заказов. Изменения уезжают через CDC в Kafka и ложатся в ClickHouse, там агрегаты по дням считаются за секунды. Свежесть до часа по требованию, при этом primary отчёта не замечает».

> [!warning] Грабли
> - `GROUP BY` за год по primary в 9 утра: заказы встали.
> - «Поставим реплику под отчёты» и забыть, что построчная реплика считает агрегаты так же долго; выигрыш только в изоляции.
> - Двойная запись из приложения в OLTP и OLAP: разъедутся. Доставка из журнала (CDC) или пакетом из базы.
> - Разный смысл метрик: отчёт считает черновики как посты.
> - Требовать от аналитики свежести «сейчас» без причины: цена — CDC, стриминг и сложность, когда хватило бы пакета раз в час.

> [!question]- Чем OLTP отличается от OLAP?
> OLTP — операции приложения: точечные запросы по ключу, маленький ответ, транзакции, построчное хранение, свежесть немедленно. OLAP — анализ совокупности операций: фильтр и агрегация миллионов строк по нескольким столбцам, колоночное хранение, свежесть минуты или часы. Их разделяют по хранилищу и ресурсам.

> [!question]- Как доставить данные в аналитическое хранилище?
> Пакетом по расписанию (SELECT изменений за период) или потоком через CDC: читать журнал базы (Debezium) → Kafka → загрузка в OLAP. Выбор по требованию к свежести: час — пакет, минуты — CDC. В обоих случаях нужен слой преобразования (витрины) и контроль смысла метрик.

> [!question]- Почему колоночное хранение быстрее для отчётов?
> Отчёт читает 3–4 столбца из миллионов строк. В колоночном хранилище столбец лежит отдельно и сжат, читается только он; в построчном приходится поднимать каждую строку целиком со всеми полями.
