В объектно-ориентированном программировании, в том числе в Kotlin, **наследование** и **композиция** — это два основных подхода для повторного использования кода и моделирования отношений между классами. Рассмотрим их различия, применение и примеры в Kotlin.

**1. Наследование**

**Наследование** — это механизм, позволяющий одному классу (наследнику) получать свойства и методы другого класса (родителя или суперкласса). В Kotlin наследование реализуется с помощью ключевых слов open и :.

**Признаки наследования**

• Используется для выражения отношения **“является” (is-a)**.
• Подкласс наследует поведение суперкласса, но может переопределить его.
• Связь между классами жесткая, изменения в базовом классе могут повлиять на наследников.

```kotlin
open class Animal {
    open fun sound() {
        println("Animal makes a sound")
    }
}

class Dog : Animal() {
    override fun sound() {
        println("Dog barks")
    }
}

fun main() {
    val dog = Dog()
    dog.sound()  // Output: Dog barks
}
```

**Когда использовать наследование**

• Когда классы имеют отношение **“is-a”** (например, Собака — это Животное).
• Когда требуется общий интерфейс или базовый функционал для нескольких классов.
• Если ожидается, что будет удобнее работать с полиморфизмом (например, передача объектов разных классов в одну функцию).

**2. Композиция**

**Композиция** — это механизм, при котором один класс использует объекты другого класса для реализации своей функциональности. Это реализуется через включение объектов других классов в виде полей (свойств).

**Признаки композиции**

• Используется для выражения отношения **“имеет” (has-a)**.
• Связь между классами слабее, чем при наследовании.
• Изменения в одном классе менее критичны для другого.

**Пример в Kotlin**

```kotlin
class Engine {
    fun start() {
        println("Engine starts")
    }
}

class Car(val engine: Engine) {
    fun drive() {
        engine.start()
        println("Car is driving")
    }
}

fun main() {
    val engine = Engine()
    val car = Car(engine)
    car.drive()
    // Output:
    // Engine starts
    // Car is driving
}
```

**Когда использовать композицию**

• Когда классы имеют отношение **“has-a”** (например, Машина имеет Двигатель).
• Когда важна гибкость и возможность изменять один класс без влияния на другой.
• Для улучшения повторного использования кода и уменьшения зависимости между классами.

| Характеристика          | Наследование                               | Композиция                  |
| ----------------------- | ------------------------------------------ | --------------------------- |
| Отношение               | "является" is-a                            | "имеет" has-a               |
| Связь                   | Жесткая связь между классами               | Слабая связь между классами |
| Гибкость                | Меньшая гибкость (зависимость от суперкласса) | Высокая гибкость         |
| Полиморфизм             | Поддерживается                             | Требует доп. интерфейсов    |
| Повторное использование | Через наследование                         | Через включение объектов    |
| Видимость protected     | -                                          | +                           |

# **🔥 Ключевые отличия абстрактного класса и интерфейса**

| **Характеристика**                | **Абстрактный класс**      | **Интерфейс**                   |
| --------------------------------- | -------------------------- | ------------------------------- |
| Поддерживает состояние (поля)     | ✅ Да                       | 🚫 Нет (только val без var)     |
| Можно наследовать несколько       | 🚫 Нет (только один класс) | ✅ Да (множественная реализация) |
| Поддерживает методы с реализацией | ✅ Да                       | ✅ Да (с default реализацией)    |
| Поддерживает абстрактные методы   | ✅ Да                       | ✅ Да                            |
| Имеет конструкторы                | ✅ Да                       | 🚫 Нет                          |
| Используется для                  | **Поведения + состояния**  | **Только поведение (контракт)** |

**Когда лучше использовать наследование или композицию в Kotlin?**

1. **Используйте наследование**, если:

• Ваши классы действительно связаны отношением “является”.
• Вам нужен общий базовый функционал или интерфейс.
• Вы работаете с полиморфизмом.

2. **Используйте композицию**, если:

• Вы хотите ослабить зависимость между классами.
• Вам нужно объединить несколько независимых функциональностей.
• Вам требуется гибкость в изменении и тестировании кода.

**Полиморфизм** — это одна из ключевых концепций объектно-ориентированного программирования (ООП), которая позволяет одному и тому же коду работать с объектами разных типов, при этом обеспечивая корректное поведение. В Kotlin полиморфизм реализуется через наследование, интерфейсы и переопределение методов.
**Основные аспекты полиморфизма**

1. **Ad-hoc полиморфизм (перегрузка методов)**

• Один метод или функцию можно определить в нескольких вариантах с разными типами или количеством параметров.

**Пример:**

```kotlin
fun printMessage(message: String) {
    println("String message: $message")
}

fun printMessage(message: Int) {
    println("Int message: $message")
}

fun main() {
    printMessage("Hello")  // String message: Hello
    printMessage(42)       // Int message: 42
}
```

2. **Полиморфизм подтипов (наследование и переопределение)**

• Позволяет использовать базовый тип (класс или интерфейс), но при этом подставлять объекты его наследников, реализующих собственное поведение.

**Пример:**
```kotlin
open class Animal {
    open fun makeSound() {
        println("Animal makes a sound")
    }
}

class Dog : Animal() {
    override fun makeSound() {
        println("Dog barks")
    }
}

class Cat : Animal() {
    override fun makeSound() {
        println("Cat meows")
    }
}

fun playWithAnimal(animal: Animal) {
    animal.makeSound()
}

fun main() {
    val dog = Dog()
    val cat = Cat()

    playWithAnimal(dog)  // Dog barks
    playWithAnimal(cat)  // Cat meows
}
```

3. **Полиморфизм интерфейсов**

• В Kotlin интерфейсы определяют контракт (набор методов), который могут реализовать разные классы.

**Пример:**

```kotlin
interface Shape {
    fun draw()
}

class Circle : Shape {
    override fun draw() {
        println("Drawing a circle")
    }
}

class Square : Shape {
    override fun draw() {
        println("Drawing a square")
    }
}

fun renderShape(shape: Shape) {
    shape.draw()
}

fun main() {
    val circle = Circle()
    val square = Square()

    renderShape(circle)  // Drawing a circle
    renderShape(square)  // Drawing a square
}
```

**Ключевые особенности полиморфизма в Kotlin**

1. **Переопределение методов:**

• В Kotlin для переопределения методов базового класса или интерфейса используется ключевое слово override.
• Базовые методы или свойства должны быть помечены как open.

2. **Позднее связывание (Late Binding):**

• Конкретный метод вызывается в зависимости от типа объекта, а не от типа ссылки, через которую объект был вызван.

3. **Работа с абстрактными классами и интерфейсами:**

• Абстрактные классы и интерфейсы позволяют задавать общий интерфейс для различных реализаций.

**Практическое применение полиморфизма**

• Создание гибких и расширяемых систем.
• Использование общих интерфейсов или базовых классов для работы с различными объектами.

• Реализация принципа **SOLID**: в частности, принципа подстановки Барбары Лисков (Liskov Substitution Principle, LSP), который говорит, что объекты суперкласса должны заменяться объектами подклассов без нарушения работы программы.

## **Отличие абстрактного класса от интерфейса**

В Kotlin абстрактные классы и интерфейсы служат для определения общих контрактов или базовых структур для классов, но они имеют разные особенности и предназначения. Вот основные отличия между ними:
  

**1. Наследование**

• **Абстрактный класс:**
• Класс может наследоваться только от одного абстрактного класса (т.к. Kotlin поддерживает только одиночное наследование для классов).
• Абстрактный класс может содержать как абстрактные (не реализованные), так и обычные (реализованные) методы.

• **Интерфейс:**

• Класс может реализовывать несколько интерфейсов.
• Интерфейс может содержать:
• Абстрактные методы (без реализации).
• Методы с реализацией (с помощью ключевого слова default или без него).
• Свойства с реализацией или без.

**2. Конструкторы**

• **Абстрактный класс:**
• Может иметь конструктор (как первичный, так и вторичные).
• Может содержать состояние (поля).

• **Интерфейс:**
• Не может иметь конструктора.
• Не может напрямую хранить состояние (только свойства без бекенда или со стандартным геттером/сеттером).

**3. Модификаторы доступа**

• **Абстрактный класс:**
• Методы и свойства могут иметь различные модификаторы доступа (public, protected, private, internal).

• **Интерфейс:**
• Методы и свойства интерфейса по умолчанию являются public, других модификаторов доступа быть не может.

**4. Область применения**

• **Абстрактный класс:**
• Используется для определения базового поведения, которое должно быть наследовано. Обычно используется, если нужно объединить общий код для нескольких классов.
• Можно добавить свойства и методы с реализацией, которые будут использоваться наследниками.

• **Интерфейс:**

• Используется для определения контракта, который класс должен выполнить. Позволяет классу реализовывать несколько контрактов (множественное наследование интерфейсов).

**6. Когда использовать?**

• **Абстрактный класс:** Когда вам нужно объединить общее поведение, состояние и предоставить базовую реализацию для группы связанных классов.

• **Интерфейс:** Когда вам нужно определить контракт (набор методов), который может быть реализован несколькими классами, не связанными друг с другом.


>Паттерн стратегия.
  Есть методы которые не можешь реализовать. (Абстрактный класс)
  Если нужен стейт. Декоратор.


## Когда лучше использовать Абстрактный класс, а когда Интерфейс ?? 

Абстрактные классы полезны, когда вам нужно предоставить **общую реализацию** и определить **основное поведение** для всех наследников. Они могут содержать как **реализованные методы**, так и **абстрактные (без реализации)**.

### **Используйте абстрактный класс, если:**

1. Вам нужно **хранить состояние** (например, поля с данными).
2. Вам нужно **определить общие методы** с реализацией, которые могут переопределяться в подклассах.
3. Ваши классы тесно связаны между собой и образуют иерархию.
4. Вам нужна возможность **использовать конструкторы**.
5. У вас **ограниченный набор классов**, которые должны наследовать этот базовый класс.


**Пример использования абстрактного класса:**

```kotlin

abstract class Animal(val name: String) {
    abstract fun makeSound() // Метод без реализации

    fun eat() { // Метод с реализацией
        println("$name ест еду")
    }
}

class Dog(name: String) : Animal(name) {
    override fun makeSound() {
        println("Гав-гав!")
    }
}

fun main() {
    val dog = Dog("Бобик")
    dog.eat()         // Бобик ест еду
    dog.makeSound()   // Гав-гав!
}
// ✅ **Когда есть общее поведение (**eat()**) и его можно переиспользовать — используем абстрактный класс**.
```

### **Когда использовать интерфейс?**

Интерфейсы полезны, когда вам нужно **определить контракт** (набор методов) без привязки к реализации. Они не могут хранить состояние (до появления val свойств с геттерами в Kotlin), но могут иметь **методы по умолчанию**.


**Используйте интерфейс, если:**

1. Вам нужна **множественная реализация** (Kotlin не поддерживает множественное наследование классов, но позволяет реализовывать несколько интерфейсов).
2. Вам **не нужно хранить состояние** (например, нет полей, кроме val-свойств).
3. Вы хотите **задать API** (контракт), который разные классы будут реализовывать по-разному.
4. Вам нужно **разделить логику между несвязанными классами**.

**Пример использования интерфейса:**

```kotlin

interface Flyable {
    fun fly() // Абстрактный метод без реализации
}

class Bird : Flyable {
    override fun fly() {
        println("Птица летит!")
    }
}

class Airplane : Flyable {
    override fun fly() {
        println("Самолёт взлетает!")
    }
}

fun main() {
    val bird = Bird()
    val airplane = Airplane()
    
    bird.fly()      // Птица летит!
    airplane.fly()  // Самолёт взлетает!
}
```


> Когда говорят, что **абстрактный класс может хранить state (состояние)**, имеют в виду, что он **может содержать поля (переменные, свойства), которые хранят данные**. Это позволяет абстрактному классу **иметь состояние**, которое будет передаваться и использоваться в его подклассах.

```kotlin

  abstract class Animal(val name: String) { // Абстрактный класс хранит состояние (поле name)
    var energy: Int = 100 // Поле состояния (меняется со временем)

    fun eat() {
        energy += 10
        println("$name ест. Энергия: $energy")
    }

    abstract fun makeSound() // Абстрактный метод (без реализации)
}

class Dog(name: String) : Animal(name) {
    override fun makeSound() {
        println("$name говорит: Гав-гав!")
    }
}

fun main() {
    val dog = Dog("Бобик")
    dog.eat()        // Бобик ест. Энергия: 110
    dog.makeSound()  // Бобик говорит: Гав-гав!
}
```


> Интерфейсы в Kotlin **не могут содержать изменяемые свойства (**var**)**, но могут содержать val (только для чтения) с реализацией геттера**.

```kotlin

interface Flyable {
    val maxAltitude: Int // Можно задать только val (но без var)

    fun fly() {
        println("Лечу на высоте $maxAltitude метров!")
    }
}

class Bird : Flyable {
    override val maxAltitude = 1000 // Реализация свойства
}

fun main() {
    val bird = Bird()
    bird.fly() // Лечу на высоте 1000 метров!
}
// 🚫 **Если бы** Flyable **пытался задать var с инициализатором/backing field — не скомпилировалось бы**.
```

> [!important] Уточнение про `var` в интерфейсе
> Интерфейс **может** объявить **абстрактный `var`** — но без backing field; хранение обязан реализовать класс:
> ```kotlin
> interface Counter {
>     var count: Int          // ✅ абстрактный var — ок
>     // var count: Int = 0   // ❌ нельзя: backing field
> }
> class CounterImpl : Counter {
>     override var count: Int = 0  // класс хранит состояние
> }
> ```
> То есть интерфейс не может **сам хранить** состояние, но может **требовать** его через `var`.

> [!tip] Что отвечать «абстрактный класс vs интерфейс»
> - **Интерфейс** — «что класс умеет» (контракт), можно реализовать **много**, нет состояния и конструктора. Дефолт для большинства абстракций в Kotlin.
> - **Абстрактный класс** — «что класс есть» + общая реализация и **состояние** (поля, конструктор), но **только один**.
> - Правило: начинай с интерфейса; бери абстрактный класс, когда нужны общее **состояние/конструктор** или защищённые (`protected`) члены.
> - **Diamond problem:** если два интерфейса дают одинаковый default-метод, Kotlin заставит переопределить его и явно выбрать через `super<Interface1>.method()`.
