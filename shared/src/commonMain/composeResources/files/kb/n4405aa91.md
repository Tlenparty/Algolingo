В программировании на языке Kotlin (и Java) память процесса делится на несколько сегментов. Два наиболее важных из них — это **Heap** (куча) и **Stack** (стек). Они выполняют разные задачи, и их объем зависит от системы, конфигурации JVM и других факторов.

## **1. Stack (Стек)**
**Стек** — это область памяти, используемая для выполнения метода. Он организован как структура данных “последним пришел — первым вышел” (LIFO). Каждый поток программы имеет собственный

## **Основные характеристики:**
1. **Размер:**
	• По умолчанию размер стека в JVM составляет ==от **256 КБ до 1 МБ** на поток==, но может быть изменен с помощью параметра -Xss.
	
2. **Расположение:**
	• Лежит в оперативной памяти и организован в виде непрерывного блока.
	
3. **Скорость:**
	• Очень быстрый доступ, так как стек управляется без необходимости явного выделения или освобождения памяти.
	
4. **Использование:**
	• Хранит:
	• Локальные переменные.
	• Адреса возврата (куда программа должна вернуться после завершения метода).
	• Параметры метода.
	• Контекст выполнения метода (например, указатель текущей инструкции).

5. **Срок жизни:**
	• Переменные в стеке существуют только до тех пор, пока выполняется метод. После завершения метода память автоматически освобождается.
```kotlin

fun main() {
    val x = 10 // Локальная переменная в стеке
    val y = calculate(x)
}

fun calculate(value: Int): Int {
    val result = value * 2 // result находится в стеке
    return result
}
// Здесь x и result хранятся в стеке. Когда метод завершает выполнение, их память автоматически освобождается.
```

## **2. Heap (Куча)**

**Куча** — это область памяти, предназначенная для динамического выделения объектов и хранения данных, которые могут существовать дольше, чем время выполнения метода.

**Основные характеристики:**
1. **Размер:**
• Размер кучи может варьироваться в зависимости от конфигурации JVM. По умолчанию:
• Минимальный размер (-Xms) — **16 МБ или больше**.
• Максимальный размер (-Xmx) — от **256 МБ до нескольких гигабайт** (например, 1–4 ГБ).
• Эти значения можно настроить вручную, например:
java -Xms512m -Xmx2048m.
2. **Расположение:**
• Лежит в оперативной памяти, и доступ к ней медленнее, чем к стеку.
3. **Скорость:**
• Более медленный доступ по сравнению со стеком, так как объекты выделяются динамически.
4. **Использование:**
• Хранит:
• Объекты (в том числе массивы и коллекции).
• Переменные, на которые ссылаются из других областей памяти.
5. **Срок жизни:**
• Объекты в куче существуют до тех пор, пока на них есть ссылки. Когда ссылки теряются, объект становится недоступным и удаляется сборщиком мусора (Garbage Collector, GC).
```kotlin
class Person(val name: String)

fun main() {
    val person = Person("Alice") // Объект "Alice" выделяется в куче
}
```
Здесь объект Person создается в куче, а ссылка на него (person) хранится в стеке. Когда ссылка теряется, объект становится доступным для сборки мусора.

**Сравнение Heap и Stack:**

| Критерий               | Stack                                | Heap                        |
| ---------------------- | ------------------------------------ | --------------------------- |
| Тип памяти             | Локальная память                     | Глобальная память           |
| Скорость доступа       | Очень быстрая                        | медленная                   |
| Срок жизни             | До завершения метода                 | Пока объект достижим        |
| Хранение               | Локальные переменные, вызовы функций | Объекты, массивы, коллекции |
| **Управление памятью** | Автоматическое                       | GC                          |

## **Почему итерация по списку происходит быстро, если она хранится в хипе ?**

### **Принцип локальности данных (Data Locality)**

• **Пространственная локальность:**
• Объекты в коллекциях, таких как массивы, хранятся последовательно в памяти. Это позволяет процессору считывать данные блоками, используя кэш (например, L1, L2, L3).
• Например, при итерации массива из 1000 элементов процессор может загрузить целые блоки памяти в кэш, ускоряя доступ.

• **Временная локальность:**
• Если одни и те же данные используются повторно (например, при вычислениях), они остаются в кэше, что ускоряет их доступ.

> И если тебе надо обратиться к 10му элементу, то ты к ссылке на массив (адрес в памяти) прибавляешь 10 * размер типа, получаешь новый адрес и обращаешься туда

> Когда ты говоришь, сделай мне массив на 10 интов, то тебе jvm выделяет 40 байт памяти (10 * 4) и все, и инты у тебя будут лежать там друг за другом

### **Виртуальная машина и Garbage Collector**

• JVM оптимизирует использование памяти в куче:
• Коллекции выделяются в “молодом поколении” кучи, которое имеет быстрые операции чтения и записи.

### **JVM-оптимизации**
• **JIT-компиляция (Just-In-Time):**
• Во время выполнения JVM анализирует код и оптимизирует горячие участки (часто выполняемые операции). Итерация по коллекции — один из таких случаев.
• JIT может разворачивать циклы, убирать проверки границ массива (если это безопасно), и выполнять инлайнинг методов, что ускоряет итерацию.
• **Escape-анализ:**
• JVM может определить, если объект коллекции используется только внутри метода, и, в некоторых случаях, выделить память в стеке вместо кучи, что ускоряет доступ.

### **Структура данных коллекции**
• **Коллекции в Kotlin и Java (например,** ArrayList**,** HashMap**) спроектированы для эффективного доступа и итерации.**
• Например, в ArrayList элементы хранятся в массиве, который является компактной и последовательной структурой в памяти. При итерации JVM может предсказать следующее чтение данных благодаря линейной организации массива.
• В HashMap используется массив с отдельными списками или деревьями для разрешения коллизий, что также оптимизировано для быстрого доступа.

### **🔥 Где хранятся переменные-поля класса в памяти JVM?**

В **JVM (Java Virtual Machine)** память делится на несколько областей:

1. **Heap (Куча)** – хранит **объекты**.
2. **Stack (Стек)** – хранит **локальные переменные** и вызовы методов.
3. **Method Area (Методная область, часть Metaspace)** – хранит **статические поля**, байт-код классов и метаданные.
4. **CPU-регистры и память для JIT-компиляции** (используются во время исполнения).

**📌 Где хранятся переменные-поля класса?**

### **1️⃣ Обычные (нестатические) поля класса (Instance Fields)**

🔹 **Хранятся в Heap (куче)** внутри объекта.
🔹 Каждый объект имеет **свои копии** полей.

```kotlin
class Person(var name: String, var age: Int)

fun main() {
    val p1 = Person("Alice", 25) 
    val p2 = Person("Bob", 30)
}
```


**Пример:**

✅ **В памяти JVM:**

• Объект p1 и его поля name, age хранятся в **Heap**.
• Объект p2 и его поля тоже хранятся в **Heap**.
• Ссылки p1 и p2 хранятся в **стеке (Stack)** внутри main().

### **2️⃣ Статические поля (Static Fields)**

🔹 **Хранятся в Metaspace (Method Area)**, общие для всех экземпляров класса.

**Пример:**
```kotlin
class Person {
    companion object {
        var count = 0  // Статическая переменная
    }
}
```

✅ **В памяти JVM:**

• count хранится **в Metaspace** (Method Area).
• Доступен всем объектам Person через Person.count.

**3️⃣ Локальные переменные (Local Variables)**

🔹 **Хранятся в Stack (стеке)**, принадлежат вызову метода и исчезают после завершения метода.
**Пример:**

```kotlin
fun example() {
    val x = 10 // Локальная переменная
}
```

✅ **В памяти JVM:**

• x создается в **Stack**, и удаляется, когда example() завершается.

**📌 Итоговое распределение памяти:**

| Тип переменной                             | Где хранится?               | Область жизни                       |
| ------------------------------------------ | --------------------------- | ----------------------------------- |
| **Поля объекта (Instance Fields)**         | **Heap (куча)**             | Живут, пока объект не удалится (GС) |
| **Статические поля (Static Fields)**       | **Metaspace (Method Area)** | Живут, пока класс загружен в JVM    |
| **Локальные переменные (Local Variables)** | **Stack (стек)**            | Исчезают после выхода из метода     |


## Почему heap медленнее stack?  

**1️⃣ Управление памятью**

• **Стек** управляется автоматически → выделение памяти ==просто сдвигает указатель стека==, а освобождение памяти — так же быстро ==откатывает его назад==.
• **Куча** требует работы ==**аллокатора памяти**== (например, malloc в C или ==new ==в Java/Kotlin), а освобождение памяти требует работы ==**сборщика мусора (GC)**==. Это делает операции медленнее.

**2️⃣ Локальность данных и кэш-память**

• **Стек** компактен, его данные хранятся в смежных областях памяти → отлично работает с процессорным кэшем (L1, L2, L3).
• **Куча** может хранить объекты в произвольных местах → хуже кэшируется, из-за чего доступ к данным медленнее.

**3️⃣ Фрагментация памяти**

• **Стек** ==не фрагментируется==, так как память выделяется последовательно.
• **Куча** ==подвержена фрагментации== (например, при частых new и delete/GC), что может замедлять доступ к данным.
*Фрагментация — это состояние памяти, при котором свободное пространство разбито на небольшие несмежные блоки, что затрудняет эффективное использование памяти.*


**4️⃣ Потокобезопасность**

• **Стек** создаётся для каждого потока отдельно → нет необходимости в синхронизации.
• **Куча** используется ==всеми потоками== → ==требует синхронизации==, что добавляет накладные расходы.

> [!tip] Коротко на собесе
> - **Stack** — на поток, LIFO, хранит фреймы вызовов: локальные переменные, **ссылки** на объекты, адреса возврата. Память освобождается автоматически при выходе из метода. Переполнение → `StackOverflowError` (глубокая рекурсия).
> - **Heap** — общая на все потоки, хранит **сами объекты**. Очищается GC. Нехватка → `OutOfMemoryError`.
> - Классика: `val p = Person()` — **объект** `Person` в heap, **ссылка** `p` в stack.
> - В Kotlin/JVM **примитивы как локальные переменные** лежат в стеке, но при боксинге (`Int?`, дженерики) уезжают в кучу.
